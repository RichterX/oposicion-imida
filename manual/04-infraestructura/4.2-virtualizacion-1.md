# 1. ¿Qué es la virtualización?

La **virtualización** es una técnica que permite crear una representación lógica o virtual de un recurso físico.

En informática podemos virtualizar:

```text
CPU
Memoria
Almacenamiento
Red
Sistemas operativos
Aplicaciones
Escritorios
```

La idea fundamental es:

```text
RECURSO FÍSICO
       ↓
CAPA DE VIRTUALIZACIÓN
       ↓
RECURSO VIRTUAL
```

---

# 2. El problema del servidor físico tradicional

Imaginemos una organización con tres aplicaciones:

```text
Aplicación A
Aplicación B
Aplicación C
```

Tradicionalmente podríamos tener:

```text
Servidor 1
↓
Aplicación A

Servidor 2
↓
Aplicación B

Servidor 3
↓
Aplicación C
```

Cada aplicación utiliza un servidor físico independiente.

---

# 3. Infrautilización

Supongamos:

```text
Servidor 1 → CPU 15 %
Servidor 2 → CPU 20 %
Servidor 3 → CPU 10 %
```

Tenemos tres máquinas físicas que gran parte del tiempo utilizan una pequeña parte de su capacidad.

Esto implica:

```text
Más servidores
↓
Más espacio
↓
Más electricidad
↓
Más refrigeración
↓
Más mantenimiento
```

Aquí aparece una de las grandes motivaciones de la virtualización.

---

# 4. Consolidación

Podemos utilizar un servidor físico más potente:

```text
                SERVIDOR FÍSICO
                      │
          ┌───────────┼───────────┐
          │           │           │
         VM1         VM2         VM3
          │           │           │
       App A        App B       App C
```

En lugar de:

```text
Servidor A
Servidor B
Servidor C
```

tenemos:

```text
1 servidor físico
+
3 máquinas virtuales
```

Esto se denomina:

> **Consolidación de servidores.**

---

# 5. ¿Qué es una máquina virtual?

Una **máquina virtual**, o **VM (Virtual Machine)**, es una representación software de un ordenador.

Una VM puede disponer de:

```text
CPU virtual
Memoria virtual
Disco virtual
Tarjetas de red virtuales
```

Y puede ejecutar un sistema operativo.

Por ejemplo:

```text
VM
├── 4 vCPU
├── 8 GB RAM
├── 100 GB disco
└── 1 vNIC
```

Dentro de ella podemos instalar:

```text
Linux
Windows
```

u otros sistemas operativos compatibles con la plataforma.

---

# 6. Máquina física frente a máquina virtual

## Máquina física

```text
CPU física
RAM física
Disco físico
NIC física
        ↓
Sistema operativo
        ↓
Aplicaciones
```

## Máquina virtual

```text
CPU virtual
RAM virtual
Disco virtual
NIC virtual
        ↓
Sistema operativo invitado
        ↓
Aplicaciones
```

La diferencia está en que los recursos virtuales son proporcionados por una capa de virtualización.

---

# 7. Host y Guest

Dos términos fundamentales:

### Host

Es el sistema físico que proporciona recursos.

```text
HOST
↓
CPU
RAM
Storage
Red
```

### Guest

Es el sistema que se ejecuta dentro del entorno virtualizado.

```text
GUEST
↓
VM
↓
Sistema operativo
↓
Aplicaciones
```

Podemos recordar:

```text
HOST
→ Aloja

GUEST
→ Está alojado
```

---

# 8. Hipervisor

El componente fundamental de muchas plataformas de virtualización es el:

> **Hipervisor**

También denominado:

> **Virtual Machine Monitor (VMM)**

Su función principal es gestionar la ejecución de máquinas virtuales y proporcionarles acceso controlado a recursos físicos.

Conceptualmente:

```text
Hardware
   ↓
Hipervisor
   ↓
Máquinas virtuales
```

---

# 9. Funciones del hipervisor

El hipervisor puede encargarse de:

```text
CPU
Memoria
Almacenamiento
Red
Aislamiento
Planificación de recursos
```

Por ejemplo:

```text
CPU física
     ↓
   HIPERVISOR
   /   |   \
  ↓    ↓    ↓
 VM1  VM2  VM3
```

El hipervisor controla cómo se utilizan los recursos.

---

# 10. El hipervisor como intermediario

Supongamos que:

```text
VM1
```

necesita ejecutar una operación de CPU.

La VM no controla directamente todo el hardware físico.

Existe una capa:

```text
VM1
 ↓
Hipervisor
 ↓
CPU física
```

Esto permite:

- Compartir recursos.
- Aislar máquinas.
- Controlar consumo.
- Administrar varias VMs.

---

# 11. Tipos de hipervisor

Existen dos categorías clásicas:

```text
Tipo 1
Tipo 2
```

La diferencia principal está en dónde se ejecuta el hipervisor.

---

# 12. Hipervisor tipo 1

También llamado:

> **Bare-metal hypervisor**

Se ejecuta directamente sobre el hardware.

```text
HARDWARE
   ↓
HIPERVISOR TIPO 1
   ↓
┌──────┬──────┬──────┐
│ VM 1 │ VM 2 │ VM 3 │
└──────┴──────┴──────┘
```

No necesita un sistema operativo convencional intermedio para realizar la función principal de virtualización.

---

# 13. Ventajas del tipo 1

Al estar directamente sobre el hardware, suele ofrecer:

- Buen rendimiento.
- Menor sobrecarga.
- Mayor control del hardware.
- Adecuación a centros de datos.
- Integración con funciones avanzadas de virtualización.

Es habitual encontrar este modelo en:

```text
CPD
Servidores empresariales
Nubes privadas
Infraestructuras de producción
```

---

# 14. Hipervisor tipo 2

También denominado:

> **Hosted hypervisor**

Se ejecuta sobre un sistema operativo convencional.

```text
HARDWARE
   ↓
SISTEMA OPERATIVO HOST
   ↓
HIPERVISOR TIPO 2
   ↓
┌──────┬──────┐
│ VM 1 │ VM 2 │
└──────┴──────┘
```

Ejemplos típicos de uso:

- Laboratorios.
- Desarrollo.
- Pruebas.
- Formación.
- Entornos de escritorio.

---

# 15. Comparación tipo 1 y tipo 2

| Característica | Tipo 1 | Tipo 2 |
|---|---|---|
| Nombre | Bare-metal | Hosted |
| Hardware | Directamente | A través del SO host |
| SO intermedio | No convencional | Sí |
| Uso habitual | Servidores / CPD | Escritorio / pruebas |
| Sobrecarga | Generalmente menor | Generalmente mayor |
| Rendimiento | Generalmente superior | Generalmente inferior |

La palabra clave:

```text
TIPO 1
↓
HARDWARE

TIPO 2
↓
SISTEMA OPERATIVO
```

---

# 16. Un ejemplo conceptual

### Tipo 1

```text
┌───────────────────────┐
│       VM Windows      │
├───────────────────────┤
│       VM Linux        │
├───────────────────────┤
│       Hipervisor      │
├───────────────────────┤
│       Hardware        │
└───────────────────────┘
```

### Tipo 2

```text
┌───────────────────────┐
│       VM Windows      │
├───────────────────────┤
│       VM Linux        │
├───────────────────────┤
│    Hipervisor tipo 2  │
├───────────────────────┤
│    Sistema operativo  │
├───────────────────────┤
│       Hardware        │
└───────────────────────┘
```

# 17. ¿Por qué virtualizar?

Las principales motivaciones son:

```text
Consolidación
Aislamiento
Flexibilidad
Utilización de recursos
Rapidez de despliegue
Facilidad de administración
Portabilidad
Continuidad
```

No todas dependen exclusivamente de la virtualización, pero esta puede facilitar enormemente estas capacidades.

---

# 18. Consolidación de servidores

Es uno de los usos clásicos.

Antes:

```text
10 servidores físicos
↓
10 SO
↓
10 aplicaciones
```

Después:

```text
2 servidores físicos
↓
10 VMs
↓
10 SO
↓
10 aplicaciones
```

La cantidad exacta dependerá de la carga y de los requisitos.

---

# 19. Mejor utilización de recursos

Supongamos:

```text
Servidor físico
CPU disponible: 100 %

Uso real: 20 %
```

Podemos aprovechar capacidad adicional mediante virtualización.

Pero hay que tener cuidado:

> **Virtualizar no crea recursos físicos nuevos.**

Si tenemos:

```text
16 cores físicos
```

seguimos teniendo:

```text
16 cores físicos
```

aunque podamos presentar diferentes cantidades de vCPU a las VMs.

---

# 20. Recursos físicos y virtuales

Esta distinción es fundamental.

```text
CPU física
↓
vCPU
```

```text
RAM física
↓
Memoria virtual asignada
```

```text
Disco físico
↓
Disco virtual
```

```text
NIC física
↓
vNIC
```

La virtualización crea una representación lógica de los recursos.

---

# 21. vCPU

Una máquina virtual puede tener:

```text
2 vCPU
```

o:

```text
4 vCPU
```

o:

```text
8 vCPU
```

La vCPU representa capacidad de procesamiento virtual asignada a la VM.

No debemos asumir que:

```text
4 vCPU
=
4 cores físicos dedicados exclusivamente
```

La relación depende de la plataforma y de la configuración.

---

# 22. Memoria virtual de una VM

Podemos asignar:

```text
VM1 → 4 GB
VM2 → 8 GB
VM3 → 16 GB
```

Total:

```text
28 GB
```

Esto debe analizarse frente a la memoria física disponible y las técnicas de gestión de memoria de la plataforma.

---

# 23. Almacenamiento virtual

Una VM puede tener:

```text
Disco virtual
```

Por ejemplo:

```text
VM1
↓
100 GB
```

El disco virtual puede estar almacenado físicamente en:

```text
SSD
HDD
RAID
NAS
SAN
Storage local
```

Esto será especialmente importante cuando estudiemos:

```text
RAID
NAS
SAN
```

en los siguientes capítulos.

---

# 24. Red virtual

Una VM puede disponer de:

```text
vNIC
```

La vNIC se conecta a una infraestructura de red virtual.

Conceptualmente:

```text
VM
↓
vNIC
↓
Switch virtual
↓
NIC física
↓
Switch físico
↓
Red
```

La red física continúa existiendo debajo de la red virtual.

---

# 25. Switch virtual

Un **virtual switch**, o vSwitch, permite conectar máquinas virtuales entre sí y con redes externas.

Conceptualmente:

```text
VM1 ──┐
      │
VM2 ──┼── vSwitch ── NIC física ── Red
      │
VM3 ──┘
```

Esto permite crear una red lógica dentro del host.

---

# 26. Aislamiento

Una ventaja importante de la virtualización es el aislamiento.

Podemos tener:

```text
VM1
VM2
VM3
```

en el mismo servidor físico.

Idealmente:

```text
VM1
```

no debería poder modificar directamente la memoria de:

```text
VM2
```

El hipervisor proporciona mecanismos para separar los entornos.

---

# 27. ¿Aislamiento significa seguridad absoluta?

No.

La virtualización proporciona mecanismos de aislamiento, pero:

```text
Aislamiento
≠
Seguridad absoluta
```

Siguen existiendo riesgos como:

- Vulnerabilidades del hipervisor.
- Configuraciones incorrectas.
- Vulnerabilidades del sistema invitado.
- Ataques de red.
- Errores administrativos.

La virtualización debe integrarse dentro de una estrategia de seguridad completa.

---

# 28. Independencia del hardware

Una máquina virtual puede abstraerse de muchos detalles físicos.

Por ejemplo:

```text
Hardware físico
↓
Hipervisor
↓
Hardware virtual
↓
Sistema operativo
```

Esto puede facilitar la movilidad de una VM entre determinados hosts compatibles.

---

# 29. Portabilidad

Una VM puede representarse mediante archivos y metadatos que permiten trasladar su entorno entre sistemas compatibles.

Por ejemplo:

```text
Host A
 ↓
VM
 ↓
Traslado
 ↓
Host B
```

La facilidad concreta depende de:

- Plataforma.
- Compatibilidad.
- Almacenamiento.
- Red.
- Configuración.
- Dependencias.

---

# 30. Encapsulación

Una VM suele estar asociada a un conjunto de archivos que representan:

```text
Configuración
Discos virtuales
Estado
Metadatos
```

Esta encapsulación facilita determinadas operaciones de administración.

No significa que una VM sea simplemente:

```text
"Un único archivo"
```

La estructura depende de la plataforma.

---

# 31. Despliegue rápido

En un entorno físico:

```text
Comprar servidor
↓
Montar
↓
Instalar SO
↓
Configurar
↓
Instalar aplicación
```

Puede llevar tiempo.

Con virtualización:

```text
Plantilla
↓
Crear VM
↓
Configurar
↓
Arrancar
```

Esto puede acelerar el aprovisionamiento.

---

# 32. Plantillas

Una plantilla puede contener una configuración base.

Por ejemplo:

```text
Linux
+
Actualizaciones
+
Paquetes
+
Configuración base
```

A partir de ella:

```text
Template
 ├── VM1
 ├── VM2
 └── VM3
```

Esto facilita despliegues homogéneos.

---

# 33. Clonación

La clonación permite crear una VM basada en otra.

Por ejemplo:

```text
VM original
    ↓
   CLON
    ↓
Nueva VM
```

Puede ser útil para:

- Laboratorios.
- Pruebas.
- Desarrollo.
- Despliegues repetitivos.

La gestión concreta de identidad, red y almacenamiento debe hacerse correctamente después de clonar.

---

# 34. Snapshots

Un **snapshot** captura el estado de una VM en un momento determinado, según las capacidades de la plataforma.

Conceptualmente:

```text
VM funcionando
      ↓
   Snapshot
      ↓
Estado guardado
```

Después podemos realizar determinados cambios.

Si algo sale mal:

```text
Rollback
↓
Estado anterior
```

Pero:

> **Un snapshot no debe confundirse con una copia de seguridad tradicional.**

---

# 35. Snapshot vs backup

### Snapshot

```text
Captura de estado
↓
Uso frecuente en operaciones puntuales
```

### Backup

```text
Copia destinada a recuperación
↓
Protección de datos
```

Un snapshot puede formar parte de una estrategia operativa, pero no sustituye automáticamente a un sistema de backup.

---

# 36. Alta disponibilidad

La virtualización puede facilitar arquitecturas de alta disponibilidad.

Por ejemplo:

```text
Host A
   │
   ├── VM1
   └── VM2

Host B
   │
   ├── VM3
   └── VM4
```

Si existe una plataforma adecuada:

```text
Fallo Host A
     ↓
Reinicio / recuperación de VMs
     ↓
Host B
```

La capacidad concreta depende de la plataforma, almacenamiento, red y configuración.

---

# 37. Migración

Una VM puede trasladarse entre hosts compatibles.

Conceptualmente:

```text
Host A
  │
  │ VM
  ↓
Host B
```

Existen distintos tipos de migración.

Uno especialmente importante es:

> **Live migration**

---

# 38. Live migration

La migración en caliente permite mover una VM entre hosts con una interrupción muy reducida, dependiendo de la plataforma y del escenario.

Conceptualmente:

```text
Host A
   │
   │ VM
   │
   ├──────────────→ Host B
   │
   └─ Servicio continúa
```

Esto puede facilitar:

- Mantenimiento.
- Balanceo.
- Optimización de recursos.
- Gestión de capacidad.

---

# 39. Migración en frío

En una migración en frío:

```text
VM
↓
Apagar
↓
Mover
↓
Encender
```

Puede producir una interrupción del servicio.

---

# 40. Comparación de migraciones

| Tipo | VM encendida | Interrupción |
|---|---|---|
| Migración en frío | No | Sí |
| Live migration | Sí | Muy reducida, según plataforma |

La live migration es especialmente útil en entornos empresariales.

---

# 41. Balanceo de carga

Si tenemos:

```text
Host A → 90 %
Host B → 30 %
```

podemos trasladar VMs:

```text
Host A
↓
Migración
↓
Host B
```

Resultado:

```text
Host A → 60 %
Host B → 60 %
```

Los valores son solamente ilustrativos.

La idea es:

> **Distribuir la carga para aprovechar mejor los recursos disponibles.**

---

# 42. Sobreasignación

Una plataforma puede permitir asignar recursos virtuales que superan la capacidad física disponible en determinados escenarios.

Por ejemplo:

```text
RAM física = 64 GB

VM1 = 32 GB
VM2 = 32 GB
VM3 = 16 GB
```

Total asignado:

```text
80 GB
```

Esto supone una sobreasignación de memoria.

No significa que todas las VMs puedan utilizar simultáneamente los 80 GB sin mecanismos adicionales.

---

# 43. Overcommit

El concepto general de asignar recursos virtuales por encima de la capacidad física se conoce como:

> **Overcommit / sobreasignación**

Puede aplicarse a determinados recursos según la plataforma.

Ventaja:

```text
Mayor utilización
```

Riesgo:

```text
Contención
↓
Degradación de rendimiento
```

---

# 44. Contención

Si varias VMs necesitan el mismo recurso simultáneamente:

```text
VM1 ─┐
VM2 ─┼── CPU
VM3 ─┘
```

el hipervisor debe gestionar el acceso.

Puede producirse:

```text
Contención
```

Por ello hay que dimensionar adecuadamente.

---

# 45. Recursos compartidos

La virtualización permite compartir:

```text
CPU
RAM
Storage
Red
```

entre múltiples VMs.

Por ejemplo:

```text
             HOST
              │
      ┌───────┼───────┐
      │       │       │
     VM1     VM2     VM3
      │       │       │
      └───────┼───────┘
              │
        Recursos físicos
```

---

# 46. Pool de recursos

En plataformas empresariales podemos agrupar recursos.

Conceptualmente:

```text
Pool
│
├── CPU
├── RAM
├── Storage
└── Red
```

Las VMs consumen recursos del conjunto según las reglas de la plataforma.

Esto facilita la administración centralizada.

---

# 47. Reserva de recursos

Podemos establecer que una VM tenga una cantidad mínima garantizada de determinado recurso.

Por ejemplo:

```text
VM crítica
↓
Reserva de CPU
```

Esto puede ayudar a evitar que otras cargas consuman todos los recursos disponibles.

---

# 48. Límites

También pueden establecerse límites.

Por ejemplo:

```text
VM
↓
Máximo de CPU
```

Aunque exista capacidad adicional en el host, la VM no podrá superar el límite configurado.

---

# 49. Shares o prioridades

En algunas plataformas existen mecanismos para establecer prioridades relativas.

Por ejemplo:

```text
VM crítica
↓
Alta prioridad

VM secundaria
↓
Prioridad menor
```

En caso de contención, el sistema puede utilizar estas prioridades para repartir recursos.

---

# 50. CPU física y vCPU

Una máquina física puede tener:

```text
16 cores físicos
```

y alojar:

```text
VM1 → 4 vCPU
VM2 → 4 vCPU
VM3 → 2 vCPU
VM4 → 4 vCPU
```

Total:

```text
14 vCPU
```

Eso no significa que cada vCPU sea un core físico dedicado.

El hipervisor planifica el uso de los recursos físicos.

---

# 51. Scheduling

El hipervisor debe decidir:

> **¿Qué VM utiliza la CPU física y cuándo?**

Esto es planificación o:

> **Scheduling**

Conceptualmente:

```text
CPU física
   │
   ├── VM1
   ├── VM2
   ├── VM3
   └── VM4
```

El hipervisor distribuye el tiempo de procesamiento.

---

# 52. Memoria

La gestión de memoria virtual puede ser más compleja que:

```text
RAM física
↓
RAM virtual
```

Las plataformas pueden utilizar diferentes técnicas para optimizar el uso de memoria.

Algunos conceptos que aparecerán en plataformas de virtualización son:

```text
Memory ballooning
Memory compression
Swapping
Transparent Page Sharing
```

No necesitamos dominarlos todavía en profundidad.

Lo importante ahora es comprender:

> **El hipervisor administra la relación entre memoria física y memoria asignada a las VMs.**

---

# 53. Almacenamiento y virtualización

Una VM puede percibir:

```text
Disco C:
100 GB
```

pero físicamente ese almacenamiento puede estar formado por:

```text
Discos físicos
↓
RAID
↓
Cabina
↓
Datastore
↓
Disco virtual
```

Esto demuestra cómo las capas de infraestructura se superponen.

---

# 54. Red y virtualización

La cadena puede ser:

```text
Aplicación
↓
Sistema operativo guest
↓
vNIC
↓
vSwitch
↓
NIC física
↓
Switch físico
↓
Red
```

Cada capa puede introducir configuración y dependencias.

# 56. Ventaja económica

La consolidación puede reducir:

```text
Hardware
Espacio
Electricidad
Refrigeración
Mantenimiento
```

Pero:

> **La virtualización no garantiza automáticamente un menor coste.**

Hay que considerar:

- Licencias.
- Storage.
- Redes.
- Software de gestión.
- Formación.
- Hardware de alta capacidad.
- Soporte.

---

# 57. Ventaja energética

Si consolidamos cargas:

```text
10 servidores
↓
3 servidores
```

podemos reducir el consumo físico.

Pero debemos recordar:

```text
Servidor físico
↓
Siempre consume
```

aunque la carga sea pequeña.

Las VMs proporcionan aislamiento a nivel de máquina virtual mediante el hipervisor.

No lo es.

# 102. Resumen de conceptos

## Virtualización

Abstracción de recursos físicos mediante software y hardware especializado.

## VM

Máquina virtual que ejecuta un sistema operativo y aplicaciones sobre recursos virtualizados.

## Host

Sistema físico que proporciona los recursos.

## Guest

Sistema operativo o entorno que se ejecuta dentro de la VM.

## Hipervisor

Capa que gestiona la ejecución de máquinas virtuales y el acceso a recursos físicos.

## Tipo 1

Hipervisor directamente sobre el hardware.

## Tipo 2

Hipervisor sobre un sistema operativo host.

## vCPU

CPU virtual asignada a una VM.

## vNIC

Interfaz de red virtual.

## vSwitch

Switch virtual para conectar VMs y redes.

## Snapshot

Captura de estado de una VM.

## Live migration

Traslado de una VM entre hosts con interrupción muy reducida, según plataforma y configuración.

## Overcommit

Sobreasignación de recursos virtuales respecto a recursos físicos.

## Clúster

Conjunto de hosts gestionados conjuntamente para proporcionar capacidades como HA o movilidad.

Snapshot y backup cumplen funciones diferentes.

❌ **No.**

Comparten el host físico y sus recursos.

> "Virtualización implica alta disponibilidad."

❌ **No automáticamente.**

La HA requiere arquitectura y configuración adecuadas.

## Trampa 6

> "Tipo 1 utiliza un sistema operativo convencional debajo del hipervisor."

❌ **No.**

La característica fundamental del tipo 1 es que se ejecuta directamente sobre el hardware.

> "Un contenedor es una máquina virtual."

❌ **No.**

Son tecnologías diferentes.

```text
+
Más aislamiento
```

sin provocar:

```text
Exceso de contención
+
Concentración de riesgo
+
Complejidad excesiva
```

Por eso el diseño es fundamental.
