# 2. El administrador VMware

Un administrador no recibe problemas diciendo:

> "Ha fallado el componente X."

Recibe problemas como:

> "La aplicación está lenta."

o:

> "La máquina virtual no arranca."

o:

> "El host ha desaparecido."

Por eso debemos aprender a recorrer la infraestructura.

```text
7. Verificar
```

# 4. Alcance

Primera pregunta:

> ¿Cuántos elementos están afectados?

Ejemplo:

```text
1 VM
```

es diferente de:

```text
20 VMs
```

y de:

```text
Todos los hosts
```

---

# 5. Patrón de fallo

Podemos utilizar:

```text
Un objeto
→ problema local

Muchos objetos del mismo host
→ problema del host

Muchas VMs de un datastore
→ investigar storage

Muchas VMs de una VLAN
→ investigar red

Todo el cluster
→ investigar infraestructura común
```

No son reglas absolutas, pero son excelentes puntos de partida.

# 6. Baseline

Antes de diagnosticar rendimiento necesitamos conocer:

> ¿Qué es normal?

Ejemplo:

```text
CPU normal:
30 %

Latency normal:
3 ms

Network:
20 %

Memory:
50 %
```

Si de repente:

```text
Storage latency:
80 ms
```

tenemos una desviación clara.

# 7. Performance vs Availability

Dos conceptos diferentes:

```text
Availability
→ ¿Está funcionando?

Performance
→ ¿Está funcionando suficientemente bien?
```

Una VM puede estar:

```text
Available ✓
Performance ❌
```

---

# 8. Reliability

Podemos pensar:

```text
Availability
→ minimizar interrupciones

Performance
→ responder adecuadamente

Reliability
→ comportamiento consistente
```

---

# 9. HA

> **vSphere High Availability (HA)**

proporciona mecanismos para reiniciar máquinas virtuales en otros hosts cuando se produce determinado tipo de fallo del host.

---

# 10. HA no es vMotion

Muy importante:

```text
HA
→ recuperación tras fallo
```

```text
vMotion
→ migración planificada / operativa
```

---

# 11. Ejemplo HA

Tenemos:

```text
ESXi01
VM01
VM02

ESXi02
VM03
```

Si:

```text
ESXi01 ❌
```

HA puede detectar el fallo y, si se cumplen las condiciones:

```text
VM01
VM02
↓
ESXi02
```

y reiniciarlas.

---

# 12. HA no mantiene necesariamente la ejecución continua

Cuando un host falla:

```text
VM
↓
fallo
↓
detección
↓
reinicio
```

Existe una interrupción.

Por tanto:

```text
HA ≠ cero downtime
```

---

# 13. HA vs Fault Tolerance

No debemos confundir:

```text
HA
→ reinicio de VM tras fallo del host
```

con:

```text
Fault Tolerance
→ tecnología orientada a continuidad de ejecución mediante redundancia de la VM
```

Las características concretas y limitaciones dependen de la versión.

---

# 14. Cluster HA

HA se configura a nivel de:

```text
Cluster
```

Conceptualmente:

```text
Cluster
│
├── ESXi01
├── ESXi02
└── ESXi03
```

con:

```text
HA
```

habilitado.

---

# 15. HA agents

Los hosts participan en el funcionamiento de HA mediante componentes/agentes de HA.

La comunicación entre hosts es fundamental.

---

# 16. Heartbeats

HA utiliza mecanismos de detección de estado, incluyendo:

```text
Heartbeats
```

para determinar si los hosts están disponibles.

---

# 17. Management Network y HA

La conectividad entre hosts es crítica.

Por eso:

```text
Management Network
```

debe estar correctamente diseñada.

---

# 18. Datastore heartbeats

En determinados escenarios, HA puede utilizar datastore heartbeats como mecanismo adicional de información sobre el estado de hosts.

Esto ayuda cuando existe un problema con la conectividad de gestión.

---

# 19. HA y aislamiento

Debemos diferenciar:

```text
Host failure
```

de:

```text
Network partition / isolation
```

No siempre que un host deja de comunicarse significa que físicamente haya muerto.

---

# 20. Host isolation

Conceptualmente:

```text
Host sigue ejecutándose
```

pero:

```text
pierde conectividad de gestión con otros hosts
```

Esto requiere un tratamiento diferente a un apagado físico.

---

# 21. Isolation response

vSphere HA permite configurar qué hacer cuando se determina una situación de aislamiento.

Las acciones pueden depender de:

```text
Configuración
Versión
Estado de las VMs
```

No debemos memorizar una única acción como universal.

---

# 22. Admission Control

Uno de los conceptos más importantes de HA:

> **Admission Control**

Su objetivo es evitar que el cluster acepte una configuración que no pueda soportar el nivel de disponibilidad configurado.

---

# 23. Ejemplo Admission Control

Tenemos:

```text
3 hosts
```

y queremos soportar:

```text
1 host failure
```

Si llenamos el cluster hasta el punto de que no queda capacidad suficiente:

```text
Host failure
↓
No capacity
↓
VMs no pueden reiniciarse
```

Admission Control intenta evitar esa situación.

---

# 24. Capacidad reservada

Conceptualmente:

```text
Cluster capacity
↓
Reserva para fallos
```

La política concreta depende de la configuración.

---

# 25. Admission Control no mejora rendimiento

Su objetivo principal es:

```text
Availability
```

no:

```text
Performance
```

---

# 26. DRS

> **Distributed Resource Scheduler (DRS)**

ayuda a gestionar la colocación y balanceo de máquinas virtuales entre hosts de un cluster según los recursos y reglas configuradas.

---

# 27. DRS y CPU/RAM

DRS trabaja principalmente con:

```text
Compute resources
```

como:

```text
CPU
Memory
```

---

# 28. DRS vs Storage DRS

Memoriza:

```text
DRS
→ Compute
```

```text
Storage DRS
→ Storage
```

---

# 29. DRS no es HA

```text
HA
→ disponibilidad ante fallos
```

```text
DRS
→ distribución / colocación de workloads
```

---

# 30. DRS ejemplo

Tenemos:

```text
ESXi01
CPU 90 %

ESXi02
CPU 30 %
```

DRS puede recomendar o realizar determinadas migraciones:

```text
VM
ESXi01
↓
vMotion
↓
ESXi02
```

según configuración.

---

# 31. DRS y vMotion

DRS puede utilizar:

```text
vMotion
```

para mover VMs entre hosts.

---

# 32. vMotion

> **vMotion**

permite migrar una máquina virtual en ejecución entre hosts compatibles.

Conceptualmente:

```text
ESXi01
   │
   │ vMotion
   ▼
ESXi02
```

---

# 33. ¿Qué se mueve?

En una migración vMotion tradicional:

```text
Estado de ejecución
Memoria
CPU state
```

se transfiere al destino.

El almacenamiento puede permanecer compartido.

---

# 34. vMotion y datastore compartido

Escenario clásico:

```text
ESXi01 ─┐
        ├── DS01
ESXi02 ─┘
```

La VM utiliza:

```text
DS01
```

y se mueve:

```text
ESXi01 → ESXi02
```

mientras su VMDK continúa en:

```text
DS01
```

---

# 35. vMotion sin storage compartido

Existen capacidades de migración que permiten combinar cambios de host y almacenamiento, según versión y condiciones.

Por eso no debemos asumir:

> "vMotion siempre requiere obligatoriamente shared storage."

La respuesta correcta depende del tipo de migración y versión.

---

# 36. Requisitos generales de vMotion

Entre otros:

```text
Hosts compatibles
Red vMotion
CPU compatibility
Networking compatible
Storage accesible
Configuración correcta
```

Los requisitos exactos dependen de la versión y escenario.

---

# 37. vMotion network

La migración puede generar mucho tráfico.

Por eso:

```text
vMotion Network
```

debe tener suficiente:

```text
Bandwidth
```

y una configuración apropiada.

---

# 38. CPU compatibility

Si los hosts tienen CPUs con diferencias importantes:

```text
vMotion
```

puede no ser posible directamente.

---

# 39. EVC

> **Enhanced vMotion Compatibility (EVC)**

permite establecer un baseline de características de CPU para facilitar la compatibilidad de vMotion entre hosts con CPUs diferentes dentro de determinadas generaciones.

---

# 40. EVC

Conceptualmente:

```text
CPU A
Features
██████████

CPU B
Features
████████

EVC
↓
Baseline común
```

---

# 41. EVC no hace CPUs idénticas

No convierte físicamente:

```text
CPU A
```

en:

```text
CPU B
```

Reduce el conjunto de características CPU expuestas a las VMs para facilitar compatibilidad.

---

# 42. Storage vMotion

> **Storage vMotion**

permite migrar los archivos de almacenamiento de una VM entre datastores compatibles.

---

# 43. Storage vMotion

Ejemplo:

```text
VM01
↓
DS-OLD
```

mover a:

```text
DS-NEW
```

sin necesidad de apagar la VM en escenarios compatibles.

---

# 44. vMotion + Storage vMotion

Podemos conceptualizar:

```text
Compute
ESXi01 → ESXi02

Storage
DS01 → DS02
```

y realizar una migración combinada cuando la configuración lo permita.

---

# 45. Maintenance Mode

Cuando queremos realizar mantenimiento en un host:

```text
ESXi01
```

podemos ponerlo en:

> **Maintenance Mode**

---

# 46. Objetivo

Antes de mantenimiento:

```text
ESXi01
```

debe quedar:

```text
Sin VMs de producción
```

según el procedimiento y configuración.

---

# 47. Evacuation

El host puede necesitar:

```text
Evacuar VMs
```

```text

```

---

# 48. Maintenance Mode y DRS

En un cluster con DRS:

```text
Maintenance Mode
↓
Evacuation
↓
DRS / vMotion
```

pueden trabajar conjuntamente según configuración.

---

# 49. Maintenance Mode no apaga necesariamente el host

Es importante:

```text
Maintenance Mode
≠
Power Off
```

El host sigue ejecutándose pero queda preparado para mantenimiento.

---

# 50. Exit Maintenance Mode

Después:

```text
Mantenimiento
↓
Verificación
↓
Exit Maintenance Mode
```

y el host vuelve a participar normalmente según configuración.

# 66. Snapshot

Un:

> **Snapshot**

captura un estado determinado de una VM y permite mantener una cadena de cambios respecto al disco base.

---

# 67. Snapshot no es backup

Repetimos porque es una trampa clásica:

```text
Snapshot
≠
Backup
```

---

# 68. Snapshot chain

Conceptualmente:

```text
Base VMDK
   ↓
Snapshot 1
   ↓
Snapshot 2
   ↓
Snapshot 3
```

---

# 69. Riesgo de snapshots largos

Cuanto más tiempo:

```text
Snapshot
```

permanece activo, más cambios pueden acumularse.

Esto puede provocar:

```text
Storage consumption
Performance impact
Management complexity
```

dependiendo del escenario.

---

# 70. Snapshot antes de actualización

Puede utilizarse un snapshot como mecanismo temporal de rollback operativo, pero no debe sustituir una estrategia de backup.

---

# 71. Snapshot removal

Eliminar un snapshot puede requerir:

```text
Consolidation
```

para integrar los cambios en el disco base.

---

# 72. Consolidation

```text

↓

```

```text

```

> **Co-stop**


# 215. La regla de oro

Cuando una VM está lenta:

> **No adivines. Mide.**

Cuando un host falla:

> **No asumas. Determina el alcance.**

Cuando vMotion falla:

> **No culpes a la red inmediatamente. Comprueba CPU, red, storage y compatibilidad.**

Cuando HA no recupera una VM:

> **Comprueba capacidad, storage, red y restricciones.**
