# 1. La idea fundamental

En la primera parte vimos:

```text
HARDWARE
   ↓
HIPERVISOR
   ↓
VMs
```

Ahora debemos mirar debajo de las VMs.

Cuando una máquina virtual solicita un recurso:

```text
VM
 ↓
Recurso virtual
 ↓
Hipervisor
 ↓
Recurso físico
```

Por tanto:

> **El hipervisor actúa como gestor y árbitro entre las máquinas virtuales y el hardware físico.**

---

# 2. Un host de ejemplo

Imaginemos:

```text
HOST FÍSICO

CPU
16 cores

RAM
128 GB

Storage
4 TB

NIC
4 × 10 GbE
```

Sobre él ejecutamos:

```text
VM1
4 vCPU
16 GB RAM

VM2
4 vCPU
32 GB RAM

VM3
2 vCPU
16 GB RAM

VM4
4 vCPU
16 GB RAM
```

Tenemos:

```text
14 vCPU
80 GB RAM
```

El host todavía dispone de recursos físicos.

Pero la situación real es bastante más compleja.

---

# 3. CPU física y vCPU

Una CPU física puede disponer de:

```text
Cores
```

y, dependiendo de la arquitectura:

```text
Threads
```

La VM ve:

```text
vCPU
```

La vCPU es una representación lógica de capacidad de procesamiento.

Podemos pensar:

```text
CPU física
      ↓
Hipervisor
      ↓
vCPU de VM
```

Pero no debemos imaginar necesariamente una relación:

```text
1 vCPU = 1 core físico dedicado
```

---

# 4. Scheduling de CPU

Si tenemos:

```text
16 cores físicos
```

y:

```text
VM1 → 4 vCPU
VM2 → 4 vCPU
VM3 → 8 vCPU
```

tenemos:

```text
16 vCPU
```

En este caso la asignación coincide numéricamente con los cores físicos, pero las VMs siguen siendo entidades virtuales.

El hipervisor debe decidir:

> **Qué vCPU ejecuta sobre qué recurso físico y en qué momento.**

Ese proceso se denomina:

> **CPU scheduling.**

---

# 5. Scheduling como reparto

Imaginemos:

```text
CPU física
│
├── VM1
├── VM2
├── VM3
└── VM4
```

Si todas solicitan CPU al mismo tiempo:

```text
VM1 ─┐
VM2 ─┤
VM3 ─┼── CPU física
VM4 ─┘
```

El hipervisor debe gestionar el acceso.

Su objetivo es:

```text
Utilizar CPU
+
Respetar prioridades
+
Mantener rendimiento
```

---

# 6. vCPU no significa dedicación

Este concepto es fundamental para el examen.

Si configuramos:

```text
VM1 = 4 vCPU
```

no podemos concluir:

```text
4 cores físicos exclusivos
```

Podemos tener:

```text
Host = 16 cores

VM1 = 4 vCPU
VM2 = 4 vCPU
VM3 = 4 vCPU
VM4 = 4 vCPU
```

Todas las VMs pueden utilizar los recursos físicos según la planificación del hipervisor.

---

# 7. Sobreasignación de CPU

También podemos encontrarnos:

```text
Host = 16 cores
```

y:

```text
VM1 = 8 vCPU
VM2 = 8 vCPU
VM3 = 8 vCPU
```

Total:

```text
24 vCPU
```

Tenemos:

```text
24 vCPU
/
16 cores físicos
```

Esto representa una sobreasignación de CPU.

Puede funcionar correctamente si las VMs no necesitan utilizar todas sus vCPU simultáneamente.

---

# 8. Ratio de sobreasignación

Podemos calcular de forma conceptual:

```text
Ratio =
vCPU asignadas
────────────────
CPU física disponible
```

En el ejemplo:

```text
24
── = 1,5
16
```

Tenemos un ratio de:

```text
1,5:1
```

Esto no implica automáticamente un problema.

El comportamiento depende de:

- Carga real.
- Patrones de uso.
- Aplicaciones.
- Contención.
- Capacidad física.

---

# 9. ¿Cuándo se convierte en un problema?

La sobreasignación puede funcionar mientras:

```text
Demanda real
<
Capacidad disponible
```

Pero si:

```text
Demanda real
>
Capacidad disponible
```

aparece:

```text
Contención
```

Las VMs tendrán que esperar recursos.

---

# 10. Contención

La contención significa que varias cargas compiten por un recurso limitado.

Ejemplo:

```text
VM1 ─┐
VM2 ─┤
VM3 ─┼── CPU
VM4 ─┘
```

Si todas necesitan CPU:

```text
Recurso físico limitado
↓
Competencia
↓
Espera
↓
Posible degradación
```

La contención puede aparecer en:

```text
CPU
RAM
Storage
Red
```

---

# 11. La carga media puede engañar

Supongamos:

```text
CPU media = 35 %
```

Podría parecer que tenemos mucho margen.

Pero quizá:

```text
8:00 → 20 %
9:00 → 25 %
10:00 → 90 %
11:00 → 25 %
```

El promedio puede ocultar picos.

Por eso el dimensionamiento debe considerar:

```text
Promedio
+
Picos
+
Tendencias
```

---

# 12. CPU Ready

En plataformas empresariales podemos encontrar métricas relacionadas con el tiempo que una VM permanece esperando para obtener CPU.

El concepto importante es:

```text
VM necesita CPU
↓
No puede ejecutarla inmediatamente
↓
Espera
```

Esto puede ser una señal de:

```text
Contención de CPU
```

No necesitamos memorizar todavía métricas específicas de VMware.

Eso lo veremos en:

```text
4.3 VMware
```

---

# 13. VM grande no siempre es mejor

Podemos pensar:

```text
"Esta aplicación necesita potencia,
le pongo 16 vCPU."
```

Pero asignar demasiadas vCPU puede no mejorar el rendimiento.

Podemos provocar:

```text
Mayor complejidad
+
Mayor competencia
+
Mayor coste de planificación
```

La regla práctica:

> **Asignar los recursos que realmente necesita la carga, no todos los recursos posibles.**

Debemos analizar:

```text
Uso máximo

Criticidad
Patrón de carga

```

# 15. Memoria física

Ahora pasamos a RAM.

Supongamos:

```text
Host = 128 GB RAM
```

Y:

```text
VM1 = 16 GB
VM2 = 32 GB
VM3 = 16 GB
VM4 = 32 GB
```

Total asignado:

```text
96 GB
```

Existe margen físico.

---

# 16. Sobreasignación de memoria

Podríamos tener:

```text
Host = 128 GB

VM1 = 64 GB
VM2 = 64 GB
VM3 = 32 GB
VM4 = 32 GB
```

Total:

```text
192 GB
```

Tenemos:

```text
192 GB asignados
128 GB físicos
```

Existe sobreasignación.

Esto no significa que las VMs puedan utilizar simultáneamente los 192 GB como si existieran físicamente.

---

# 17. ¿Cómo puede funcionar?

Las plataformas de virtualización pueden utilizar diferentes técnicas de gestión de memoria.

Entre ellas podemos encontrar:

```text
Ballooning
Compresión
Swapping
Compartición de páginas
```

La disponibilidad concreta depende de la plataforma.

---

# 18. Ballooning

El ballooning es una técnica mediante la cual un componente dentro del sistema operativo invitado puede colaborar con el hipervisor para recuperar memoria que no está siendo utilizada de forma prioritaria.

Conceptualmente:

```text
Host necesita RAM
       ↓
Hipervisor solicita memoria
       ↓
Balloon driver
       ↓
Guest libera memoria
       ↓
Host recupera capacidad
```

---

# 19. ¿Por qué es útil?

Permite:

```text
Reutilizar memoria
```

sin tener que recurrir inmediatamente a mecanismos más lentos.

Pero existe una condición:

> **El guest debe tener memoria recuperable.**

Si la VM realmente necesita toda su RAM:

```text
Memoria libre ≈ 0
```

el ballooning no puede solucionar mágicamente la falta de memoria.

---

# 20. Compresión de memoria

Otra técnica posible es:

```text
Memoria
↓
Comprimir páginas
↓
Utilizar menos espacio físico
```

La compresión puede ser más rápida que acceder a almacenamiento, aunque introduce consumo de CPU.

Conceptualmente:

```text
RAM insuficiente
↓
Compresión
↓
Más capacidad efectiva
```

---

# 21. Swapping

Cuando no existe suficiente memoria física, una plataforma puede recurrir a almacenamiento como mecanismo de respaldo.

Conceptualmente:

```text
RAM
↓
Presión de memoria
↓
Swap
↓
Storage
```

El problema:

```text
RAM
≫
Storage
```

en términos de velocidad y latencia.

Por eso el swapping excesivo puede provocar:

```text
Degradación severa del rendimiento
```

---

# 22. Jerarquía conceptual de memoria

Podemos imaginar:

```text
CPU Cache
   ↓
RAM
   ↓
SSD
   ↓
HDD
```

A medida que bajamos:

```text
Más capacidad
+
Mayor latencia
```

Por eso queremos mantener las cargas activas en niveles rápidos.

---

# 23. Presión de memoria

Cuando la demanda de RAM se aproxima o supera la capacidad disponible:

```text
Presión de memoria
```

Podemos observar:

```text
Ballooning
↓
Compresión
↓
Swapping
```

dependiendo de la plataforma y del escenario.

La idea importante:

> **La presión de memoria puede degradar el rendimiento.**

---

# 24. Memoria asignada vs utilizada

Una VM puede tener:

```text
16 GB asignados
```

pero utilizar:

```text
6 GB
```

No debemos confundir:

```text
Configurado
```

con:

```text
Utilizado
```

Para planificar capacidad debemos observar ambos.

---

# 25. Reserva de memoria

Una plataforma puede permitir establecer:

```text
Reserva
```

Esto indica una cantidad de recurso que debe garantizarse a una VM según las reglas de la plataforma.

Por ejemplo:

```text
VM crítica
RAM configurada = 16 GB
Reserva = 8 GB
```

La reserva no significa necesariamente:

```text
16 GB físicos dedicados
```

---

# 26. Límite de memoria

También podemos establecer:

```text
Límite
```

que restringe el máximo de recursos que puede consumir una VM.

Conceptualmente:

```text
VM
↓
No puede superar
↓
Límite configurado
```

---

# 27. Prioridad o shares

En caso de competencia por recursos, podemos establecer prioridades relativas.

Ejemplo:

```text
VM crítica
→ Alta prioridad

VM secundaria
→ Baja prioridad
```

Si existe contención, la plataforma puede utilizar estas prioridades para decidir cómo repartir los recursos.

---

# 28. Reserva, límite y prioridad

Una forma sencilla de recordarlo:

```text
RESERVA
↓
"Necesito garantizar al menos esto."
```

```text
LÍMITE
↓
"No quiero que superes esto."
```

```text
PRIORIDAD / SHARES
↓
"Si competimos, yo tengo preferencia."
```

# 29. Almacenamiento virtual

Pasamos ahora a:

```text
Storage
```

Una VM puede ver:

```text
Disco virtual de 200 GB
```

Pero físicamente puede existir una cadena:

```text
VM
 ↓
Disco virtual
 ↓
Datastore
 ↓
Storage físico
 ↓
Discos
```

---

# 30. Disco virtual

Un disco virtual representa almacenamiento que el sistema operativo invitado percibe como un dispositivo.

Por ejemplo:

```text
VM
│
└── Disk 1
     └── 200 GB
```

El guest no necesita conocer necesariamente dónde están físicamente los discos.

---

# 31. Datastore

Un **datastore** es un recurso lógico de almacenamiento utilizado por la plataforma de virtualización para alojar elementos de las VMs.

Puede contener:

```text
Discos virtuales
Configuraciones
Metadatos
Otros archivos
```

El datastore abstrae parte de la infraestructura física.

---

# 32. Cadena de almacenamiento

Una arquitectura podría ser:

```text
VM
↓
Disco virtual
↓
Datastore
↓
SAN
↓
Cabina
↓
RAID
↓
Discos físicos
```

Otra:

```text
VM
↓
Disco virtual
↓
Datastore
↓
Storage local
↓
Discos físicos
```

Y otra:

```text
VM
↓
Disco virtual
↓
Datastore
↓
NAS / almacenamiento compatible
```

Los detalles concretos dependen de la plataforma.

---

# 33. I/O

I/O significa:

> **Input / Output**

En almacenamiento representa operaciones de lectura y escritura.

Por ejemplo:

```text
Aplicación
↓
Guest
↓
Disco virtual
↓
Datastore
↓
Storage
↓
Disco
```

Cada capa puede influir en el rendimiento.

---

# 34. IOPS

Una métrica importante es:

> **IOPS = Input/Output Operations Per Second**

Representa, de forma simplificada:

```text
Operaciones de entrada/salida por segundo
```

No debemos confundir:

```text
IOPS
```

con:

```text
Throughput
```

---

# 35. Throughput

El throughput representa la cantidad de datos transferidos por unidad de tiempo.

Por ejemplo:

```text
MB/s
GB/s
```

Podemos tener:

```text
Muchos IOPS
```

con operaciones pequeñas.

O:

```text
Pocos IOPS
```

con operaciones grandes.

Por eso:

```text
IOPS ≠ Throughput
```

---

# 36. Latencia de almacenamiento

La latencia es el tiempo que tarda una operación en completarse.

Conceptualmente:

```text
Solicitud
↓
Storage
↓
Respuesta
```

Cuanto menor sea la latencia:

```text
Mejor respuesta
```

en igualdad de condiciones.

---

# 37. Ejemplo

Supongamos:

```text
Storage A
10.000 IOPS
5 ms

Storage B
10.000 IOPS
1 ms
```

Ambos tienen:

```text
10.000 IOPS
```

pero:

```text
Storage B
```

tiene menor latencia.

Esto puede resultar importante para determinadas aplicaciones.

---

# 38. I/O burst

Algunas cargas no son constantes.

Podemos tener:

```text
Normal → 2.000 IOPS
Pico → 20.000 IOPS
```

Si dimensionamos únicamente para:

```text
2.000 IOPS
```

podemos sufrir problemas durante el pico.

Por eso:

```text
Promedio
+
Picos
```

también importa en almacenamiento.

---

# 39. Thin provisioning

Una técnica común es:

> **Thin provisioning**

Conceptualmente:

```text
VM ve:
1 TB
```

pero físicamente podemos no haber reservado inmediatamente:

```text
1 TB completo
```

El almacenamiento físico se consume según las necesidades y las políticas de la plataforma.

---

# 40. Thick provisioning

En un modelo thick:

```text
Disco virtual = capacidad provisionada
```

y el espacio físico puede reservarse de forma más inmediata, dependiendo del formato y configuración.

La distinción exacta depende de la plataforma.

---

# 41. Thin vs Thick

| Thin | Thick |
|---|---|
| Asignación progresiva | Asignación más inmediata |
| Ahorro inicial de espacio | Espacio reservado |
| Riesgo de sobreaprovisionamiento | Menor riesgo de quedarse sin espacio por crecimiento oculto |
| Requiere monitorización | Más predecible |

La clave:

```text
THIN
→ Crece según necesidad

THICK
→ Reserva capacidad
```

---

# 42. Riesgo del thin provisioning

Imaginemos:

```text
Storage físico = 1 TB
```

Creamos:

```text
VM1 = 600 GB
VM2 = 600 GB
```

Tenemos:

```text
1,2 TB provisionados
```

pero:

```text
1 TB físico
```

Puede funcionar inicialmente si las VMs no utilizan todo el espacio.

Pero si ambas crecen:

```text
Storage lleno
↓
Problemas
```

Por eso:

> **Thin provisioning exige monitorización y planificación.**

---

# 43. Snapshots y almacenamiento

Los snapshots pueden consumir espacio adicional.

Por eso:

```text
Snapshot
↓
No es gratis
```

Cuanto más tiempo se mantienen y cuanto más cambian los datos, mayor puede ser su impacto en almacenamiento.

Esto es importante operativamente.

---

# 44. I/O y snapshots

Si una VM genera muchas escrituras:

```text
Muchos cambios
↓
Snapshot
↓
Mayor crecimiento potencial
```

Por ello los snapshots deben utilizarse con criterio.

---

# 45. Storage latency

Si el storage presenta:

```text
Latencia elevada
```

podemos tener:

```text
VM lenta
```

aunque:

```text
CPU = 20 %
RAM = 40 %
```

Esto demuestra nuevamente que:

> **Un problema de rendimiento no siempre es un problema de CPU.**

# 48. vNIC

La vNIC es la interfaz de red que ve la VM.

Por ejemplo:

```text
VM1
├── vNIC1
└── vNIC2
```

Puede utilizarse para separar tipos de tráfico.

---

# 49. vSwitch

El vSwitch funciona como un switch lógico.

Por ejemplo:

```text
VM1 ──┐
VM2 ──┼── vSwitch
VM3 ──┘
```

También puede conectarse a:

```text
NIC física
```

para acceder a la red externa.

---

# 50. Red física y virtual

```text
                    HOST
                     │
          ┌──────────┴──────────┐
```

---

# 51. VLAN

Las VLAN permiten segmentar lógicamente una red física.

Por ejemplo:

```text
VLAN 10
Gestión

VLAN 20
Producción

VLAN 30
Storage
```

Esto puede permitir separar tráfico.

La configuración exacta depende de la plataforma y de la red física.

---

# 52. Tráfico de gestión

Puede existir una red específica para:

```text
Gestión del host
Gestión de VMs
Plataforma de virtualización
```

Esta red debe protegerse adecuadamente.

---

# 53. Tráfico de almacenamiento

También podemos tener:

```text
Storage traffic
```

especialmente importante cuando utilizamos almacenamiento compartido.

Podemos separar:

```text
Management
VM
Storage
Migration
```

mediante redes lógicas y/o físicas según el diseño.

---

# 54. Tráfico de migración

La migración entre hosts puede generar bastante tráfico.

Por ejemplo:

```text
Host A
 ↓
Memoria / estado VM
 ↓
Host B
```

Si tenemos varias migraciones simultáneas:

```text
Red
↓
Mayor utilización
```

Por eso la red debe dimensionarse adecuadamente.

---

# 55. NIC teaming

Podemos utilizar varias interfaces físicas para mejorar:

```text
Redundancia
+
Capacidad
```

Conceptualmente:

```text
vSwitch
  │
  ├── NIC1
  └── NIC2
```

Si:

```text
NIC1 ❌
```

podemos mantener conectividad mediante:

```text
NIC2
```

dependiendo de la configuración.

---

# 56. Redundancia de red

La idea completa:

```text
VM
│
├── vNIC A
│      ↓
│    vSwitch
│      ↓
│    NIC A
│
└── vNIC B
       ↓
     vSwitch
       ↓
     NIC B
```

Puede conectarse a switches físicos redundantes.

Así reducimos puntos únicos de fallo.

---

# 57. Redundancia no es solamente duplicar NIC

Podemos tener:

```text
2 NIC
```

pero:

```text
Ambas conectadas al mismo switch
```

Si el switch falla:

```text
NIC A ❌
NIC B ❌
```

Por eso debemos analizar:

```text
NIC
↓
Switch
↓
Enlace
↓
Red
```

---

# 58. Recursos compartidos

Hasta ahora hemos visto:

```text
CPU
RAM
Storage
Red
```

Todos ellos pueden ser compartidos entre VMs.

La virtualización permite convertirlos en:

```text
Pools de recursos
```

que pueden administrarse mediante políticas.

---

# 59. Resource Pool

Un resource pool puede agrupar recursos para un conjunto de VMs.

Conceptualmente:

```text
POOL
│
├── CPU
└── RAM
     │
 ┌───┼────┐
 │   │    │
VM1 VM2  VM3
```

Puede ayudar a organizar y controlar recursos.

---

# 60. Reserva

Una reserva puede garantizar una cantidad mínima de recursos.

Ejemplo:

```text
VM crítica
CPU:
Reserva = 2 GHz
```

Conceptualmente:

```text
Garantizado
↓
2 GHz
```

El comportamiento exacto depende de la plataforma.

---

# 61. Límite

El límite define un techo.

Ejemplo:

```text
VM
Límite CPU = 4 GHz
```

Aunque exista más capacidad disponible:

```text
Máximo configurado
↓
4 GHz
```

---

# 62. Shares

Las shares o prioridades relativas permiten decidir qué VM recibe mayor peso cuando existe competencia.

Por ejemplo:

```text
VM crítica
Shares = High

VM secundaria
Shares = Low
```

En situación de contención:

```text
VM crítica
↓
Mayor prioridad relativa
```

---

# 81. La paradoja de la virtualización

La virtualización permite:

```text
Reducir servidores físicos
```

pero puede aumentar:

```text
Dependencia de cada host
```

Por eso:

```text
Consolidación
+
Redundancia
```

deben ir juntas.

---

# 82. Ejemplo

Antes:

```text
Servidor A → Aplicación A
Servidor B → Aplicación B
Servidor C → Aplicación C
Servidor D → Aplicación D
```

Después:

```text
Host A
├── VM A
├── VM B
├── VM C
└── VM D
```

Si Host A falla:

```text
A
B
C
D
```

pueden verse afectados simultáneamente.

Por eso añadimos:

```text
Host B
Host C
```

y mecanismos de:

```text
HA
Migración
Redundancia
```

# 83. Concentración y blast radius

Un fallo físico puede afectar a muchas VMs.

Esto se denomina conceptualmente:

```text
Mayor blast radius
```

Es decir:

```text
Un único fallo
↓
Muchas cargas afectadas
```

La consolidación mejora eficiencia, pero debemos controlar este riesgo.

---

# 84. Anti-affinity

En determinadas plataformas podemos establecer reglas para evitar colocar ciertas VMs juntas.

Por ejemplo:

```text
VM1 ─┐
     ├── No mismo host
VM2 ─┘
```

Esto puede utilizarse para:

```text
Servidores redundantes
Controladores
Servicios críticos
```

La finalidad:

> **Evitar que un único fallo físico afecte a ambas instancias.**

---

# 85. Affinity

El concepto contrario puede ser:

```text
Affinity
```

que permite preferir que determinados recursos permanezcan juntos.

Ejemplo conceptual:

```text
VM1
+
VM2
↓
Mismo host
```

Puede utilizarse cuando existe una razón técnica o de rendimiento.

---

# 86. Anti-affinity vs affinity

```text
AFFINITY
↓
"Quiero que estén juntos."
```

```text
ANTI-AFFINITY
↓
"Quiero que estén separados."
```

**a) Contención.**

# 103. Storage del caso

Supongamos:

```text
VM1 → 20.000 IOPS
VM2 → 2.000 IOPS
VM3 → 3.000 IOPS
VM4 → 2.000 IOPS
```

Total aproximado:

```text
27.000 IOPS
```

Si nuestro almacenamiento soporta:

```text
10.000 IOPS
```

tenemos un problema.

Aunque:

```text
CPU = correcta
RAM = correcta
```

el storage será el cuello de botella.

---

# 104. Red del caso

Supongamos:

```text
NIC A
NIC B
```

Pero:

```text
NIC A → Switch A
NIC B → Switch A
```

Tenemos:

```text
Switch A
```

como dependencia crítica.

Una arquitectura más robusta sería:

```text
NIC A → Switch A

NIC B → Switch B
```

---

# 105. Memoria del caso

Supongamos:

```text
RAM física = 128 GB
RAM asignada = 96 GB
```

Tenemos:

```text
32 GB
```

de diferencia física disponible antes de considerar otros consumos.

No debemos interpretar esos 32 GB como:

```text
"RAM libre garantizada para las VMs"
```

porque el host y la plataforma también consumen recursos.

# 106. CPU del caso

```text
16 cores físicos
```
