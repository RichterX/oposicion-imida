# 1. NAS como sistema completo

Un error habitual es pensar:

``` text
NAS = discos
```

Realmente tenemos:

``` text
                NAS
                 │
      ┌──────────┼──────────┐
      │          │          │
    NETWORK    COMPUTE    STORAGE
      │          │          │
     NIC        CPU        RAID
     VLAN       RAM        Pool
     Switch     Cache      Volume
      │          │          │
      └──────────┼──────────┘
                 │
              SERVICES
                 │
            SMB / NFS
```

Por eso el rendimiento debe analizarse de extremo a extremo.

------------------------------------------------------------------------

# 2. Las tres métricas fundamentales

En almacenamiento aparecen constantemente:

``` text
IOPS
Throughput
Latency
```

------------------------------------------------------------------------

# 3. IOPS

> **IOPS = Input/Output Operations Per Second**

Indica cuántas operaciones de entrada/salida puede procesar el sistema
por segundo.

Ejemplo:

``` text
50.000 IOPS
```

significa aproximadamente:

``` text
50.000 operaciones de I/O por segundo
```

------------------------------------------------------------------------

# 4. Throughput

El:

> **Throughput**

indica la cantidad de datos transferidos por unidad de tiempo.

Ejemplos:

``` text
500 MB/s
1 GB/s
10 Gb/s
```

------------------------------------------------------------------------

# 5. Latencia

La:

> **Latency**

es el tiempo que tarda una operación en completarse.

Ejemplo:

``` text
1 ms
```

puede ser mucho mejor para determinadas cargas que:

``` text
20 ms
```

------------------------------------------------------------------------

# 6. IOPS vs throughput

Supongamos:

``` text
100 IOPS
×
1 MB
=
100 MB/s
```

Pero:

``` text
100.000 IOPS
×
4 KB
≈
390,6 MB/s
```

Por tanto:

> **IOPS por sí solo no indica el throughput.**

------------------------------------------------------------------------

# 7. Tamaño de bloque

La cantidad de datos transferida por operación importa.

Por ejemplo:

``` text
4 KB
```

frente a:

``` text
1 MB
```

puede producir resultados radicalmente diferentes.

------------------------------------------------------------------------

Antes de dimensionar un NAS debemos conocer:

``` text
Workload
```

Preguntas:

``` text

¿Archivos grandes?
¿Lectura?

¿Acceso aleatorio?
¿Acceso secuencial?

¿Cuántas aplicaciones?
```

# 9. Sequential workload

Un workload secuencial puede parecer:

``` text
A → B → C → D → E
```

Ejemplo:

``` text
Copiar un archivo de vídeo de 50 GB
```

------------------------------------------------------------------------

# 10. Random workload

Un workload aleatorio:

``` text
A → X → C → Z → B
```

Ejemplo:

``` text
Aplicación accediendo a miles de pequeños archivos
```

------------------------------------------------------------------------

``` text
10 millones de archivos pequeños
```

puede estar limitado por:

``` text
Metadata
Directory operations
Open/close
Permissions
Filesystem
```

aunque sus discos tengan mucho throughput secuencial.

# 15. Caché

Una:

> **Cache**

almacena temporalmente datos para acelerar operaciones futuras.

------------------------------------------------------------------------

# 16. Read cache

Una:

> **Read cache**

puede almacenar datos leídos recientemente.

Si vuelven a solicitarse:

``` text
Client
↓
Cache hit
↓
Return data
```

se evita acceder al almacenamiento físico.

------------------------------------------------------------------------

# 17. Cache hit

Cuando los datos están en caché:

``` text
Cache hit
```

------------------------------------------------------------------------

# 18. Cache miss

Cuando no están:

``` text
Cache miss
↓
Storage access
```

------------------------------------------------------------------------

# 19. Write cache

Una:

> **Write cache**

puede almacenar temporalmente datos pendientes de escribir.

Modelo:

``` text
Client
↓
Write cache
↓
Storage
```

------------------------------------------------------------------------

# 20. Ventaja

Puede reducir la latencia percibida de determinadas escrituras.

------------------------------------------------------------------------

# 21. Riesgo

Si tenemos:

``` text
Write cache
+
Power loss
```

podemos perder datos que todavía no hayan llegado al almacenamiento
persistente.

------------------------------------------------------------------------

# 22. BBU / protección de caché

Algunos sistemas empresariales protegen la caché mediante:

``` text
Battery Backup Unit
```

o tecnologías equivalentes.

------------------------------------------------------------------------

# 23. Flash-backed cache

Otros sistemas utilizan:

``` text
Flash
```

para proteger datos pendientes de escritura.

------------------------------------------------------------------------

# 24. Regla de oro

> **Write-back cache debe disponer de una estrategia de protección
> adecuada.**

------------------------------------------------------------------------

# 25. SSD cache

Algunos NAS permiten utilizar:

``` text
SSD
```

como caché frente a discos HDD.

Conceptualmente:

``` text
Clients
   ↓
NAS
   ↓
SSD Cache
   ↓
HDD Storage
```

------------------------------------------------------------------------

# 26. ¿Siempre mejora?

No.

Depende del:

``` text
Workload
Cache size
Access pattern
Read/write ratio
NAS implementation
```

------------------------------------------------------------------------

# 27. SSD cache y sequential workload

Si el workload es:

``` text
Large sequential files
```

la caché puede tener un beneficio limitado.

------------------------------------------------------------------------

# 28. SSD cache y random workload

En determinados workloads aleatorios:

``` text
Random reads
Small blocks
```

una caché SSD puede resultar mucho más útil.

------------------------------------------------------------------------

# 29. Network bottleneck

Aunque tengamos:

``` text
Fast SSD
Fast RAID
```

si la red es:

``` text
1 GbE
```

puede convertirse en el cuello de botella.

# 31. Capacidad

Otra dimensión fundamental:

``` text
Performance
+
Capacity
```

Un NAS debe dimensionarse para ambas.

------------------------------------------------------------------------

# 32. Raw capacity

Si tenemos:

``` text
4 × 10 TB
```

la capacidad bruta es:

``` text
40 TB
```

------------------------------------------------------------------------

# 33. Usable capacity

Después de:

``` text
RAID
Metadata
Filesystem
Snapshots
Reserved space
```

la capacidad utilizable será menor.

------------------------------------------------------------------------

# 34. RAID 6 ejemplo

Con:

``` text
6 × 10 TB
```

en RAID 6, aproximadamente:

``` text
40 TB
```

de capacidad antes de otros overheads.

------------------------------------------------------------------------

# 35. Capacidad no es rendimiento

Más capacidad:

``` text
≠
Más rendimiento
```

Y más rendimiento:

``` text
≠
Más capacidad
```

# 36. Capacity planning

``` text

+

+

+

+

+
```

------------------------------------------------------------------------

# 37. Crecimiento

Si una empresa genera:

``` text
2 TB/month
```

y tenemos:

``` text
20 TB free
```

podemos estimar aproximadamente:

``` text
10 months
```

sin considerar overheads ni cambios de crecimiento.

# 38. Growth rate

``` text
Linear
```

o:

``` text

```

# 39. Capacity monitoring

``` text

Snapshot usage
```

# 40. Thin provisioning

> **Thin provisioning**

permite presentar más capacidad lógica de la físicamente disponible.

Ejemplo:

``` text
Physical:
100 TB

Logical:
150 TB
```

------------------------------------------------------------------------

# 41. Ventaja

Permite aprovechar mejor el almacenamiento cuando no todos los
consumidores utilizan su capacidad asignada simultáneamente.

------------------------------------------------------------------------

# 42. Riesgo

Si el consumo real supera:

``` text
Physical capacity
```

podemos quedarnos sin espacio.

------------------------------------------------------------------------

# 43. Overprovisioning

Thin provisioning puede producir:

``` text
Overprovisioning
```

------------------------------------------------------------------------

# 44. Ejemplo

``` text
NAS physical = 100 TB

Share A = 50 TB
Share B = 50 TB
Share C = 50 TB
```

Tenemos:

``` text
150 TB logical
```

sobre:

``` text
100 TB physical
```

# 45. Monitorización de thin provisioning

# 46. Deduplicación

> **Deduplication**

elimina bloques o datos duplicados para ahorrar espacio.

Ejemplo:

``` text
File A
File B
```

comparten grandes cantidades de información.

En lugar de almacenar dos veces:

``` text
Data
Data
```

podemos almacenar:

``` text
Data
↙  ↘
A   B
```

------------------------------------------------------------------------

# 47. Beneficio

Puede reducir:

``` text
Storage consumption
```

especialmente en workloads con mucha redundancia.

------------------------------------------------------------------------

# 48. Coste

La deduplicación puede requerir:

``` text
CPU
RAM
Metadata
```

------------------------------------------------------------------------

# 49. Compresión

La:

> **Compression**

reduce el tamaño de los datos representándolos de forma más eficiente.

------------------------------------------------------------------------

# 50. Dedup vs compression

``` text
Deduplication
→ elimina duplicados

Compression
→ reduce representación de los datos
```

Pueden coexistir.

------------------------------------------------------------------------

# 51. Snapshots

Una snapshot representa:

``` text
Estado de los datos
en un momento determinado
```

------------------------------------------------------------------------

# 52. Copy-on-write

Una técnica habitual es:

> **Copy-on-write**

Conceptualmente:

``` text
Original data
↓
Snapshot
```

Cuando se modifica un bloque:

``` text
Original
↓
Preserved for snapshot

New version
↓
Written elsewhere
```

------------------------------------------------------------------------

# 53. Snapshot space

Las snapshots pueden consumir capacidad adicional.

Si muchos datos cambian:

``` text
Snapshot space
↑
```

------------------------------------------------------------------------

# 54. Retención

Una política puede ser:

``` text
Hourly → 24
Daily → 7
Weekly → 4
Monthly → 12
```

El esquema real depende del negocio.

------------------------------------------------------------------------

# 55. Snapshot retention

Retención excesiva:

``` text
Storage consumption ↑
```

Retención insuficiente:

``` text
Recovery options ↓
```

------------------------------------------------------------------------

# 56. Snapshot y backup

De nuevo:

``` text
Snapshot
≠
Backup
```

Una snapshot normalmente depende del sistema donde reside.

------------------------------------------------------------------------

# 57. Backup

Un:

> **Backup**

es una copia mantenida con el objetivo de recuperar datos.

------------------------------------------------------------------------

# 58. Backup vs snapshot

  -----------------------------------------------------------------------
  Característica          Snapshot                Backup
  ----------------------- ----------------------- -----------------------
  Recuperación rápida     Sí                      Puede ser más lenta

  Vive en mismo sistema   Frecuente               No debería ser el único
                                                  destino

  Protección ante pérdida Limitada si solo está   Sí, si existe copia
  NAS                     allí                    independiente

  Historial               Sí                      Sí

  Sustituto completo      No                      Sí, como parte de una
                                                  estrategia
  -----------------------------------------------------------------------

# 61. Inmutabilidad

Una copia:

> **Immutable**

no puede modificarse o eliminarse durante el periodo protegido.

------------------------------------------------------------------------

# 62. Ransomware

La inmutabilidad puede ayudar frente a:

``` text
Ransomware
```

porque el atacante no debería poder modificar/eliminar la copia
protegida.

------------------------------------------------------------------------

# 63. Air gap

Un:

> **Air gap**

separa físicamente o lógicamente la copia del sistema de producción.

Conceptualmente:

``` text
Production
     X
Backup
```

------------------------------------------------------------------------

# 64. NAS y ransomware

Una estrategia robusta puede combinar:

``` text
RAID
+
Snapshots
+
Backup

+
Offsite
```

# 65. Replication

La:

> **Replication**

mantiene una copia de los datos en otro sistema.

Ejemplo:

``` text
NAS A
  │
  │ Replication
  ▼
NAS B
```

------------------------------------------------------------------------

# 66. Replicación síncrona

En replicación síncrona:

``` text
Write
↓
Primary + Secondary
↓
Acknowledgement
```

dependiendo de la implementación.

------------------------------------------------------------------------

# 67. Ventaja

Puede reducir:

``` text
RPO
```

porque los datos se replican prácticamente al mismo tiempo.

------------------------------------------------------------------------

# 68. Coste

La sincronía puede requerir:

``` text
Low latency
Reliable network
More bandwidth
```

------------------------------------------------------------------------

# 69. Replicación asíncrona

En replicación asíncrona:

``` text
Primary
↓
Replication
↓
Secondary
```

existe cierto retraso.

------------------------------------------------------------------------

# 70. Ventaja

Puede ser más adecuada para:

``` text
Long-distance replication
```

------------------------------------------------------------------------

# 71. Desventaja

Existe un:

``` text
Replication lag
```

y puede perderse parte de los cambios recientes si el primario falla.

------------------------------------------------------------------------

# 72. RPO

Recordemos:

> **RPO = Recovery Point Objective**

Indica cuánto dato podemos permitirnos perder.

------------------------------------------------------------------------

# 73. Ejemplo

``` text
RPO = 15 min
```

significa que idealmente no deberíamos perder más de:

``` text
15 minutes of data
```

------------------------------------------------------------------------

# 74. RTO

> **RTO = Recovery Time Objective**

Indica cuánto tiempo podemos tardar en restaurar el servicio.

------------------------------------------------------------------------

# 75. Ejemplo

``` text
RTO = 2 hours
```

El servicio debería recuperarse dentro de ese objetivo.

------------------------------------------------------------------------

# 76. RPO vs RTO

``` text
RPO
→ cuánto dato puedo perder

RTO
→ cuánto tiempo puedo estar sin servicio
```
