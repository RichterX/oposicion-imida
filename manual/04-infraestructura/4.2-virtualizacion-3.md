# 1. El ciclo de vida de una máquina virtual

Una VM no aparece directamente en producción.

Normalmente existe un ciclo:

```text
Planificación
    ↓
Creación
    ↓
Configuración
    ↓
Despliegue
    ↓
Operación
    ↓
Mantenimiento
    ↓
Migración / modificación
    ↓
Backup / protección
    ↓
Retirada
```

Podemos dividirlo en:

```text
BUILD
↓
RUN
↓
PROTECT
↓
RETIRE
```

# 3. No crear VMs sin control

Una infraestructura virtualizada puede crecer rápidamente.

Por ejemplo:

```text
Lunes
10 VMs

Viernes
35 VMs
```

Si no existe control:

```text
VM sprawl
```

El **VM sprawl** es el crecimiento descontrolado de máquinas virtuales.

Puede producir:

- Consumo innecesario de CPU.
- Consumo de RAM.
- Consumo de almacenamiento.
- Riesgos de seguridad.
- Dificultades de inventario.
- VMs olvidadas.
- Costes innecesarios.

# 11. Clon completo

Un clon completo es una copia independiente de la VM original.

Conceptualmente:

```text
VM Original
    ↓
Copia
    ↓
VM Clon
```

El clon tiene sus propios recursos de almacenamiento.

Ventaja:

```text
Independencia
```

Desventaja:

```text
Más consumo de storage
```

---

# 12. Clon enlazado

Un clon enlazado puede depender de discos o bloques de una VM base.

Conceptualmente:

```text
Base
 │
 ├── Clone 1
 ├── Clone 2
 └── Clone 3
```

Ventaja:

```text
Menor consumo inicial
```

Desventaja:

```text
Dependencia de la base
+
Mayor complejidad
```

La disponibilidad y comportamiento exactos dependen de la plataforma.

---

# 13. Full clone vs linked clone

| Característica | Full clone | Linked clone |
|---|---|---|
| Independencia | Alta | Depende de base |
| Storage inicial | Mayor | Menor |
| Dependencia | Menor | Mayor |
| Uso típico | Entornos permanentes | Labs / testing |

# 17. Snapshot

Un snapshot representa una captura del estado de una VM en un momento determinado, según la plataforma.

Conceptualmente:

```text
VM
│
├── Estado actual
│
└── Snapshot
      ↓
   Punto de referencia
```

---

# 18. ¿Para qué utilizar un snapshot?

Un uso habitual es:

```text
Antes de un cambio importante
↓
Crear snapshot
↓
Realizar cambio
↓
Comprobar
```

Si el cambio falla:

```text
Rollback
```

Esto puede ser útil para:

- Actualizaciones.
- Cambios de configuración.
- Pruebas controladas.

---

# 19. Snapshot no es backup

Esta distinción debe quedar grabada:

```text
SNAPSHOT
↓
Punto de estado operativo
```

```text
BACKUP
↓
Copia destinada a recuperación
```

Un snapshot puede depender del mismo sistema de almacenamiento que la VM.

Si ese almacenamiento falla:

```text
VM ❌
Snapshot ❌
```

Por tanto:

> **No debemos utilizar snapshots como sustituto de una estrategia de backup.**

---

# 20. El problema de los snapshots largos

Supongamos:

```text
Día 1
Snapshot
```

Y mantenemos la VM durante:

```text
30 días
```

mientras los datos cambian continuamente.

El snapshot puede acumular cambios según el mecanismo utilizado.

Resultado:

```text
Más consumo
+
Mayor complejidad
+
Mayor riesgo operativo
```

Por eso:

> **Los snapshots deben tener una finalidad y una duración controladas.**

---

# 21. Snapshot antes de actualizar

Ejemplo:

```text
Servidor
↓
Snapshot
↓
Actualización
↓
Prueba
```

Si todo funciona:

```text
Eliminar snapshot
```

No:

```text
"Lo dejo por si acaso durante seis meses."
```

---

# 22. Backup

Un backup es una copia destinada a permitir recuperación ante pérdida o corrupción.

Podemos proteger:

```text
VM completa
Discos
Configuración
Datos
Aplicaciones
```

dependiendo de la solución.

---

# 23. Backup vs snapshot

| Característica | Snapshot | Backup |
|---|---|---|
| Objetivo principal | Estado operativo | Recuperación |
| Protección ante fallo del mismo storage | Limitada | Puede ser alta si es independiente |
| Retención | Generalmente corta | Puede ser larga |
| Uso | Cambios / rollback | Recuperación |
| Sustituto del backup | ❌ | ✅ |

---

# 24. Backup de VMs

Una estrategia puede ser:

```text
VM
 ↓
Backup
 ↓
Repositorio independiente
```

Idealmente:

```text
Host / Storage
       ↓
Backup
       ↓
Otro sistema
```

Esto reduce el riesgo de perder:

```text
VM
+
Backup
```

simultáneamente.

---

# 25. Regla 3-2-1

Una estrategia clásica de backup es:

```text
3 copias
2 medios diferentes
1 copia fuera del sitio
```

Ejemplo:

```text
Producción
   ↓
Backup local
   ↓
Backup secundario
   ↓
Copia externa
```

Los detalles pueden adaptarse a las necesidades de la organización.

---

# 26. Retención

No todos los backups deben conservarse para siempre.

Podemos definir:

```text
Diarios
Semanales
Mensuales
Anuales
```

según:

```text
Política
Normativa
Necesidades de negocio
Capacidad
```

---

# 27. Backup completo

Un backup completo copia el conjunto definido de datos.

Ventaja:

```text
Restauración sencilla
```

Desventaja:

```text
Más espacio
+
Más tiempo
```

---

# 28. Backup incremental

Un incremental copia los cambios desde el último backup correspondiente según la estrategia utilizada.

Conceptualmente:

```text
Full
↓
Incremental 1
↓
Incremental 2
↓
Incremental 3
```

Ventaja:

```text
Menos datos por ejecución
```

Desventaja:

```text
Restauración puede requerir varios conjuntos
```

---

# 29. Backup diferencial

Un diferencial copia cambios desde el último backup completo.

Ejemplo:

```text
Full
↓
Diff 1
↓
Diff 2
↓
Diff 3
```

Cada diferencial puede crecer respecto al full.

---

# 30. Full vs incremental vs diferencial

| Tipo | Referencia |
|---|---|
| Full | Todo el conjunto |
| Incremental | Cambios desde el backup anterior correspondiente |
| Diferencial | Cambios desde el último full |

---

# 31. Restauración

El valor de un backup no está en:

```text
"Tener muchos archivos."
```

Está en:

```text
Poder recuperar.
```

Por eso:

> **Un backup que nunca se ha probado no debe considerarse una garantía absoluta de recuperación.**

---

# 32. Pruebas de restauración

Debemos comprobar:

```text
Backup
↓
Restore
↓
Validación
```

Por ejemplo:

```text
¿Arranca la VM?
¿Arranca el SO?
¿Funcionan las aplicaciones?
¿Los datos son correctos?
¿La red funciona?
```

# 33. Migración

La migración consiste en mover una VM o sus recursos de un lugar a otro.

Podemos migrar:

```text
VM
```

entre:

```text
Hosts
```

o:

```text
Storage
```

entre:

```text
Datastores
```

---

# 34. Migración en frío

Proceso:

```text
Apagar VM
↓
Mover
↓
Encender VM
```

Ventaja:

```text
Más sencilla
```

Desventaja:

```text
Interrupción
```

---

# 35. Migración en caliente

También llamada:

> **Live migration**

Permite mover una VM mientras permanece encendida, reduciendo la interrupción.

Conceptualmente:

```text
Host A
  │
  │ VM ejecutándose
  │
  ├──────────────→ Host B
  │
  │
Servicio continúa
```

---

# 36. ¿Cómo puede moverse una VM encendida?

Conceptualmente:

```text
1. Preparar destino
2. Reservar recursos
3. Copiar estado / memoria
4. Mantener sincronización
5. Transferir cambios finales
6. Cambiar ejecución al destino
7. Liberar origen
```

No necesitamos memorizar todavía el algoritmo concreto de una plataforma.

Lo importante es:

> **La VM puede trasladarse sin realizar un apagado convencional.**

---

# 37. Requisitos de live migration

Dependiendo de la plataforma pueden ser necesarios:

```text
Compatibilidad de CPU
Red adecuada
Recursos disponibles
Storage compatible
Configuración de red
Permisos
```

Por tanto:

> **Live migration no significa "puedo mover cualquier VM a cualquier servidor".**

---

# 38. Migración de almacenamiento

Podemos mover:

```text
VM
```

de:

```text
Datastore A
```

a:

```text
Datastore B
```

sin necesariamente moverla a otro host.

Conceptualmente:

```text
VM
 ↓
Datastore A
 ↓
Datastore B
```

Esto puede utilizarse para:

- Mantenimiento.
- Balanceo de almacenamiento.
- Migración tecnológica.
- Liberación de capacidad.

---

# 39. Migración de host y storage

Podemos tener:

```text
Migración de compute
```

y:

```text
Migración de storage
```

Son conceptos diferentes.

### Compute

```text
Host A
↓
Host B
```

### Storage

```text
Datastore A
↓
Datastore B
```

---

# 40. Migración combinada

Algunas plataformas permiten mover simultáneamente:

```text
Host
+
Storage
```

Esto proporciona mayor flexibilidad.

Conceptualmente:

```text
Host A + Storage A
          │
          ↓
Host B + Storage B
```

---

# 41. Alta disponibilidad

La alta disponibilidad, o:

> **HA - High Availability**

busca reducir el tiempo durante el cual un servicio permanece indisponible tras un fallo.

En virtualización:

```text
Host A
↓
Falla
↓
Host B
↓
VM recuperada
```

---

# 42. HA no es tolerancia a fallos

Debemos distinguir:

```text
HA
```

de:

```text
Fault Tolerance
```

HA puede implicar:

```text
Reinicio
```

mientras que una tecnología de tolerancia a fallos puede intentar:

```text
Continuidad prácticamente inmediata
```

Las capacidades concretas dependen de la plataforma.

---

# 43. HA y reinicio

Un escenario típico:

```text
Host A
├── VM1
├── VM2
└── VM3
```

Falla:

```text
Host A ❌
```

El sistema HA puede detectar:

```text
Host failure
```

y:

```text
Registrar VMs afectadas
↓
Seleccionar host disponible
↓
Reiniciar VMs
```

---

# 44. HA implica interrupción

Si una VM estaba ejecutándose y el host muere:

```text
VM
↓
Fallo
↓
Reinicio
```

Existe un intervalo de indisponibilidad.

Por tanto:

```text
HA
≠
Cero downtime
```

---

# 45. Fault Tolerance

Una arquitectura de tolerancia a fallos busca mantener una instancia redundante sincronizada.

Conceptualmente:

```text
VM primaria
     │
     │ sincronización
     ▼
VM secundaria
```

Si la primaria falla:

```text
Secundaria
↓
Continúa
```

Esto puede reducir drásticamente la interrupción.

No todas las plataformas o cargas soportan esta capacidad de la misma forma.

---

# 46. HA vs FT

| Concepto | Idea |
|---|---|
| HA | Recuperación / reinicio tras fallo |
| FT | Continuidad mediante redundancia sincronizada |

Para examen:

```text
HA
→ Recupera

FT
→ Mantiene continuidad
```

Es una simplificación conceptual, pero útil para recordar la diferencia.

---

# 47. Clúster

Para proporcionar HA normalmente necesitamos varios hosts.

```text
CLÚSTER
│
├── Host A
├── Host B
└── Host C
```

Las VMs pueden distribuirse entre ellos.

---

# 48. Recursos del clúster

Un clúster permite contemplar recursos como:

```text

```

Esto facilita:


# 49. Failover

Cuando un servicio pasa de un recurso principal a otro disponible hablamos de:

> **Failover**

Conceptualmente:

```text
Primario
   ↓
Fallo
   ↓
Secundario
```

---

# 50. Failback

Después de recuperar el recurso original:

```text
Secundario
↓
Primario
```

podemos realizar:

> **Failback**

No siempre es necesario hacerlo inmediatamente.

---

# 51. Heartbeat

Los sistemas de alta disponibilidad necesitan detectar si un componente está operativo.

Un mecanismo habitual es un:

> **Heartbeat**

Conceptualmente:

```text
Host A
  ↓
"Estoy vivo"

Host B
  ↓
"Estoy vivo"
```

Si un nodo deja de responder:

```text
Heartbeat perdido
↓
Posible fallo
```

La plataforma realiza mecanismos adicionales para confirmar el estado y evitar falsos positivos.

---

# 52. Split-brain

Un problema clásico en sistemas distribuidos es:

> **Split-brain**

Ocurre cuando diferentes nodos creen que tienen autoridad o que el otro ha fallado.

Conceptualmente:

```text
Host A
"Host B está muerto"

Host B
"Host A está muerto"
```

Ambos podrían intentar asumir responsabilidades.

Esto puede provocar:

```text
Corrupción
Conflictos
Comportamientos inconsistentes
```

---

# 53. Quorum

Para evitar determinados problemas de coordinación pueden utilizarse mecanismos de:

> **Quorum**

La idea:

```text
Mayoría
↓
Decisión válida
```

El funcionamiento concreto depende de la tecnología.

---

> **Recovery Point Objective**

> **Recovery Time Objective**


Conceptualmente:

> El servicio debería recuperarse dentro de aproximadamente una hora.

|---|---|

| Mayor sensibilidad a latencia | Más adecuada para distancia |

|---|---|

| Normalmente mismo entorno | Puede implicar otro sitio |
| Fallos de componentes | Desastres mayores |
| Recuperación rápida | Recuperación planificada |

# 121. ⚠️ Trampas de examen

## Trampa 1

> "Snapshot = backup."

❌ Falso.

---

## Trampa 2

> "HA garantiza cero downtime."

❌ Falso.

HA puede requerir reinicio de la VM.

---

## Trampa 3

> "Live migration permite mover cualquier VM a cualquier host."

❌ Falso.

Existen requisitos de compatibilidad.

---

## Trampa 4

> "Replicación sustituye siempre al backup."

❌ Falso.

Una corrupción o eliminación puede replicarse.

---

## Trampa 5

> "Un host redundante elimina todos los puntos únicos de fallo."

❌ Falso.

Puede existir:

```text
Storage
Red
Electricidad
Switch
```

como SPOF.

---

## Trampa 6

> "Una VM clonada puede utilizarse inmediatamente como copia idéntica en producción."

⚠️ Riesgo.

Puede contener:

```text
Hostname
IP
MAC
Identidad
Certificados
```

duplicados.

---

## Trampa 7

> "HA = FT."

❌ No.

Son mecanismos conceptualmente diferentes.

---

## Trampa 8

> "DR = HA."

❌ No.

HA resuelve determinados fallos operativos; DR aborda desastres mayores.
