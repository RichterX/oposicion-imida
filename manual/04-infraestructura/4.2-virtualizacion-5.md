# 1. La seguridad en virtualización

Virtualizar no elimina la necesidad de seguridad.

De hecho, introduce nuevas capas:

```text
Físico
↓
Hipervisor
↓
Management
↓
Red virtual
↓
VM
↓
Aplicación
```

Cada capa debe protegerse.

---

# 2. Superficie de ataque

Una plataforma virtualizada puede exponer:

```text
Host
Hipervisor
vCenter / Management
APIs
Redes virtuales
Storage
VMs
Backups
Credenciales
```

Un atacante que comprometa el plano de gestión puede obtener capacidades sobre muchas VMs.

---

# 3. Blast radius

El:

> **Blast radius**

es el alcance potencial de un incidente.

En un servidor físico:

```text
Servidor comprometido
↓
Una carga principal
```

En virtualización:

```text
Host comprometido
↓
Muchas VMs
```

Por tanto:

> **La consolidación mejora eficiencia, pero aumenta la concentración de impacto.**

---

# 4. Hipervisor como objetivo crítico

Si un atacante compromete el hipervisor:

```text
VM1
VM2
VM3
VM4
```

pueden quedar expuestas.

Por eso el hipervisor debe recibir:

```text
Parches
Hardening
Control de acceso
Monitorización
Auditoría
```

---

# 5. Management plane

El plano de gestión permite realizar acciones como:

```text

Eliminar VM
Migrar VM
Modificar CPU
Modificar RAM
Cambiar redes
Administrar hosts
```

Es una de las zonas más sensibles.

# 6. Principio de mínimo privilegio

Ejemplo:



# 8. MFA

> **Multi-Factor Authentication**

```text

+
Segundo factor
```

# 11. Hardening

El:

> **Hardening**

consiste en reducir la superficie de ataque de un sistema.

Puede incluir:

```text
Desactivar servicios innecesarios
Cerrar puertos
Limitar accesos
Aplicar parches
Configurar autenticación
Eliminar cuentas innecesarias
Aplicar políticas
```

---

# 12. Hardening del host

Un host virtualizado debería:

```text
Estar actualizado
Tener configuración segura
Tener acceso restringido
Estar monitorizado
Tener logs
```

---

# 13. Hardening de la VM

La VM también necesita:

```text
Parches
Firewall
Usuarios seguros
Antimalware cuando proceda
Logs
Actualizaciones
```

La virtualización no sustituye la seguridad del sistema operativo.

Conceptualmente:

```text
VM1
│
├── Recursos virtuales propios
│
VM2
│
├── Recursos virtuales propios
```

El hipervisor controla el acceso a los recursos físicos.

# 24. Microsegmentación

La:

> **Microsegmentación**

lleva la segmentación a un nivel más granular.

En lugar de:

```text
Red A
Red B
```

podemos establecer políticas:

```text
VM1 → VM2 permitido
VM1 → VM3 bloqueado
```

según identidad, aplicación o política.

---

# 25. Firewall distribuido

Conceptualmente:

```text

↓
Firewall distribuido
↓
Otra VM
```

Esto puede reducir la dependencia de un firewall físico central para determinadas políticas internas.


```text

↔

```

La microsegmentación es especialmente importante para controlar tráfico este-oeste.

# 33. CPU Ready

En virtualización, una VM puede estar preparada para ejecutar instrucciones pero esperando tiempo de CPU físico.

Conceptualmente:

```text
VM quiere CPU
↓
CPU física ocupada
↓
VM espera
```

Este tiempo puede reflejar:

> **CPU Ready**

Un valor elevado sostenido puede indicar contención.

---

# 34. CPU contention

Ejemplo:

```text
Host
32 cores físicos

VMs
100 vCPU
```

Puede existir:

```text
Overcommit
```

Si todas las VMs demandan CPU simultáneamente:

```text
Contención
```

---

# 35. Oversubscription

La:

> **Oversubscription**

consiste en asignar virtualmente más recursos de los físicamente disponibles.

Ejemplo:

```text
32 cores físicos
64 vCPU
```

Esto no significa necesariamente que esté mal.

Depende de:

```text
Patrón de carga
Picos
Contención
Aplicaciones
```

---

# 36. Oversubscription de memoria

También puede existir:

```text
RAM física
<
RAM virtual asignada
```

Las plataformas pueden utilizar mecanismos como:

```text
Ballooning
Compresión
Swapping
```

según la tecnología.

---

# 37. Monitorización de memoria

Debemos observar:

```text
Uso
Ballooning
Compression
Swap
Active memory
```

Si existe swapping excesivo:

```text
Rendimiento ↓
```

# 38. Storage latency

Uno de los indicadores más importantes del almacenamiento es:

> **Latencia**

Si una VM tarda mucho en leer o escribir:

```text
Aplicación lenta
```

aunque:

```text
CPU = 20 %
RAM = 40 %
```

---

# 39. Diagnóstico por capas

Cuando una VM está lenta:

```text
Aplicación
↓
Guest OS
↓
VM
↓
Host
↓
Storage / Network
↓
Infraestructura física
```

No debemos asumir inmediatamente:

```text
CPU alta
```

---

# 40. Caso de troubleshooting

Usuario:

> "La base de datos está lenta."

Observamos:

```text
CPU VM = 30 %
RAM = 50 %
```

Podríamos pensar:

```text
CPU/RAM correctas
```

Pero vemos:

```text
Storage latency = elevada
```

Posible conclusión:

```text
Problema de I/O
```

---

# 41. Storage contention

Supongamos:

```text
VM A → 30.000 IOPS
VM B → 2.000 IOPS
VM C → 2.000 IOPS
```

Si el datastore no puede proporcionar el rendimiento:

```text
Contención
```

---

# 42. Network troubleshooting

Si una VM no tiene conectividad:

```text
1. Guest NIC
2. IP
3. Gateway
4. DNS
5. vNIC
6. Port Group
7. VLAN
8. vSwitch
9. Uplink
10. Switch físico
```

---

# 43. Orden lógico

No conviene saltar directamente a:

```text
"El switch físico está roto."
```

Primero debemos comprobar:

```text
¿La VM tiene IP?
¿La NIC está conectada?
¿El port group es correcto?
¿La VLAN es correcta?
```

---

# 44. Storage troubleshooting

Si una VM tiene problemas de I/O:

```text

↓
Virtual disk
↓
Controller
↓
Datastore
↓
Path
↓
Network / Fabric
↓

```

Debemos localizar dónde aparece la latencia.

---

# 45. Host troubleshooting

Si varias VMs están lentas simultáneamente:

```text
VM1 lenta
VM2 lenta
VM3 lenta
```

es más probable que debamos investigar:

```text
Host
Storage
Network
```

en lugar de asumir que las tres aplicaciones fallaron simultáneamente.

# 46. Correlación


# 47. Baseline de rendimiento

Debemos conocer el comportamiento normal.

Ejemplo:

```text
CPU normal: 30-50 %
Storage latency normal: 2-5 ms

```

```text

```

tenemos una desviación clara.

> **Nested virtualization**

Conceptualmente:

```text

↓

↓
```

# 51. ¿Para qué sirve?

Puede utilizarse para:



# 57. VM vs contenedor

## Máquina virtual

```text

↓
Hipervisor
↓
VM
↓

↓

```

## Contenedor

```text

↓

↓

↓

```

---

# 58. Diferencia fundamental

Una VM normalmente virtualiza:

```text
Una máquina completa
```

mientras que un contenedor comparte:

```text
Kernel del sistema operativo
```

con otros contenedores.

---


---

# 60. Ventajas de VMs

Las VMs proporcionan:

```text
Mayor aislamiento

```

---

# 61. VM vs container

| Característica | VM | Contenedor |
|---|---|---|
| Guest OS | Sí | Comparte kernel |
| Overhead | Mayor | Menor |
| Aislamiento | Alto | Alto, pero diferente |
| Arranque | Más lento | Muy rápido |
| SO diferente | Sí | Depende del host/kernel |
| Densidad | Menor | Mayor |

# 124. 🧠 Superresumen

Si tuvieras que explicar todo 4.2 en dos minutos:

> La virtualización permite abstraer recursos físicos mediante un hipervisor para ejecutar múltiples máquinas virtuales sobre un mismo hardware. Cada VM dispone de recursos virtuales como CPU, memoria, almacenamiento y red, que finalmente dependen de recursos físicos.

> En entornos empresariales se agrupan hosts en clústeres para proporcionar capacidades como alta disponibilidad, migración y gestión de recursos. Tecnologías como vMotion permiten migrar VMs entre hosts, mientras Storage vMotion permite mover su almacenamiento. DRS ayuda a gestionar y equilibrar recursos, y mecanismos como HA permiten recuperar cargas ante determinados fallos.

> El almacenamiento puede ser local o compartido mediante tecnologías como NAS y SAN. La redundancia mediante múltiples caminos, controladoras y dispositivos reduce puntos únicos de fallo. El diseño debe contemplar capacidad suficiente para fallos y mantenimiento, por ejemplo mediante arquitecturas N+1.

> La protección requiere diferenciar snapshots, backups y replicación. Snapshot sirve principalmente como punto temporal de rollback, mientras que el backup está orientado a recuperación. RPO define cuánto dato puede perderse y RTO cuánto tiempo puede tardarse en recuperar el servicio.

> La infraestructura debe proteger el hipervisor, el plano de gestión, las redes, el storage y las VMs mediante hardening, mínimo privilegio, RBAC, MFA, segmentación, monitorización y auditoría.

> Finalmente, la virtualización no debe confundirse con contenedores. Una VM virtualiza una máquina completa con su sistema operativo invitado, mientras que los contenedores comparten el kernel del sistema operativo anfitrión.
