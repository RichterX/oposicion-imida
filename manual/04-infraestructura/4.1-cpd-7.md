# 1. El CPD como sistema

Después de estudiar cada componente por separado, debemos cambiar la perspectiva.

Un CPD no es:

```text
Un conjunto de servidores
```

Es un sistema formado por múltiples subsistemas interdependientes.

Podemos representarlo así:

```text
                         CPD
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
    CÓMPUTO              RED             STORAGE
       │                  │                  │
       └──────────────────┼──────────────────┘
                          │
                    INFRAESTRUCTURA
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
   ELECTRICIDAD        CLIMATIZACIÓN      SEGURIDAD
       │                  │                  │
       └──────────────────┼──────────────────┘
                          │
                    OPERACIÓN
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
  MONITORIZACIÓN       CAMBIOS          MANTENIMIENTO
       │                  │                  │
       └──────────────────┼──────────────────┘
                          │
                    DISPONIBILIDAD
```

La disponibilidad final depende de todas estas piezas.

---

# 2. Primera regla del CPD

La primera gran regla que debemos recordar es:

> **No debemos diseñar componentes aislados. Debemos diseñar sistemas completos.**

Por ejemplo:

```text
Servidor redundante
```

no garantiza alta disponibilidad si:

```text
Único switch
```

es un punto único de fallo.

Del mismo modo:

```text
Dos UPS
```

no garantizan una infraestructura redundante si:

```text
Ambos dependen del mismo cuadro eléctrico
```

Y:

```text
Dos sistemas HVAC
```

no garantizan resiliencia si ambos dependen de:

```text
Una única fuente eléctrica crítica
```

---

# 3. El principio de extremo a extremo

Cuando analicemos una infraestructura debemos recorrer toda la cadena.

Por ejemplo, para alimentación:

```text
RED
 ↓
TRANSFORMACIÓN
 ↓
UPS
 ↓
DISTRIBUCIÓN
 ↓
PDU
 ↓
FUENTE SERVIDOR
 ↓
SERVIDOR
```

Preguntamos:

> ¿Dónde puede fallar?

---

# 4. Ejemplo de análisis de extremo a extremo

Tenemos:

```text
UPS A
UPS B
```

Parece redundante.

Pero:

```text
UPS A ─┐
       ├── Cuadro único ── PDU ── Servidor
UPS B ─┘
```

Si falla:

```text
Cuadro único ❌
```

ambos caminos pueden perderse.

Conclusión:

```text
Dos UPS
≠
Dos caminos independientes
```

---

# 5. Redundancia real

La redundancia debe extenderse a las dependencias críticas.

Una arquitectura robusta podría ser:

```text
              ┌── UPS A ── PDU A ── PSU A ┐
              │                            │
FUENTE A ─────┘                            │
                                           ├── SERVIDOR
FUENTE B ─────┐                            │
              │                            │
              └── UPS B ── PDU B ── PSU B ┘
```

Cada camino debe mantenerse independiente hasta donde sea necesario.

---

# 6. Fuentes redundantes del servidor

Un servidor crítico puede disponer de:

```text
PSU A
PSU B
```

Idealmente:

```text
PSU A
 ↓
PDU A
 ↓
Ruta A
```

y:

```text
PSU B
 ↓
PDU B
 ↓
Ruta B
```

Así podemos perder una ruta sin perder el servidor.

---

# 7. Redundancia de red

El mismo principio:

```text
          SERVIDOR
          /      \
       NIC A    NIC B
        │         │
      SW A      SW B
        │         │
      RED A     RED B
```

Si:

```text
SW A ❌
```

la conectividad puede continuar por:

```text
SW B
```

si el diseño y la configuración lo permiten.

---

# 8. Redundancia del almacenamiento

También podemos aplicar redundancia al almacenamiento.

Por ejemplo:

```text
Servidor
   │
   ├── Storage A
   │
   └── Storage B
```

Pero debemos analizar:

```text
Controladoras
Enlaces
Switches
Fuentes
Cabinas
```

Una cabina redundante puede seguir dependiendo de un único switch.

Por tanto:

> **La redundancia debe analizarse en toda la cadena de acceso al almacenamiento.**

---

# 9. Climatización como sistema crítico

La refrigeración debe considerarse parte de la disponibilidad.

Podemos tener:

```text
Servidores
   ↓
Generan calor
   ↓
Climatización
```

Si la climatización falla:

```text
Temperatura ↑
   ↓
Protección térmica
   ↓
Rendimiento reducido
   ↓
Apagado / fallo
   ↓
Servicio afectado
```

Por tanto:

```text
Electricidad
+
Climatización
=
Infraestructura crítica
```

---

# 10. Flujo de aire

La distribución física debe facilitar:

```text
Aire frío
   ↓
Entrada servidores
   ↓
Componentes
   ↓
Aire caliente
   ↓
Salida
```

Y evitar:

```text
Aire caliente
   ↓
Entrada servidores
```

Por eso:

```text
Cold aisle
+
Hot aisle
+
Contención
```

son estrategias importantes.

# 11. Electricidad y calor están relacionados

Existe una relación directa:

```text
Más servidores
      ↓
Más consumo
      ↓
Más calor
      ↓
Mayor necesidad de refrigeración
      ↓
Mayor consumo de infraestructura
```

Esto significa que añadir capacidad informática puede afectar simultáneamente a:

```text
Espacio
Electricidad
Climatización
Red
PUE
```

# 12. La capacidad tiene varias dimensiones

Nunca debemos preguntar solamente:

> "¿Cuántas U quedan?"

Debemos preguntar:

```text
¿Cuánto espacio queda?

¿Cuánta potencia eléctrica queda?

¿Cuánta capacidad térmica queda?

¿Cuántos puertos de red quedan?

¿Cuánto almacenamiento queda?

¿Cuánta capacidad de cómputo queda?
```

Por tanto:

```text
CAPACIDAD
=
ESPACIO
+
ENERGÍA
+
CLIMA
+
RED
+
CÓMPUTO
+
STORAGE
```

---

# 13. El cuello de botella

La infraestructura puede quedar limitada por cualquiera de sus recursos.

Ejemplo:

```text
Espacio       70 %
Electricidad  80 %
Red           60 %
Storage       55 %
Clima         95 %
```

El recurso crítico puede ser:

```text
Climatización
```

Aunque exista mucho espacio físico.

Por tanto:

> **La capacidad efectiva está limitada por el recurso que se agota antes para el escenario concreto.**

---

# 14. Margen

No debemos planificar al:

```text
100 %
```

de capacidad.

Ejemplo:

```text
Capacidad eléctrica = 100 kW
Carga = 75 kW
```

Tenemos:

```text
25 kW
```

de margen.

Ese margen permite absorber:

- Crecimiento.
- Variaciones.
- Picos.
- Determinados fallos.
- Necesidades operativas.

El margen adecuado depende de la arquitectura y los requisitos.

# 15. UPS, generador y PDU

Recordemos las funciones:

```text
UPS / SAI
↓
Respaldo inmediato

GENERADOR
↓
Respaldo prolongado

PDU
↓
Distribución
```

No debemos confundirlos.

Una pregunta de test puede presentar los tres juntos.

La clave:

```text
UPS = continuidad inmediata
Generador = respaldo prolongado
PDU = distribución
```

---

# 16. Cadena eléctrica completa

Podemos construir:

```text
                 RED
                  │
                  ▼
                UPS
                  │
                  ▼
                 PDU
                  │
                  ▼
               SERVIDOR
                  ▲
                  │
              GENERADOR
```

En una arquitectura crítica:

```text
RED A ── UPS A ── PDU A ── PSU A
                                      \
                                       SERVIDOR
                                      /
RED B ── UPS B ── PDU B ── PSU B
```

La idea es disponer de caminos independientes.

---

# 17. Redundancia N+1

Recordemos:

```text
N
↓
Necesidad mínima
```

y:

```text
N+1
↓
Necesidad + una unidad adicional
```

Ejemplo:

```text
Necesitamos 3 HVAC
```

Instalamos:

```text
4 HVAC
```

Entonces:

```text
N = 3
N+1 = 4
```

Si falla una:

```text
1 ❌
3 ✅
```

La capacidad necesaria continúa disponible.

---

# 18. 2N

En una arquitectura 2N:

```text
Sistema A
+
Sistema B
```

Cada sistema está diseñado para proporcionar la capacidad requerida de acuerdo con el diseño.

Conceptualmente:

```text
CAPACIDAD REQUERIDA

Sistema A → capacidad completa
Sistema B → capacidad completa
```

Esto proporciona una independencia mayor que N+1.

# 22. Tier III

```text
Tier II
+
```

La palabra clave:

# 23. Tier IV

```text
Tier III

Tolerancia a fallos
```

La palabra clave:

> **Fallo.**

Un fallo individual no debería interrumpir la carga crítica según el diseño.

# 24. Mantenimiento vs fallo

Esta distinción es esencial:

```text
MANTENIMIENTO
"Voy a sacar algo de servicio."

↓
Tier III
```

Mientras:

```text
FALLO
"Algo acaba de romperse."

↓
Tier IV
```

Tier IV mantiene además las capacidades de mantenimiento concurrente.

# 25. Disponibilidad

La disponibilidad responde:

> **¿Durante cuánto tiempo está operativo el servicio?**

De forma simplificada:

```text
Disponibilidad =
Tiempo operativo
────────────────
Tiempo total
```

Cuantos más nueves:

```text
99 %
99,9 %
99,99 %
99,999 %
```

menor tiempo de indisponibilidad permitido.

---

# 26. Fiabilidad

La fiabilidad responde:

> **¿Con qué frecuencia falla el sistema?**

No es exactamente lo mismo que disponibilidad.

Podemos tener:

```text
Fallos frecuentes
+
Reparaciones extremadamente rápidas
=
Alta disponibilidad potencial
```

Por eso:

```text
Fiabilidad ≠ Disponibilidad
```

---

# 27. Mantenibilidad

La mantenibilidad responde:

> **¿Qué facilidad tenemos para reparar el sistema?**

Una alta mantenibilidad puede reducir:

```text
MTTR
↓
Tiempo de recuperación
↓
Indisponibilidad
```

---

# 28. MTBF y MTTR

```text
MTBF
↓
Mean Time Between Failures
↓
Tiempo medio entre fallos
```

```text
MTTR
↓
Mean Time To Repair
↓
Tiempo medio de reparación
```

Regla mental:

```text
MTBF
↓
BETWEEN
↓
ENTRE fallos

MTTR
↓
REPAIR
↓
REPARAR
```

---

# 29. Fórmula conceptual

Podemos relacionar:

```text
Disponibilidad ≈ MTBF / (MTBF + MTTR)
```

La idea:

```text
MTBF ↑
↓
Mejor disponibilidad potencial

MTTR ↓
↓
Mejor disponibilidad potencial
```

# 31. Hot swap y hot spare

```text

↓
```


```text

Hot Spare
```
```text
↓
```

# 91. La filosofía de diseño

La filosofía puede resumirse en siete preguntas:

```text
1. ¿Qué servicio quiero proporcionar?
```

```text
2. ¿Qué disponibilidad necesito?
```

```text
3. ¿Qué puede fallar?
```

```text
4. ¿Qué ocurre si falla?
```

```text
5. ¿Existe una alternativa?
```

```text
6. ¿Puedo mantenerlo sin interrumpir?
```

```text
7. ¿Lo he probado?
```

Estas siete preguntas resumen buena parte de la filosofía de infraestructura crítica.
