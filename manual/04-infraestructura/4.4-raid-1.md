# 1. ¿Qué significa RAID?

RAID significa:

> **Redundant Array of Independent Disks**

En español:

> **Conjunto redundante de discos independientes**

La idea fundamental es combinar varios discos físicos para presentarlos y utilizarlos como un sistema de almacenamiento determinado.

---

# 2. ¿Para qué existe RAID?

Un único disco tiene varios problemas potenciales:

```text
Fallo físico
↓
Pérdida de disponibilidad
```

Además:

```text
Un único disco
↓
Rendimiento limitado
```

RAID permite diseñar diferentes estrategias.

Por ejemplo:

```text
Más rendimiento
```

o:

```text
Más tolerancia a fallos
```

o:

```text
Equilibrio entre rendimiento, capacidad y redundancia
```

---

# 3. RAID no significa simplemente "más discos"

Esta es una idea importante.

Tener:

```text
4 discos
```

no significa automáticamente:

```text
RAID
```

RAID implica una organización concreta de los datos.

---

# 4. Array

Un:

> **RAID Array**

es un conjunto de discos físicos gestionados siguiendo un determinado nivel de RAID.

Ejemplo:

```text
Disk 1
Disk 2
Disk 3
Disk 4
```

pueden formar:

```text
RAID Array
```

---

# 5. Disco físico

Un disco físico es el dispositivo real:

```text
HDD
SSD
```

conectado al servidor o controlador.

Ejemplo:

```text
SSD 1 TB
SSD 1 TB
SSD 1 TB
SSD 1 TB
```

---

# 6. Disco lógico

Un controlador RAID puede presentar el conjunto de discos como:

```text
Logical Disk
```

o:

```text
Virtual Disk
```

No confundirlo con una:

```text
VM
```

En el contexto de RAID, "disco lógico" se refiere al volumen lógico presentado por el sistema RAID.

---

# 7. Ejemplo

Tenemos:

```text
4 × 1 TB
```

El controlador puede presentar:

```text
Logical Disk
```

al sistema operativo.

El sistema operativo puede verlo como:

```text
/dev/sdb
```

o como un disco físico equivalente dependiendo de la plataforma.

---

# 8. Controller

Un:

> **RAID Controller**

gestiona las operaciones del array.

Conceptualmente:

```text
Operating System
       │
       ▼
RAID Controller
       │
 ┌─────┼─────┬─────┐
 ▼     ▼     ▼     ▼
Disk  Disk  Disk  Disk
```

---

# 9. RAID por hardware

En un:

> **Hardware RAID**

un controlador dedicado realiza las operaciones RAID.

Conceptualmente:

```text
OS
↓
RAID Controller
↓
Disks
```

---

# 10. RAID por software

En:

> **Software RAID**

las operaciones RAID son gestionadas principalmente por el sistema operativo o software.

Conceptualmente:

```text
OS
↓
Software RAID
↓
Disks
```

---

# 11. Hardware RAID vs Software RAID

| Característica | Hardware RAID | Software RAID |
|---|---|---|
| Gestión | Controlador | SO/software |
| Coste | Mayor | Menor |
| Dependencia | Controller | Sistema operativo |
| Gestión | Centralizada en controller | Desde software |
| Portabilidad | Depende del controller | Depende del SO |
| Caché | Puede existir en controller | Depende del sistema |

No existe una regla universal de:

```text
Hardware = siempre mejor
```

La elección depende de:

```text
Arquitectura
Coste
Rendimiento
Gestión
Requisitos
```

---

# 12. Controller failure

Una consideración importante en hardware RAID:

```text
Discos
+
Controller
```

Si falla el controlador, debemos garantizar que:

```text
El array pueda recuperarse
```

mediante:

```text
Controller replacement
```

compatible, configuración almacenada, o mecanismos equivalentes según plataforma.

---

# 13. RAID metadata

El controlador necesita conocer información como:

```text
Discos pertenecientes al array
RAID level
Orden
Estado
Configuración
```

Esta información forma parte de los metadatos del array.

---

# 14. ¿Qué intenta optimizar RAID?

Tres objetivos aparecen constantemente:

```text
CAPACIDAD
RENDIMIENTO
REDUNDANCIA
```

No podemos maximizar siempre los tres simultáneamente.

---

# 15. Capacidad

Si tenemos:

```text
4 × 1 TB
```

la capacidad física bruta es aproximadamente:

```text
4 TB
```

pero la capacidad útil dependerá del nivel RAID.

---

# 16. Raw capacity

> **Raw Capacity**

es la capacidad total física instalada.

Ejemplo:

```text
4 × 1 TB
=
4 TB raw
```

---

# 17. Usable capacity

> **Usable Capacity**

es la capacidad disponible después de aplicar:

```text
RAID
Overhead
Metadata
```

según el sistema.

---

# 18. Raw vs usable

Nunca confundas:

```text
Raw
```

con:

```text
Usable
```

Ejemplo:

```text
8 × 1 TB
```

no implica necesariamente:

```text
8 TB utilizables
```

---

# 19. Rendimiento

El rendimiento del almacenamiento suele analizarse mediante:

```text
IOPS
Throughput
Latency
```

---

# 20. IOPS

> **Input/Output Operations Per Second**

indica cuántas operaciones de entrada/salida pueden realizarse por segundo.

Ejemplo:

```text
20.000 IOPS
```

significa aproximadamente:

```text
20.000 operaciones de I/O por segundo
```

bajo las condiciones y tamaño de operación correspondientes.

---

# 21. Throughput

El:

> **Throughput**

representa la cantidad de datos transferidos por unidad de tiempo.

Normalmente:

```text
MB/s
GB/s
```

---

# 22. IOPS vs Throughput

No son lo mismo.

```text
IOPS
→ número de operaciones
```

```text
Throughput
→ cantidad de datos transferidos
```

---

# 23. Latencia

La:

> **Latency**

es el tiempo que tarda una operación de I/O.

Normalmente se expresa en:

```text
ms
```

---

# 24. IOPS, throughput y tamaño de bloque

Existe una relación importante:

```text
Throughput ≈ IOPS × I/O size
```

Por ejemplo, conceptualmente:

```text
10.000 IOPS
×
64 KB
```

producen un throughput diferente al de:

```text
10.000 IOPS
×
4 KB
```

Por eso no debemos comparar IOPS sin conocer:

```text
Block size
Read/write mix
Queue depth
Workload
```

---

# 25. Lecturas y escrituras

Una carga puede ser:

```text
Read-heavy
```

o:

```text
Write-heavy
```

o:

```text
Mixed
```

---

# 26. Random vs Sequential

Otro factor importante:

```text
Sequential I/O
```

frente a:

```text
Random I/O
```

---

# 27. Sequential I/O

Los datos se acceden de forma relativamente consecutiva.

Ejemplo:

```text
Block 1
Block 2
Block 3
Block 4
```

---

# 28. Random I/O

Las operaciones pueden dirigirse a posiciones diferentes:

```text
Block 1
Block 900
Block 23
Block 7000
```

---

# 29. HDD

Un:

> **Hard Disk Drive**

utiliza componentes mecánicos.

Conceptualmente:

```text
Platters
+
Heads
+
Motor
```

---

# 30. HDD y latencia

La mecánica introduce:

```text
Seek
Rotational latency
```

por lo que el acceso aleatorio puede ser significativamente más lento que en SSD.

---

# 31. SSD

Un:

> **Solid State Drive**

utiliza memoria flash y no depende de platos giratorios.

Por ello puede ofrecer:

```text
Menor latencia
Mayor IOPS
```

dependiendo del modelo y workload.

---

# 32. SSD no significa infinito

Los SSD también tienen:

```text
Desgaste
Endurance
Write cycles
```

---

# 33. Endurance

La:

> **Endurance**

indica la resistencia esperada del dispositivo frente a escrituras.

En entornos empresariales pueden aparecer métricas como:

```text
DWPD
TBW
```

---

# 34. DWPD

> **Drive Writes Per Day**

indica conceptualmente cuántas veces puede escribirse la capacidad completa del disco por día durante el periodo especificado por el fabricante.

---

# 35. TBW

> **Terabytes Written**

representa una cantidad total de datos escritos asociada a la resistencia especificada del dispositivo.

---

# 36. RAID y redundancia

La redundancia permite que:

```text
Fallo de un disco
```

no implique necesariamente:

```text
Pérdida del array
```

---

# 37. Tolerancia a fallos

La:

> **Fault Tolerance**

indica cuántos fallos puede soportar un sistema sin perder los datos o la disponibilidad del conjunto, según el nivel RAID y la implementación.

---

# 38. Redundancia no significa backup

Esta frase debe quedar grabada:

> **RAID no es un backup.**

---

# 39. ¿Por qué RAID no es backup?

Porque RAID protege principalmente frente a:

```text
Fallo de disco
```

pero no necesariamente frente a:

```text
Borrado accidental
Corrupción lógica
Ransomware
Error humano
Desastre
```

---

# 40. Ejemplo

Tenemos:

```text
RAID 5
```

y un administrador elimina:

```text
database.db
```

RAID no sabe que fue un error.

La eliminación se replica según la lógica del sistema.

Resultado:

```text
Dato eliminado
```

---

# 41. RAID + Backup

La arquitectura correcta suele ser:

```text
RAID
+
Backup
```

No:

```text
RAID
en lugar de
Backup
```

---

# 42. RAID 0

RAID 0 utiliza:

> **Striping**

---

# 43. Striping

Los datos se distribuyen entre varios discos.

Ejemplo:

```text
Disk 1     Disk 2
  A           B
  C           D
  E           F
```

---

# 44. Ventaja de RAID 0

Permite:

```text
Mayor rendimiento
```

porque varias unidades pueden trabajar en paralelo.

---

# 45. Desventaja de RAID 0

No existe redundancia.

Si falla:

```text
1 disco
```

puede perderse:

```text
Todo el array
```

---

# 46. Capacidad RAID 0

Con:

```text
2 × 1 TB
```

aproximadamente:

```text
2 TB útiles
```

---

# 47. RAID 0

Resumen:

```text
RAID 0
→ Striping
→ Rendimiento ↑
→ Capacidad ↑
→ Redundancia ❌
```

---

# 48. RAID 1

RAID 1 utiliza:

> **Mirroring**

---

# 49. Mirroring

Los mismos datos se escriben en:

```text
Disk 1
Disk 2
```

Ejemplo:

```text
Disk 1       Disk 2
   A            A
   B            B
   C            C
```

---

# 50. Ventaja RAID 1

Permite tolerar el fallo de:

```text
Un disco
```

en una configuración de dos discos.

---

# 51. Desventaja RAID 1

La capacidad útil es aproximadamente:

```text
50 %
```

con dos discos del mismo tamaño.

---

# 52. Ejemplo RAID 1

```text
2 × 1 TB
```

aproximadamente:

```text
1 TB útil
```

---

# 53. RAID 1

Resumen:

```text
RAID 1
→ Mirroring
→ Redundancia ↑
→ Lectura puede beneficiarse
→ Capacidad útil ↓
```

---

# 54. RAID 5

RAID 5 combina:

```text
Striping
+
Parity
```

---

# 55. Paridad

La paridad permite reconstruir información cuando falla un disco.

Conceptualmente:

```text
Data
+
Data
+
Parity
```

---

# 56. Distribución de RAID 5

La paridad se distribuye entre los discos.

No existe necesariamente:

```text
Un único disco dedicado exclusivamente a parity
```

---

# 57. RAID 5

Requiere como mínimo:

```text
3 discos
```

---

# 58. Tolerancia RAID 5

RAID 5 soporta:

```text
1 fallo de disco
```

---

# 59. RAID 5

Resumen:

```text
RAID 5
→ Striping + distributed parity
→ 1 disco de tolerancia
→ Buena capacidad
→ Penalización de escritura
```

---

# 60. Capacidad RAID 5

Con:

```text
4 × 1 TB
```

aproximadamente:

```text
3 TB útiles
```

antes de otros overheads.

---

# 61. RAID 6

RAID 6 utiliza:

```text
Striping
+
Double parity
```

---

# 62. Tolerancia RAID 6

RAID 6 puede soportar:

```text
2 fallos de disco
```

---

# 63. RAID 6

Requiere como mínimo:

```text
4 discos
```

---

# 64. Capacidad RAID 6

Con:

```text
6 × 1 TB
```

aproximadamente:

```text
4 TB útiles
```

porque se utiliza capacidad equivalente a dos discos para la doble paridad.

---

# 65. RAID 6

Resumen:

```text
RAID 6
→ Striping
→ Double parity
→ 2 discos de tolerancia
→ Más capacidad útil que RAID 1
→ Más tolerancia que RAID 5
→ Mayor overhead de escritura
```

---

# 66. RAID 10

RAID 10 combina:

```text
Mirroring
+
Striping
```

---

# 67. Estructura RAID 10

Conceptualmente:

```text
        STRIPING
       /        \
    MIRROR     MIRROR
    /   \      /   \
   D1   D2    D3   D4
```

---

# 68. RAID 10

Requiere como mínimo:

```text
4 discos
```

---

# 69. Ventaja RAID 10

Ofrece:

```text
Buen rendimiento
+
Redundancia
```

especialmente interesante para workloads con muchas escrituras.

---

# 70. Capacidad RAID 10

Con:

```text
4 × 1 TB
```

aproximadamente:

```text
2 TB útiles
```

---

# 71. RAID 10 y fallos

RAID 10 puede tolerar múltiples fallos dependiendo de qué discos fallen.

Ejemplo:

```text
Mirror A
D1 + D2

Mirror B
D3 + D4
```

Si falla:

```text
D1
+
D3
```

el array puede continuar porque queda:

```text
D2
+
D4
```

Pero si fallan:

```text
D1
+
D2
```

se pierde completamente:

```text
Mirror A
```

y el array falla.

---

# 72. RAID 10

Resumen:

```text
RAID 10
→ Mirroring + Striping
→ Excelente rendimiento
→ Buena redundancia
→ ~50 % capacidad útil
→ 4 discos mínimo
```

---

# 73. Tabla inicial de RAID

| Nivel | Técnica | Mínimo | Fallos tolerados | Capacidad aproximada |
|---|---|---:|---:|---:|
| RAID 0 | Striping | 2 | 0 | N |
| RAID 1 | Mirroring | 2 | 1 | N/2 |
| RAID 5 | Striping + parity | 3 | 1 | (N-1) |
| RAID 6 | Striping + double parity | 4 | 2 | (N-2) |
| RAID 10 | Mirror + striping | 4 | Depende | N/2 |

Donde:

```text
N = número de discos
```

si los discos tienen la misma capacidad.

# 75. Discos de diferente tamaño

Si mezclamos:

```text
1 TB
1 TB
2 TB
```

no debemos asumir automáticamente que:

```text
4 TB
```

estarán disponibles.

La capacidad utilizable depende del controlador y de cómo gestione los discos.

# 76. Hot Spare

Un:

> **Hot Spare**

es un disco reservado para reemplazar automáticamente o facilitar la reconstrucción de un disco que ha fallado, según la configuración.

---

# 77. Ejemplo

Tenemos:

```text
RAID 5
+
Hot Spare
```

Si falla:

```text
Disk 2
```

el:

```text
Hot Spare
```

puede entrar en el proceso de rebuild.

---

# 78. Hot Spare

No debemos confundir:

```text
Hot Spare
```

con:

```text
Backup
```

Un hot spare es:

```text
disco de sustitución
```

---

# 79. Global Hot Spare

Puede estar disponible para:

```text
Múltiples arrays
```

según el controlador.

---

# 80. Dedicated Hot Spare

Puede estar asignado a:

```text
Un array concreto
```

---

# 81. Rebuild

Cuando un disco falla:

```text
Disk Failure
↓
Array Degraded
↓
Replacement
↓
Rebuild
```

---

# 82. Array degraded

Un array:

> **Degraded**

continúa funcionando, pero ha perdido parte de su redundancia.

---

# 83. Ejemplo

RAID 5:

```text
D1 ✓
D2 ✓
D3 ❌
D4 ✓
```

El array puede continuar funcionando:

```text
DEGRADED
```

---

# 84. Rebuild

Durante el rebuild:

```text
Datos
+
Paridad
```

se utilizan para reconstruir la información del disco perdido.

---

# 85. Rebuild y rendimiento

Durante un rebuild puede aumentar:

```text
I/O
```

y disminuir:

```text
Performance
```

dependiendo del sistema y carga.

---

# 86. Rebuild y riesgo

Mientras un RAID 5 está reconstruyendo:

```text
1 disco perdido
```

si falla otro disco:

```text
Array failure
```

---

# 87. RAID 6 durante rebuild

RAID 6 tiene una ventaja:

```text
Puede soportar dos fallos
```

Por tanto, durante la reconstrucción tras un fallo, conserva una tolerancia adicional frente a un segundo fallo, dentro de los límites del diseño.

---

# 88. Rebuild time

Los discos modernos pueden tener:

```text
Capacidades muy grandes
```

por lo que reconstruir un array puede tardar bastante.

---

# 89. URE

Un concepto clásico de almacenamiento:

> **Unrecoverable Read Error (URE)**

es un error de lectura que no puede corregirse mediante mecanismos normales del dispositivo.

---

# 90. URE y RAID 5

En arrays grandes, los errores de lectura durante un rebuild pueden aumentar el riesgo de problemas de recuperación.

Por eso RAID 6 puede resultar más adecuado en determinados escenarios de alta capacidad.

---

# 91. No memorices una regla universal

No debemos decir:

```text
RAID 6 siempre es mejor que RAID 5
```

La elección depende de:

```text
Workload
Capacity
Write profile
Performance
Cost
Risk
Rebuild characteristics
```

---

# 92. RAID 50 y RAID 60

Existen niveles combinados:

```text
RAID 50
RAID 60
```

que combinan arrays RAID 5/6 mediante striping adicional.

Conceptualmente:

```text
RAID 50
→ Stripe across RAID 5 groups
```

```text
RAID 60
→ Stripe across RAID 6 groups
```

---

# 93. ¿Por qué utilizar RAID 50/60?

Pueden buscar:

```text
Mayor capacidad
Distribución del riesgo
Rendimiento
```

dependiendo de arquitectura.

---

# 94. RAID 10 vs RAID 5

Una comparación muy importante:

| Característica | RAID 5 | RAID 10 |
|---|---:|---:|
| Técnica | Paridad | Mirroring + striping |
| Mínimo | 3 | 4 |
| Tolerancia | 1 disco | Depende del fallo |
| Escrituras | Más penalización | Generalmente mejores |
| Capacidad | Mayor | ~50 % |
| Rebuild | Puede ser costoso | Generalmente más sencillo |
| Uso típico | Capacidad + redundancia | Rendimiento + redundancia |

---

# 95. RAID 5 vs RAID 6

| Característica | RAID 5 | RAID 6 |
|---|---:|---:|
| Paridad | 1 | 2 |
| Fallos tolerados | 1 | 2 |
| Mínimo | 3 | 4 |
| Capacidad | Mayor | Menor |
| Escrituras | Mejor que RAID 6 en algunos escenarios | Mayor overhead |
| Protección | Menor | Mayor |

---

# 98. Base de datos

```text
Muchas escrituras aleatorias
```

puede beneficiarse de:

```text

```

dependiendo de la arquitectura.

# 99. Archivo masivo

Un workload principalmente:

```text
Sequential
```

puede tener requisitos diferentes.

---

# 100. Alta capacidad

En grandes arrays:

```text
RAID 6
```

puede resultar atractivo por su tolerancia a dos fallos.

# 101. RAID 0

Puede utilizarse cuando:

```text
Rendimiento
```

es más importante que:

```text
Redundancia
```

```text
Críticos
```

# 107. Write-back cache

| Write-through | Menor | Menor dependencia de caché |
