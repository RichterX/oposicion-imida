# 1. La red de una VM

Empecemos por la cadena más importante:

```text
VM
↓
vNIC
↓
Port Group
↓
vSwitch
↓
Uplink
↓
NIC física
↓
Switch físico
↓
Red
```

Esta cadena debería convertirse en una asociación automática.

---

# 2. vNIC

Una:

> **vNIC**

es la tarjeta de red virtual de una máquina virtual.

Ejemplo:

```text
VM-APP01
│
├── vCPU
├── RAM
├── VMDK
└── vNIC
```

La VM percibe:

```text
Una tarjeta de red
```

aunque físicamente no exista una tarjeta dedicada a esa VM.

---

# 3. NIC física

El host ESXi dispone de tarjetas de red físicas:

```text
vmnic0
vmnic1
vmnic2
vmnic3
```

Estas son:

> **NIC físicas**

---

# 4. vNIC vs NIC física

Memoriza:

```text
vNIC
→ pertenece a la VM
```

```text
vmnic
→ pertenece al host ESXi
```

---

# 5. El puente

¿Cómo conectamos:

```text
vNIC
```

con:

```text
vmnic
```

?

Mediante:

```text
vSwitch
```

Conceptualmente:

```text
VM
│
└── vNIC
      │
      ▼
   vSwitch
      │
      ▼
   vmnic0
      │
      ▼
Switch físico
```

---

# 6. vSwitch

Un:

> **vSwitch**

es un switch virtual.

Permite conectar:

```text
VMs
```

con:

```text
redes físicas
```

y también conectar:

```text
VM ↔ VM
```

dentro del propio entorno virtual.

---

# 7. VM a VM

Dos VMs en el mismo host pueden comunicarse mediante el switch virtual.

```text
VM1
 │
vNIC
 │
 ├──── vSwitch ────┐
 │                 │
vNIC               │
 │                 │
VM2                │
```

No necesariamente necesitan salir físicamente del host.

---

# 8. Uplink

Un:

> **Uplink**

es la conexión desde el switch virtual hacia una interfaz física del host.

Ejemplo:

```text
vSwitch
│
├── vmnic0
└── vmnic1
```

---

# 9. Uplink y NIC

Podemos pensar:

```text
vSwitch
↓
Uplink
↓
vmnic
```

En la terminología de VMware, los uplinks representan las conexiones del switch virtual hacia las interfaces físicas.

---

# 10. Port Group

Uno de los conceptos más importantes:

> **Port Group**

Un Port Group define un conjunto de puertos virtuales con características comunes.

Por ejemplo:

```text
PG-PROD
PG-MGMT
PG-VMOTION
PG-DB
```

---

# 11. Port Group como punto de conexión

Una VM no suele conectarse simplemente:

```text
vNIC → vmnic
```

sino:

```text
vNIC
↓
Port Group
↓
vSwitch
↓
Uplink
↓
vmnic
```

---

# 12. VLAN en Port Group

Un Port Group puede estar asociado a una:

```text
VLAN
```

Ejemplo:

```text
PG-PROD
VLAN 20
```

Entonces las VMs conectadas a ese Port Group utilizan esa configuración de red.

---

# 13. Ejemplo

Tenemos:

```text
VM-APP01
VM-APP02
VM-APP03
```

conectadas a:

```text
PG-PROD
```

y:

```text
VLAN 20
```

Conceptualmente:

```text
VM01 ─┐
VM02 ─┼── PG-PROD ── VLAN 20
VM03 ─┘
```

---

# 14. Port Groups diferentes

Podemos tener:

```text
PG-PROD
VLAN 20

PG-DB
VLAN 30

PG-MGMT
VLAN 10
```

Esto permite separar distintos tipos de tráfico.

---

# 15. Segmentación

Una razón fundamental para utilizar VLANs es:

```text
Segmentación
```

Por ejemplo:

```text
VLAN 10
Management

VLAN 20
Production

VLAN 30
Database

VLAN 40
Backup
```

---

# 16. VLAN

Una:

> **VLAN**

permite crear redes lógicas independientes dentro de una infraestructura Ethernet.

Podemos tener:

```text
Switch físico
├── VLAN 10
├── VLAN 20
├── VLAN 30
└── VLAN 40
```

---

# 17. VMware y VLAN

La VLAN puede configurarse de diferentes maneras dependiendo del tipo de Port Group y diseño.

Para una VM, conceptualmente:

```text
vNIC
↓
Port Group
↓
VLAN
```

---

# 18. VLAN ID

Un Port Group puede tener un:

```text
VLAN ID
```

Ejemplo:

```text
VLAN ID = 20
```

---

# 19. VLAN tagging

El tagging consiste en asociar información de VLAN a las tramas Ethernet.

En VMware debemos conocer diferentes modelos.

---

# 20. VLAN 0 / None

En determinados escenarios:

```text
VLAN ID = 0 / None
```

significa que el Port Group no está configurando una VLAN específica para tagging.

El comportamiento exacto depende del entorno físico y configuración.

---

# 21. VLAN 802.1Q

El estándar:

> **IEEE 802.1Q**

define el etiquetado VLAN en Ethernet.

Una trama puede llevar información como:

```text
VLAN ID
```

---

# 22. Virtual Guest Tagging

Existe el concepto:

> **Virtual Guest Tagging (VGT)**

en el que el guest puede participar en el etiquetado VLAN.

Conceptualmente:

```text
Guest
↓
VLAN tags
↓
vSwitch
↓
Physical switch
```

Esto se utiliza en escenarios específicos.

---

# 23. Virtual Switch Tagging

También encontramos:

> **Virtual Switch Tagging (VST)**

donde el switch virtual gestiona el tagging VLAN.

Conceptualmente:

```text
VM
↓
vSwitch
↓
VLAN tag
↓
Physical network
```

Es un modelo habitual para redes virtualizadas.

---

# 24. External Switch Tagging

Otro concepto histórico:

> **External Switch Tagging (EST)**

donde el tagging se realiza en el switch físico.

Conceptualmente:

```text
VM
↓
vSwitch
↓
Physical switch
↓
VLAN
```

---

# 25. VST vs VGT vs EST

Para examen:

```text
EST
→ tagging en switch físico
```

```text
VST
→ tagging en switch virtual
```

```text
VGT
→ tagging gestionado por el guest
```

La terminología exacta puede depender de la documentación y versión.

---

# 26. Standard vSwitch

Uno de los dos grandes tipos:

> **vSphere Standard Switch (vSS)**

Es un switch virtual configurado individualmente en cada host ESXi.

---

# 27. Arquitectura vSS

Imagina:

```text
ESXi01
│
└── vSwitch0
    ├── Port Group A
    ├── Port Group B
    └── vmnic0
```

Otro host:

```text
ESXi02
│
└── vSwitch0
    ├── Port Group A
    ├── Port Group B
    └── vmnic0
```

Son configuraciones independientes aunque tengan el mismo nombre.

---

# 28. Consecuencia

En vSS:

```text
Host A
→ configuración local

Host B
→ configuración local
```

Por tanto:

```text
Cambiar A
≠
Cambiar B
```

automáticamente.

---

# 29. Distributed Switch

El segundo gran modelo:

> **vSphere Distributed Switch (vDS)**

proporciona una gestión distribuida de la red virtual.

---

# 30. Arquitectura vDS

Conceptualmente:

```text
             vCenter
                │
                ▼
              vDS
           /        \
       ESXi01      ESXi02
         │            │
      vmnic0        vmnic0
```

La configuración lógica se administra de forma centralizada.

---

# 31. vSS vs vDS

Memorización:

```text
vSS
→ configuración por host
```

```text
vDS
→ configuración centralizada
```

---

# 32. Ventaja principal de vDS

Si tenemos:

```text
20 hosts
```

con:

```text
VLAN 20
VLAN 30
VLAN 40
```

gestionar un vDS puede reducir la configuración manual repetitiva.

---

# 33. Requisitos

El uso de funcionalidades concretas de vDS depende de:

```text
Versión
Licencia / edición
Configuración
```

No debemos asumir que todas las funcionalidades están disponibles en cualquier edición.

---

# 34. Distributed Port Group

En vDS encontramos:

> **Distributed Port Group**

Conceptualmente:

```text
vDS
│
├── DPG-PROD
├── DPG-MGMT
└── DPG-VMOTION
```

---

# 35. Port Group vs Distributed Port Group

```text
Standard Port Group
→ asociado a vSS
```

```text
Distributed Port Group
→ asociado a vDS
```

---

# 36. Uplink en vDS

Un vDS utiliza:

```text
Uplinks
```

para conectar los hosts con la red física.

Conceptualmente:

```text
vDS
│
├── Uplink 1
├── Uplink 2
└── Uplink 3
```

---

# 37. Host membership

Los hosts deben estar asociados al:

```text
vDS
```

para utilizar sus redes distribuidas.

---

# 38. Distributed Port

El vDS administra puertos virtuales distribuidos.

Conceptualmente:

```text
vDS
│
├── Port
├── Port
├── Port
└── Port
```

Las VMs se conectan mediante:

```text
Distributed Port Group
```

# 39. Network policies

Los switches virtuales permiten configurar políticas relacionadas con:

```text
Security
Traffic shaping
Teaming / failover
```

---

# 40. Security policies

Entre las políticas de seguridad clásicas de VMware encontramos:

```text
Promiscuous Mode
MAC Address Changes
Forged Transmits
```

---

# 41. Promiscuous Mode

Normalmente una interfaz recibe:

```text
Tráfico dirigido a su MAC
```

En:

> **Promiscuous Mode**

puede recibir tráfico adicional que normalmente no estaría dirigido a esa interfaz.

---

# 42. Riesgo

Permitir promiscuous mode indiscriminadamente puede:

```text
Aumentar exposición
```

Por eso debe habilitarse solo cuando sea necesario.

---

# 43. MAC Address Changes

Una VM tiene una:

```text
MAC address
```

La política:

> **MAC Address Changes**

controla determinados cambios respecto a la MAC que VMware espera para una interfaz virtual.

---

# 44. Forged Transmits

Una VM puede intentar transmitir tramas utilizando una MAC diferente de la esperada.

La política:

> **Forged Transmits**

controla ese comportamiento.

---

# 45. Las tres políticas

Memoriza:

```text
Promiscuous Mode
→ recibir tráfico adicional

MAC Address Changes
→ cambios de MAC

Forged Transmits
→ transmitir con MAC diferente
```

---

# 46. Seguridad por defecto

En una infraestructura segura:

```text
No habilitar
```

estas capacidades sin necesidad.

Debemos aplicar:

```text
Least privilege
```

también a nivel de red.

---

# 47. Traffic Shaping

Los switches virtuales pueden disponer de:

> **Traffic Shaping**

para controlar determinados patrones de tráfico.

Conceptualmente:

```text
VM
↓
Port Group
↓
Traffic Shaping
↓
Network
```

---

# 48. Rate limiting

Podemos limitar:

```text
Mbps
```

o establecer parámetros relacionados con el tráfico.

Esto puede ayudar a evitar que una carga monopolice un enlace.

---

# 49. NIC Teaming

Podemos utilizar múltiples NIC físicas:

```text
vmnic0
vmnic1
```

para proporcionar:

```text
Redundancia
```

y, según configuración:

```text
Distribución de tráfico
```

---

# 50. Teaming

Conceptualmente:

```text
vSwitch
├── vmnic0
└── vmnic1
```

Si:

```text
vmnic0 ❌
```

podemos utilizar:

```text
vmnic1 ✓
```

según la política de failover.

---

# 51. Teaming no significa automáticamente agregación

Tener:

```text
2 NIC
```

no significa necesariamente:

```text
2 × ancho de banda
```

Depende de:

```text
Load balancing
Switch físico
LACP
Workload
```

---

# 52. Load balancing

VMware puede utilizar diferentes políticas para decidir por qué uplink enviar tráfico.

---

# 53. Route Based on Originating Port

Una política clásica:

> **Route based on originating port**

asigna el tráfico basándose en el puerto virtual de origen.

Conceptualmente:

```text
VM1 → Uplink 1
VM2 → Uplink 2
VM3 → Uplink 1
```

---

# 54. Route Based on Source MAC Hash

Otra política:

> **Route based on source MAC hash**

utiliza la MAC de origen para determinar el uplink.

---

# 55. IP Hash

Otra opción:

> **Route based on IP hash**

utiliza información IP para seleccionar el uplink.

Suele estar relacionada con configuraciones de agregación en el switch físico.

---

# 56. Explicit Failover Order

También podemos utilizar:

> **Explicit Failover Order**

donde se define el orden:

```text
Active:
vmnic0

Standby:
vmnic1
```

---

# 57. Failover

El concepto:

```text
Active
↓
Falla
↓
Standby
```

permite mantener conectividad cuando existe redundancia.

---

# 58. Active/Active vs Active/Standby

Podemos tener:

```text
Active/Active
```

donde varios enlaces pueden utilizarse.

O:

```text
Active/Standby
```

donde uno espera como respaldo.

La disponibilidad depende de la política concreta.

---

# 59. Switch físico

No podemos estudiar teaming VMware sin estudiar el switch físico.

Ejemplo:

```text
ESXi
├── vmnic0 ── Switch A
└── vmnic1 ── Switch B
```

Esto ofrece mayor independencia ante fallo.

---

# 60. Diseño débil

```text
ESXi
├── vmnic0 ── Switch A
└── vmnic1 ── Switch A
```

Si:

```text
Switch A ❌
```

perdemos ambos enlaces.

---

# 61. Diseño redundante

```text
ESXi
├── vmnic0 ── Switch A
└── vmnic1 ── Switch B
```

Ahora:

```text
Switch A ❌
```

no necesariamente elimina toda la conectividad.

---

```text

└── Link 2 ──┴── LAG
```

# 63. LACP y vDS

# 64. LACP no es failover puro

# 197. 🏆 Resumen final

La idea central de esta parte:

> **VMware virtualiza también la conectividad.**

Una VM no necesita una NIC física dedicada.

Utiliza:

```text
vNIC
↓
Port Group
↓
vSwitch / vDS
↓
Uplink
↓
NIC física
```

Y el host ESXi utiliza:

```text
VMkernel
↓
vmk
```

para determinados servicios de infraestructura.

# 198. Frases de memorización

> **vNIC pertenece a la VM.**

> **vmnic pertenece al host físico.**

> **vmk pertenece al VMkernel.**

> **vSwitch conecta virtualmente.**

> **Uplink conecta con el mundo físico.**

> **Port Group define cómo se conecta una VM.**

> **vSS se administra por host.**

> **vDS se administra de forma distribuida.**

> **VLAN segmenta.**

> **Teaming proporciona redundancia y puede distribuir tráfico.**

> **NIOC controla/prioriza tráfico según configuración.**

> **vMotion mueve la ejecución entre hosts.**

> **Storage vMotion mueve almacenamiento.**
