# 1. ¿Qué es VMware?

Cuando hablamos de VMware en el contexto de infraestructura, estamos hablando de un ecosistema de tecnologías de virtualización y gestión de centros de datos.

Históricamente, VMware se convirtió en uno de los principales referentes de la virtualización de servidores.

Actualmente forma parte de:

> **Broadcom**

Para nuestro estudio, lo importante no es tanto la historia empresarial como comprender la arquitectura tecnológica.

---

# 2. VMware no es solamente ESXi

Este es uno de los primeros conceptos que debemos fijar.

Es muy habitual escuchar:

> "Tenemos VMware."

Pero eso no identifica una única tecnología.

En una infraestructura VMware podemos encontrar diferentes componentes:

```text
vSphere
│
├── ESXi
├── vCenter Server
├── Clusters
├── vMotion
├── HA
├── DRS
├── Datastores
├── Networking
└── Management
```

---

# 3. VMware vs vSphere

Una confusión muy habitual es utilizar ambos términos como si fueran exactamente lo mismo.

De forma conceptual:

```text
VMware
↓
Fabricante / ecosistema tecnológico

vSphere
↓
Plataforma de virtualización de servidores
```

Para nuestro examen, interesa especialmente:

```text
vSphere
```

como plataforma que incluye los componentes necesarios para virtualizar y administrar infraestructura.

---

# 4. ESXi

> **VMware ESXi**

es el hipervisor de VMware utilizado para ejecutar máquinas virtuales directamente sobre el hardware físico.

Su arquitectura es:

```text
Hardware físico
       ↓
     ESXi
       ↓
      VMs
```

Esto lo convierte en un:

> **Hipervisor de Tipo 1**

---

# 5. Recordatorio: Tipo 1

En un hipervisor Tipo 1:

```text
Hardware
↓
Hipervisor
↓
Máquinas virtuales
```

No existe un sistema operativo generalista convencional entre:

```text
Hardware
```

y:

```text
Hipervisor
```

---

# 6. Comparación con Tipo 2

Tipo 1:

```text
Hardware
↓
ESXi
↓
VM
```

Tipo 2:

```text
Hardware
↓
Windows / Linux / macOS
↓
Hipervisor
↓
VM
```

El modelo de ESXi es:

```text
Bare metal
```

---

# 7. Host ESXi

Un servidor físico que ejecuta ESXi recibe normalmente el nombre de:

> **ESXi host**

Conceptualmente:

```text
ESXi Host
│
├── CPU física
├── RAM física
├── NICs físicas
├── Storage
└── ESXi
```

Encima de ESXi:

```text
VMs
```

Supongamos un servidor:

```text
2 sockets CPU
64 cores

4 NICs
8 discos
```

Instalamos:

```text
VMware ESXi
```

Tenemos:

```text
HOST-01
│
├── VM-WEB

└── VM-MONITORING
```

# 9. ¿Qué hace ESXi?

ESXi se encarga de proporcionar la capa de virtualización.

Entre otras funciones, debe:

```text
Gestionar CPU
Gestionar memoria
Gestionar dispositivos
Gestionar I/O
Gestionar redes virtuales
Gestionar almacenamiento
Ejecutar VMs
```

```text
            │         │         │
            └─────────┼─────────┘
```

# 11. El hardware físico

El host proporciona:

```text
CPU
RAM
Storage
Network
```

ESXi abstrae estos recursos y los presenta a las VMs.

# 12. CPU virtual

Una VM no recibe directamente una CPU física completa.

Se le asignan:

> **vCPU**

Por ejemplo:

```text
VM-APP
4 vCPU
```

ESXi se encarga de programar esas vCPU sobre los procesadores físicos.

---

# 13. Memoria virtual

Una VM puede tener:

```text
16 GB vRAM
```

mientras el host dispone de:

```text
512 GB RAM física
```

ESXi gestiona la correspondencia entre:

```text
Memoria virtual
```

y:

```text
Memoria física
```

---

# 14. Disco virtual

Una VM puede tener:

```text
VMDK
```

como disco virtual.

Conceptualmente:

```text
VM
│
└── Virtual Disk
       │
       └── Datastore
              │
              └── Storage físico
```

---

# 15. VMDK

> **VMDK**

es uno de los formatos asociados a discos virtuales de VMware.

Podemos pensar en él como:

```text
Disco virtual
```

No debemos confundir:

```text
VMDK
```

con:

```text
Disco físico
```

El VMDK es una representación virtual del almacenamiento.

---

# 16. NIC virtual

Una VM puede disponer de:

```text
vNIC
```

que es una interfaz de red virtual.

La ruta conceptual es:

```text
Aplicación
↓
Guest OS
↓
vNIC
↓
vSwitch
↓
NIC física
↓
Switch físico
```

---

# 17. Hardware virtual

Una VM puede tener dispositivos virtuales como:

```text
vCPU
vRAM
vDisk
vNIC
Controladores virtuales
CD/DVD virtual
```

El guest OS interactúa con:

```text
Hardware virtual
```

en lugar de manipular directamente el hardware físico en la mayoría de los casos.

---

# 18. El guest OS

El sistema operativo instalado dentro de una VM es el:

> **Guest Operating System**

Ejemplos:

```text
Windows Server
Linux
```

La arquitectura es:

```text
Hardware físico
↓
ESXi
↓
VM
↓
Guest OS
↓
Aplicaciones
```

---

# 19. Aplicaciones

Dentro del guest encontramos:

```text
OS
│
├── Servicios
├── Aplicaciones
└── Datos
```

Por tanto:

```text
ESXi
```

no es el sistema operativo de la VM.

---

# 20. ESXi y Guest OS

Debemos distinguir:

```text
ESXi
→ Hipervisor

Windows Server / Linux
→ Guest OS
```

Esta distinción es una pregunta de examen muy sencilla y muy frecuente.

---

# 21. Host vs Guest

Otra asociación fundamental:

```text
Host
→ Sistema físico que ejecuta el hipervisor
```

```text
Guest
→ Sistema operativo que se ejecuta dentro de una VM
```

Por ejemplo:

```text
HOST
ESXi

GUEST
Windows Server
```

---

# 22. Arquitectura básica

La arquitectura completa:

```text
┌──────────────────────────────┐
│        Aplicaciones          │
├──────────────────────────────┤
│        Guest OS              │
├──────────────────────────────┤
│     Máquina Virtual          │
│ vCPU | vRAM | vDisk | vNIC   │
├──────────────────────────────┤
```

# 23. ¿Dónde está vCenter?

Aquí aparece otro componente fundamental.

Tenemos:

```text
Host A
└── ESXi

Host B
└── ESXi

Host C
└── ESXi
```

Podemos administrarlos individualmente.

Pero en una infraestructura grande queremos:

```text
Gestión centralizada
```

Ahí aparece:

> **vCenter Server**

---

# 24. vCenter Server

vCenter Server proporciona una capa centralizada de gestión para infraestructuras vSphere.

Conceptualmente:

```text
             vCenter Server
                   │
        ┌──────────┼──────────┐
        │          │          │
      ESXi A     ESXi B     ESXi C
        │          │          │
       VMs        VMs        VMs
```

---

# 25. ESXi vs vCenter

Memorización:

```text
ESXi
→ Ejecuta las VMs
```

```text
vCenter
→ Gestiona centralmente la infraestructura
```

Esta es una de las distinciones más importantes de todo el capítulo.

---

# 26. ¿Puede existir ESXi sin vCenter?

Sí.

Un host ESXi puede administrarse de forma independiente.

Conceptualmente:

```text
Administrador
↓
ESXi Host
↓
VMs
```

Pero se pierden o limitan muchas capacidades de gestión centralizada y funcionalidades de nivel de clúster.

---

# 27. ¿Puede existir vCenter sin ESXi?

vCenter necesita gestionar recursos de una infraestructura compatible.

Por sí mismo:

```text
vCenter
```

no ejecuta las VMs como lo hace ESXi.

La relación conceptual es:

```text
vCenter
↓
gestiona
↓
ESXi
↓
ejecuta
↓
VMs
```

---

```text
│

```

Los componentes concretos y funcionalidades disponibles dependen de la versión y edición.

# 30. Plano de ejecución

En el plano de ejecución tenemos:

```text
ESXi
↓
VMs
```

# 31. Plano de gestión

En el plano de gestión:

```text
vCenter
↓
Hosts
↓
Clusters
↓
VMs
```

# 32. Una analogía técnica

Podemos imaginar:

```text
ESXi
=
motor
```

y:

```text
vCenter
=
centro de control
```

El motor ejecuta el trabajo.

El centro de control coordina y administra.

No son equivalentes.

# 33. Inventario

vCenter organiza los recursos mediante un inventario lógico.

Podemos tener:

```text
Datacenter
│
├── Cluster
│   ├── Host A
│   ├── Host B
│   └── Host C
│
└── VMs
```

La estructura exacta puede contener más niveles y objetos.

---

# 34. Datacenter en vCenter

En vSphere, un objeto:

> **Datacenter**

es una agrupación lógica de recursos.

No debemos confundirlo automáticamente con:

> edificio físico.

---

# 35. Datacenter lógico vs CPD físico

Esto es importante.

```text
CPD
→ Ubicación física
```

mientras:

```text
vSphere Datacenter
→ Objeto lógico de inventario
```

No necesariamente representan exactamente la misma cosa.

---

# 36. Cluster

Dentro del inventario podemos tener:

```text
Datacenter
│
└── Cluster
    ├── Host A
    ├── Host B
    └── Host C
```

El clúster permite agrupar hosts y habilitar determinadas capacidades.

---

# 37. Host

Dentro del cluster:

```text
Host A
Host B
Host C
```

Cada uno es un servidor físico con ESXi.

---

# 38. Virtual Machine

Las VMs pueden estar asociadas a:

```text
Host
Cluster
Datacenter
```

según la organización del inventario.

---

# 39. Folder

vCenter también permite utilizar carpetas lógicas para organizar objetos.

Ejemplo:

```text
VMs
├── Production
├── Development
└── Testing
```

La organización lógica no implica necesariamente:

```text
Storage físico diferente
```

ni:

```text
Red física diferente
```

---

# 40. Resource Pool

Los:

> **Resource Pools**

permiten organizar y controlar recursos de CPU y memoria para grupos de cargas.

Conceptualmente:

```text
Cluster
│
├── Production Pool
│   ├── VM1
│   └── VM2
│
└── Development Pool
    ├── VM3
    └── VM4
```

No debemos confundir un Resource Pool con un datastore.

---

# 41. Datastore

Un:

> **Datastore**

es una representación lógica del almacenamiento utilizada por vSphere para alojar determinados archivos de las VMs y otros recursos.

Conceptualmente:

```text
VM
│
├── Configuración
├── VMDK
└── Otros archivos
       │
       ▼
   Datastore
```

---

# 42. Datastore no es necesariamente un disco

Puede estar respaldado por:

```text
Storage local
SAN
NAS
```

Por tanto:

```text
Datastore
```

es una abstracción lógica.

# 56. Shutdown Guest OS

```text

↓
```

# 57. Power Off

Equivale conceptualmente a cortar la alimentación virtual:

```text
VM
↓
Power Off
```

Puede provocar pérdida de datos si el guest estaba escribiendo.

Por tanto:

> **Siempre que sea posible, es preferible un apagado ordenado.**

# 58. Reset

> **Reset**

Puede ser más brusco que solicitar un reinicio al sistema operativo.

# 62. VM suspendida

Suspender una VM guarda su estado para poder reanudarla posteriormente.

No debe confundirse con:

```text
Snapshot
```

ni:

```text

```

En VMware, un snapshot representa un estado temporal de una VM y permite volver a un punto anterior según las condiciones y configuración.

Conceptualmente:

```text
VM
↓
Snapshot
↓
Cambios posteriores
```

No debe utilizarse como sustituto de backup.

# 64. Snapshot y rendimiento

Los snapshots pueden afectar:

# 72. vCenter como punto crítico

```text
vCenter caído
```

```text

```

---

# 73. Si vCenter falla

Conceptualmente, las VMs que ya están ejecutándose sobre ESXi no desaparecen automáticamente porque vCenter deje de estar disponible.

El impacto principal está en:

```text
Gestión centralizada
```

y determinadas operaciones que dependen de vCenter.

Esta distinción es importante.

---

# 74. Si un ESXi falla

Aquí sí tenemos un problema con las VMs que estaban ejecutándose en ese host.

Si existe:

```text
HA
```

y se cumplen sus condiciones:

```text
VMs
↓
Pueden ser reiniciadas en otros hosts
```

---

# 75. Comparación

```text
vCenter ❌

Problema de gestión

↓
Problema de ejecución de las VMs de ese host
```


> "Si vCenter cae, todas las VMs se apagan."

❌ Incorrecto.

El fallo de vCenter afecta principalmente a la gestión y a determinadas operaciones. Las VMs que ya están ejecutándose en los hosts ESXi no desaparecen automáticamente por ese motivo.
