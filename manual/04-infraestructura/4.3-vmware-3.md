# 1. El problema de gestionar muchos hosts

Imagina que tenemos:

```text
ESXi-01
ESXi-02
ESXi-03
ESXi-04
ESXi-05
```

y:

```text
120 VMs
```

Podríamos administrar cada host individualmente.

Pero aparecerían problemas:

```text
Configuración
Permisos
Inventario
Migraciones
Clustering
Monitorización
Políticas
```

Necesitamos una capa superior.

---

# 2. La solución: vCenter Server

vCenter proporciona gestión centralizada de la infraestructura vSphere.

Conceptualmente:

```text
                    vCenter
                       │
       ┌───────────────┼───────────────┐
       │               │               │
     ESXi-01         ESXi-02         ESXi-03
       │               │               │
      VMs             VMs             VMs
```

El administrador trabaja principalmente contra:

```text
vCenter
```

en lugar de tener que entrar continuamente en cada host.

---

# 3. ESXi y vCenter

Esta asociación debe quedar grabada:

```text
ESXi
→ Hipervisor
→ Ejecuta VMs
→ Gestiona recursos del host
```

```text
vCenter
→ Gestión centralizada
→ Inventario
→ Clusters
→ Políticas
→ Operaciones avanzadas
```

---

# 4. vCenter no sustituye a ESXi

Una infraestructura no funciona así:

```text
Hardware
↓
vCenter
↓
VM
```

La arquitectura sigue siendo:

```text
Hardware
↓
ESXi
↓
VM
```

y:

```text
vCenter
↓
Gestiona ESXi
```

Por tanto:

```text
vCenter
```

no es el hipervisor.

# 13. Cluster

Un:

> **Cluster**

agrupa hosts ESXi para proporcionar capacidades de gestión y disponibilidad.

Ejemplo:

```text
Cluster-01
│
├── ESXi-01
├── ESXi-02
└── ESXi-03
```

---

# 14. ¿Por qué agrupar hosts?

Porque determinadas funcionalidades trabajan a nivel de cluster:

```text
HA
DRS
EVC
```

Además podemos gestionar capacidad de forma conjunta.

---

# 15. Cluster como conjunto de recursos

```text

```

```text

```

Esto es una simplificación conceptual.

La capacidad efectiva depende de:

```text

HA
DRS
Configuración
```

---

# 16. Capacidad agregada vs capacidad disponible

No debemos confundir:

```text
Capacidad instalada
```

con:

```text
Capacidad utilizable
```

Ejemplo:

```text
3 hosts
256 GB cada uno
= 768 GB
```

Pero si queremos:

```text
N+1
```

no deberíamos considerar toda esa capacidad como disponible para producción.

---

# 17. N+1 en VMware

Supongamos:

```text
3 hosts
```

y queremos tolerar:

```text
1 fallo de host
```

Debemos mantener suficiente capacidad para ejecutar las cargas restantes tras perder un host.

Conceptualmente:

```text
Host A ─┐
Host B ─┼── Producción
Host C ─┘

Si Host A falla:

Host B + Host C
↓
Deben poder absorber la carga necesaria
```

---

# 18. HA

En un cluster compatible podemos habilitar:

> **vSphere HA**

Su objetivo es mejorar la disponibilidad de las cargas ante determinados fallos de hosts.

Conceptualmente:

```text
Host A ❌
   ↓
VM
   ↓
Reinicio en Host B
```

No significa:

```text
Cero downtime
```

porque normalmente existe un periodo de detección y reinicio.

---

# 19. DRS

> **vSphere DRS**

está relacionado con la gestión y balanceo de recursos dentro del cluster.

Conceptualmente:

```text
Cluster
│
├── Host A 🔥
├── Host B 🙂
└── Host C 🙂
```

DRS puede ayudar a distribuir cargas según las políticas y configuración disponibles.

---

# 20. HA vs DRS

Memorización:

```text
HA
→ Disponibilidad ante fallo
```

```text
DRS
→ Gestión / balanceo de recursos
```

No son lo mismo.

---

# 21. EVC

> **Enhanced vMotion Compatibility**

facilita la compatibilidad de CPU entre hosts de determinadas generaciones.

Conceptualmente:

```text
CPU Host A
CPU Host B
CPU Host C

↓ EVC

Conjunto de características CPU compatible
```

Esto puede facilitar:

```text
vMotion
```

entre hosts con diferencias de CPU.

---

# 22. vMotion y cluster

vMotion permite migrar una VM en ejecución entre hosts compatibles.

Conceptualmente:

```text
VM
│
├── Host A
│
└──→ Host B
```

El cluster facilita la organización de hosts que participan en estas operaciones.

