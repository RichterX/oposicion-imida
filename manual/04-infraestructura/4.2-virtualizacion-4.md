# 1. De un host a una infraestructura

Hasta ahora hemos pensado en:

```text
HOST
│
├── VM1
├── VM2
└── VM3
```

Esto funciona, pero no es suficiente para una infraestructura empresarial crítica.

Podemos evolucionar a:

```text
CLÚSTER
│
├── Host A
├── Host B
└── Host C
```

Y sobre ellos:

```text
VMs
```

distribuidas según políticas.

---

# 2. ¿Por qué utilizar varios hosts?

Principalmente por:

```text
Redundancia
+
Alta disponibilidad
+
Mantenimiento
+
Balanceo
+
Escalabilidad
```

Si tenemos un único host:

```text
Host ❌
↓
Todas las VMs afectadas
```

Con varios hosts:

```text
Host A ❌
↓
Otros hosts disponibles
```

---

# 3. Clúster

Un clúster es un conjunto de hosts administrados como una unidad lógica para proporcionar determinadas capacidades comunes.

Conceptualmente:

```text
CLUSTER-01
│
├── Host A
├── Host B
└── Host C
```

Las capacidades concretas dependen de la plataforma.

---

# 4. Host

El host es el servidor físico que ejecuta el hipervisor.

Por ejemplo:

```text
HOST-A
CPU
RAM
NIC
Storage
```

Encima:

```text
Hipervisor
```

Y después:

```text
VMs
```

---

# 5. Datacenter lógico

En plataformas empresariales podemos encontrar agrupaciones superiores al clúster.

Conceptualmente:

```text
DATACENTER
│
├── CLUSTER-01
│   ├── Host A
│   ├── Host B
│   └── Host C
│
└── CLUSTER-02
    ├── Host D
    └── Host E
```

La terminología exacta depende de la plataforma.

---

# 6. Resource Pool

Dentro de una infraestructura podemos agrupar recursos.

```text
CLUSTER
│
├── Pool Producción
│   ├── VM1
│   ├── VM2
│   └── VM3
│
└── Pool Desarrollo
    ├── VM4
    └── VM5
```

Los pools pueden utilizarse para aplicar políticas de recursos.

---

# 7. La idea del clúster

Un clúster permite que pensemos:

```text
Host A
+
Host B
+
Host C
```

como:

```text
Capacidad conjunta
```

aunque los recursos físicos sigan perteneciendo a hosts individuales.

---

# 8. Capacidad agregada

Supongamos:

```text
Host A
16 cores
128 GB RAM

Host B
16 cores
128 GB RAM

Host C
16 cores
128 GB RAM
```

Capacidad física agregada:

```text
48 cores
384 GB RAM
```

Pero no debemos interpretar esto como:

```text
48 cores disponibles siempre
```

porque debemos reservar capacidad para:

```text
Fallos
Overhead
Picos
Mantenimiento
```

---

# 9. Capacidad efectiva

Si necesitamos sobrevivir al fallo de un host, debemos reservar recursos.

Por ejemplo:

```text
3 hosts
```

Cada uno:

```text
16 cores
128 GB
```

Capacidad total:

```text
48 cores
384 GB
```

Pero con política N+1:

```text
Capacidad utilizable aproximada
= capacidad de 2 hosts
```

Es decir:

```text
32 cores
256 GB
```

como referencia de diseño.

---

# 10. N+1

La expresión:

> **N+1**

significa que existe capacidad suficiente para soportar el fallo de un componente adicional.

Ejemplo:

```text
Necesitamos 2 hosts
+
1 host de reserva
```

Tenemos:

```text
3 hosts
```

Si uno falla:

```text
2 hosts
```

siguen disponibles.

---

# 11. N+2

Si queremos tolerar dos fallos:

```text
N+2
```

Ejemplo:

```text
4 hosts
```

para una carga que podría funcionar con:

```text
2 hosts
```

Los otros:

```text
2 hosts
```

representan margen adicional.

---

# 12. N+1 no es una garantía mágica

Tener:

```text
3 hosts
```

no garantiza automáticamente:

```text
N+1
```

Debemos comprobar:

```text
CPU
RAM
Storage
Red
Licencias
Configuración
```

Además:

```text
¿Puede el clúster reiniciar todas las VMs
si un host falla?
```

---

# 13. HA

La alta disponibilidad permite reaccionar ante determinados fallos.

Conceptualmente:

```text
Host A
↓
Fallo
↓
Detección
↓
Host B/C
↓
Reinicio de VMs
```

---

# 14. HA y capacidad

Supongamos:

```text
Host A
├── VM1 32 GB
├── VM2 32 GB
└── VM3 32 GB

Host B
├── VM4 32 GB
└── VM5 32 GB
```

Si:

```text
Host A ❌
```

Host B necesita disponer de memoria suficiente.

Si no:

```text
HA
↓
No puede recuperar todo correctamente
```

---

# 15. Failover capacity

Por tanto, un clúster debe mantener:

```text
Capacidad de failover
```

Es decir:

> Recursos suficientes para asumir las cargas que podrían quedar afectadas por un fallo.

---

# 16. Admission control

En plataformas empresariales puede existir un mecanismo que impida aceptar nuevas cargas si hacerlo comprometería la capacidad de recuperación ante fallos.

Conceptualmente:

```text
¿Hay capacidad para soportar fallo?
        │
      Sí ↓
   Permitir
        │
      No ↓
   Rechazar / advertir
```

En VMware este concepto aparecerá asociado a:

> **vSphere HA Admission Control**

---

# 17. ¿Por qué es importante?

Sin una política de reserva:

```text
Clúster
↓
Se llena progresivamente
↓
Se pierde margen
↓
Host falla
↓
No hay capacidad
↓
HA incompleto
```

Por tanto:

> **La alta disponibilidad necesita capacidad disponible.**

---

# 18. Balanceo

Supongamos:

```text
Host A → 90 %
Host B → 30 %
Host C → 40 %
```

Podemos intentar redistribuir VMs.

Por ejemplo:

```text
Mover VM1:
Host A
↓
Host B
```

Resultado:

```text
Host A → 70 %
Host B → 50 %
Host C → 40 %
```

---

# 19. Balanceo manual

Un administrador puede analizar:

```text
Uso CPU
Uso RAM
Storage
Red
```

y mover VMs manualmente.

Pero en infraestructuras grandes:

```text
Manual
↓
Lento
↓
Difícil de mantener
```

---

# 20. Balanceo automático

Las plataformas pueden automatizar decisiones.

Conceptualmente:

```text
Monitorización
↓
Analizar carga
↓
Detectar desequilibrio
↓
Seleccionar VM
↓
Migrar
```

---

# 21. DRS

En VMware existe:

> **Distributed Resource Scheduler (DRS)**

Su finalidad está relacionada con la gestión y distribución de recursos en el clúster.

Conceptualmente:

```text
CLUSTER
│
├── Host A 90 %
├── Host B 20 %
└── Host C 30 %
        ↓
      DRS
        ↓
    Migraciones
        ↓
├── Host A 60 %
├── Host B 50 %
└── Host C 40 %
```

Los detalles y modos concretos los veremos en 4.3.

---

# 22. DRS no es HA

Esta distinción es importante.

```text
HA
↓
Disponibilidad ante fallo
```

```text
DRS
↓
Gestión / equilibrio de recursos
```

Podemos tener:

```text
HA activado
```

sin utilizar necesariamente:

```text
DRS
```

y viceversa, según la plataforma y configuración.

---

# 23. DRS y migración

Para mover una VM:

```text
Host A
↓
Host B
```

DRS puede utilizar mecanismos de migración disponibles en la plataforma.

En VMware aparece:

> **vMotion**

---

# 24. vMotion

vMotion permite migrar una VM en ejecución entre hosts compatibles.

Conceptualmente:

```text
HOST A
   │
   │ vMotion
   ▼
HOST B
```

La VM continúa funcionando con una interrupción mínima.

---

# 25. vMotion y CPU

Uno de los problemas de la migración es:

```text
CPU origen
≠
CPU destino
```

Si el guest utiliza instrucciones que el destino no soporta:

```text
Problema
```

Por eso existen mecanismos de compatibilidad.

---

# 26. Compatibilidad de CPU

Podemos simplificar:

```text
Host A
CPU moderna

Host B
CPU antigua
```

Una VM que utiliza instrucciones exclusivas de la CPU moderna podría no ser migrable directamente.

La plataforma puede ofrecer mecanismos para presentar un conjunto compatible de instrucciones.

---

# 27. EVC

En VMware:

> **Enhanced vMotion Compatibility (EVC)**

permite establecer una línea base de características de CPU para facilitar migraciones entre determinados hosts.

Conceptualmente:

```text
CPU A ─┐
       ├── Conjunto compatible
CPU B ─┘
```

Esto no convierte físicamente una CPU en otra.

---

# 28. vMotion y red

Una migración genera tráfico.

```text
Host A
↓
Memoria / estado de VM
↓
Host B
```

Por eso debemos disponer de:

```text
Red suficiente
```

---

# 29. vMotion network

En VMware suele configurarse una red específica para tráfico de vMotion.

Conceptualmente:

```text
VM Network
↓
Tráfico de VMs

Management
↓
Gestión

vMotion
↓
Migraciones

Storage
↓
Almacenamiento
```

Separar tipos de tráfico puede mejorar:

```text
Seguridad
+
Rendimiento
+
Previsibilidad
```

---

# 30. Storage vMotion

También podemos migrar el almacenamiento de una VM.

Conceptualmente:

```text
VM
│
├── Host A
│
└── Datastore A
          ↓
     Storage vMotion
          ↓
      Datastore B
```

La VM puede continuar ejecutándose según las capacidades de la plataforma.

---

# 31. vMotion vs Storage vMotion

Memorización:

```text
vMotion
→ Cambia de host

Storage vMotion
→ Cambia de almacenamiento
```

Y puede existir una operación combinada:

```text
Host A + Datastore A
          ↓
Host B + Datastore B
```

---

# 32. Caso práctico

Tenemos:

```text
Host A
VM1
VM2

Host B
VM3
VM4
```

Y:

```text
Datastore A
```

queremos retirar el storage.

Podemos mover:

```text
VM1
VM2
```

a:

```text
Datastore B
```

mediante una operación de migración de almacenamiento compatible.

# 33. Redes virtuales

Una infraestructura empresarial necesita redes virtuales bien diseñadas.

Podemos separar:

```text
Management
VM
vMotion
Storage
Backup
```

---

# 34. ¿Por qué separar tráfico?

Porque mezclar todo puede producir:

```text
Competencia
+
Saturación
+
Riesgos de seguridad
```

Ejemplo:

```text
Backup consume 9 Gbps
↓
Misma red
↓
vMotion lento
↓
Aplicaciones afectadas
```

---

# 35. Segmentación

Podemos utilizar:

```text
VLAN
```

para separar redes lógicas.

Ejemplo:

```text
VLAN 10
Management

VLAN 20
Producción

VLAN 30
Storage

VLAN 40
vMotion

VLAN 50
Backup
```

---

# 36. Port Group

En plataformas como VMware podemos definir grupos lógicos de puertos.

Conceptualmente:

```text
vSwitch
│
├── Port Group Management
├── Port Group VM Network
├── Port Group vMotion
└── Port Group Backup
```

Cada port group puede asociarse a una determinada configuración de red.

---

# 37. vSwitch estándar

Un switch virtual estándar se configura a nivel de host.

Conceptualmente:

```text
HOST A
│
└── vSwitch
    ├── VM1
    ├── VM2
    └── NIC física
```

Si tenemos muchos hosts:

```text
Host A → configuración propia
Host B → configuración propia
Host C → configuración propia
```

Esto puede aumentar el trabajo administrativo.

---

# 38. Distributed Switch

Un switch distribuido permite gestionar la configuración de red de forma centralizada para varios hosts compatibles.

Conceptualmente:

```text
      Distributed Switch
       /       |       \
      /        |        \
 Host A      Host B     Host C
```

Ventaja:

```text
Configuración centralizada
+
Consistencia
```

En VMware:

> **vSphere Distributed Switch (VDS)**

---

# 39. Standard vs Distributed

| Standard Switch | Distributed Switch |
|---|---|
| Configuración por host | Gestión centralizada |
| Más trabajo repetitivo | Mayor consistencia |
| Adecuado para escenarios sencillos | Adecuado para entornos grandes |
| Asociado al host | Configuración distribuida |

Los detalles exactos dependen de la edición y versión.

```text
vSwitch

NIC física

Switch físico
```

Puede existir:

```text
vmnic0
vmnic1
```

por ejemplo.

---

# 41. Uplink

Un uplink es una conexión desde el switch virtual hacia la infraestructura física.

Conceptualmente:

```text
VM
↓
vSwitch
↓
Uplink
↓
NIC física
↓
Switch
```

---

# 42. Teambing

Podemos utilizar varios uplinks:

```text
vSwitch
├── Uplink 1
└── Uplink 2
```

para:

```text
Redundancia
Balanceo
```

según la política configurada.

---

# 43. VLAN tagging

Las VLAN permiten transportar diferentes redes lógicas por infraestructura física compartida.

Conceptualmente:

```text
VM
↓
Port Group
↓
VLAN
↓
Switch físico
```

La configuración debe ser coherente extremo a extremo.

---

# 44. Error típico de VLAN

Tenemos:

```text
Port Group
VLAN 30
```

pero el switch físico no está configurado correctamente para transportar:

```text
VLAN 30
```

Resultado:

```text
VM
↓
Sin conectividad
```

Por eso:

> **La configuración virtual y física debe estar coordinada.**

---

# 45. MTU

Otro concepto de red importante es:

> **MTU - Maximum Transmission Unit**

Indica el tamaño máximo de una unidad de transmisión de red.

Una configuración inconsistente puede causar problemas.

---

# 46. Jumbo Frames

En determinados entornos se pueden utilizar:

```text
Jumbo Frames
```

con MTU superior a la convencional.

Pueden ser útiles especialmente en determinados escenarios de:

```text
Storage
Virtualización
Redes de alto rendimiento
```

Pero:

> **Todo el camino debe soportar la configuración.**

---

# 47. Problema de MTU

Supongamos:

```text
Host
↓
Switch A
↓
Switch B
↓
Storage
```

```text
Problemas de conectividad
+
Fragmentación / descarte
+
Rendimiento
```

---

# 48. Storage local

Una VM puede utilizar almacenamiento local del host.

```text
Host
│
└── Discos locales
      ↓
   Datastore
      ↓
     VM
```

Ventajas:

```text
Simplicidad
Baja dependencia de red de storage
```

Desventajas:

```text
Menor compartición
Migración más limitada
Dependencia del host
```

---

# 49. Storage compartido

Podemos utilizar almacenamiento accesible por varios hosts.

```text
Host A ─┐
Host B ─┼── Storage compartido
Host C ─┘
```

Esto facilita:

```text
Migración
HA
Mantenimiento
```

# 50. NAS

NAS significa:

> **Network Attached Storage**

Normalmente proporciona almacenamiento orientado a archivos.

Conceptualmente:

```text
Hosts
  │
  │ Red
  ▼
NAS
```

Protocolos habituales pueden incluir:

```text
NFS
SMB
```

La utilización concreta depende de la plataforma.

---

# 51. SAN

SAN significa:

> **Storage Area Network**

Proporciona una infraestructura de almacenamiento orientada típicamente a bloques.

Conceptualmente:

```text
Hosts
  │
  │ Red de storage
  ▼
SAN
  │
Cabina
```

Protocolos pueden incluir:

```text
Fibre Channel
iSCSI
```

---

# 52. NAS vs SAN

Memorización básica:

```text
NAS
→ Archivo

SAN
→ Bloque
```

Aunque existen matices y tecnologías que difuminan algunos límites, esta asociación es fundamental para el examen.

# 53. Datastore y storage

El hipervisor presenta:

```text
Datastore
```

mientras que detrás puede existir:

```text

```

Por tanto:

```text
Datastore
```

# 54. Multipathing

Cuando existe más de un camino hacia el almacenamiento:

```text

└── Path B
       ↓
Storage
```

podemos utilizar:

> **Multipathing**

Esto puede proporcionar:

```text
Redundancia
+

+
Balanceo
```

según la configuración.

---

# 55. Single path

Si tenemos:

```text
Host
↓
NIC
↓
Switch
↓
Storage
```

un fallo en cualquiera de los elementos puede interrumpir el acceso.

---

# 56. Multipath

Con varios caminos:

```text
          ┌── Switch A ──┐
Host ─────┤              ├── Storage
          └── Switch B ──┘
```

podemos sobrevivir a determinados fallos.

---

# 57. Redundancia completa

Una arquitectura robusta puede tener:

```text
Host A
├── NIC A → Switch A
└── NIC B → Switch B

Host B
├── NIC A → Switch A
└── NIC B → Switch B

          ↓

     Storage redundante
```

Y el storage puede disponer de:

```text
Controladoras
Fuentes
RAID
Caminos
```

redundantes.

---

# 58. SPOF

> **Single Point of Failure**

es un componente cuya pérdida puede provocar la interrupción del servicio.

Ejemplos:

```text
Switch único
Storage único
Controladora única
Fuente única
Host único
```

---

# 59. Encontrar SPOF

Ante un diseño:

```text
Host A
Host B
Storage
Switch
```

preguntamos:

```text
¿Qué ocurre si falla Host A?
¿Qué ocurre si falla Host B?
¿Qué ocurre si falla Storage?
¿Qué ocurre si falla Switch?
¿Qué ocurre si falla un enlace?
¿Qué ocurre si falla una fuente?
```

---

# 60. Redundancia no significa duplicar servidores

Podemos tener:

```text
2 hosts
```

pero:

```text
1 switch
```

Entonces:

```text
Switch ❌
↓
Ambos hosts aislados
```

Tenemos redundancia de:

```text
Host
```

pero no:

```text
Red
```

---

# 61. Redundancia extremo a extremo

La redundancia debe analizar:

```text
Compute
↓
Network
↓

↓

↓
Cooling
```

# 63. PDU

Una:

> **Power Distribution Unit**

distribuye alimentación eléctrica a los equipos del rack.

Conceptualmente:

```text
UPS
↓
PDU
↓
Servidores
```

```text
PDU A
PDU B
```

---

# 64. Virtualización y CPD

La infraestructura virtual depende directamente del diseño del CPD.

Tenemos:

```text
CPD
│
├── Power
├── Cooling
├── Network
├── Storage
└── Compute
```

Y encima:

```text
Virtualización
```

---

# 65. Failure domains

Un dominio de fallo es un conjunto de componentes que pueden verse afectados por el mismo evento.

Ejemplo:

```text
Rack A
↓
Problema eléctrico
↓
Todos los hosts del rack
```

Podemos distribuir:

```text
Host A → Rack A
Host B → Rack B
Host C → Rack C
```

para reducir impacto.

---

# 66. Affinity por dominio

No basta con separar VMs en hosts diferentes si:

```text
Todos están en el mismo rack.
```

Podemos tener:

```text
VM1 → Host A → Rack A
VM2 → Host B → Rack A
```

Si Rack A falla:

```text
VM1 ❌
VM2 ❌
```

---

# 67. Anti-affinity física

Una arquitectura más robusta:

```text
VM1 → Host A → Rack A
VM2 → Host B → Rack B
```

Esto reduce el impacto de:

```text
Rack failure
```

---

# 68. Clústeres y dominios de fallo

Un clúster debe diseñarse considerando:



# 71. Capacidad vs redundancia

Podemos aumentar:

```text
Número de hosts
```

pero también debemos considerar:

