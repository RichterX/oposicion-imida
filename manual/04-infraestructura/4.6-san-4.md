# 1. La SAN empresarial

Una SAN empresarial no es simplemente:

``` text
Servidor
↓
Cable
↓
Disco
```

Una arquitectura completa puede ser:

``` text
                 HOSTS
          ┌───────┴───────┐
          │               │
       Fabric A         Fabric B
          │               │
          └───────┬───────┘
                  │
          STORAGE ARRAY
          ┌───────┴───────┐
          │               │
      Controller A    Controller B
          │               │
          └───────┬───────┘
                  │
              Storage Pool
                  │
              RAID / Tier
                  │
               Volumes
                  │
                 LUNs
```

# 5. Cache

La cabina puede utilizar memoria rápida para acelerar operaciones.

``` text
Host
↓
Controller
↓
Cache
↓
Disks
```

------------------------------------------------------------------------

# 6. Read cache

Puede utilizarse para acelerar lecturas repetidas:

``` text
Disk
↓
Cache
↓
Future read
```

------------------------------------------------------------------------

# 7. Write cache

Puede aceptar temporalmente escrituras antes de que lleguen al
almacenamiento físico.

``` text
Host
↓
Write cache
↓
Storage
```

------------------------------------------------------------------------

# 8. Riesgo del write cache

Si se confirma una escritura antes de almacenarla físicamente:

``` text
Power failure
```

podría existir riesgo de pérdida de datos.

Por eso las cabinas empresariales protegen la caché mediante mecanismos
como:

``` text
Battery-backed cache
Flash-backed cache
Non-volatile memory
```

según plataforma.

``` text
Volumes
↓
LUNs
```

# 10. Ventaja de los pools

disco individualmente.

``` text
RAID
```

# 17. Tier de capacidad

# 19. Hot data

Datos utilizados frecuentemente:

``` text
Hot
```

``` text
SSD / NVMe
```

# 20. Cold data

Datos utilizados con poca frecuencia:

``` text
Cold
```

# 21. Automatic tiering

``` text
Automatic data movement
```

# 22. Thin provisioning

> **Thin Provisioning**

Permite presentar más capacidad lógica de la que se ha reservado
físicamente inicialmente.

``` text
Physical pool:
10 TB
```

Podemos presentar:

``` text
LUN A = 8 TB
LUN B = 8 TB
```

Capacidad lógica:

``` text
16 TB
```

aunque físicamente inicialmente tengamos:

``` text
10 TB
```

# 24. Overprovisioning

``` text
Overprovisioning
```

# 25. Ventaja

``` text
Capacity utilization

Provisioning speed
```

# 26. Riesgo

``` text
Pool full
```

podemos tener:

``` text
I/O errors
VM failures
Application failures
```

dependiendo de la plataforma y configuración.

# 29. Deduplicación

La:

> **Deduplicación**

elimina bloques de datos redundantes.

Conceptualmente:

``` text
Data A
Data A
Data A
```

puede almacenarse como:

``` text
Data A
Reference
Reference
```

según implementación.

------------------------------------------------------------------------

# 30. Ventaja

Puede reducir:

``` text
Physical storage consumption
```

especialmente en cargas con mucha redundancia.

------------------------------------------------------------------------

# 31. Compresión

La:

> **Compresión**

reduce el tamaño físico de los datos utilizando algoritmos de
compresión.

------------------------------------------------------------------------

# 32. Deduplicación vs compresión

``` text
Deduplication
→ elimina duplicados

Compression
→ representa los datos de forma más compacta
```

------------------------------------------------------------------------

# 33. Snapshot

Una:

> **Snapshot**

representa un punto en el tiempo del estado de los datos.

------------------------------------------------------------------------

# 34. Snapshot no es backup

Muy importante:

``` text
Snapshot
≠
Backup
```

Una snapshot normalmente depende de la infraestructura primaria.

------------------------------------------------------------------------

# 35. Riesgo

Si perdemos:

``` text
Storage Array
```

también podemos perder:

``` text
Snapshots
```

que residan en esa misma cabina.

------------------------------------------------------------------------

# 36. Snapshot y recuperación

Una snapshot puede ser útil para:

``` text
Quick rollback
Testing
Development
Short-term recovery
```

según escenario.

------------------------------------------------------------------------

# 37. Clones

Un:

> **Clone**

puede crear una copia utilizable de un volumen o conjunto de datos.

------------------------------------------------------------------------

# 38. Snapshot vs clone

Conceptualmente:

``` text
Snapshot
→ punto en el tiempo

Clone
→ copia utilizable
```

La implementación exacta varía.

------------------------------------------------------------------------

# 39. Replicación

La:

> **Replicación**

mantiene una copia de los datos en otro sistema o ubicación.

------------------------------------------------------------------------

# 40. Replicación local

Puede existir dentro del mismo entorno:

``` text
Array A
↓
Array B
```

------------------------------------------------------------------------

# 41. Replicación remota

También:

``` text
Site A
↓
Network
↓
Site B
```

------------------------------------------------------------------------

# 42. Replicación síncrona

En una replicación síncrona:

``` text
Write
↓
Site A
↓
Site B
↓
Acknowledgement
```

El objetivo es que ambos lados estén sincronizados antes de confirmar la
operación, según la implementación.

------------------------------------------------------------------------

# 43. Ventaja síncrona

Puede proporcionar:

``` text
Very low RPO
```

incluso cercano a:

``` text
RPO ≈ 0
```

si la arquitectura lo permite.

------------------------------------------------------------------------

# 44. Requisito

La replicación síncrona suele requerir:

``` text
Low latency
Reliable network
Sufficient bandwidth
```

------------------------------------------------------------------------

# 45. Distancia

La distancia entre sitios es importante porque:

``` text
Distance
↓
Latency
```

------------------------------------------------------------------------

# 46. Replicación asíncrona

En replicación asíncrona:

``` text
Write
↓
Site A
↓
Acknowledgement
↓
Replication later
↓
Site B
```

------------------------------------------------------------------------

# 47. Ventaja

Puede funcionar mejor en:

``` text
Longer distances
```

------------------------------------------------------------------------

# 48. Riesgo

Existe:

``` text
Replication lag
```

------------------------------------------------------------------------

# 49. RPO

> **RPO = Recovery Point Objective**

Define cuánta pérdida de datos temporal es aceptable.

------------------------------------------------------------------------

# 50. Ejemplo RPO

Si:

``` text
RPO = 15 minutes
```

el diseño debe intentar limitar la pérdida potencial a aproximadamente:

``` text
15 minutes of data
```

------------------------------------------------------------------------

# 51. RTO

> **RTO = Recovery Time Objective**

define cuánto tiempo puede tardarse en recuperar el servicio.

------------------------------------------------------------------------

# 52. Ejemplo RTO

Si:

``` text
RTO = 1 hour
```

el servicio debería recuperarse dentro del objetivo establecido de:

``` text
1 hour
```

------------------------------------------------------------------------

# 53. RPO vs RTO

Memoriza:

``` text
RPO
→ ¿Cuántos datos puedo perder?

RTO
→ ¿Cuánto tiempo puedo estar caído?
```

------------------------------------------------------------------------

# 54. Backup

Un:

> **Backup**

es una copia destinada a permitir recuperación.

------------------------------------------------------------------------

# 55. Backup vs replication

``` text
Replication
→ continuidad / copia operativa

Backup
→ recuperación histórica
```

------------------------------------------------------------------------

# 56. ¿Por qué no basta con replicación?

Si un archivo es:

``` text
Deleted
```

y la eliminación se replica inmediatamente:

``` text
Site A
↓
Delete
↓
Site B
```

ambos pueden quedar sin el archivo.

------------------------------------------------------------------------

# 57. Backup histórico

Un backup permite mantener:

``` text
Versiones anteriores
```

según política.

------------------------------------------------------------------------

# 58. Regla 3-2-1

Una estrategia clásica:

``` text
3 copies
2 different media
1 offsite
```

------------------------------------------------------------------------

# 59. Inmutabilidad

Los backups pueden protegerse mediante:

``` text
Immutable storage
```

para dificultar:

``` text
Deletion
Modification
Ransomware impact
```

------------------------------------------------------------------------

# 60. SAN y ransomware

Una SAN no proporciona automáticamente protección contra ransomware.

Debemos considerar:

``` text
Access control
Snapshots
Immutable backups
Replication
Offsite copies
Monitoring
```

``` text
   │ Replication
   ▼
```

------------------------------------------------------------------------

# 64. Failover

Si:

``` text
Site A
```

``` text
Site B
```

puede asumir los servicios según el plan de DR.

# 65. Failback

Cuando Site A vuelve:

``` text
Site B
↓
Site A
```

puede restaurarse la operación primaria.

# 66. DR no es solo tecnología

``` text
Processes
```

# 67. Pruebas de DR

# 68. Storage performance

Tres conceptos esenciales:

``` text
IOPS
Throughput
Latency
```

------------------------------------------------------------------------

# 69. IOPS

> **IOPS = Input/Output Operations Per Second**

mide operaciones de entrada/salida por segundo.

------------------------------------------------------------------------

# 70. Ejemplo

``` text
50,000 IOPS
```

significa aproximadamente:

``` text
50,000 operaciones I/O por segundo
```

------------------------------------------------------------------------

# 71. Throughput

El:

> **Throughput**

mide cantidad de datos transferidos por unidad de tiempo.

Por ejemplo:

``` text
GB/s
MB/s
```

------------------------------------------------------------------------

# 72. Latencia

La:

> **Latency**

mide cuánto tiempo tarda una operación.

Por ejemplo:

``` text
0.5 ms
```

------------------------------------------------------------------------

# 73. IOPS vs throughput

No son lo mismo.

``` text
IOPS
→ cantidad de operaciones

Throughput
→ cantidad de datos
```

------------------------------------------------------------------------

# 74. Ejemplo

Supongamos:

``` text
1000 IOPS
```

con bloques de:

``` text
4 KB
```

Throughput aproximado:

``` text
1000 × 4 KB
= 4000 KB/s
≈ 4 MB/s
```

------------------------------------------------------------------------

# 75. Otro ejemplo

``` text
1000 IOPS
```

con bloques de:

``` text
1 MB
```

Produce aproximadamente:

``` text
1000 MB/s
```

La misma cantidad de IOPS puede generar throughput completamente
diferente.

------------------------------------------------------------------------

# 76. Lecturas y escrituras

También debemos diferenciar:

``` text
Read IOPS
Write IOPS
```

------------------------------------------------------------------------

# 77. Read/write ratio

Una carga puede ser:

``` text
70% Read
30% Write
```

o:

``` text
20% Read
80% Write
```

# 78. Workload



# 155. 🏆 Reglas de oro

``` text
1. RAID protege frente a determinados fallos de discos.
2. SAN proporciona conectividad de almacenamiento.
3. Thin provisioning permite sobreasignación lógica.
4. Thin provisioning requiere monitorización de capacidad física.
5. Deduplicación elimina redundancia de datos.
6. Compresión reduce representación física.
7. Snapshot no equivale a backup.
8. Replication no equivale a backup.
9. RPO indica pérdida de datos temporal aceptable.
10. RTO indica tiempo objetivo de recuperación.
11. IOPS mide operaciones por segundo.
12. Throughput mide cantidad de datos transferidos.
13. Latency mide tiempo de respuesta.
14. Random I/O y sequential I/O tienen comportamientos distintos.
15. Queue depth debe ajustarse al workload.
16. Oversubscription puede provocar congestión.
17. Capacity planning debe considerar crecimiento.
18. Headroom es necesario.
19. Rebuild puede afectar al rendimiento.
20. MPIO proporciona múltiples paths en Windows.
21. DM-Multipath proporciona multipathing en Linux.
22. VMware utiliza VMFS para determinados datastores.
23. VAAI permite determinadas operaciones de offload.
24. SIOC permite gestionar determinadas prioridades de I/O.
25. Dual fabric reduce determinados SPOF.
26. Dos paths no garantizan redundancia si comparten infraestructura.
27. Management plane debe protegerse.
28. Firmware debe mantenerse dentro de versiones soportadas.
29. Los cambios importantes deben documentarse.
30. Toda arquitectura debe considerar fallos y recuperación.
```
