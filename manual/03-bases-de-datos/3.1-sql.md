# ¿Qué inconvenientes tiene una hoja de cálculo?

Imaginemos que un ciudadano posee diez parcelas.

| Nombre | Municipio | Parcela |
|---------|-----------|----------|

- Mayor consumo de espacio.
- Riesgo de inconsistencias.
- Mayor dificultad para actualizar los datos.

# La solución: Bases de datos relacionales

En lugar de repetir continuamente la misma información:

La dividimos en varias tablas.

Por ejemplo:

```
Ciudadanos

↓

Parcelas

↓

Municipios

↓

Cultivos
```

Cada tabla almacena únicamente un tipo de información.

Las relaciones entre ellas permiten reconstruir posteriormente toda la información necesaria.

---

# ¿Qué es una base de datos?

Una base de datos es un conjunto organizado de información relacionado entre sí y almacenado de forma estructurada.

Su objetivo consiste en:

- Almacenar información.
- Organizarla.
- Consultarla rápidamente.
- Actualizarla de forma segura.
- Evitar duplicidades.

---

# ¿Qué significa "relacional"?

Una base de datos relacional organiza la información en:

```
Tablas
```

Y establece relaciones entre ellas.

Por ejemplo:

```
Ciudadanos

↓

Municipios
```

Un ciudadano pertenece a un municipio.

O bien:

```
Parcelas

↓

Cultivos
```

Una parcela puede contener un determinado cultivo.

Las relaciones evitan repetir continuamente la misma información.

# ¿Qué es una tabla?

Una tabla almacena información sobre un único tipo de elemento.

Por ejemplo:

```
Ciudadanos
```

Podría contener:

| id | nombre | apellidos | municipio |
|----|---------|------------|------------|
|1|Pedro|García|Murcia|
|2|Ana|López|Lorca|
|3|Luis|Martínez|Cartagena|

Cada fila representa un ciudadano.

---

# Registros

Cada fila recibe el nombre de:

```
Registro
```

También puede encontrarse el término:

```
Tupla
```

Aunque en la práctica el término "registro" es mucho más habitual.

Ejemplo:

| id | nombre |
|----|---------|
|1|Pedro|

Ese conjunto constituye un registro.

---

# Campos

Cada columna representa una característica del registro.

Se denomina:

```
Campo
```

En nuestro ejemplo:

- id
- nombre
- apellidos
- municipio

son campos de la tabla.

---

# Un ejemplo completo

```
Tabla

↓

Ciudadanos
```

Contiene:

| id | nombre | municipio |
|----|---------|------------|
|1|Pedro|Murcia|

En este ejemplo:

- Tabla → Ciudadanos.
- Registro → Toda la fila.
- Campo → Cada columna.
- Valor → El contenido concreto de cada celda.

```
↓

```

# Conceptos importantes

Antes de continuar debes recordar:

- Una base de datos organiza información estructurada.
- Una base de datos relacional utiliza tablas relacionadas entre sí.
- Cada tabla almacena un único tipo de información.
- Cada fila constituye un registro.
- Cada columna representa un campo.
- Cada celda contiene un valor.
- Para identificar de forma única un registro utilizaremos una clave primaria.

---

# La clave primaria (Primary Key)

En el apartado anterior vimos un problema.

Imaginemos la siguiente tabla.

| Nombre | Municipio |
|---------|------------|
|Pedro García|Murcia|
|Pedro García|Murcia|

¿Cómo sabemos cuál es cuál?

Simplemente observando el nombre resulta imposible.

Necesitamos un identificador que sea único.

Ese identificador recibe el nombre de:

```
Clave Primaria

Primary Key (PK)
```

---

# ¿Qué es una clave primaria?

Una clave primaria es un campo (o conjunto de campos) que identifica de forma única cada registro de una tabla.

En otras palabras:

```
No puede repetirse.
```

Y además:

```
No puede contener valores NULL.
```

Cada registro debe poseer exactamente una clave primaria.

---

# Ejemplo

Nuestra tabla de ciudadanos podría quedar así.

| id | nombre | municipio |
|----|---------|------------|
|1|Pedro García|Murcia|
|2|Pedro García|Murcia|
|3|Ana López|Lorca|

Ahora sí podemos distinguir ambos registros.

Aunque existan dos personas con el mismo nombre.

---

# Características de una clave primaria

Una buena clave primaria debe cumplir:

- Ser única.
- No admitir valores nulos.
- Permanecer estable.
- Identificar un único registro.

En la mayoría de aplicaciones actuales suele utilizarse un número entero autoincremental.

Por ejemplo:

```
1

2

3

4

5
```

---

# ¿Por qué no utilizar el DNI?

Podría parecer una buena idea.

Sin embargo:

Aunque el DNI suele ser único, no siempre resulta la mejor opción.

Por ejemplo:

- Puede cambiar el formato.
- Existen ciudadanos extranjeros.
- Puede almacenarse incorrectamente.
- No todas las tablas representan personas.

Por ello suele utilizarse un identificador interno.

---

# ¿Qué ocurre si eliminamos un registro?

Supongamos:

| id | nombre |
|----|---------|
|1|Pedro|
|2|Ana|
|3|Luis|

Eliminamos:

```
id = 2
```

La tabla quedaría:

| id | nombre |
|----|---------|
|1|Pedro|
|3|Luis|

Observa que normalmente **no se reutiliza** el identificador eliminado.

Esto garantiza que cada registro conserve su identidad histórica.

---

# Claves naturales y claves artificiales

Existen dos formas habituales de identificar registros.

## Clave natural

Es un dato que ya existe en el mundo real.

Ejemplos:

- DNI.
- Matrícula.
- Número de bastidor.
- ISBN.

---

## Clave artificial

Es un identificador generado por la propia base de datos.

Por ejemplo:

```
id = 1528
```

No tiene significado fuera del sistema.

Pero simplifica enormemente las relaciones entre tablas.

Actualmente es la opción más utilizada.

---

# La clave foránea (Foreign Key)

Hasta ahora cada tabla era independiente.

Pero una base de datos relacional necesita conectar unas tablas con otras.

Aquí aparece un nuevo concepto.

```
Clave Foránea

Foreign Key (FK)
```

---

# Un ejemplo

Disponemos de dos tablas.

## Municipios

| id | nombre |
|----|---------|
|1|Murcia|
|2|Lorca|
|3|Cartagena|

---

## Ciudadanos

| id | nombre | id_municipio |
|----|---------|--------------|
|1|Pedro|1|
|2|Ana|2|
|3|Luis|3|

Observa que:

La tabla **Ciudadanos** ya no almacena el nombre del municipio.

Solo almacena:

```
id_municipio
```

Ese campo apunta al identificador de otra tabla.

---

# ¿Qué hemos conseguido?

Si el municipio cambia de nombre.

Por ejemplo:

```
Murcia

↓

Murcia Capital
```

Solo tendremos que modificar:

```
Una única fila.
```

Todos los ciudadanos seguirán apuntando al mismo municipio.

Hemos eliminado duplicidades.

---

# ¿Qué es una relación?

Una relación conecta registros pertenecientes a tablas distintas.

Visualmente:

```
Municipios

id = 1

↓

Ciudadanos

id_municipio = 1
```

La clave foránea permite establecer esa conexión.

---

# Integridad referencial

Imaginemos el siguiente caso.

Tabla Municipios:

| id | nombre |
|----|---------|
|1|Murcia|
|2|Lorca|

Ahora intentamos insertar:

| id | nombre | id_municipio |
|----|---------|--------------|
|1|Pedro|25|

El municipio:

```
25
```

No existe.

¿Qué debería hacer la base de datos?

La respuesta es:

```
Rechazar la operación.
```

Este mecanismo recibe el nombre de:

```
Integridad referencial.
```

---

# ¿Por qué es importante?

Evita que aparezcan datos incoherentes.

Sin integridad referencial podrían existir:

- Ciudadanos pertenecientes a municipios inexistentes.
- Parcelas asociadas a cultivos inexistentes.
- Subvenciones vinculadas a ciudadanos eliminados.

La base de datos protege automáticamente la consistencia de la información.

---

# Nuestro modelo

A partir de ahora utilizaremos una estructura similar a esta.

```
Municipios
      │
      │
      ▼
Ciudadanos
      │
      │
      ▼
Parcelas
      │
      │
      ▼
Cultivos
      │
      │
      ▼
Subvenciones
```

Cada tabla tendrá:

- Una clave primaria.
- Varias claves foráneas cuando sea necesario.

Así es como funcionan la mayoría de bases de datos relacionales.

---

# Conceptos importantes

Antes de continuar debes recordar:

- La clave primaria identifica de forma única cada registro.
- No puede repetirse ni contener valores NULL.
- La clave foránea referencia la clave primaria de otra tabla.
- Las relaciones permiten conectar distintas tablas.
- La integridad referencial impide crear relaciones inválidas.
- Las bases de datos modernas utilizan habitualmente claves artificiales autoincrementales como identificadores principales.

# ¿Qué es un SGBD?

Hasta ahora hemos hablado de:

- Tablas.
- Registros.
- Claves.
- Relaciones.

Pero todavía no hemos respondido una pregunta fundamental.

¿Quién almacena realmente toda esa información?

La respuesta es:

```
SGBD

Sistema Gestor de Bases de Datos
```

En inglés:

```
DBMS

Database Management System
```

---

# ¿Qué hace un SGBD?

Un Sistema Gestor de Bases de Datos es el software encargado de administrar una o varias bases de datos.

Entre otras funciones:

- Almacena la información.
- Permite consultar los datos.
- Inserta nuevos registros.
- Actualiza información existente.
- Elimina registros.
- Gestiona usuarios.
- Controla permisos.
- Realiza copias de seguridad.
- Garantiza la integridad de los datos.

En otras palabras:

Es el programa que trabaja con nuestras bases de datos.

---

# Un ejemplo sencillo

Imaginemos una biblioteca.

Los libros representan:

```
La base de datos.
```

El bibliotecario representa:

```
El SGBD.
```

Los usuarios solicitan información.

El bibliotecario:

- Busca libros.
- Los ordena.
- Los presta.
- Controla quién puede acceder.

El bibliotecario no es el libro.

Del mismo modo:

El SGBD no es la base de datos.

Es quien la administra.

---

# SQL no es un programa

Aquí aparece una de las confusiones más habituales.

Muchas personas piensan que:

```
SQL

=

Programa
```

No es correcto.

SQL es:

```
Un lenguaje.
```

Igual que:

- HTML.
- CSS.
- Java.
- PHP.

No almacena información por sí mismo.

Simplemente permite comunicarnos con el SGBD.

---

# Entonces...

Podemos imaginar la siguiente situación.

```
Usuario

↓

Escribe SQL

↓

SGBD

↓

Base de datos

↓

Respuesta
```

El usuario nunca accede directamente a la base de datos.

Siempre lo hace a través del gestor.

Existen numerosos sistemas gestores de bases de datos.

Los más habituales son:

| SGBD | Fabricante |

| MariaDB | Comunidad / MariaDB Foundation |

Todos ellos entienden SQL.

Pero cada uno incorpora características propias.

# SQL es un estándar

SQL está definido mediante un estándar internacional.

Eso significa que una consulta como:

```sql
SELECT nombre
FROM ciudadanos;
```

funcionará prácticamente igual en:

- PostgreSQL.
- MySQL.
- Oracle.
- SQL Server.

Sin embargo:

Cada fabricante añade posteriormente funciones específicas.

---

# ¿Por qué existen varios SGBD?

Si todos utilizan SQL...

¿Por qué existen tantos?

Porque cada uno está especializado en necesidades diferentes.

Por ejemplo:

### PostgreSQL

- Muy robusto.
- Gran cumplimiento del estándar SQL.
- Excelente integridad.
- Muy utilizado por Administraciones Públicas.

---

### MySQL

- Muy popular en aplicaciones web.
- Fácil de administrar.
- Muy extendido junto con PHP.

---

### Oracle Database

- Orientado a grandes organizaciones.
- Elevado rendimiento.
- Gran escalabilidad.
- Muy presente en banca y grandes empresas.

---

### SQLite

- Muy ligero.
- No necesita servidor.
- Utilizado en aplicaciones móviles y software de escritorio.

# ¿Qué significa "consultar"?

Consultar una base de datos consiste simplemente en pedirle información.

Por ejemplo:

> "Quiero ver todos los ciudadanos."

O bien:

> "Quiero conocer todas las parcelas."

O incluso:

> "Muéstrame todos los municipios."

Para ello utilizaremos el comando más importante de SQL:

```sql

```

# SELECT

La instrucción **SELECT** se utiliza para recuperar información de una o varias tablas.

Es, probablemente, la sentencia SQL más utilizada.

Su estructura básica es:

```sql
SELECT columnas
FROM tabla;
```

Observa que la consulta se lee casi como una frase.

```
SELECT

↓

¿Qué quiero ver?

↓

FROM

↓

¿De dónde quiero obtenerlo?
```

---

# Nuestra primera consulta

Supongamos que queremos visualizar todos los ciudadanos.

La consulta sería:

```sql
SELECT *
FROM ciudadanos;
```

Resultado:

| id | nombre | municipio |
|----|---------|------------|
|1|Pedro García|Murcia|
|2|Ana López|Lorca|
|3|Luis Martínez|Cartagena|

---

# ¿Qué significa el asterisco (*)?

El símbolo:

```sql
*
```

significa:

```
Todas las columnas.
```

Por tanto:

```sql
SELECT *
FROM ciudadanos;
```

equivale a decir:

> "Muéstrame toda la información almacenada en la tabla Ciudadanos."

---

# Seleccionar columnas concretas

Muchas veces no necesitamos todos los datos.

Por ejemplo:

Solo queremos conocer el nombre de los ciudadanos.

La consulta sería:

```sql
SELECT nombre
FROM ciudadanos;
```

Resultado:

| nombre |
|---------|
|Pedro García|
|Ana López|
|Luis Martínez|

---

# Seleccionar varias columnas

También podemos solicitar únicamente algunos campos.

Ejemplo:

```sql
SELECT nombre, municipio
FROM ciudadanos;
```

Resultado:

| nombre | municipio |
|---------|------------|
|Pedro García|Murcia|
|Ana López|Lorca|
|Luis Martínez|Cartagena|

Las columnas se separan mediante comas.

---

# ¿Qué hace realmente FROM?

La cláusula:

```sql
FROM
```

indica la tabla sobre la que queremos trabajar.

Por ejemplo:

```sql
SELECT *
FROM parcelas;
```

o bien:

```sql
SELECT *
FROM municipios;
```

Sin indicar la tabla, el SGBD no sabría dónde buscar la información.

---

# SQL se lee como una frase

Observa el siguiente ejemplo.

```sql
SELECT nombre
FROM ciudadanos;
```

Podemos leerlo así:

```
Selecciona

↓

el campo nombre

↓

de la tabla ciudadanos.
```

Otro ejemplo:

```sql
SELECT nombre, municipio
FROM ciudadanos;
```

Significa:

```
Quiero ver

↓

el nombre

↓

y el municipio

↓

de todos los ciudadanos.
```

---

# ¿Importa el uso de mayúsculas?

Estas dos consultas son equivalentes.

```sql
SELECT nombre
FROM ciudadanos;
```

```sql
select nombre
from ciudadanos;
```

Ambas funcionan exactamente igual.

Sin embargo, existe una convención ampliamente utilizada.

---

# Convención de escritura

Habitualmente se escriben:

Las palabras reservadas en mayúsculas.

```sql
SELECT
FROM
WHERE
ORDER BY
GROUP BY
```

Mientras que:

- Tablas.
- Campos.
- Alias.

se escriben en minúsculas.

Por ejemplo:

```sql
SELECT nombre, municipio
FROM ciudadanos;
```

No es obligatorio.

Pero mejora mucho la legibilidad.

---

# El punto y coma

Las instrucciones SQL suelen finalizar con:

```sql
;
```

Este símbolo indica el final de una sentencia.

En muchos gestores es obligatorio.

En otros, dependiendo de la herramienta utilizada, puede omitirse.

Como norma general:

Es recomendable escribirlo siempre.

---

# Errores frecuentes

Los errores más habituales al comenzar son:

❌ Escribir mal el nombre de la tabla.

```sql

```

cuando la tabla se llama:

```sql
ciudadanos
```

---

❌ Escribir mal un campo.

```sql

```

cuando el campo correcto es:

```sql
nombre
```

---

❌ Olvidar la cláusula FROM.

```sql

```

¿De qué tabla?

El SGBD no puede saberlo.

---

# Conceptos importantes

Antes de continuar debes recordar:

- **SELECT** permite recuperar información.
- **FROM** indica la tabla sobre la que se realiza la consulta.
- El símbolo **\*** representa todas las columnas de una tabla.
- Podemos seleccionar una o varias columnas separándolas mediante comas.
- Es recomendable escribir las palabras reservadas en mayúsculas y finalizar las sentencias con punto y coma (`;`).

# Filtrando información con WHERE

Hasta ahora todas nuestras consultas devolvían **todos los registros** de una tabla.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos;
```

Resultado:

| id | nombre | municipio |
|----|---------|------------|
|1|Pedro García|Murcia|
|2|Ana López|Lorca|
|3|Luis Martínez|Cartagena|
|4|María Pérez|Murcia|

Pero...

¿Y si solo queremos los ciudadanos de Murcia?

Necesitamos filtrar la información.

---

# La cláusula WHERE

La cláusula:

```sql
WHERE
```

permite establecer una condición.

Solo se devolverán los registros que la cumplan.

Su estructura básica es:

```sql
SELECT columnas
FROM tabla
WHERE condición;
```

---

# Primer ejemplo

Queremos obtener únicamente los ciudadanos de Murcia.

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia';
```

Resultado:

| id | nombre | municipio |
|----|---------|------------|
|1|Pedro García|Murcia|
|4|María Pérez|Murcia|

Los ciudadanos de Lorca y Cartagena ya no aparecen.

---

# El operador "="

El operador:

```sql
=
```

significa:

```
Igual a.
```

Por ejemplo:

```sql
WHERE municipio = 'Murcia'
```

Puede leerse como:

> "Solo aquellos registros cuyo municipio sea Murcia."

---

# Comparando números

También podemos comparar valores numéricos.

Supongamos la tabla:

| id | nombre |
|----|---------|
|1|Pedro|
|2|Ana|
|3|Luis|

Consulta:

```sql
SELECT *
FROM ciudadanos
WHERE id = 2;
```

Resultado:

| id | nombre |
|----|---------|
|2|Ana|

---

# Operadores de comparación

Además del operador "=" existen otros muy utilizados.

| Operador | Significado |
|----------|-------------|
| = | Igual que |
| <> | Distinto de |
| > | Mayor que |
| < | Menor que |
| >= | Mayor o igual que |
| <= | Menor o igual que |

Todos ellos pueden utilizarse dentro de una cláusula WHERE.

---

# Ejemplo con "mayor que"

Supongamos una tabla de parcelas.

| id | superficie |
|----|------------|
|1|250|
|2|900|
|3|1200|

Consulta:

```sql
SELECT *
FROM parcelas
WHERE superficie > 500;
```

Resultado:

| id | superficie |
|----|------------|
|2|900|
|3|1200|

---

# Buscar valores distintos

También podemos solicitar los registros que **no** cumplan una condición.

Ejemplo:

```sql
SELECT *
FROM ciudadanos
WHERE municipio <> 'Murcia';
```

Resultado:

| id | nombre | municipio |
|----|---------|------------|
|2|Ana López|Lorca|
|3|Luis Martínez|Cartagena|

---

# Comparando fechas

Los operadores funcionan igualmente con fechas.

Ejemplo:

```sql
SELECT *
FROM subvenciones
WHERE fecha > '2025-01-01';
```

Se obtendrán únicamente las subvenciones posteriores al 1 de enero de 2025.

---

# Comparando texto

Los campos de texto deben escribirse entre comillas simples.

Correcto:

```sql
WHERE municipio = 'Murcia'
```

Incorrecto:

```sql
WHERE municipio = Murcia
```

El gestor interpretaría "Murcia" como un nombre de columna y generaría un error.

---

# ¿Podemos utilizar varias condiciones?

Sí.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia'
AND id > 2;
```

Todavía no estudiaremos los operadores lógicos.

Lo veremos en el siguiente apartado.

Por ahora basta con saber que una consulta puede contener más de una condición.

---

# Errores frecuentes

### ❌ Confundir "=" con "=="

En SQL:

```sql
=
```

Es suficiente.

No existe:

```sql
==
```

como ocurre en otros lenguajes de programación.

---

### ❌ Olvidar las comillas

Incorrecto:

```sql
WHERE nombre = Pedro
```

Correcto:

```sql
WHERE nombre = 'Pedro'
```

---

### ❌ Utilizar el nombre de una columna inexistente

Incorrecto:

```sql
WHERE ciudad = 'Murcia'
```

si la columna realmente se llama:

```sql
municipio
```

El gestor devolverá un error indicando que dicha columna no existe.

---

# Ejemplo completo

Queremos conocer todas las parcelas cuya superficie sea superior a 1.000 metros cuadrados.

Consulta:

```sql
SELECT id, superficie
FROM parcelas
WHERE superficie > 1000;
```

Podemos leerla como una frase:

> "Selecciona el identificador y la superficie de las parcelas cuya superficie sea mayor de 1.000."

---

# Conceptos importantes

Antes de continuar debes recordar:

- **WHERE** permite filtrar registros.
- Solo se muestran los registros que cumplen la condición.
- Los textos deben escribirse entre comillas simples.
- Los operadores de comparación más habituales son: `=`, `<>`, `>`, `<`, `>=` y `<=`.
- Una consulta puede contener una o varias condiciones.

---

# Combinando condiciones: AND, OR y NOT

Hasta ahora únicamente hemos utilizado una condición.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia';
```

Pero en la práctica esto suele ser insuficiente.

Muchas veces necesitamos realizar consultas más específicas.

Por ejemplo:

- Ciudadanos de Murcia **mayores de edad**.
- Parcelas de Murcia **o** Lorca.
- Técnicos que **no** pertenezcan al departamento agrícola.

Para ello utilizaremos los operadores lógicos.

---

# El operador AND

El operador:

```sql
AND
```

significa:

```
Y
```

Todas las condiciones deben cumplirse simultáneamente.

---

## Ejemplo

Supongamos la siguiente tabla.

| id | nombre | municipio | edad |
|----|---------|------------|------|
|1|Pedro|Murcia|45|
|2|Ana|Murcia|17|
|3|Luis|Lorca|33|
|4|María|Murcia|28|

Consulta:

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia'
AND edad >= 18;
```

Resultado:

| nombre | edad |
|---------|------|
|Pedro|45|
|María|28|

Ana no aparece porque, aunque vive en Murcia, no cumple la segunda condición.

---

# ¿Cómo se interpreta?

Podemos leer la consulta así:

> "Quiero los ciudadanos que vivan en Murcia **y además** tengan 18 años o más."

Si una sola condición no se cumple, el registro no aparecerá.

---

# El operador OR

El operador:

```sql
OR
```

significa:

```
O
```

Basta con que una de las condiciones sea verdadera.

---

## Ejemplo

Queremos obtener todos los ciudadanos que vivan en Murcia o Lorca.

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia'
OR municipio = 'Lorca';
```

Resultado:

| nombre | municipio |
|---------|------------|
|Pedro|Murcia|
|Ana|Murcia|
|Luis|Lorca|
|María|Murcia|

Solo quedarían excluidos los ciudadanos de otros municipios.

---

# ¿Cómo se interpreta?

La consulta significa:

> "Muéstrame todos los ciudadanos cuyo municipio sea Murcia **o** Lorca."

No es necesario que ambas condiciones se cumplan.

Con una es suficiente.

---

# El operador NOT

El operador:

```sql
NOT
```

invierte el resultado de una condición.

Es decir:

```
NO
```

---

## Ejemplo

Queremos conocer todos los ciudadanos que no viven en Murcia.

```sql
SELECT *
FROM ciudadanos
WHERE NOT municipio = 'Murcia';
```

Resultado:

| nombre | municipio |
|---------|------------|
|Luis|Lorca|

También podríamos escribir:

```sql
SELECT *
FROM ciudadanos
WHERE municipio <> 'Murcia';
```

Ambas consultas producen el mismo resultado.

---

# Combinando varios operadores

Los operadores pueden utilizarse conjuntamente.

Ejemplo:

```sql
SELECT *
FROM ciudadanos
WHERE municipio = 'Murcia'
AND edad >= 18
AND edad <= 65;
```

La consulta devuelve:

- Ciudadanos de Murcia.
- Mayores o iguales a 18 años.
- Menores o iguales a 65 años.

Las tres condiciones deben cumplirse.

---

# Otro ejemplo

Supongamos que buscamos ciudadanos de Murcia o Lorca que sean mayores de edad.

```sql
SELECT *
FROM ciudadanos
WHERE (municipio = 'Murcia'
OR municipio = 'Lorca')
AND edad >= 18;
```

Resultado:

| nombre | municipio | edad |
|---------|------------|------|
|Pedro|Murcia|45|
|Luis|Lorca|33|
|María|Murcia|28|

Observa el uso de los paréntesis.

---

# La importancia de los paréntesis

Los paréntesis permiten indicar el orden en el que deben evaluarse las condiciones.

Sin paréntesis:

```sql
WHERE municipio = 'Murcia'
OR municipio = 'Lorca'
AND edad >= 18;
```

El resultado puede no ser el esperado.

Con paréntesis:

```sql
WHERE (municipio = 'Murcia'
OR municipio = 'Lorca')
AND edad >= 18;
```

La intención queda perfectamente definida.

Como norma general:

Cuando combines `AND` y `OR`, utiliza siempre paréntesis para evitar errores y mejorar la legibilidad.

---

# Orden de evaluación

SQL evalúa primero:

1. Paréntesis.
2. NOT.
3. AND.
4. OR.

Aunque conocer este orden es útil, el uso de paréntesis hace que las consultas sean más claras y reduce la posibilidad de errores.

---

# Errores frecuentes

### ❌ Confundir AND con OR

Consulta:

```sql
WHERE municipio = 'Murcia'
AND municipio = 'Lorca'
```

Nunca devolverá resultados.

Un mismo registro no puede pertenecer simultáneamente a ambos municipios.

---

### ❌ Olvidar los paréntesis

Incorrecto:

```sql
WHERE municipio = 'Murcia'
OR municipio = 'Lorca'
AND edad >= 18;
```

Aunque SQL lo interpreta correctamente según su precedencia, la intención no resulta evidente.

Es preferible escribir:

```sql
WHERE (municipio = 'Murcia'
OR municipio = 'Lorca')
AND edad >= 18;
```

---

### ❌ Utilizar demasiadas condiciones

Consultas excesivamente largas pueden resultar difíciles de mantener.

Es recomendable escribirlas de forma ordenada, colocando cada condición en una línea distinta.

---

# Buenas prácticas

Una consulta con varias condiciones suele escribirse así:

```sql
SELECT nombre,
       municipio,
       edad
FROM ciudadanos
WHERE municipio = 'Murcia'
  AND edad >= 18
  AND edad <= 65;
```

Esta forma mejora notablemente la legibilidad.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `AND` exige que todas las condiciones sean verdaderas.
- `OR` requiere que al menos una condición sea verdadera.
- `NOT` invierte el resultado de una condición.
- Los paréntesis permiten controlar el orden de evaluación.
- Es recomendable utilizar paréntesis siempre que se combinen `AND` y `OR`.
- Una buena presentación de las consultas facilita su lectura y mantenimiento.

---

# Operadores avanzados de filtrado

Hasta ahora hemos utilizado operadores sencillos:

```sql
=
<>
>
<
>=
<=
```

Sin embargo, SQL incorpora operadores mucho más potentes que permiten realizar búsquedas complejas de forma muy sencilla.

Los más utilizados son:

- LIKE
- IN
- BETWEEN
- IS NULL

---

# El operador LIKE

El operador:

```sql
LIKE
```

permite buscar textos que cumplen un determinado patrón.

Es especialmente útil cuando no conocemos el valor completo.

---

## Ejemplo

Queremos localizar todos los ciudadanos cuyo nombre comienza por "Pe".

```sql
SELECT *
FROM ciudadanos
WHERE nombre LIKE 'Pe%';
```

Resultado:

| nombre |
|---------|
|Pedro García|
|Pedro Martínez|

---

# El comodín %

El símbolo:

```text
%
```

representa:

> Cualquier número de caracteres.

Por ejemplo:

```sql
LIKE 'Pe%'
```

Significa:

> Empieza por "Pe" y puede continuar con cualquier texto.

---

## Más ejemplos

Termina por "ez":

```sql
SELECT *
FROM ciudadanos
WHERE apellidos LIKE '%ez';
```

Resultado:

| apellidos |
|------------|
|Martínez|
|López|
|Sánchez|

---

Contiene la palabra "arc":

```sql
SELECT *
FROM ciudadanos
WHERE nombre LIKE '%arc%';
```

Resultado:

| nombre |
|---------|
|García|
|Marcelo|

---

# El comodín _

Además del símbolo `%`, SQL dispone de otro comodín:

```text
_
```

Representa:

```
Un único carácter.
```

Ejemplo:

```sql
LIKE 'P_dro'
```

Coincidiría con:

```
Pedro
```

pero no con:

```
Pedrito
```

---

# El operador IN

Supongamos que queremos obtener los ciudadanos de Murcia o Lorca.

Podríamos escribir:

```sql
WHERE municipio = 'Murcia'
OR municipio = 'Lorca'
```

Existe una forma mucho más elegante.

```sql
SELECT *
FROM ciudadanos
WHERE municipio IN ('Murcia','Lorca');
```

Resultado:

| nombre | municipio |
|---------|------------|
|Pedro|Murcia|
|Ana|Murcia|
|Luis|Lorca|

---

# ¿Cuándo utilizar IN?

Siempre que queramos comparar un mismo campo con varios valores.

Por ejemplo:

```sql
WHERE id IN (3,7,12,25)
```

Es mucho más legible que escribir:

```sql
WHERE id=3
OR id=7
OR id=12
OR id=25
```

---

# El operador BETWEEN

BETWEEN permite comprobar si un valor pertenece a un intervalo.

Ejemplo:

```sql
SELECT *
FROM parcelas
WHERE superficie BETWEEN 500 AND 1500;
```

Resultado:

| superficie |
|-------------|
|750|
|1200|
|1450|

---

# ¿Qué incluye BETWEEN?

Muy importante.

BETWEEN incluye ambos extremos.

Es decir:

```sql
BETWEEN 500 AND 1500
```

equivale a:

```sql
>= 500

AND

<= 1500
```

---

# Otro ejemplo

Obtener subvenciones concedidas durante el año 2025.

```sql
SELECT *
FROM subvenciones
WHERE fecha BETWEEN '2025-01-01'
              AND '2025-12-31';
```

Es una forma muy habitual de trabajar con fechas.

---

# Valores NULL

En una base de datos no todos los campos contienen necesariamente un valor.

Ejemplo:

| nombre | teléfono |
|---------|-----------|
|Pedro|968123456|
|Ana|NULL|
|Luis|968987654|

NULL significa:

```
Valor desconocido

o

No disponible.
```

No significa:

- Cadena vacía.
- Cero.
- Falso.

Es un concepto diferente.

---

# Buscar valores NULL

Supongamos que queremos localizar los ciudadanos sin teléfono.

La consulta sería:

```sql
SELECT *
FROM ciudadanos
WHERE telefono IS NULL;
```

Resultado:

| nombre |
|---------|
|Ana|

---

# Buscar valores existentes

También podemos hacer lo contrario.

```sql
SELECT *
FROM ciudadanos
WHERE telefono IS NOT NULL;
```

Resultado:

| nombre |
|---------|
|Pedro|
|Luis|

---

# ¿Por qué no utilizar "="?

Muchos principiantes escriben:

```sql
WHERE telefono = NULL
```

Esto es incorrecto.

Con NULL siempre debemos utilizar:

```sql
IS NULL
```

o

```sql
IS NOT NULL
```

Nunca:

```sql
= NULL
```

---

# Combinando operadores

Todos estos operadores pueden utilizarse conjuntamente.

Ejemplo:

```sql
SELECT nombre,
       municipio
FROM ciudadanos
WHERE municipio IN ('Murcia','Lorca')
  AND nombre LIKE 'P%'
  AND telefono IS NOT NULL;
```

La consulta devuelve:

- Ciudadanos de Murcia o Lorca.
- Cuyo nombre comienza por "P".
- Que además tienen teléfono registrado.

---

# Buenas prácticas

Cuando una consulta contiene varias condiciones:

- Escribe cada condición en una línea distinta.
- Utiliza sangrado.
- Emplea mayúsculas para las palabras reservadas.
- Agrupa condiciones relacionadas.

Ejemplo:

```sql
SELECT nombre,
       municipio
FROM ciudadanos
WHERE municipio IN ('Murcia','Lorca')
  AND superficie BETWEEN 500 AND 1500
  AND telefono IS NOT NULL;
```

La consulta resulta mucho más fácil de leer y mantener.

---

# Errores frecuentes

### ❌ Confundir LIKE con =

Incorrecto:

```sql
WHERE nombre = 'Pe%'
```

Correcto:

```sql
WHERE nombre LIKE 'Pe%'
```

---

### ❌ Olvidar las comillas

Incorrecto:

```sql
LIKE Pe%
```

Correcto:

```sql
LIKE 'Pe%'
```

---

### ❌ Comparar NULL con "="

Incorrecto:

```sql
WHERE telefono = NULL
```

Correcto:

```sql
WHERE telefono IS NULL
```

---

### ❌ Sustituir IN por múltiples OR

Aunque ambas consultas producen el mismo resultado:

```sql
WHERE municipio IN ('Murcia','Lorca')
```

es mucho más clara y fácil de mantener.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `LIKE` permite buscar textos mediante patrones.
- `%` representa cualquier número de caracteres.
- `_` representa un único carácter.
- `IN` simplifica la comparación de un campo con varios valores.
- `BETWEEN` selecciona valores comprendidos entre dos límites, ambos incluidos.
- `IS NULL` busca valores desconocidos o no definidos.
- `IS NOT NULL` selecciona únicamente los registros que contienen un valor.
- Los operadores pueden combinarse libremente dentro de una cláusula `WHERE`.

---

# Ordenando y limitando resultados

Hasta ahora hemos aprendido a:

- Seleccionar información.
- Filtrar registros.

Sin embargo, las bases de datos no garantizan el orden en el que devuelven los resultados.

Por ello, si queremos un orden concreto, debemos indicarlo explícitamente.

---

# ORDER BY

La cláusula:

```sql
ORDER BY
```

permite ordenar los registros obtenidos por una consulta.

Su estructura es:

```sql
SELECT columnas
FROM tabla
ORDER BY columna;
```

---

# Orden ascendente

Por defecto, SQL ordena los resultados de forma ascendente.

Ejemplo:

```sql
SELECT nombre
FROM ciudadanos
ORDER BY nombre;
```

Resultado:

| nombre |
|---------|
|Ana López|
|Luis Martínez|
|María Pérez|
|Pedro García|

---

# ASC

También podemos indicar el orden de forma explícita.

```sql
SELECT nombre
FROM ciudadanos
ORDER BY nombre ASC;
```

`ASC` significa:

```
Ascending

↓

Ascendente
```

Es exactamente equivalente al ejemplo anterior.

---

# Orden descendente

Si queremos invertir el orden:

```sql
SELECT nombre
FROM ciudadanos
ORDER BY nombre DESC;
```

Resultado:

| nombre |
|---------|
|Pedro García|
|María Pérez|
|Luis Martínez|
|Ana López|

---

# Ordenar por varias columnas

Podemos ordenar utilizando más de un criterio.

Ejemplo:

```sql
SELECT nombre,
       municipio
FROM ciudadanos
ORDER BY municipio,
         nombre;
```

Primero se ordenará por municipio.

Dentro de cada municipio, por nombre.

---

# Ejemplo

Resultado:

| nombre | municipio |
|---------|------------|
|Luis Martínez|Cartagena|
|Ana López|Lorca|
|María Pérez|Murcia|
|Pedro García|Murcia|

Observa que:

Los ciudadanos de Murcia aparecen agrupados.

Y, dentro del grupo, ordenados alfabéticamente.

---

# LIMIT

En muchas ocasiones no necesitamos todos los registros.

Por ejemplo:

Solo queremos visualizar los cinco primeros.

Utilizamos:

```sql
LIMIT
```

Ejemplo:

```sql
SELECT *
FROM ciudadanos
LIMIT 5;
```

Resultado:

Solo se muestran cinco registros.

---

# ¿Para qué sirve LIMIT?

Es muy útil para:

- Consultas rápidas.
- Pruebas.
- Mostrar resultados paginados.
- Reducir el volumen de información.

---

# OFFSET

OFFSET permite omitir un determinado número de registros antes de comenzar a devolver resultados.

Ejemplo:

```sql
SELECT *
FROM ciudadanos
LIMIT 5
OFFSET 10;
```

Significa:

- Ignora los 10 primeros registros.
- Devuelve los 5 siguientes.

---

# Paginación

LIMIT y OFFSET suelen utilizarse conjuntamente.

Ejemplo:

Página 1:

```sql
LIMIT 10 OFFSET 0;
```

Página 2:

```sql
LIMIT 10 OFFSET 10;
```

Página 3:

```sql
LIMIT 10 OFFSET 20;
```

Es el mecanismo habitual utilizado por muchas aplicaciones web para mostrar resultados por páginas.

---

# Funciones de agregación

Hasta ahora cada fila producía un resultado.

Pero muchas veces necesitamos obtener un resumen.

Por ejemplo:

- ¿Cuántos ciudadanos existen?
- ¿Cuál es la superficie media?
- ¿Cuál es la parcela más grande?

Para ello utilizamos las funciones de agregación.

---

# COUNT

COUNT devuelve el número de registros.

Ejemplo:

```sql
SELECT COUNT(*)
FROM ciudadanos;
```

Resultado:

```
1548
```

Significa:

La tabla contiene 1.548 ciudadanos.

---

# SUM

SUM calcula la suma de un campo numérico.

Ejemplo:

```sql
SELECT SUM(superficie)
FROM parcelas;
```

Resultado:

```
487520
```

Representa la suma de todas las superficies.

---

# AVG

AVG calcula la media aritmética.

Ejemplo:

```sql
SELECT AVG(superficie)
FROM parcelas;
```

Resultado:

```
682,45
```

Es la superficie media de las parcelas.

---

# MIN

MIN devuelve el valor mínimo.

Ejemplo:

```sql
SELECT MIN(superficie)
FROM parcelas;
```

Resultado:

```
120
```

Corresponde a la parcela de menor superficie.

---

# MAX

MAX devuelve el valor máximo.

Ejemplo:

```sql
SELECT MAX(superficie)
FROM parcelas;
```

Resultado:

```
3520
```

Corresponde a la parcela de mayor superficie.

---

# Resumen de funciones

| Función | Descripción |
|----------|-------------|
| COUNT() | Cuenta registros |
| SUM() | Suma valores |
| AVG() | Calcula la media |
| MIN() | Obtiene el valor mínimo |
| MAX() | Obtiene el valor máximo |

Son las funciones de agregación más utilizadas y aparecen con frecuencia en oposiciones.

---

# Ejemplos completos

Número de ciudadanos:

```sql
SELECT COUNT(*)
FROM ciudadanos;
```

---

Superficie total:

```sql
SELECT SUM(superficie)
FROM parcelas;
```

---

Parcela más grande:

```sql
SELECT MAX(superficie)
FROM parcelas;
```

---

Edad media:

```sql
SELECT AVG(edad)
FROM ciudadanos;
```

---

# Errores frecuentes

### ❌ Pensar que ORDER BY modifica la tabla

ORDER BY **no cambia el orden en el que los datos se almacenan**.

Únicamente ordena el resultado mostrado por la consulta.

---

### ❌ Olvidar el criterio de orden

Incorrecto:

```sql
ORDER BY;
```

Siempre debe indicarse una columna.

---

### ❌ Utilizar SUM sobre texto

Incorrecto:

```sql
SUM(nombre)
```

SUM solo tiene sentido sobre campos numéricos.

---

### ❌ Confundir COUNT(*) con COUNT(columna)

```sql
COUNT(*)
```

Cuenta todas las filas.

Mientras que:

```sql
COUNT(columna)
```

Solo cuenta las filas donde esa columna no contiene `NULL`.

Esta diferencia suele aparecer en preguntas de examen.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `ORDER BY` ordena el resultado de una consulta.
- `ASC` indica orden ascendente y `DESC` descendente.
- Es posible ordenar por varias columnas.
- `LIMIT` restringe el número de filas devueltas.
- `OFFSET` permite omitir un número determinado de registros.
- `COUNT`, `SUM`, `AVG`, `MIN` y `MAX` son las funciones de agregación más utilizadas.
- `ORDER BY` no modifica la información almacenada, únicamente el orden en que se presenta.

---

# Relacionando tablas con JOIN

Hasta ahora todas nuestras consultas trabajaban sobre una única tabla.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos;
```

O bien:

```sql
SELECT *
FROM municipios;
```

Pero...

¿Qué ocurre si queremos obtener esta información?

```
Pedro García

↓

Murcia
```

El nombre del ciudadano está en una tabla.

El nombre del municipio está en otra distinta.

Necesitamos relacionarlas.

---

# ¿Por qué existen varias tablas?

Recordemos nuestro modelo.

```
Municipios
```

| id | nombre |
|----|---------|
|1|Murcia|
|2|Lorca|
|3|Cartagena|

---

```
Ciudadanos
```

| id | nombre | id_municipio |
|----|---------|--------------|
|1|Pedro|1|
|2|Ana|2|
|3|Luis|3|

Observa que la tabla **Ciudadanos** no almacena el nombre del municipio.

Solo guarda:

```
id_municipio
```

Una clave foránea.

---

# El problema

Si ejecutamos:

```sql
SELECT *
FROM ciudadanos;
```

Obtendremos:

| nombre | id_municipio |
|---------|--------------|
|Pedro|1|
|Ana|2|
|Luis|3|

Pero...

¿Qué significa:

```
1
```

?

El usuario realmente quiere leer:

```
Murcia
```

No un identificador.

---

# La solución

Necesitamos combinar ambas tablas.

Para ello SQL incorpora:

```sql
JOIN
```

JOIN significa:

```
Unir
```

Permite combinar registros pertenecientes a varias tablas relacionadas.

---

# INNER JOIN

El tipo de JOIN más utilizado es:

```sql
INNER JOIN
```

Su estructura general es:

```sql
SELECT columnas
FROM tabla1
INNER JOIN tabla2
ON condición;
```

Observa que aparece una nueva palabra:

```sql
ON
```

---

# ¿Qué significa ON?

La cláusula:

```sql
ON
```

indica cómo deben relacionarse ambas tablas.

En nuestro ejemplo:

```sql
ciudadanos.id_municipio

=

municipios.id
```

Es decir:

La clave foránea apunta a la clave primaria.

---

# Nuestro primer JOIN

```sql
SELECT ciudadanos.nombre,
       municipios.nombre
FROM ciudadanos
INNER JOIN municipios
ON ciudadanos.id_municipio = municipios.id;
```

Resultado:

| nombre | nombre |
|---------|---------|
|Pedro|Murcia|
|Ana|Lorca|
|Luis|Cartagena|

Ahora sí aparece el nombre del municipio.

---

# ¿Qué ha ocurrido?

SQL ha realizado automáticamente la siguiente operación.

```
Ciudadanos

↓

id_municipio

↓

Municipios

↓

id
```

Y ha unido ambos registros.

Todo gracias a la relación existente entre ambas tablas.

---

# Alias

Escribir continuamente:

```sql
ciudadanos.id_municipio
```

puede resultar pesado.

Por ello suelen utilizarse alias.

Ejemplo:

```sql
SELECT c.nombre,
       m.nombre
FROM ciudadanos c
INNER JOIN municipios m
ON c.id_municipio = m.id;
```

Donde:

```
c

↓

Ciudadanos
```

```
m

↓

Municipios
```

La consulta es exactamente la misma.

Pero mucho más cómoda de escribir.

---

# Un ejemplo más completo

Supongamos ahora estas tablas.

```
Cultivos
```

| id | cultivo |
|----|----------|
|1|Limonero|
|2|Naranjo|

---

```
Parcelas
```

| id | superficie | id_cultivo |
|----|------------|-------------|
|1|520|1|
|2|1300|2|

Consulta:

```sql
SELECT p.id,
       p.superficie,
       c.cultivo
FROM parcelas p
INNER JOIN cultivos c
ON p.id_cultivo = c.id;
```

Resultado:

| id | superficie | cultivo |
|----|------------|----------|
|1|520|Limonero|
|2|1300|Naranjo|

---

# ¿Por qué utilizar JOIN?

Porque evita repetir información.

Imagina que el nombre:

```
Murcia
```

estuviera almacenado miles de veces.

Si cambiara el nombre del municipio habría que modificar miles de registros.

Con JOIN:

Solo existe un registro.

Todos los ciudadanos apuntan a él.

---

# ¿Qué devuelve INNER JOIN?

Solo devuelve los registros que tienen correspondencia en ambas tablas.

Por ejemplo:

Si existe un ciudadano cuyo municipio no aparece en la tabla Municipios.

No aparecerá en el resultado.

Más adelante veremos otros tipos de JOIN que sí muestran esos registros.

---

# Errores frecuentes

### ❌ Unir columnas incorrectas

Incorrecto:

```sql
ON ciudadanos.id = municipios.id
```

Correcto:

```sql
ON ciudadanos.id_municipio = municipios.id
```

Siempre debemos relacionar:

Clave foránea

↓

Clave primaria.

---

### ❌ Olvidar la cláusula ON

Incorrecto:

```sql
INNER JOIN municipios;
```

El gestor no sabe cómo relacionar ambas tablas.

---

### ❌ No utilizar alias cuando la consulta crece

Aunque no es obligatorio.

Los alias mejoran mucho la legibilidad.

Especialmente cuando intervienen tres o más tablas.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `JOIN` permite combinar información de varias tablas.
- `INNER JOIN` solo devuelve los registros que tienen correspondencia en ambas tablas.
- `ON` indica la condición utilizada para relacionar las tablas.
- Lo habitual es relacionar una clave foránea con la clave primaria de otra tabla.
- Los alias (`c`, `m`, `p`, etc.) simplifican la escritura de consultas complejas.
- Una base de datos relacional obtiene gran parte de su potencia gracias al uso de `JOIN`.

---

# Otros tipos de JOIN

En el apartado anterior estudiamos:

```sql
INNER JOIN
```

Este tipo de JOIN devuelve únicamente los registros que tienen correspondencia en ambas tablas.

Pero...

¿Qué ocurre si una tabla contiene registros que no existen en la otra?

Veámoslo con un ejemplo.

---

# Nuestras tablas

## Municipios

| id | nombre |
|----|---------|
|1|Murcia|
|2|Lorca|
|3|Cartagena|
|4|Caravaca|

---

## Ciudadanos

| id | nombre | id_municipio |
|----|---------|--------------|
|1|Pedro|1|
|2|Ana|2|
|3|Luis|3|

Observa que:

```
Caravaca
```

no tiene ciudadanos asociados.

---

# INNER JOIN

Consulta:

```sql
SELECT c.nombre,
       m.nombre
FROM ciudadanos c
INNER JOIN municipios m
ON c.id_municipio = m.id;
```

Resultado:

| Ciudadano | Municipio |
|------------|------------|
|Pedro|Murcia|
|Ana|Lorca|
|Luis|Cartagena|

Caravaca no aparece.

¿Por qué?

Porque no existe ningún ciudadano relacionado con ese municipio.

---

# LEFT JOIN

LEFT JOIN devuelve:

- Todos los registros de la tabla situada a la izquierda.
- Y únicamente las coincidencias de la tabla derecha.

Su estructura es:

```sql
SELECT columnas
FROM tabla1
LEFT JOIN tabla2
ON condición;
```

---

# Ejemplo

```sql
SELECT m.nombre,
       c.nombre
FROM municipios m
LEFT JOIN ciudadanos c
ON m.id = c.id_municipio;
```

Resultado:

| Municipio | Ciudadano |
|------------|------------|
|Murcia|Pedro|
|Lorca|Ana|
|Cartagena|Luis|
|Caravaca|NULL|

Observa que:

Caravaca aparece igualmente.

Como no existe ningún ciudadano asociado:

```
NULL
```

ocupa ese lugar.

---

# ¿Cuándo utilizar LEFT JOIN?

Cuando queremos conservar **todos los registros de la primera tabla**, aunque no tengan relación con la segunda.

Ejemplos:

- Municipios sin ciudadanos.
- Cultivos sin parcelas.
- Técnicos sin incidencias asignadas.

Es uno de los JOIN más utilizados.

---

# RIGHT JOIN

RIGHT JOIN funciona exactamente al contrario.

Conserva todos los registros de la tabla situada a la derecha.

Ejemplo:

```sql
SELECT c.nombre,
       m.nombre
FROM ciudadanos c
RIGHT JOIN municipios m
ON c.id_municipio = m.id;
```

El resultado será equivalente al LEFT JOIN anterior.

La diferencia está únicamente en qué tabla se considera principal.

---

# ¿Se utiliza mucho RIGHT JOIN?

No demasiado.

En la práctica:

Muchos desarrolladores prefieren reordenar las tablas y utilizar siempre:

```sql
LEFT JOIN
```

porque resulta más sencillo de leer.

Por ello es habitual encontrar muy pocos RIGHT JOIN en proyectos reales.

---

# FULL OUTER JOIN

Existe un tercer tipo de unión.

```
FULL OUTER JOIN
```

Devuelve:

- Todos los registros de la tabla izquierda.
- Todos los registros de la tabla derecha.
- Coincidan o no.

Cuando no existe correspondencia:

Se rellenan los campos con:

```
NULL
```

---

# Ejemplo conceptual

Supongamos:

Tabla A

```
1

2

3
```

Tabla B

```
2

3

4
```

---

## INNER JOIN

Resultado:

```
2

3
```

Solo los elementos comunes.

---

## LEFT JOIN

Resultado:

```
1

2

3
```

Todos los elementos de la izquierda.

---

## RIGHT JOIN

Resultado:

```
2

3

4
```

Todos los elementos de la derecha.

---

## FULL OUTER JOIN

Resultado:

```
1

2

3

4
```

Todos los registros de ambas tablas.

---

# ¿Qué ocurre con MySQL?

Es importante conocer una diferencia entre gestores.

PostgreSQL y Oracle soportan:

```sql
FULL OUTER JOIN
```

Sin embargo:

Las versiones tradicionales de MySQL no lo implementan directamente.

Cuando se necesita este comportamiento suele construirse combinando:

- LEFT JOIN.
- RIGHT JOIN.
- UNION.

Es una diferencia clásica entre gestores de bases de datos.

---

# Resumen visual

| Tipo | Registros devueltos |
|-------|---------------------|
| INNER JOIN | Solo coincidencias |
| LEFT JOIN | Todos los de la izquierda + coincidencias |
| RIGHT JOIN | Todos los de la derecha + coincidencias |
| FULL OUTER JOIN | Todos los registros de ambas tablas |

---

# ¿Cuál utilizar?

En la práctica:

- **INNER JOIN** → cuando solo interesan registros relacionados.
- **LEFT JOIN** → cuando la tabla principal debe aparecer completa.
- **RIGHT JOIN** → poco frecuente; normalmente puede sustituirse por un LEFT JOIN invirtiendo las tablas.
- **FULL OUTER JOIN** → cuando interesa conocer todos los registros, tengan o no correspondencia.

---

# Errores frecuentes

### ❌ Confundir LEFT JOIN con INNER JOIN

Muchos estudiantes creen que ambos devuelven el mismo resultado.

La diferencia aparece precisamente cuando existen registros sin correspondencia.

---

### ❌ Pensar que NULL indica un error

Cuando un LEFT JOIN devuelve:

```
NULL
```

No significa que la consulta haya fallado.

Simplemente indica que no existe un registro relacionado.

---

### ❌ Utilizar RIGHT JOIN por costumbre

Aunque es completamente válido.

La mayoría de desarrolladores prefieren escribir consultas utilizando LEFT JOIN siempre que sea posible, reorganizando las tablas para mantener una lectura más natural.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `INNER JOIN` devuelve únicamente los registros que coinciden en ambas tablas.
- `LEFT JOIN` conserva todos los registros de la tabla izquierda.
- `RIGHT JOIN` conserva todos los registros de la tabla derecha.
- `FULL OUTER JOIN` devuelve todos los registros de ambas tablas.
- Cuando no existe una correspondencia, SQL rellena los campos de la otra tabla con `NULL`.
- En proyectos reales, `LEFT JOIN` suele utilizarse con mucha más frecuencia que `RIGHT JOIN`.

---

# Agrupando información con GROUP BY

Hasta ahora nuestras consultas devolvían registros individuales.

Por ejemplo:

```sql
SELECT nombre,
       municipio
FROM ciudadanos;
```

Resultado:

| nombre | municipio |
|---------|------------|
|Pedro|Murcia|
|Ana|Murcia|
|Luis|Lorca|
|María|Murcia|
|Carlos|Cartagena|

Pero...

¿Y si queremos responder a esta pregunta?

> ¿Cuántos ciudadanos hay en cada municipio?

Ya no queremos ver cada ciudadano.

Queremos obtener un resumen.

Para ello utilizaremos:

```sql
GROUP BY
```

---

# ¿Qué hace GROUP BY?

La cláusula:

```sql
GROUP BY
```

agrupa los registros que tienen el mismo valor en una o varias columnas.

Después podremos realizar cálculos sobre cada grupo.

Visualmente:

```
Murcia

↓

Pedro

Ana

María

↓

3 ciudadanos
```

---

# Primer ejemplo

Consulta:

```sql
SELECT municipio,
       COUNT(*)
FROM ciudadanos
GROUP BY municipio;
```

Resultado:

| municipio | COUNT(*) |
|------------|-----------|
|Murcia|3|
|Lorca|1|
|Cartagena|1|

Observa que ya no aparece un registro por ciudadano.

Ahora aparece un registro por municipio.

---

# ¿Por qué funciona?

SQL realiza internamente dos pasos:

1. Agrupa todos los registros con el mismo municipio.
2. Cuenta cuántos registros contiene cada grupo.

---

# Otro ejemplo

Queremos conocer la superficie total cultivada en cada municipio.

```sql
SELECT municipio,
       SUM(superficie)
FROM parcelas
GROUP BY municipio;
```

Resultado:

| municipio | SUM(superficie) |
|------------|-----------------|
|Murcia|8450|
|Lorca|3260|
|Cartagena|5910|

---

# Calculando medias

También podemos utilizar:

```sql
AVG()
```

Ejemplo:

```sql
SELECT municipio,
       AVG(superficie)
FROM parcelas
GROUP BY municipio;
```

Resultado:

| municipio | AVG(superficie) |
|------------|-----------------|
|Murcia|704,16|
|Lorca|815,00|
|Cartagena|985,00|

---

# Utilizando MIN y MAX

Consulta:

```sql
SELECT municipio,
       MAX(superficie)
FROM parcelas
GROUP BY municipio;
```

Resultado:

| municipio | MAX(superficie) |
|------------|-----------------|
|Murcia|1800|
|Lorca|1300|
|Cartagena|2200|

Podríamos hacer exactamente lo mismo utilizando:

```sql
MIN()
```

---

# GROUP BY con varias columnas

No estamos limitados a una única columna.

Ejemplo:

```sql
SELECT municipio,
       cultivo,
       COUNT(*)
FROM parcelas
GROUP BY municipio,
         cultivo;
```

Resultado:

| municipio | cultivo | COUNT(*) |
|------------|----------|-----------|
|Murcia|Limonero|5|
|Murcia|Naranjo|3|
|Lorca|Olivo|4|

Ahora cada grupo viene determinado por la combinación de ambas columnas.

---

# Una regla muy importante

Observa la siguiente consulta.

```sql
SELECT municipio,
       nombre
FROM ciudadanos
GROUP BY municipio;
```

¿Es correcta?

No.

¿Por qué?

Porque:

```
nombre
```

no pertenece al agrupamiento.

Y tampoco estamos aplicando ninguna función de agregación sobre él.

---

# La regla general

Cuando utilizamos:

```sql
GROUP BY
```

todas las columnas del `SELECT` deben cumplir una de estas condiciones:

- Formar parte del `GROUP BY`.
- O estar dentro de una función de agregación.

Por ejemplo:

Correcto:

```sql
SELECT municipio,
       COUNT(*)
FROM ciudadanos
GROUP BY municipio;
```

Correcto:

```sql
SELECT municipio,
       AVG(edad)
FROM ciudadanos
GROUP BY municipio;
```

Incorrecto:

```sql
SELECT municipio,
       nombre
FROM ciudadanos
GROUP BY municipio;
```

---

# Ordenando grupos

Es perfectamente válido combinar:

```sql
GROUP BY
```

con:

```sql
ORDER BY
```

Ejemplo:

```sql
SELECT municipio,
       COUNT(*)
FROM ciudadanos
GROUP BY municipio
ORDER BY COUNT(*) DESC;
```

Resultado:

| municipio | COUNT(*) |
|------------|-----------|
|Murcia|3|
|Cartagena|2|
|Lorca|1|

Ahora los municipios aparecen ordenados por número de ciudadanos.

---

# Errores frecuentes

### ❌ Pensar que GROUP BY ordena

No.

Agrupar y ordenar son operaciones diferentes.

Si queremos un orden concreto debemos utilizar:

```sql
ORDER BY
```

---

### ❌ Seleccionar columnas que no pertenecen al grupo

Incorrecto:

```sql
SELECT municipio,
       nombre
FROM ciudadanos
GROUP BY municipio;
```

La consulta generará un error en la mayoría de gestores.

---

### ❌ Confundir COUNT(*) con COUNT(columna)

```sql
COUNT(*)
```

Cuenta todas las filas.

Mientras que:

```sql
COUNT(columna)
```

ignora aquellas donde esa columna contiene `NULL`.

---

# Buenas prácticas

Cuando una consulta contiene agrupaciones, resulta recomendable escribirla así:

```sql
SELECT municipio,
       COUNT(*) AS total_ciudadanos,
       AVG(edad) AS edad_media
FROM ciudadanos
GROUP BY municipio
ORDER BY total_ciudadanos DESC;
```

Además de mejorar la legibilidad, el uso de alias (`AS`) hace que el resultado sea mucho más comprensible.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `GROUP BY` agrupa registros con el mismo valor.
- Las funciones de agregación calculan un resultado para cada grupo.
- Todas las columnas del `SELECT` deben pertenecer al `GROUP BY` o utilizar una función de agregación.
- `GROUP BY` no ordena automáticamente los resultados.
- Es habitual combinar `GROUP BY` con `ORDER BY`.
- `COUNT(*)`, `SUM()`, `AVG()`, `MIN()` y `MAX()` son las funciones más utilizadas junto con `GROUP BY`.

---

# Filtrando grupos con HAVING

En el apartado anterior aprendimos a agrupar registros utilizando:

```sql
GROUP BY
```

Por ejemplo:

```sql
SELECT municipio,
       COUNT(*)
FROM ciudadanos
GROUP BY municipio;
```

Resultado:

| municipio | COUNT(*) |
|------------|-----------|
|Murcia|15|
|Lorca|4|
|Cartagena|9|
|Caravaca|2|

Pero...

¿Qué ocurre si únicamente queremos los municipios que tienen más de 5 ciudadanos?

Muchos principiantes intentan escribir:

```sql
SELECT municipio,
       COUNT(*)
FROM ciudadanos
WHERE COUNT(*) > 5
GROUP BY municipio;
```

La consulta es incorrecta.

---

# ¿Por qué no funciona?

Recordemos el orden lógico en el que SQL procesa una consulta.

```
FROM

↓

WHERE

↓

GROUP BY

↓

HAVING

↓

SELECT

↓

ORDER BY
```

Observa un detalle importante.

Cuando SQL ejecuta:

```sql
WHERE
```

Todavía **no existen los grupos**.

Por tanto:

No puede calcular:

```sql
COUNT(*)
```

Porque aún no ha agrupado los registros.

---

# La solución

Para filtrar grupos utilizamos:

```sql
HAVING
```

Su estructura es:

```sql
SELECT columnas
FROM tabla
GROUP BY columna
HAVING condición;
```

---

# Primer ejemplo

Queremos mostrar únicamente los municipios con más de cinco ciudadanos.

```sql
SELECT municipio,
       COUNT(*) AS total
FROM ciudadanos
GROUP BY municipio
HAVING COUNT(*) > 5;
```

Resultado:

| municipio | total |
|------------|-------|
|Murcia|15|
|Cartagena|9|

Lorca y Caravaca desaparecen porque no alcanzan el mínimo solicitado.

---

# ¿Qué hace realmente HAVING?

Podemos imaginar el proceso así.

Primero SQL agrupa.

```
Murcia

↓

15 ciudadanos
```

```
Lorca

↓

4 ciudadanos
```

Después aplica HAVING.

```
¿Es mayor que 5?

↓

Sí

↓

Se muestra.
```

```
¿Es mayor que 5?

↓

No

↓

Se descarta.
```

---

# WHERE y HAVING

Esta diferencia suele aparecer constantemente en oposiciones.

| WHERE | HAVING |
|---------|---------|
| Filtra registros | Filtra grupos |
| Se ejecuta antes del GROUP BY | Se ejecuta después del GROUP BY |
| No puede utilizar funciones de agregación | Sí puede utilizar funciones de agregación |

Es una de las tablas que conviene memorizar.

---

# Utilizando varias condiciones

HAVING admite operadores lógicos igual que WHERE.

Ejemplo:

```sql
SELECT municipio,
       COUNT(*) AS total
FROM ciudadanos
GROUP BY municipio
HAVING COUNT(*) > 5
AND COUNT(*) < 20;
```

Resultado:

Obtendremos únicamente los municipios cuyo número de ciudadanos esté comprendido entre ambos valores.

---

# HAVING con SUM

Supongamos la tabla:

```
Parcelas
```

Queremos conocer únicamente los municipios cuya superficie cultivada supera las 10.000 hectáreas.

```sql
SELECT municipio,
       SUM(superficie) AS total
FROM parcelas
GROUP BY municipio
HAVING SUM(superficie) > 10000;
```

---

# HAVING con AVG

También podemos filtrar medias.

Ejemplo:

```sql
SELECT municipio,
       AVG(superficie) AS media
FROM parcelas
GROUP BY municipio
HAVING AVG(superficie) > 800;
```

Solo aparecerán aquellos municipios cuya superficie media sea superior a 800.

---

# ¿Podemos utilizar WHERE y HAVING juntos?

Sí.

De hecho es bastante habitual.

Ejemplo:

```sql
SELECT municipio,
       COUNT(*) AS total
FROM ciudadanos
WHERE edad >= 18
GROUP BY municipio
HAVING COUNT(*) > 10;
```

¿Qué hace esta consulta?

Primero:

```
WHERE
```

Elimina todos los menores de edad.

Después:

```
GROUP BY
```

Agrupa únicamente los adultos.

Finalmente:

```
HAVING
```

Conserva solo los municipios con más de diez ciudadanos adultos.

---

# Un ejemplo completo

Queremos conocer los municipios donde:

- Existen ciudadanos mayores de edad.
- Hay más de cinco ciudadanos adultos.

Consulta:

```sql
SELECT municipio,
       COUNT(*) AS adultos
FROM ciudadanos
WHERE edad >= 18
GROUP BY municipio
HAVING COUNT(*) > 5
ORDER BY adultos DESC;
```

Observa cómo intervienen varias cláusulas en una misma consulta.

Cada una tiene una función distinta.

---

# Errores frecuentes

### ❌ Utilizar funciones de agregación en WHERE

Incorrecto:

```sql
WHERE COUNT(*) > 5
```

Correcto:

```sql
HAVING COUNT(*) > 5
```

---

### ❌ Pensar que HAVING sustituye a WHERE

No.

Cada cláusula tiene una finalidad distinta.

Siempre que sea posible, los filtros sobre registros deben realizarse mediante:

```sql
WHERE
```

---

### ❌ Omitir GROUP BY

Aunque algunos gestores permiten determinados casos especiales, lo habitual es utilizar `HAVING` junto con `GROUP BY`.

---

# Buenas prácticas

Una consulta compleja suele escribirse siguiendo este orden:

```sql
SELECT municipio,
       COUNT(*) AS total
FROM ciudadanos
WHERE edad >= 18
GROUP BY municipio
HAVING COUNT(*) > 10
ORDER BY total DESC;
```

Mantener siempre el mismo orden facilita enormemente la lectura.

---

# Resumen visual

```
FROM

↓

WHERE

↓

GROUP BY

↓

HAVING

↓

SELECT

↓

ORDER BY
```

Recuerda la diferencia fundamental:

```
WHERE

↓

Filtra registros.
```

```
HAVING

↓

Filtra grupos.
```

---

# Conceptos importantes

Antes de continuar debes recordar:

- `HAVING` permite filtrar grupos creados mediante `GROUP BY`.
- `WHERE` filtra registros antes del agrupamiento.
- `HAVING` se ejecuta después de `GROUP BY`.
- Las funciones de agregación (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) se utilizan habitualmente dentro de `HAVING`.
- Es perfectamente válido combinar `WHERE`, `GROUP BY`, `HAVING` y `ORDER BY` en una misma consulta.
- La diferencia entre `WHERE` y `HAVING` es una de las preguntas más frecuentes en oposiciones y entrevistas técnicas.

---

# Subconsultas (Subqueries)

Hasta ahora todas nuestras consultas trabajaban directamente sobre una tabla.

Por ejemplo:

```sql
SELECT nombre
FROM ciudadanos;
```

O bien:

```sql
SELECT nombre
FROM ciudadanos
WHERE municipio = 'Murcia';
```

Pero...

¿Qué ocurre cuando la información que necesitamos todavía no la conocemos?

Por ejemplo:

> ¿Qué ciudadanos viven en el municipio cuyo identificador es 3?

Primero debemos averiguar qué municipio corresponde al identificador.

Después buscar los ciudadanos.

Aquí aparecen las subconsultas.

---

# ¿Qué es una subconsulta?

Una subconsulta es una consulta SQL que se ejecuta dentro de otra consulta.

Su resultado es utilizado por la consulta principal.

Visualmente:

```
Consulta principal

↓

Necesita un dato

↓

Ejecuta otra consulta

↓

Obtiene el resultado

↓

Continúa ejecutándose
```

---

# Nuestro primer ejemplo

Supongamos estas tablas.

## Municipios

| id | nombre |
|----|---------|
|1|Murcia|
|2|Lorca|
|3|Cartagena|

---

## Ciudadanos

| id | nombre | id_municipio |
|----|---------|--------------|
|1|Pedro|1|
|2|Ana|3|
|3|Luis|2|

Queremos obtener los ciudadanos que viven en Cartagena.

Pero imaginemos que solo conocemos el nombre del municipio.

No su identificador.

---

# Paso 1

Primero averiguamos el identificador.

```sql
SELECT id
FROM municipios
WHERE nombre = 'Cartagena';
```

Resultado:

```
3
```

---

# Paso 2

Después buscamos los ciudadanos.

```sql
SELECT nombre
FROM ciudadanos
WHERE id_municipio = 3;
```

Resultado:

```
Ana
```

---

# La subconsulta

Podemos combinar ambos pasos.

```sql
SELECT nombre
FROM ciudadanos
WHERE id_municipio = (
    SELECT id
    FROM municipios
    WHERE nombre = 'Cartagena'
);
```

SQL realiza automáticamente ambas operaciones.

Primero ejecuta la consulta interior.

Después utiliza el resultado en la consulta exterior.

---

# ¿Qué ocurre internamente?

Podemos imaginar el proceso así.

```
Consulta exterior

↓

Necesita un municipio

↓

Ejecuta la subconsulta

↓

Obtiene:

3

↓

Continúa

↓

Busca ciudadanos con id_municipio = 3
```

Todo ocurre automáticamente.

---

# Subconsultas que devuelven varios valores

Hasta ahora la subconsulta devolvía un único resultado.

Pero puede devolver varios.

Por ejemplo:

Queremos obtener los ciudadanos que viven en Murcia o Lorca.

La subconsulta sería:

```sql
SELECT id
FROM municipios
WHERE nombre IN ('Murcia','Lorca');
```

Resultado:

```
1

2
```

Ya no podemos utilizar:

```sql
=
```

Porque ahora existen varios valores.

---

# Utilizando IN

La consulta correcta será:

```sql
SELECT nombre
FROM ciudadanos
WHERE id_municipio IN (
    SELECT id
    FROM municipios
   WHERE nombre IN ('Murcia','Lorca')
);
```

Resultado:

| nombre |
|---------|
|Pedro|
|Luis|

---

# Subconsultas con funciones de agregación

Las subconsultas también pueden calcular valores.

Por ejemplo:

Queremos localizar las parcelas cuya superficie sea superior a la media.

Primero calculamos la media.

```sql
SELECT AVG(superficie)
FROM parcelas;
```

Supongamos que el resultado es:

```
850
```

---

Después buscamos las parcelas.

```sql
SELECT *
FROM parcelas
WHERE superficie > (
    SELECT AVG(superficie)
    FROM parcelas
);
```

Resultado:

Todas las parcelas cuya superficie supera la media.

Esta es una de las aplicaciones más habituales de las subconsultas.

---

# ¿Dónde pueden utilizarse?

Las subconsultas pueden aparecer en numerosos lugares.

Por ejemplo:

En un `WHERE`:

```sql
WHERE id IN (...)
```

---

En un `FROM`:

```sql
FROM (
    SELECT ...
)
```

---

Incluso dentro del propio `SELECT`.

Aunque estos casos los estudiaremos más adelante.

---

# Ventajas de las subconsultas

Permiten:

- Dividir un problema complejo en varios pasos.
- Evitar cálculos manuales.
- Escribir consultas más expresivas.
- Reutilizar resultados intermedios.

Muchas consultas complejas pueden entenderse fácilmente si se leen de dentro hacia fuera.

---

# Leyendo una subconsulta

Veamos de nuevo el ejemplo.

```sql
SELECT nombre
FROM ciudadanos
WHERE id_municipio = (
    SELECT id
    FROM municipios
    WHERE nombre = 'Cartagena'
);
```

Una buena forma de leerla es:

1. Busca el identificador del municipio llamado Cartagena.
2. Con ese identificador, busca los ciudadanos correspondientes.

Pensar así facilita mucho la comprensión.

---

# Errores frecuentes

### ❌ Utilizar "=" cuando la subconsulta devuelve varios resultados

Incorrecto:

```sql
WHERE id_municipio = (
    SELECT id
    FROM municipios
)
```

Si la subconsulta devuelve varias filas, SQL generará un error.

En estos casos debe utilizarse:

```sql
IN
```

---

### ❌ Pensar que las subconsultas siempre son más rápidas

No necesariamente.

En algunos casos un `JOIN` puede resultar más eficiente.

La elección dependerá del problema que queramos resolver y del optimizador del SGBD.

---

### ❌ Intentar ejecutar primero la consulta exterior

Recuerda:

La consulta interior se resuelve antes.

Después continúa la consulta principal.

---

# Buenas prácticas

Cuando una subconsulta ocupa varias líneas:

- Indéntala correctamente.
- Utiliza paréntesis.
- Coloca la consulta interior con un nivel adicional de sangrado.

Ejemplo:

```sql
SELECT nombre
FROM ciudadanos
WHERE id_municipio = (
    SELECT id
    FROM municipios
    WHERE nombre = 'Cartagena'
);
```

La consulta resulta mucho más fácil de leer.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Una subconsulta es una consulta incluida dentro de otra.
- La consulta interior se ejecuta antes que la exterior.
- Si la subconsulta devuelve un único valor puede utilizarse `=`.
- Si devuelve varios valores suele utilizarse `IN`.
- Las subconsultas permiten resolver problemas complejos dividiéndolos en pasos más sencillos.
- Es recomendable leer las subconsultas desde el nivel más interno hacia el exterior.

---

# Subconsultas avanzadas: EXISTS, ANY, ALL y subconsultas correlacionadas

En el apartado anterior vimos que una subconsulta puede devolver:

- Un único valor.
- Varios valores.

Ahora estudiaremos operadores que permiten realizar consultas más complejas.

Aunque su uso es menos frecuente que `JOIN` o `GROUP BY`, conviene conocerlos porque aparecen en documentación técnica, entrevistas y, ocasionalmente, en preguntas de oposición.

---

# EXISTS

El operador:

```sql
EXISTS
```

comprueba si una subconsulta devuelve **al menos un registro**.

No le interesa el contenido.

Solo necesita saber si existe algún resultado.

Visualmente:

```
¿Existe algún registro?

↓

Sí

↓

TRUE
```

```
¿Existe algún registro?

↓

No

↓

FALSE
```

---

# Primer ejemplo

Queremos obtener los municipios que tienen al menos un ciudadano registrado.

```sql
SELECT nombre
FROM municipios m
WHERE EXISTS (
    SELECT 1
    FROM ciudadanos c
    WHERE c.id_municipio = m.id
);
```

Resultado:

| Municipio |
|------------|
|Murcia|
|Lorca|
|Cartagena|

Si Caravaca no tiene ciudadanos, no aparecerá.

---

# ¿Por qué SELECT 1?

Es muy habitual encontrar consultas como esta:

```sql
SELECT 1
```

En realidad:

El valor no importa.

Podría escribirse:

```sql
SELECT *
```

o incluso:

```sql
SELECT id
```

Lo único que necesita `EXISTS` es comprobar si la subconsulta devuelve alguna fila.

Por convenio se suele utilizar:

```sql
SELECT 1
```

porque deja claro que el contenido es irrelevante.

---

# NOT EXISTS

También podemos hacer lo contrario.

Obtener municipios sin ciudadanos.

```sql
SELECT nombre
FROM municipios m
WHERE NOT EXISTS (
    SELECT 1
    FROM ciudadanos c
    WHERE c.id_municipio = m.id
);
```

Resultado:

| Municipio |
|------------|
|Caravaca|

Es una consulta muy útil para detectar registros "huérfanos" o sin relaciones.

---

# ANY

El operador:

```sql
ANY
```

compara un valor con **cualquiera** de los valores devueltos por una subconsulta.

Ejemplo:

Queremos obtener las parcelas cuya superficie sea mayor que **alguna** de las parcelas de Lorca.

```sql
SELECT *
FROM parcelas
WHERE superficie > ANY (
    SELECT superficie
    FROM parcelas
    WHERE municipio = 'Lorca'
);
```

Si la condición se cumple para al menos uno de los valores devueltos por la subconsulta, el registro será seleccionado.

---

# ALL

El operador:

```sql
ALL
```

es más exigente.

La condición debe cumplirse para **todos** los valores devueltos.

Ejemplo:

```sql
SELECT *
FROM parcelas
WHERE superficie > ALL (
    SELECT superficie
    FROM parcelas
    WHERE municipio = 'Lorca'
);
```

En este caso solo aparecerán las parcelas cuya superficie sea mayor que **todas** las parcelas de Lorca.

---

# Diferencia entre ANY y ALL

Supongamos que la subconsulta devuelve:

```
300

600

900
```

Consulta:

```sql
superficie > ANY (...)
```

Basta con que la superficie sea mayor que **uno** de esos valores.

Por ejemplo:

```
650
```

Es mayor que 300 y 600.

La condición se cumple.

---

Consulta:

```sql
superficie > ALL (...)
```

Ahora debe ser mayor que:

```
300

600

900
```

Es decir:

Debe ser superior a **900**.

---

# Subconsultas correlacionadas

Hasta ahora nuestras subconsultas eran independientes.

Podían ejecutarse por sí solas.

Ejemplo:

```sql
SELECT id
FROM municipios
WHERE nombre = 'Murcia';
```

Una subconsulta correlacionada funciona de otra forma.

Depende de la consulta exterior.

---

# Ejemplo

```sql
SELECT nombre
FROM municipios m
WHERE EXISTS (
    SELECT 1
    FROM ciudadanos c
    WHERE c.id_municipio = m.id
);
```

Observa:

```sql
m.id
```

pertenece a la consulta exterior.

La subconsulta necesita ese valor para ejecutarse.

Por eso recibe el nombre de:

```
Subconsulta correlacionada
```

---

# ¿Cómo se ejecuta?

Podemos imaginar el siguiente proceso.

```
Municipio: Murcia

↓

Ejecutar subconsulta

↓

¿Tiene ciudadanos?

↓

Sí

↓

Mostrar Murcia
```

Después:

```
Municipio: Lorca

↓

Ejecutar subconsulta

↓

¿Tiene ciudadanos?

↓

Sí
```

Después:

```
Municipio: Caravaca

↓

Ejecutar subconsulta

↓

¿Tiene ciudadanos?

↓

No

↓

No mostrar
```

La subconsulta se ejecuta una vez por cada fila de la consulta principal.

---

# ¿JOIN o EXISTS?

Muchas consultas pueden escribirse de ambas formas.

Ejemplo:

Con JOIN:

```sql
SELECT DISTINCT m.nombre
FROM municipios m
INNER JOIN ciudadanos c
ON c.id_municipio = m.id;
```

Con EXISTS:

```sql
SELECT nombre
FROM municipios m
WHERE EXISTS (
    SELECT 1
    FROM ciudadanos c
    WHERE c.id_municipio = m.id
);
```

Ambas devuelven el mismo resultado.

La elección dependerá del problema y del optimizador del SGBD.

---

# Errores frecuentes

### ❌ Pensar que EXISTS devuelve datos

No.

`EXISTS` solo responde:

- Existe.
- No existe.

Nada más.

---

### ❌ Confundir ANY con ALL

Recuerda:

```
ANY

↓

Al menos uno.
```

```
ALL

↓

Todos.
```

---

### ❌ Pensar que una subconsulta correlacionada puede ejecutarse sola

No.

Depende de los valores de la consulta exterior.

---

# Buenas prácticas

- Utiliza `EXISTS` cuando únicamente necesites comprobar la existencia de registros relacionados.
- Utiliza `JOIN` cuando necesites recuperar columnas de varias tablas.
- Emplea alias claros (`c`, `m`, `p`, etc.) para facilitar la lectura de subconsultas correlacionadas.
- Indenta siempre las subconsultas para distinguir claramente la consulta principal de la consulta interna.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `EXISTS` comprueba si una subconsulta devuelve al menos un registro.
- `NOT EXISTS` selecciona aquellos registros para los que no existe ninguna correspondencia.
- `ANY` compara un valor con cualquiera de los valores devueltos por una subconsulta.
- `ALL` exige que la condición se cumpla para todos los valores.
- Una subconsulta correlacionada depende de la consulta exterior y se ejecuta para cada fila procesada.
- En muchos casos, una consulta puede resolverse tanto con `JOIN` como con `EXISTS`; la elección dependerá del objetivo y de la claridad de la solución.

---

# Vistas (VIEW)

Hasta ahora todas nuestras consultas debían escribirse completamente cada vez.

Por ejemplo:

```sql
SELECT c.nombre,
       m.nombre AS municipio
FROM ciudadanos c
INNER JOIN municipios m
ON c.id_municipio = m.id;
```

La consulta funciona correctamente.

Pero...

¿Y si necesitamos utilizarla todos los días?

¿Y si otras aplicaciones también necesitan ese mismo resultado?

¿Tenemos que escribirla siempre?

La respuesta es:

```
No.
```

Para ello existen las vistas.

---

# ¿Qué es una vista?

Una vista (**VIEW**) es una consulta SQL almacenada con un nombre.

Podemos imaginarla como una:

```
Tabla virtual.
```

No contiene datos propios.

Simplemente almacena la consulta necesaria para obtenerlos.

---

# Un ejemplo

Supongamos la siguiente consulta.

```sql
SELECT c.nombre,
       m.nombre AS municipio
FROM ciudadanos c
INNER JOIN municipios m
ON c.id_municipio = m.id;
```

Podemos guardarla con el nombre:

```
vista_ciudadanos
```

---

# Crear una vista

La sintaxis es:

```sql
CREATE VIEW nombre_vista AS
SELECT ...
```

Ejemplo:

```sql
CREATE VIEW vista_ciudadanos AS

SELECT c.nombre,
       m.nombre AS municipio
FROM ciudadanos c
INNER JOIN municipios m
ON c.id_municipio = m.id;
```

La vista queda almacenada dentro de la base de datos.

---

# Utilizar una vista

A partir de ese momento podemos consultarla como si fuese una tabla.

```sql
SELECT *
FROM vista_ciudadanos;
```

Resultado:

| nombre | municipio |
|---------|------------|
|Pedro|Murcia|
|Ana|Lorca|
|Luis|Cartagena|

Mucho más sencillo.

---

# ¿Dónde están los datos?

Una pregunta muy habitual.

La vista:

```
NO
```

almacena datos.

Los datos siguen estando en:

- Ciudadanos.
- Municipios.

Cada vez que consultamos la vista:

El SGBD ejecuta automáticamente la consulta almacenada.

---

# Ventajas de las vistas

Las vistas permiten:

- Simplificar consultas complejas.
- Reutilizar código SQL.
- Ocultar la complejidad de múltiples JOIN.
- Mejorar la seguridad.
- Facilitar el mantenimiento.

---

# Un ejemplo práctico

Supongamos que una aplicación únicamente necesita:

- Nombre.
- Municipio.

No necesita conocer:

- id_municipio.
- Relaciones.
- JOIN.

La aplicación simplemente consulta:

```sql
SELECT *
FROM vista_ciudadanos;
```

La vista hace todo el trabajo.

---

# Seguridad mediante vistas

Las vistas también permiten limitar la información accesible.

Imaginemos la tabla:

```
Ciudadanos
```

| id | nombre | dni | teléfono |
|----|---------|------|-----------|

No queremos mostrar:

- DNI.
- Teléfono.

Creamos una vista.

```sql
CREATE VIEW vista_publica AS

SELECT nombre
FROM ciudadanos;
```

Los usuarios consultarán únicamente:

```sql
SELECT *
FROM vista_publica;
```

Nunca accederán directamente al resto de columnas.

---

# Actualización de datos

Muchas vistas permiten realizar operaciones como:

```sql
INSERT

UPDATE

DELETE
```

Sin embargo:

No todas son actualizables.

Por ejemplo:

Una vista basada en varias tablas mediante JOIN suele presentar restricciones.

El comportamiento depende del SGBD.

En la práctica, muchas vistas se utilizan únicamente para consultas.

---

# Modificar una vista

Podemos cambiar su definición.

En muchos gestores:

```sql
CREATE OR REPLACE VIEW
```

Ejemplo:

```sql
CREATE OR REPLACE VIEW vista_ciudadanos AS

SELECT nombre,
       municipio
FROM ...
```

La vista conservará su nombre, pero utilizará la nueva consulta.

---

# Eliminar una vista

Si deja de ser necesaria:

```sql
DROP VIEW vista_ciudadanos;
```

La vista desaparece.

Importante:

Solo se elimina la vista.

Las tablas originales permanecen intactas.

---

# ¿Qué diferencia existe entre una tabla y una vista?

| Tabla | Vista |
|--------|--------|
| Almacena datos | No almacena datos (salvo vistas materializadas) |
| Ocupa espacio | Almacena únicamente la definición de la consulta |
| Puede consultarse directamente | Se consulta igual que una tabla |
| Puede existir sin otras tablas | Depende normalmente de una o varias tablas |

---

# Vistas materializadas

Algunos SGBD, como PostgreSQL u Oracle, incorporan un tipo especial.

```
Materialized View
```

En este caso:

Sí se almacenan físicamente los resultados.

Ventajas:

- Consultas muy rápidas.

Inconvenientes:

- Es necesario refrescar la vista cuando cambian los datos.

No todos los gestores implementan esta funcionalidad de la misma forma.

---

# Errores frecuentes

### ❌ Pensar que una vista almacena datos

No.

Salvo las vistas materializadas.

Una vista tradicional únicamente almacena una consulta.

---

### ❌ Eliminar una vista creyendo que se eliminan los datos

```sql
DROP VIEW
```

No afecta a las tablas originales.

Solo desaparece la definición de la vista.

---

### ❌ Utilizar vistas para cualquier consulta

Las vistas son muy útiles.

Pero no es necesario crear una vista para cada consulta que escribimos.

Conviene utilizarlas cuando una consulta:

- Se reutiliza con frecuencia.
- Resulta compleja.
- Debe ocultar parte de la información.

---

# Buenas prácticas

- Utilizar nombres descriptivos (`vista_ciudadanos`, `vista_parcelas`, etc.).
- Documentar el propósito de la vista.
- Evitar crear vistas excesivamente complejas.
- Utilizar vistas para simplificar el acceso a información utilizada habitualmente.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Una vista es una consulta almacenada con un nombre.
- Se comporta como una tabla virtual.
- Las vistas tradicionales no almacenan datos.
- Permiten reutilizar consultas complejas y mejorar la seguridad.
- `CREATE VIEW` crea una vista.
- `DROP VIEW` elimina únicamente la vista, no los datos.
- Algunos gestores incorporan vistas materializadas, que sí almacenan físicamente los resultados.

---

# Índices (INDEX)

Hasta ahora hemos aprendido a consultar información.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos
WHERE nombre = 'Pedro García';
```

La consulta parece muy sencilla.

Pero...

¿Qué ocurre si la tabla contiene:

- 100 registros.
- 10.000 registros.
- 1.000.000 de registros.

¿Cómo encuentra la base de datos ese ciudadano?

---

# Un ejemplo cotidiano

Imagina un libro de 2.000 páginas.

Quieres localizar el capítulo:

```
PostGIS
```

Tienes dos opciones.

## Opción 1

Comenzar por la página 1.

Leer todas las páginas hasta encontrarlo.

```
Página 1

↓

Página 2

↓

Página 3

↓

...

↓

Página 1437
```

Funciona.

Pero resulta muy lento.

---

## Opción 2

Abrir el índice del libro.

```
PostGIS

↓

Página 1437
```

Llegas prácticamente de forma inmediata.

Eso mismo hace un índice en una base de datos.

---

# ¿Qué es un índice?

Un índice es una estructura de datos que permite localizar registros mucho más rápidamente.

No modifica la información.

Simplemente facilita encontrarla.

Podemos imaginarlo así.

```
Tabla

↓

Índice

↓

Registro
```

---

# ¿Qué ocurre sin índice?

Supongamos una tabla.

```
Ciudadanos
```

Contiene:

```
1.500.000 registros
```

Consulta:

```sql
SELECT *
FROM ciudadanos
WHERE dni='12345678A';
```

Si el campo:

```
dni
```

no posee un índice.

El SGBD deberá revisar:

```
Fila 1

↓

Fila 2

↓

Fila 3

↓

...

↓

Fila 1.500.000
```

Este proceso recibe el nombre de:

```
Table Scan

o

Full Table Scan
```

---

# ¿Qué ocurre con un índice?

Si el campo:

```
dni
```

está indexado.

La búsqueda será mucho más rápida.

El gestor consulta primero el índice.

Después accede directamente al registro.

```
Índice

↓

12345678A

↓

Fila 874.352
```

No necesita recorrer toda la tabla.

---

# Crear un índice

La sintaxis básica es:

```sql
CREATE INDEX nombre_indice
ON tabla (columna);
```

Ejemplo:

```sql
CREATE INDEX idx_ciudadanos_dni
ON ciudadanos (dni);
```

A partir de ese momento:

Las búsquedas por DNI serán mucho más rápidas.

---

# ¿Sobre qué columnas conviene crear índices?

Normalmente sobre columnas utilizadas con frecuencia en:

- WHERE.
- JOIN.
- ORDER BY.
- GROUP BY.

Por ejemplo:

```sql
WHERE dni = ...
```

```sql
WHERE email = ...
```

```sql
JOIN municipios
```

---

# ¿Todas las columnas deben tener índice?

No.

Crear demasiados índices también tiene inconvenientes.

Cada índice ocupa espacio.

Y además debe actualizarse cuando:

- Insertamos registros.
- Modificamos registros.
- Eliminamos registros.

Por ello:

Más índices no siempre significa mejor rendimiento.

---

# Clave primaria e índices

Una pregunta muy frecuente.

¿La clave primaria posee índice?

La respuesta es:

```
Sí.
```

En prácticamente todos los SGBD.

Cuando definimos:

```sql
PRIMARY KEY
```

El gestor crea automáticamente un índice asociado.

Por ello:

No debemos crear otro índice adicional sobre esa misma columna.

---

# Índices únicos

También podemos crear índices que impidan valores duplicados.

Ejemplo:

```sql
CREATE UNIQUE INDEX idx_email
ON ciudadanos (email);
```

Ahora:

Dos ciudadanos no podrán compartir el mismo correo electrónico.

---

# Índices compuestos

Un índice también puede abarcar varias columnas.

Ejemplo:

```sql
CREATE INDEX idx_nombre_apellidos
ON ciudadanos (nombre, apellidos);
```

Resulta útil cuando las consultas suelen utilizar ambas columnas conjuntamente.

---

# ¿Qué tipo de índice utiliza PostgreSQL?

Aunque existen distintos tipos.

El más habitual es:

```
B-Tree
```

Es el índice por defecto en PostgreSQL, MySQL y muchos otros gestores.

Permite realizar búsquedas muy eficientes.

Más adelante, en el capítulo de PostgreSQL, estudiaremos otros tipos como:

- Hash.
- GiST.
- GIN.
- BRIN.

Especialmente importantes para PostGIS.

---

# EXPLAIN

¿Cómo sabemos si una consulta utiliza un índice?

Los SGBD incorporan herramientas para analizar el plan de ejecución.

La más conocida es:

```sql
EXPLAIN
```

Ejemplo:

```sql
EXPLAIN

SELECT *
FROM ciudadanos
WHERE dni='12345678A';
```

El gestor mostrará:

- Si utiliza un índice.
- Si realiza un recorrido completo de la tabla.
- El coste estimado de la consulta.

Es una herramienta fundamental para optimizar bases de datos.

---

# ¿Un índice siempre mejora el rendimiento?

No.

Si una consulta devuelve prácticamente todos los registros.

Por ejemplo:

```sql
SELECT *
FROM ciudadanos;
```

El índice aporta muy poca ventaja.

En ocasiones.

El gestor decide ignorarlo.

Y recorrer directamente toda la tabla.

---

# Errores frecuentes

### ❌ Crear índices sobre todas las columnas

No es recomendable.

Cada índice:

- Ocupa espacio.
- Consume memoria.
- Debe mantenerse actualizado.

---

### ❌ Crear un índice sobre la clave primaria

No tiene sentido.

El SGBD ya lo crea automáticamente.

---

### ❌ Pensar que un índice acelera INSERT

Sucede justamente lo contrario.

Cada inserción también debe actualizar todos los índices afectados.

Por ello:

Muchos índices aceleran las consultas.

Pero ralentizan las operaciones de escritura.

---

### ❌ Pensar que EXPLAIN ejecuta la consulta

Generalmente:

No.

EXPLAIN muestra el plan previsto por el optimizador.

Es una herramienta de análisis.

---

# Buenas prácticas

- Crear índices únicamente sobre columnas utilizadas con frecuencia en búsquedas.
- Revisar periódicamente las consultas lentas.
- Utilizar `EXPLAIN` para comprender cómo trabaja el optimizador.
- Evitar índices innecesarios.
- Aprovechar el índice automático creado por las claves primarias.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Un índice permite localizar registros de forma mucho más rápida.
- No almacena los datos; almacena una estructura que facilita su búsqueda.
- Los índices mejoran el rendimiento de muchas consultas, especialmente aquellas que utilizan `WHERE`, `JOIN` u `ORDER BY`.
- También consumen espacio y ralentizan las operaciones de inserción, modificación y borrado.
- Las claves primarias crean un índice automáticamente.
- `EXPLAIN` permite analizar cómo ejecutará el SGBD una consulta y comprobar si utiliza índices.

# Transacciones y propiedades ACID

Hasta ahora hemos ejecutado instrucciones SQL de forma independiente.

Por ejemplo:

```sql
UPDATE cuentas
SET saldo = saldo - 500
WHERE id = 1;
```

O bien:

```sql
INSERT INTO ciudadanos (...);
```

Pero...

¿Qué ocurre cuando una operación está formada por varios pasos?

Por ejemplo:

Una transferencia bancaria.

```
Cuenta A

↓

Restar dinero

↓

Cuenta B

↓

Sumar dinero
```

Si una de las operaciones falla, los datos quedarían inconsistentes.

Para evitar este problema existen las transacciones.

---

# ¿Qué es una transacción?

Una transacción es un conjunto de operaciones SQL que se ejecutan como una única unidad lógica.

Su objetivo es garantizar que:

- Todas las operaciones se realizan correctamente.

o bien:

- Ninguna de ellas produce efectos.

No existe un estado intermedio.

---

# Un ejemplo

Supongamos dos cuentas.

| Cuenta | Saldo |
|---------|-------|
|Pedro|1000 €|
|Ana|500 €|

Queremos transferir:

```
200 €
```

La operación requiere:

1.

```sql
UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;
```

2.

```sql
UPDATE cuentas
SET saldo = saldo + 200
WHERE id = 2;
```

Ambas instrucciones forman parte de una única operación lógica.

---

# BEGIN

Una transacción comienza mediante:

```sql
BEGIN;
```

Ejemplo:

```sql
BEGIN;
```

A partir de ese momento:

Las operaciones quedan agrupadas.

Todavía no son permanentes.

---

# COMMIT

Si todas las operaciones finalizan correctamente:

```sql
COMMIT;
```

Ejemplo:

```sql
BEGIN;

UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;

UPDATE cuentas
SET saldo = saldo + 200
WHERE id = 2;

COMMIT;
```

Después del `COMMIT`:

Los cambios quedan almacenados definitivamente.

---

# ROLLBACK

¿Qué ocurre si aparece un error?

Supongamos:

```
Cuenta A

↓

Descontar 200 €

↓

Error del servidor
```

No podemos dejar la base de datos en ese estado.

Utilizamos:

```sql
ROLLBACK;
```

Ejemplo:

```sql
BEGIN;

UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;

ROLLBACK;
```

Resultado:

Todo vuelve exactamente al estado anterior.

Es como si la transacción nunca hubiera existido.

---

# ¿Por qué son tan importantes?

Las transacciones protegen la integridad de los datos.

Sin ellas podrían aparecer situaciones como:

- Transferencias incompletas.
- Pedidos sin líneas de detalle.
- Facturas sin productos.
- Subvenciones parcialmente registradas.

En sistemas críticos esto sería inaceptable.

---

# Las propiedades ACID

Las transacciones cumplen cuatro propiedades fundamentales.

Se conocen mediante el acrónimo:

```
ACID
```

- Atomicity.
- Consistency.
- Isolation.
- Durability.

Son uno de los conceptos más importantes de las bases de datos relacionales.

---

# A · Atomicidad

Una transacción es indivisible.

Ocurre una de estas dos situaciones.

```
Todo.

o

Nada.
```

Nunca:

```
Solo una parte.
```

Ejemplo:

Una transferencia bancaria.

No puede descontarse el dinero sin abonarlo después.

---

# C · Consistencia

Una transacción debe llevar la base de datos desde un estado válido a otro estado válido.

Las reglas de integridad siguen cumpliéndose.

Ejemplos:

- No existen claves foráneas inválidas.
- No aparecen registros duplicados donde no están permitidos.
- Las restricciones continúan respetándose.

---

# I · Aislamiento (Isolation)

Varias transacciones pueden ejecutarse simultáneamente.

Sin embargo:

Cada una debe comportarse como si fuera la única que se está ejecutando.

Esto evita problemas como:

- Lecturas inconsistentes.
- Actualizaciones perdidas.
- Datos parcialmente modificados.

El grado de aislamiento puede configurarse mediante distintos niveles, que estudiaremos más adelante en PostgreSQL.

---

# D · Durabilidad (Durability)

Cuando ejecutamos:

```sql
COMMIT;
```

Los cambios quedan almacenados de forma permanente.

Incluso si inmediatamente después:

- Se apaga el servidor.
- Se produce un corte eléctrico.
- Reinicia el sistema operativo.

El gestor garantiza que los datos comprometidos no se perderán.

---

# Resumen de ACID

| Letra | Propiedad | Significado |
|--------|-----------|-------------|
| A | Atomicity | Todo o nada |
| C | Consistency | Mantiene la integridad de los datos |
| I | Isolation | Las transacciones no interfieren entre sí |
| D | Durability | Los cambios confirmados son permanentes |

Esta tabla aparece con mucha frecuencia en oposiciones.

---

# SAVEPOINT

En ocasiones no queremos deshacer toda la transacción.

Podemos crear puntos de restauración intermedios.

Ejemplo:

```sql
BEGIN;

UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;

SAVEPOINT paso1;

UPDATE cuentas
SET saldo = saldo + 200
WHERE id = 2;
```

Si la segunda operación falla:

```sql
ROLLBACK TO SAVEPOINT paso1;
```

Solo se desharán las operaciones posteriores a ese punto.

Finalmente:

```sql
COMMIT;
```

---

# Ejemplo completo

```sql
BEGIN;

UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;

UPDATE cuentas
SET saldo = saldo + 200
WHERE id = 2;

COMMIT;
```

Si cualquier operación produce un error:

```sql
ROLLBACK;
```

La base de datos recuperará automáticamente el estado anterior.

---

# Errores frecuentes

### ❌ Pensar que cada sentencia SQL es una transacción

Depende del SGBD y del modo de funcionamiento.

Muchos gestores utilizan **autocommit**, confirmando automáticamente cada sentencia.

Cuando necesitamos agrupar varias operaciones debemos iniciar explícitamente una transacción.

---

### ❌ Olvidar ejecutar COMMIT

Mientras la transacción no se confirme:

Los cambios pueden no ser permanentes.

---

### ❌ Confundir COMMIT con guardar un archivo

`COMMIT` no guarda un documento.

Confirma definitivamente las modificaciones realizadas sobre la base de datos.

---

### ❌ Pensar que ROLLBACK solo deshace la última instrucción

No.

`ROLLBACK` revierte toda la transacción, salvo que se utilicen puntos de restauración (`SAVEPOINT`).

---

# Buenas prácticas

- Mantener las transacciones lo más cortas posible.
- Confirmar (`COMMIT`) únicamente cuando todas las operaciones hayan finalizado correctamente.
- Utilizar `ROLLBACK` ante cualquier error.
- Evitar mantener transacciones abiertas durante mucho tiempo para reducir bloqueos y mejorar el rendimiento.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Una transacción agrupa varias operaciones SQL en una única unidad lógica.
- `BEGIN` inicia una transacción.
- `COMMIT` confirma definitivamente los cambios.
- `ROLLBACK` deshace las operaciones realizadas durante la transacción.
- `SAVEPOINT` permite crear puntos intermedios de recuperación.
- Las propiedades **ACID** garantizan la fiabilidad de las transacciones:
  - **Atomicity**: todo o nada.
  - **Consistency**: mantiene la integridad.
  - **Isolation**: las transacciones no interfieren entre sí.
  - **Durability**: los cambios confirmados son permanentes.
