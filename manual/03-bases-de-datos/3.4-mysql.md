# ¿Qué es MySQL?

MySQL es un **Sistema Gestor de Bases de Datos Relacional** (SGBD o DBMS).

Permite:

- Almacenar información.
- Consultar datos mediante SQL.
- Crear y modificar estructuras.
- Gestionar usuarios y permisos.
- Ejecutar transacciones.
- Mantener la integridad de los datos.

Es uno de los sistemas gestores de bases de datos más utilizados del mundo.

---


Por ejemplo:

```sql

```

MySQL es el software encargado de interpretar esa instrucción y trabajar con los datos.

```
MySQL AB
```
```
    ↓

Oracle Corporation
```

Actualmente MySQL es desarrollado y mantenido por Oracle.

# InnoDB

InnoDB es el motor de almacenamiento predeterminado de MySQL en las versiones modernas.

Es especialmente importante porque proporciona:

- Transacciones.
- Propiedades ACID.
- Claves foráneas.
- Bloqueo a nivel de fila.
- Recuperación ante fallos.
- Control de concurrencia.

Para aplicaciones modernas.

InnoDB es normalmente la elección recomendada.

---

# MyISAM

MyISAM fue históricamente uno de los motores más utilizados.

Destacaba por:

- Simplicidad.
- Buen rendimiento en determinadas consultas.
- Bajo consumo.

Pero presenta una limitación fundamental frente a InnoDB:

```text
No proporciona transacciones.
```

Además.

No ofrece claves foráneas como InnoDB.

Por ello.

Su utilización en nuevas aplicaciones es mucho menos habitual.

---

# InnoDB frente a MyISAM

| Característica | InnoDB | MyISAM |
|----------------|--------|--------|
| Transacciones | Sí | No |
| ACID | Sí | No |
| Claves foráneas | Sí | No |
| Bloqueo de filas | Sí | Principalmente a nivel de tabla |
| Recuperación ante fallos | Sí | Más limitada |
| Uso recomendado | Aplicaciones modernas | Casos específicos / legado |

Para la mayoría de aplicaciones actuales:

```text
InnoDB
```

es la opción adecuada.

# InnoDB: arquitectura y funcionamiento

InnoDB es el motor de almacenamiento predeterminado de MySQL en las versiones modernas.

Es especialmente importante porque proporciona las características necesarias para trabajar con aplicaciones transaccionales.

Entre ellas:

- Transacciones.
- Propiedades ACID.
- Claves foráneas.
- Control de concurrencia.
- Recuperación ante fallos.
- Bloqueo a nivel de fila.

---

# Arquitectura de InnoDB

Podemos representar de forma simplificada sus principales componentes:

```text
                 InnoDB
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
   Buffer Pool   Redo Log    Undo Log
        │
        ▼
    Datafiles
```

Además, InnoDB utiliza diferentes estructuras internas para gestionar:

- Índices.
- Bloqueos.
- Transacciones.
- Metadatos.
- Espacio de almacenamiento.

---

# Buffer Pool

Uno de los componentes más importantes de InnoDB es:

```text
InnoDB Buffer Pool
```

Es una zona de memoria utilizada para almacenar temporalmente:

- Páginas de datos.
- Páginas de índices.
- Información modificada pendiente de escribir.

Su objetivo principal es reducir los accesos al disco.

---

# ¿Por qué es importante?

El acceso a memoria es mucho más rápido que el acceso al almacenamiento.

Supongamos una consulta:

```sql
SELECT *
FROM clientes
WHERE id = 10;
```

InnoDB primero intenta encontrar las páginas necesarias en el Buffer Pool.

```text
Consulta

↓

Buffer Pool

↓

¿Está el dato?

├── Sí → Utilizarlo
│
└── No → Leer desde disco
```

Esto mejora considerablemente el rendimiento.

---

# Páginas

InnoDB organiza los datos en unidades llamadas:

```text
Pages
```

Una página contiene información de tablas o índices.

El Buffer Pool trabaja principalmente con estas páginas.

Por tanto:

```text
Disco

↓

Páginas

↓

Buffer Pool

↓

Consultas
```

---

# Dirty Pages

Cuando una página de memoria ha sido modificada pero todavía no se ha escrito en disco se denomina:

```text
Dirty Page
```

Por ejemplo:

```text
Disco

saldo = 1000
```

Una transacción modifica el valor:

```text
Buffer Pool

saldo = 800
```

Mientras el cambio todavía no se ha escrito en disco:

```text
Página = Dirty
```

Posteriormente InnoDB escribirá esa página en los archivos de datos.

---

# Redo Log

InnoDB utiliza un mecanismo de registro de cambios denominado:

```text
Redo Log
```

Su función principal está relacionada con la recuperación ante fallos.

La idea fundamental es:

```text
Cambio

↓

Redo Log

↓

Datafile
```

Si el servidor falla antes de que todas las páginas modificadas hayan llegado al disco.

InnoDB puede utilizar el Redo Log para reconstruir los cambios necesarios.

---

# Redo Log y PostgreSQL WAL

Este concepto resulta muy familiar si vienes del capítulo de PostgreSQL.

| PostgreSQL | MySQL / InnoDB |
|------------|----------------|
| WAL | Redo Log |
| Registro de cambios | Registro de cambios |
| Recuperación tras fallos | Recuperación tras fallos |
| Durabilidad | Durabilidad |

No son exactamente el mismo mecanismo interno.

Pero conceptualmente resuelven problemas muy similares.

---

# Undo Log

Ahora aparece otro componente fundamental:

```text
Undo Log
```

Mientras que el Redo Log permite reconstruir cambios.

El Undo Log permite recuperar información anterior.

Su utilización está relacionada principalmente con:

- `ROLLBACK`.
- MVCC.
- Lecturas consistentes.

---

# Ejemplo de Undo Log

Supongamos:

```text
saldo = 1000
```

Ejecutamos:

```sql
UPDATE cuentas
SET saldo = 800
WHERE id = 1;
```

InnoDB necesita conservar información que permita conocer el estado anterior:

```text
1000
```

Si posteriormente hacemos:

```sql
ROLLBACK;
```

puede utilizar esa información para deshacer el cambio.

---

# Redo frente a Undo

Una distinción fundamental:

| Redo Log | Undo Log |
|----------|----------|
| Reaplica cambios | Permite deshacer cambios |
| Recuperación | Rollback |
| Durabilidad | MVCC / lecturas consistentes |
| "Qué debo volver a hacer" | "Qué había antes" |

Podemos recordarlo así:

```text
REDO

↓

Volver a hacer
```

```text
UNDO

↓

Deshacer
```

---

# MVCC en InnoDB

InnoDB también utiliza:

```text
MVCC

Multi-Version Concurrency Control
```

Esto permite mantener diferentes versiones de los registros para que las transacciones puedan trabajar de forma concurrente.

Una transacción puede observar una versión consistente de los datos sin bloquear necesariamente las operaciones de otras transacciones.

---

# Ejemplo de MVCC

Supongamos:

```text
saldo = 1000
```

Una transacción modifica:

```text
saldo = 800
```

Mientras otra transacción todavía necesita consultar el estado anterior.

Gracias a MVCC.

Puede acceder a una versión consistente del registro.

```text
Versión anterior
1000

        ↓

Versión nueva
800
```

El Undo Log participa en este mecanismo proporcionando información sobre versiones anteriores.

---

# Transacciones

InnoDB proporciona soporte completo para transacciones.

Podemos utilizar:

```sql
START TRANSACTION;
```

Realizar operaciones:

```sql
UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;
```

Y confirmar:

```sql
COMMIT;
```

O cancelar:

```sql
ROLLBACK;
```

---

# ACID

Gracias a InnoDB.

Las aplicaciones pueden trabajar con transacciones que proporcionan las propiedades:

```text
ACID
```

Recordemos:

- **Atomicity** → Atomicidad.
- **Consistency** → Consistencia.
- **Isolation** → Aislamiento.
- **Durability** → Durabilidad.

Estas propiedades son fundamentales para aplicaciones como:

- Bancos.
- Tiendas online.
- Sistemas de reservas.
- ERP.
- Aplicaciones empresariales.

---

# Bloqueos

Además de MVCC.

InnoDB utiliza mecanismos de bloqueo para controlar modificaciones simultáneas.

Uno de sus puntos fuertes es el:

```text
Row-Level Locking
```

o bloqueo a nivel de fila.

---

# Bloqueo a nivel de fila

Supongamos:

```text
Tabla cuentas
```

Tenemos:

```text
id | saldo
---|------
1  | 1000
2  | 500
```

Una transacción modifica:

```text
id = 1
```

Otra transacción puede trabajar simultáneamente sobre:

```text
id = 2
```

En determinadas circunstancias.

Esto resulta mucho más eficiente que bloquear toda la tabla.

---

# Claves foráneas

InnoDB también proporciona soporte para:

```text
FOREIGN KEY
```

Ejemplo:

```sql
CREATE TABLE pedidos (
    id INT PRIMARY KEY,
    cliente_id INT,
    FOREIGN KEY (cliente_id)
        REFERENCES clientes(id)
);
```

Esto permite mantener la integridad referencial entre tablas.

---

# Índices y almacenamiento

InnoDB utiliza una estructura especialmente importante:

```text
Clustered Index
```

En una tabla con una clave primaria.

Los registros de la tabla se organizan físicamente según la estructura del índice agrupado asociado a la clave primaria.

Por ello.

La elección de la clave primaria puede tener un impacto importante sobre el almacenamiento y el rendimiento.

---

# ¿Qué ocurre si no existe PRIMARY KEY?

Si una tabla InnoDB no tiene una clave primaria.

InnoDB intenta utilizar un índice `UNIQUE` adecuado como índice agrupado.

Si tampoco existe.

InnoDB crea internamente un identificador oculto para organizar los registros.

Por ello.

En aplicaciones reales resulta recomendable definir siempre una clave primaria adecuada.

---

# Flujo simplificado de una modificación

Podemos resumir una operación así:

```text
UPDATE
  │
  ▼
Buffer Pool
  │
  ├── Undo Log
  │
  └── Redo Log
          │
          ▼
       Datafiles
```

Cada componente cumple una función diferente.

---

# InnoDB frente a MyISAM

Recordemos la diferencia fundamental:

| Característica | InnoDB | MyISAM |
|----------------|--------|--------|
| Transacciones | Sí | No |
| ACID | Sí | No |
| FOREIGN KEY | Sí | No |
| MVCC | Sí | No |
| Bloqueo de filas | Sí | Principalmente tabla |
| Recuperación avanzada | Sí | Más limitada |

Para aplicaciones modernas.

InnoDB suele ser la elección natural.

---

# Errores frecuentes

### ❌ Confundir Redo Log y Undo Log

No realizan la misma función.

```text
Redo → recuperar/reaplicar cambios
Undo → deshacer y proporcionar versiones anteriores
```

---

### ❌ Pensar que MVCC elimina todos los bloqueos

No.

MVCC reduce la necesidad de determinados bloqueos.

Pero InnoDB sigue utilizando bloqueos para garantizar la consistencia.

---

### ❌ Pensar que Buffer Pool es una copia permanente de la base de datos

No.

Es una caché en memoria.

Los datos persistentes se encuentran en los archivos de almacenamiento.

---

### ❌ Pensar que todas las tablas InnoDB necesitan un índice agrupado creado manualmente

No.

InnoDB crea o selecciona automáticamente la estructura utilizada como clustered index.

---

# Buenas prácticas

- Utilizar InnoDB para aplicaciones transaccionales modernas.
- Definir siempre una clave primaria.
- Elegir cuidadosamente las claves primarias.
- Evitar transacciones innecesariamente largas.
- Monitorizar el uso del Buffer Pool.
- Utilizar índices adecuados.
- Comprender los bloqueos antes de optimizar consultas concurrentes.

---

# Conceptos importantes

Antes de continuar debes recordar:

- **InnoDB** es el motor de almacenamiento principal de MySQL.
- El **Buffer Pool** mantiene páginas de datos e índices en memoria para reducir accesos al disco.
- Las páginas modificadas pendientes de escritura se denominan **Dirty Pages**.
- El **Redo Log** permite recuperar cambios tras un fallo.
- El **Undo Log** permite deshacer operaciones y participa en MVCC.
- InnoDB utiliza **MVCC** para proporcionar lecturas consistentes y mejorar la concurrencia.
- InnoDB proporciona transacciones, ACID, claves foráneas y bloqueo a nivel de fila.
- Las tablas InnoDB utilizan un **clustered index**, normalmente asociado a la clave primaria.
- La elección de una buena clave primaria es importante para el rendimiento y almacenamiento.

# Copias de seguridad y recuperación en MySQL

Una base de datos no está realmente administrada hasta que existe una estrategia fiable de recuperación.

Los fallos pueden producirse por:

- Errores humanos.
- Fallos de hardware.
- Corrupción de datos.
- Eliminaciones accidentales.
- Problemas de software.
- Ataques de seguridad.

Por ello, MySQL proporciona diferentes mecanismos para realizar copias de seguridad y recuperar la información.

---

# Tipos de copias de seguridad

Podemos distinguir principalmente entre:

```text
Copias lógicas
```

y:

```text
Copias físicas
```

---

# Copias lógicas

Una copia lógica exporta la estructura y los datos de las tablas.

En lugar de copiar directamente los archivos internos de MySQL, genera instrucciones que permiten reconstruir la información.

Por ejemplo:

```sql
CREATE TABLE clientes (...);

INSERT INTO clientes VALUES (...);
```

La herramienta clásica para realizar este tipo de copia es:

```text
mysqldump
```

---

# mysqldump

`mysqldump` es una herramienta de línea de comandos incluida en MySQL.

Permite exportar:

- Una base de datos.
- Varias bases de datos.
- Tablas concretas.
- Estructura.
- Datos.

---

# Realizar una copia

Ejemplo:

```bash
mysqldump -u root -p agricultura > agricultura.sql
```

Se genera:

```text
agricultura.sql
```

Este archivo contiene las instrucciones necesarias para reconstruir la información.

---

# Restaurar un mysqldump

Podemos restaurar la copia utilizando el cliente `mysql`.

```bash
mysql -u root -p agricultura < agricultura.sql
```

El cliente ejecutará las instrucciones contenidas en el archivo.

---

# Exportar únicamente la estructura

Podemos utilizar:

```bash
mysqldump -u root -p --no-data agricultura > estructura.sql
```

El parámetro:

```text
--no-data
```

evita exportar los registros.

La copia contendrá principalmente:

- CREATE DATABASE.
- CREATE TABLE.
- Índices.
- Restricciones.

---

# Exportar únicamente los datos

También podemos realizar lo contrario.

```bash
mysqldump -u root -p --no-create-info agricultura > datos.sql
```

El parámetro:

```text
--no-create-info
```

evita incluir las sentencias de creación de tablas.

---

# Copiar una tabla concreta

También podemos seleccionar tablas específicas.

```bash
mysqldump -u root -p agricultura clientes > clientes.sql
```

En este caso:

```text
agricultura
```

es la base de datos.

Y:

```text
clientes
```

es la tabla que queremos exportar.

---

# Varias tablas

También podemos especificar varias:

```bash
mysqldump -u root -p agricultura clientes pedidos facturas > datos.sql
```

---

# Todas las bases de datos

Para exportar todas las bases de datos:

```bash
mysqldump -u root -p --all-databases > backup.sql
```

Esto genera una copia lógica global.

---

# Copias físicas

Una copia física consiste en copiar directamente los archivos que utiliza MySQL para almacenar la información.

Este tipo de copia puede ser mucho más eficiente para bases de datos grandes.

Sin embargo, requiere conocer correctamente la arquitectura y el estado del servidor.

---

# Copias en caliente

Una copia en caliente permite realizar el backup mientras el servidor continúa funcionando.

Esto resulta fundamental en sistemas que no pueden detenerse.

Con InnoDB existen herramientas y mecanismos específicos para realizar este tipo de copias de forma consistente.

---

# mysqldump y consistencia

Cuando utilizamos `mysqldump` con tablas InnoDB.

Es habitual utilizar:

```text
--single-transaction
```

Por ejemplo:

```bash
mysqldump \
-u root \
-p \
--single-transaction \
agricultura > agricultura.sql
```

Esta opción permite realizar una copia consistente utilizando una única transacción, evitando bloquear las tablas de forma general durante la exportación.

Es especialmente útil para tablas InnoDB.

---

# ¿Qué hace --single-transaction?

La idea fundamental es:

```text
Inicio de transacción

↓

Snapshot consistente

↓

Exportación

↓

Fin
```

Mientras la copia se está realizando.

Otros usuarios pueden continuar trabajando con la base de datos.

Esta opción resulta especialmente interesante gracias al soporte MVCC de InnoDB.

---

# Importante

`--single-transaction` no debe entenderse como una solución universal.

Está especialmente orientado a tablas transaccionales como:

```text
InnoDB
```

No proporciona exactamente las mismas garantías para motores que no utilizan transacciones.

Por ello.

Siempre debemos conocer el motor de almacenamiento utilizado.

---

# Compresión

Las copias lógicas pueden ocupar bastante espacio.

Podemos comprimirlas directamente.

Por ejemplo:

```bash
mysqldump -u root -p agricultura | gzip > agricultura.sql.gz
```

Para restaurarla:

```bash
gunzip -c agricultura.sql.gz | mysql -u root -p agricultura
```

Esto puede reducir considerablemente el espacio necesario.

---

# Binlog

Además de las copias.

MySQL dispone de:

```text
Binary Log

(binlog)
```

El binlog registra cambios realizados sobre la base de datos.

Entre otras operaciones:

- INSERT.
- UPDATE.
- DELETE.
- Cambios de estructura.

Su utilización es fundamental para:

- Replicación.
- Recuperación.
- Auditoría de determinadas operaciones.

---

# Binary Log y recuperación

Podemos combinar:

```text
Backup completo

+

Binary Log
```

para reconstruir los cambios realizados después de la copia.

Por ejemplo:

```text
02:00

↓

Backup completo
```

```text
02:01 - 05:30

↓

Binary Log
```

Si ocurre un fallo a las:

```text
05:15
```

podemos restaurar la copia y aplicar los cambios registrados posteriormente.

---

# Point-in-Time Recovery

Esta estrategia permite recuperar la base de datos hasta un instante concreto.

Conceptualmente:

```text
Backup

+

Binary Log

↓

Point-in-Time Recovery
```

Por ejemplo:

```text
10:00
Backup
   │
   ├── 10:15 INSERT
   ├── 10:30 UPDATE
   ├── 10:45 DELETE
   └── 11:00 ERROR
             ↓
        Recuperar hasta
        10:59:59
```

Es una técnica muy importante en entornos de producción.

---

# Comparación con PostgreSQL

Ahora podemos conectar varios conceptos.

| MySQL | PostgreSQL |
|-------|------------|
| `mysqldump` | `pg_dump` |
| Binary Log | WAL |
| Point-in-Time Recovery | PITR |
| InnoDB | PostgreSQL MVCC |
| `mysql` | `psql` |

No son implementaciones idénticas.

Pero la finalidad general de varios de estos mecanismos es comparable.

---

# Comparación con Oracle

También podemos establecer otra correspondencia.

| MySQL | Oracle |
|-------|--------|
| `mysqldump` | RMAN |
| Binary Log | Redo / Archive Log |
| PITR | Recuperación mediante RMAN |
| InnoDB | Motor transaccional de Oracle |

De nuevo.

Son mecanismos diferentes.

La comparación sirve únicamente para comprender qué problema intenta resolver cada tecnología.

---

# Estrategia de backup

Una buena estrategia no consiste simplemente en ejecutar:

```bash
mysqldump
```

una vez.

Debe definir:

- Frecuencia.
- Retención.
- Ubicación.
- Automatización.
- Cifrado.
- Verificación.
- Procedimiento de restauración.

---

# Regla 3-2-1

Una estrategia clásica es la regla:

```text
3 copias

2 medios diferentes

1 copia fuera de las instalaciones
```

Por ejemplo:

```text
Servidor principal
        │
        ├── Backup local
        │
        ├── Backup en almacenamiento secundario
        │
        └── Backup remoto
```

Esto protege frente a diferentes tipos de incidentes.

---

# Verificar las copias

Una copia que nunca ha sido restaurada es una copia que todavía no ha demostrado ser útil.

Por ello.

Conviene realizar restauraciones de prueba.

Por ejemplo:

```text
Backup

↓

Servidor de pruebas

↓

Restauración

↓

Verificación
```

Esto permite detectar copias corruptas o procedimientos incompletos.

---

# Automatización

Los backups pueden programarse mediante herramientas del sistema operativo.

En Linux.

Una opción tradicional es:

```text
cron
```

Ejemplo conceptual:

```text
Cada noche

↓

mysqldump

↓

backup.sql

↓

Compresión

↓

Almacenamiento externo
```

En entornos profesionales también pueden utilizarse plataformas específicas de backup.

---

# Errores frecuentes

### ❌ Pensar que mysqldump es una copia física

No.

`mysqldump` genera una copia lógica.

---

### ❌ Pensar que un backup sustituye al binlog

No.

Cumplen funciones diferentes.

Una estrategia avanzada puede utilizar ambos.

---

### ❌ No probar las restauraciones

Una copia que no puede restaurarse correctamente no cumple su objetivo.

---

### ❌ Guardar todas las copias en el mismo servidor

Si el servidor se destruye.

Las copias podrían desaparecer junto con él.

---

### ❌ Utilizar --single-transaction sin conocer los motores

Esta opción resulta especialmente adecuada para InnoDB.

No debe asumirse que proporciona las mismas garantías con todos los motores.

---

# Buenas prácticas

- Realizar copias periódicas.
- Utilizar `--single-transaction` para copias consistentes de tablas InnoDB cuando corresponda.
- Conservar los Binary Logs cuando se requiera recuperación avanzada.
- Almacenar copias fuera del servidor principal.
- Cifrar información sensible.
- Automatizar las copias.
- Probar periódicamente la restauración.
- Definir políticas claras de retención.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `mysqldump` realiza copias lógicas de MySQL.
- Las copias pueden incluir estructura, datos o ambos.
- `--single-transaction` permite realizar copias consistentes de tablas InnoDB sin bloquearlas de forma general.
- El **Binary Log** registra cambios realizados sobre la base de datos.
- La combinación de una copia completa y Binary Logs permite implementar recuperación hasta un instante concreto.
- Las copias deben almacenarse en ubicaciones independientes y comprobarse mediante restauraciones de prueba.
- La regla 3-2-1 es una estrategia clásica para reducir el riesgo de pérdida de copias.

---

# Replicación y alta disponibilidad

Una base de datos puede contener información crítica.

Por ello, no siempre es suficiente con disponer de copias de seguridad.

Imaginemos:

```text
Servidor MySQL

↓

💥 Fallo
```

Si necesitamos restaurar una copia de seguridad.

El servicio puede permanecer detenido durante un periodo de tiempo.

Para reducir este problema.

Podemos mantener otro servidor con una copia de los datos.

Esto recibe el nombre de:

```text
Replicación
```

---

# ¿Qué es la replicación?

La replicación consiste en mantener una o varias copias de una base de datos sincronizadas con un servidor principal.

De forma simplificada:

```text
Servidor principal

        ↓

   Cambios

        ↓

Servidor réplica
```

La réplica recibe los cambios realizados en el servidor principal.

---

# Source y Replica

La terminología moderna de MySQL utiliza principalmente:

```text
Source
```

para el servidor que origina los cambios.

Y:

```text
Replica
```

para el servidor que los reproduce.

Históricamente se utilizaron los términos:

```text
Master

Slave
```

En documentación moderna se recomienda utilizar:

```text
Source

Replica
```

---

# ¿Para qué sirve?

La replicación puede utilizarse para:

- Alta disponibilidad.
- Recuperación ante fallos.
- Distribución de lecturas.
- Escalabilidad.
- Copias de datos.
- Mantenimiento del servidor principal.

---

# Arquitectura básica

Podemos representar una configuración sencilla:

```text
             Source
                │
        Binary Log
                │
        ┌───────┴───────┐
        ▼               ▼
     Replica 1       Replica 2
```

El servidor principal registra los cambios en el Binary Log.

Las réplicas reciben esos cambios y los aplican.

---

# Binary Log y replicación

Recordemos el apartado anterior.

MySQL dispone de:

```text
Binary Log
```

El Binary Log registra los cambios realizados sobre el servidor.

La replicación utiliza esta información para mantener las réplicas actualizadas.

Por tanto:

```text
Consulta de modificación

↓

Source

↓

Binary Log

↓

Replica

↓

Aplicación del cambio
```

---

# Replicación asíncrona

Una característica importante de la replicación tradicional de MySQL es que suele funcionar de forma:

```text
Asíncrona
```

Esto significa que el Source no tiene que esperar necesariamente a que la Replica confirme que ha recibido y aplicado el cambio.

Por ejemplo:

```text
Source

↓

Escribe cambio

↓

Continúa trabajando
```

Mientras:

```text
Replica

↓

Recibe cambio

↓

Lo aplica posteriormente
```

---

# Ventaja de la replicación asíncrona

La principal ventaja es el rendimiento.

El servidor principal no necesita esperar a todas las réplicas.

Esto reduce la latencia.

---

# Inconveniente

Existe una pequeña posibilidad de que la réplica se encuentre retrasada.

Por ejemplo:

```text
Source

ID = 100
```

Mientras:

```text
Replica

ID = 98
```

La réplica todavía no ha aplicado los últimos cambios.

Esto se conoce como:

```text
Replication Lag
```

---

# Replication Lag

El *Replication Lag* representa el retraso entre el estado del Source y el estado de una Replica.

Puede deberse a:

- Carga elevada.
- Red lenta.
- Consultas pesadas.
- Problemas de almacenamiento.
- Diferencias de capacidad entre servidores.

Debe monitorizarse en sistemas críticos.

---

# GTID

MySQL incorpora:

```text
GTID
```

que significa:

```text
Global Transaction Identifier
```

Un GTID identifica de forma única una transacción dentro del sistema de replicación.

Esto facilita:

- Configuración de réplicas.
- Recuperación.
- Cambio de Source.
- Administración de topologías.

---

# ¿Por qué son útiles los GTID?

Imaginemos:

```text
Source A
    ↓
Replica B
```

Si necesitamos cambiar la topología.

Los GTID permiten identificar exactamente qué transacciones ya han sido ejecutadas.

La réplica puede determinar qué transacciones necesita todavía.

Esto simplifica considerablemente la administración.

---

# Replicación basada en eventos

El Source registra eventos en el Binary Log.

Las réplicas reciben esos eventos.

Después los ejecutan.

Podemos visualizarlo así:

```text
Transacción

↓

Binary Log

↓

Evento

↓

Replica

↓

Aplicación
```

---

# Replicación basada en filas

MySQL puede registrar los cambios utilizando distintos formatos.

Uno de los más importantes es:

```text
ROW
```

En este modo.

El Binary Log registra los cambios realizados sobre las filas.

Por ejemplo:

```sql
UPDATE clientes
SET activo = 1
WHERE id = 15;
```

La información registrada permite reproducir el cambio sobre la réplica.

---

# Replicación basada en sentencias

También existe:

```text
STATEMENT
```

En este modo.

Se registra la sentencia SQL que produjo el cambio.

Por ejemplo:

```sql
UPDATE clientes
SET activo = 1
WHERE id = 15;
```

La réplica ejecutará esa sentencia.

---

# Replicación mixta

También existe:

```text
MIXED
```

que combina los dos enfoques.

MySQL puede utilizar sentencias en determinadas situaciones y filas en otras.

---

# ROW frente a STATEMENT

| ROW | STATEMENT |
|-----|-----------|
| Registra cambios sobre filas | Registra sentencias SQL |
| Mayor precisión | Puede generar menos información en algunos casos |
| Reduce determinados problemas de determinismo | Puede presentar problemas con determinadas consultas |
| Muy utilizado en entornos modernos | Más dependiente del comportamiento de las consultas |

En muchas instalaciones modernas.

La replicación basada en filas es una opción habitual.

---

# Failover

Supongamos:

```text
Source

💥 Fallo
```

Podemos promover una réplica para convertirse en el nuevo Source.

Esto recibe el nombre de:

```text
Failover
```

La finalidad es mantener disponible el servicio.

---

# Promoción de una réplica

Podemos imaginar:

```text
Antes

Source
  ↓
Replica
```

Después del fallo:

```text
Después

Nuevo Source
```

La antigua réplica pasa a desempeñar el papel principal.

---

# Replicación no es backup

Este concepto es extremadamente importante.

Una réplica:

```text
Replica cambios
```

Una copia de seguridad:

```text
Conserva una copia histórica
```

Si ejecutamos accidentalmente:

```sql
DROP TABLE clientes;
```

el cambio puede propagarse a la réplica.

Por tanto:

```text
Replica ≠ Backup
```

Una infraestructura profesional necesita ambas cosas.

---

# Alta disponibilidad

La replicación puede utilizarse como parte de una estrategia de:

```text
High Availability
```

o:

```text
Alta disponibilidad
```

El objetivo es minimizar:

```text
Downtime
```

es decir.

El tiempo durante el cual el servicio permanece inaccesible.

---

# InnoDB Cluster

MySQL dispone de una solución de alta disponibilidad denominada:

```text
InnoDB Cluster
```

Está basada en:

```text
MySQL Group Replication
```

y permite construir grupos de servidores MySQL coordinados.

Una arquitectura simplificada sería:

```text
        InnoDB Cluster

      ┌──────┬──────┐
      ▼      ▼      ▼
    Nodo 1  Nodo 2  Nodo 3
```

Los nodos mantienen la información sincronizada y pueden participar en mecanismos de recuperación automática.

---

# Group Replication

```text
MySQL Group Replication
```

permite que varios servidores MySQL formen un grupo coordinado.

Entre sus características se encuentran:

- Replicación entre miembros.
- Detección de determinados fallos.
- Coordinación del grupo.
- Soporte para configuraciones de alta disponibilidad.

Es una tecnología fundamental en arquitecturas modernas de MySQL.

---

# InnoDB ClusterSet

En arquitecturas todavía más avanzadas.

MySQL ofrece:

```text
InnoDB ClusterSet
```

que permite trabajar con grupos de InnoDB Cluster distribuidos entre diferentes ubicaciones.

Puede utilizarse para construir arquitecturas destinadas a:

- Recuperación ante desastres.
- Alta disponibilidad geográfica.
- Continuidad del servicio.

Para el nivel de este temario.

Es suficiente conocer su existencia y finalidad general.

---

# Lecturas desde réplicas

Una aplicación puede distribuir determinadas consultas de lectura entre diferentes réplicas.

Por ejemplo:

```text
                    Source
                   /      \
                  /        \
             Escrituras    Cambios
                            │
                     ┌──────┴──────┐
                     ▼             ▼
                 Replica 1     Replica 2
                     │             │
                  Lecturas      Lecturas
```

Esto permite aumentar la capacidad de lectura.

Sin embargo.

Las aplicaciones deben tener en cuenta el posible:

```text
Replication Lag
```

---

# Ventajas de la replicación

- Alta disponibilidad.
- Distribución de lecturas.
- Escalabilidad.
- Recuperación ante fallos.
- Reducción de carga del servidor principal.

---

# Limitaciones

- Puede existir retraso entre Source y Replica.
- La configuración puede ser compleja.
- No sustituye a los backups.
- Las aplicaciones deben gestionar correctamente los cambios de servidor.
- Un fallo de red puede interrumpir temporalmente la sincronización.

---

# Errores frecuentes

### ❌ Pensar que una réplica sustituye a un backup

No.

Los cambios destructivos pueden propagarse.

---

### ❌ Pensar que las réplicas siempre están sincronizadas al instante

En replicación asíncrona puede existir:

```text
Replication Lag
```

---

### ❌ Confundir GTID con Binary Log

No son lo mismo.

```text
Binary Log
    ↓
Registro de eventos
```

Mientras:

```text
GTID
    ↓
Identificación única de transacciones
```

---

### ❌ Confundir RAC de Oracle con Group Replication

Son tecnologías diferentes.

Ambas buscan alta disponibilidad.

Pero su arquitectura y funcionamiento son distintos.

---

# Buenas prácticas

- Monitorizar el Replication Lag.
- Utilizar GTID cuando sea adecuado para la arquitectura.
- Proteger y conservar los Binary Logs.
- Mantener réplicas en infraestructuras independientes.
- Definir procedimientos claros de failover.
- No considerar las réplicas como sustituto de los backups.
- Probar periódicamente los procedimientos de recuperación.

---

# Conceptos importantes

Antes de continuar debes recordar:

- La replicación mantiene una o varias réplicas sincronizadas con un Source.
- El **Binary Log** es fundamental para la replicación tradicional de MySQL.
- La replicación puede ser asíncrona, por lo que puede existir *Replication Lag*.
- **GTID** identifica de forma única las transacciones y facilita la administración de la replicación.
- MySQL admite replicación basada en `STATEMENT`, `ROW` y `MIXED`.
- Una réplica no sustituye a una copia de seguridad.
- **InnoDB Cluster** utiliza Group Replication para construir arquitecturas de alta disponibilidad.
- El **failover** permite promover una réplica para asumir el servicio cuando falla el servidor principal.

---

# Optimización y diagnóstico de MySQL

Una base de datos puede funcionar correctamente y, sin embargo, presentar problemas de rendimiento.

Algunos síntomas habituales son:

- Consultas lentas.
- Alto consumo de CPU.
- Mucho uso de memoria.
- Lecturas excesivas de disco.
- Demasiadas conexiones.
- Bloqueos.
- Esperas entre transacciones.

La administración de MySQL incluye herramientas para identificar estos problemas.

---

# El proceso de optimización

La optimización no debería comenzar modificando parámetros al azar.

Un procedimiento razonable es:

```text
Problema
   ↓
Medición
   ↓
Identificación de la causa
   ↓
Cambio
   ↓
Medición nuevamente
```

La idea fundamental es:

> No optimizar lo que no se ha medido.

---

# EXPLAIN

Una de las herramientas más importantes para analizar consultas SQL es:

```sql
EXPLAIN
```

Permite conocer cómo MySQL pretende ejecutar una consulta.

Por ejemplo:

```sql
EXPLAIN
SELECT *
FROM clientes
WHERE email = 'pedro@example.com';
```

El resultado proporciona información sobre el plan de ejecución.

---

# ¿Qué podemos descubrir?

`EXPLAIN` puede ayudarnos a determinar:

- Qué tabla se consulta.
- Qué índice se utiliza.
- Cuántas filas estima MySQL que tendrá que examinar.
- Cómo se combinan las tablas.
- Qué tipo de acceso se utiliza.

Esto resulta especialmente útil cuando una consulta tarda demasiado.

---

# Ejemplo

Supongamos:

```sql
SELECT *
FROM clientes
WHERE email = 'pedro@example.com';
```

Si existe:

```text
INDEX(email)
```

MySQL puede utilizar ese índice para localizar rápidamente el registro.

Sin índice.

Podría necesitar revisar gran parte de la tabla.

---

# Índices

Un índice permite localizar información de forma más eficiente.

Podemos imaginar una tabla:

```text
clientes

id
nombre
email
telefono
```

Si realizamos frecuentemente:

```sql
SELECT *
FROM clientes
WHERE email = '...';
```

Puede ser útil crear:

```sql
CREATE INDEX idx_clientes_email
ON clientes(email);
```

---

# Ventajas de los índices

Los índices pueden mejorar considerablemente:

- SELECT.
- WHERE.
- JOIN.
- ORDER BY.
- GROUP BY.

Pero tienen un coste.

---

# Coste de los índices

Cada índice ocupa almacenamiento.

Además.

Cuando modificamos una tabla:

```text
INSERT
UPDATE
DELETE
```

MySQL también debe mantener los índices afectados.

Por tanto:

```text
Más índices

↓

Consultas potencialmente más rápidas

pero

↓

Más almacenamiento
+

Mayor coste de escritura
```

No debemos crear índices indiscriminadamente.

---

# Índices compuestos

Podemos crear índices utilizando varias columnas.

Por ejemplo:

```sql
CREATE INDEX idx_clientes_nombre_ciudad
ON clientes(nombre, ciudad);
```

Este índice puede resultar útil para determinadas consultas que utilizan:

```text
nombre
```

y:

```text
ciudad
```

---

# Orden de las columnas

En un índice compuesto:

```text
(nombre, ciudad)
```

el orden importa.

El índice está organizado primero por:

```text
nombre
```

y después por:

```text
ciudad
```

Por ello.

No debe asumirse que:

```text
(nombre, ciudad)
```

y:

```text
(ciudad, nombre)
```

son equivalentes.

---

# Regla del prefijo izquierdo

Un índice:

```text
(nombre, ciudad)
```

puede resultar útil para consultas que comienzan utilizando:

```text
nombre
```

Por ejemplo:

```sql
WHERE nombre = 'Pedro'
```

o:

```sql
WHERE nombre = 'Pedro'
AND ciudad = 'Murcia'
```

Pero puede no ser adecuado para una consulta que utilice únicamente:

```sql
WHERE ciudad = 'Murcia'
```

Este concepto se conoce como:

```text
Leftmost Prefix
```

o prefijo izquierdo.

---

# Índices y Laravel

Esto resulta especialmente importante en aplicaciones Laravel.

Supongamos una consulta:

```php
User::where('email', $email)->first();
```

Si:

```text
email
```

no está indexado.

MySQL podría tener que examinar muchos registros.

Si existe un índice adecuado:

```text
email INDEX
```

la búsqueda puede ser mucho más eficiente.

---

# EXPLAIN y Laravel

Una consulta generada por Laravel también puede analizarse con:

```sql
EXPLAIN
```

Por ejemplo:

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'pedro@example.com';
```

Esto permite investigar si la base de datos está utilizando correctamente los índices.

---

# EXPLAIN ANALYZE

En versiones modernas de MySQL también existe:

```sql
EXPLAIN ANALYZE
```

A diferencia de un `EXPLAIN` tradicional.

`EXPLAIN ANALYZE` ejecuta la consulta y proporciona información sobre su ejecución real.

Esto permite comparar:

```text
Estimación del optimizador

vs

Comportamiento real
```

Es especialmente útil para detectar estimaciones incorrectas.

---

# Slow Query Log

MySQL incorpora un mecanismo para registrar consultas que tardan demasiado.

Se denomina:

```text
Slow Query Log
```

Puede utilizarse para detectar consultas problemáticas.

Por ejemplo:

```text
Consulta 1 → 0.01 s
Consulta 2 → 0.03 s
Consulta 3 → 8.42 s  ← ⚠️
Consulta 4 → 0.02 s
```

La tercera consulta merece investigación.

---

# ¿Qué permite detectar?

El Slow Query Log puede ayudar a encontrar:

- Consultas excesivamente lentas.
- Consultas que no utilizan índices adecuadamente.
- Operaciones que examinan demasiados registros.
- Problemas recurrentes de rendimiento.

---

# performance_schema

MySQL incorpora un sistema de instrumentación denominado:

```text
Performance Schema
```

Permite recopilar información sobre el funcionamiento interno del servidor.

Puede proporcionar información relacionada con:

- Consultas.
- Esperas.
- Bloqueos.
- Memoria.
- E/S.
- Actividad de las sesiones.

Es una herramienta fundamental para diagnóstico avanzado.

---

# sys Schema

MySQL también incorpora:

```text
sys
```

El esquema `sys` proporciona vistas diseñadas para facilitar el análisis de la información recogida por Performance Schema.

En lugar de trabajar siempre con estructuras internas complejas.

Podemos consultar vistas más sencillas.

Por ejemplo:

```sql
SELECT *
FROM sys.schema_table_statistics;
```

Esto puede ayudar a identificar tablas con mucha actividad.

---

# SHOW PROCESSLIST

Ya vimos este comando anteriormente:

```sql
SHOW PROCESSLIST;
```

Es una herramienta sencilla pero extremadamente útil.

Permite observar las conexiones activas.

Por ejemplo:

```text
Id
User
Host
db
Command
Time
State
Info
```

Podemos detectar:

- Consultas que llevan mucho tiempo.
- Conexiones bloqueadas.
- Usuarios con muchas sesiones.
- Operaciones en ejecución.

---

# SHOW FULL PROCESSLIST

La versión:

```sql
SHOW FULL PROCESSLIST;
```

proporciona más información sobre las consultas.

Resulta especialmente útil cuando la consulta SQL mostrada está truncada.

---

# Conexiones

MySQL limita el número de conexiones simultáneas mediante parámetros de configuración.

Podemos consultar:

```sql
SHOW VARIABLES LIKE 'max_connections';
```

Y comprobar cuántas conexiones están actualmente abiertas:

```sql
SHOW STATUS LIKE 'Threads_connected';
```

---

# Threads_connected

La variable:

```text
Threads_connected
```

indica el número de conexiones actualmente abiertas.

Por ejemplo:

```text
max_connections = 200

Threads_connected = 175
```

Esto podría indicar que el servidor está acercándose a su límite de conexiones.

---

# Threads_running

También podemos consultar:

```sql
SHOW STATUS LIKE 'Threads_running';
```

Indica aproximadamente cuántos hilos están ejecutando trabajo activamente en ese momento.

Es diferente de:

```text
Threads_connected
```

porque una conexión puede estar abierta sin estar ejecutando una consulta.

---

# CPU, memoria y disco

El rendimiento de MySQL no depende únicamente de SQL.

También debemos observar el sistema operativo.

Por ejemplo:

```text
CPU
RAM
Disco
I/O
Red
```

En Linux podemos utilizar herramientas como:

```bash
top
```

```bash
htop
```

```bash
iostat
```

```bash
vmstat
```

---

# Problemas habituales

Un servidor MySQL lento puede tener muchas causas.

Por ejemplo:

```text
Consulta sin índice
        ↓
Muchas filas examinadas
        ↓
Mayor CPU / I/O
        ↓
Consulta lenta
```

O:

```text
Demasiadas conexiones
        ↓
Mayor consumo de memoria
        ↓
Presión sobre el servidor
        ↓
Degradación del rendimiento
```

Por ello.

Es importante analizar el sistema completo.

---

# Bloqueos

Las transacciones pueden generar bloqueos.

Por ejemplo:

```text
Transacción A

UPDATE cliente 1
```

Mientras:

```text
Transacción B

UPDATE cliente 1
```

La segunda transacción puede tener que esperar.

Los bloqueos son necesarios para mantener la consistencia.

El problema aparece cuando:

- Son demasiado frecuentes.
- Se mantienen durante mucho tiempo.
- Generan esperas entre transacciones.

---

# Deadlocks

Un problema más grave es un:

```text
Deadlock
```

Se produce cuando dos transacciones esperan recursos que posee la otra.

Ejemplo:

```text
Transacción A
    │
    ├── Bloquea fila 1
    │
    └── Espera fila 2
             ↑
             │
Transacción B
    │
    ├── Bloquea fila 2
    │
    └── Espera fila 1
```

Tenemos un ciclo.

```text
A espera a B

B espera a A
```

La situación no puede resolverse por sí sola.

---

# Prevención de deadlocks

Algunas buenas prácticas:

- Mantener las transacciones cortas.
- Acceder a los recursos en un orden consistente.
- Evitar operaciones innecesariamente grandes dentro de una transacción.
- Utilizar índices adecuados.
- Investigar los deadlocks registrados por MySQL.

Los deadlocks pueden ocurrir incluso en aplicaciones correctamente diseñadas.

Por ello.

La aplicación debería estar preparada para reintentar determinadas transacciones cuando corresponda.

---

# Optimización de consultas

Un procedimiento habitual puede ser:

```text
1. Identificar consulta lenta
        ↓
2. Ejecutar EXPLAIN
        ↓
3. Analizar índices
        ↓
4. Revisar número de filas examinadas
        ↓
5. Revisar JOIN y filtros
        ↓
6. Modificar consulta o índices
        ↓
7. Medir nuevamente
```

Este enfoque es mucho más fiable que modificar parámetros del servidor al azar.

---

# N+1 y MySQL

En aplicaciones ORM.

Puede aparecer el conocido problema:

```text
N+1
```

Por ejemplo:

```text
1 consulta para obtener usuarios

+

N consultas para obtener sus pedidos
```

Si tenemos:

```text
1000 usuarios
```

podríamos terminar ejecutando:

```text
1001 consultas
```

Aunque cada consulta individual sea rápida.

El conjunto puede resultar muy costoso.

---

# Soluciones

En Laravel.

Una solución habitual es utilizar:

```php
User::with('orders')->get();
```

en lugar de cargar la relación de forma repetitiva.

La base de datos sigue siendo la misma.

Pero reducimos el número de consultas enviadas a MySQL.

---

# Optimización no significa solamente crear índices

Una consulta puede ser lenta por muchas razones:

- Falta de índices.
- Índices incorrectos.
- Demasiadas filas.
- JOIN ineficientes.
- N+1.
- Bloqueos.
- Mala configuración.
- Falta de memoria.
- Almacenamiento lento.

Por ello.

El diagnóstico debe realizarse de forma sistemática.

---

# Errores frecuentes

### ❌ Crear índices para todas las columnas

Los índices tienen un coste.

Deben crearse cuando aportan un beneficio real.

---

### ❌ Mirar únicamente la CPU

Un servidor puede estar limitado por:

- Disco.
- Memoria.
- Bloqueos.
- Red.

---

### ❌ Utilizar EXPLAIN sin interpretar el resultado

La herramienta proporciona información.

El administrador debe analizarla dentro del contexto de la consulta.

---

### ❌ Aumentar max_connections como solución universal

Más conexiones no significa necesariamente más rendimiento.

Puede aumentar considerablemente el consumo de memoria y empeorar el problema.

---

### ❌ Culpar siempre a MySQL

En aplicaciones web.

El problema puede encontrarse en:

- Código.
- ORM.
- Consultas.
- Índices.
- Arquitectura.
- Servidor.

El diagnóstico debe abarcar toda la cadena.

---

# Buenas prácticas

- Utilizar `EXPLAIN` para analizar consultas importantes.
- Utilizar `EXPLAIN ANALYZE` cuando sea necesario conocer el comportamiento real.
- Activar y revisar el Slow Query Log.
- Utilizar Performance Schema y el esquema `sys`.
- Monitorizar conexiones y consultas activas.
- Mantener las transacciones cortas.
- Diseñar índices basándose en las consultas reales.
- Medir los cambios después de optimizar.
- Monitorizar también CPU, memoria, disco y red.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `EXPLAIN` permite analizar el plan de ejecución de una consulta.
- `EXPLAIN ANALYZE` permite analizar su ejecución real.
- Los índices pueden acelerar las consultas, pero tienen un coste de almacenamiento y escritura.
- Los índices compuestos dependen del orden de sus columnas.
- El **Slow Query Log** permite identificar consultas lentas.
- **Performance Schema** proporciona información detallada sobre el funcionamiento del servidor.
- El esquema **sys** facilita el análisis de esa información.
- `SHOW PROCESSLIST` permite observar conexiones y consultas activas.
- `Threads_connected` representa las conexiones abiertas.
- `Threads_running` representa los hilos que están ejecutando trabajo.
- Los bloqueos son necesarios para mantener la consistencia, pero pueden provocar esperas.
- Un **deadlock** ocurre cuando dos o más transacciones esperan recursos bloqueados entre sí.
- La optimización debe comenzar con mediciones y diagnóstico, no con cambios arbitrarios de configuración.
- En aplicaciones ORM también debe vigilarse el problema **N+1**.

MySQL es un Sistema Gestor de Bases de Datos Relacional (SGBD) especialmente utilizado en aplicaciones web y entornos empresariales.

Durante este capítulo hemos estudiado su arquitectura, el motor InnoDB, la administración, las copias de seguridad, la replicación y las técnicas de diagnóstico y optimización.

---

# 1. Conceptos fundamentales

MySQL debe diferenciarse de SQL.

```text
SQL
↓
Lenguaje

MySQL
↓
Sistema Gestor de Bases de Datos
```

MySQL utiliza una arquitectura:

```text
Aplicación
    ↓
Cliente MySQL
    ↓
Servidor MySQL
    ↓
Motor de almacenamiento
    ↓
Datos
```

El servidor MySQL suele ejecutarse mediante:

```text
mysqld
```

El puerto TCP predeterminado es:

```text
3306
```

---

# 2. Bases de datos y esquemas

En MySQL:

```text
DATABASE ≈ SCHEMA
```

Ambos términos hacen referencia prácticamente al mismo concepto.

Por ejemplo:

```sql
CREATE DATABASE agricultura;
```

También puede utilizarse:

```sql
CREATE SCHEMA agricultura;
```

Esta característica diferencia a MySQL de PostgreSQL, donde una base de datos puede contener múltiples esquemas independientes.

---

# 3. Motores de almacenamiento

Una característica fundamental de MySQL es la utilización de motores de almacenamiento.

Los motores históricos y actuales incluyen:

- InnoDB.
- MyISAM.
- MEMORY.
- CSV.
- Archive.

El motor principal en las versiones modernas es:

```text
InnoDB
```

---

# 4. InnoDB

InnoDB es el motor de almacenamiento transaccional de referencia de MySQL.

Proporciona:

- Transacciones.
- ACID.
- MVCC.
- Claves foráneas.
- Bloqueo a nivel de fila.
- Recuperación ante fallos.

Su arquitectura incluye componentes como:

```text
InnoDB
│
├── Buffer Pool
├── Redo Log
├── Undo Log
├── Índices
└── Bloqueos
```

---

# 5. Buffer Pool

El:

```text
InnoDB Buffer Pool
```

es una zona de memoria utilizada para almacenar páginas de datos e índices.

Su objetivo principal es reducir los accesos al almacenamiento.

El flujo simplificado es:

```text
Consulta
   ↓
Buffer Pool
   ↓
¿Datos disponibles?
   ├── Sí → Utilizar memoria
   └── No → Leer desde disco
```

Las páginas modificadas que todavía no se han escrito en disco reciben el nombre de:

```text
Dirty Pages
```

---

# 6. Redo Log

El:

```text
Redo Log
```

registra información necesaria para recuperar cambios después de un fallo.

Conceptualmente:

```text
Cambio
   ↓
Redo Log
   ↓
Datafiles
```

Su finalidad es comparable al:

```text
WAL
```

de PostgreSQL.

---

# 7. Undo Log

El:

```text
Undo Log
```

conserva información sobre versiones anteriores de los datos.

Participa principalmente en:

- `ROLLBACK`.
- MVCC.
- Lecturas consistentes.

Una forma sencilla de recordarlo:

```text
REDO
↓
Volver a aplicar cambios

UNDO
↓
Deshacer cambios
```

---

# 8. MVCC

InnoDB utiliza:

```text
MVCC

Multi-Version Concurrency Control
```

Permite que las transacciones trabajen simultáneamente manteniendo versiones consistentes de los datos.

El Undo Log participa en la conservación de versiones anteriores.

---

# 9. Transacciones

InnoDB proporciona soporte para transacciones.

Ejemplo:

```sql
START TRANSACTION;

UPDATE cuentas
SET saldo = saldo - 100
WHERE id = 1;

COMMIT;
```

O para cancelar:

```sql
ROLLBACK;
```

Las transacciones proporcionan las propiedades:

```text
ACID
```

---

# 10. Índices y Clustered Index

InnoDB utiliza un:

```text
Clustered Index
```

para organizar los registros.

Normalmente está asociado a la:

```text
PRIMARY KEY
```

La elección de una buena clave primaria puede afectar al:

- Rendimiento.
- Almacenamiento.
- Ordenación de los datos.

Por ello se recomienda definir una clave primaria adecuada en las tablas.

---

# 11. MyISAM

MyISAM es un motor histórico de MySQL.

A diferencia de InnoDB:

| Característica | InnoDB | MyISAM |
|----------------|--------|--------|
| Transacciones | Sí | No |
| ACID | Sí | No |
| FOREIGN KEY | Sí | No |
| MVCC | Sí | No |
| Bloqueo de filas | Sí | No |
| Recuperación avanzada | Sí | Más limitada |

En aplicaciones modernas suele preferirse:

```text
InnoDB
```

# 19. Point-in-Time Recovery

Podemos combinar:

```text
Backup

+

Binary Log

↓

Point-in-Time Recovery
```

Por ejemplo:

```text
02:00
Backup
   ↓
02:01
INSERT
   ↓
03:15
UPDATE
   ↓
04:30
DELETE accidental
```

Podemos restaurar el backup y aplicar los cambios únicamente hasta un momento anterior al error.

Una estrategia clásica de backup es:


# 21. Replicación

La replicación mantiene una o varias copias sincronizadas con un servidor principal.

Terminología moderna:

```text
Source
```

y:

```text
Replica
```

Arquitectura:

```text
             Source
                │
          Binary Log
                │
        ┌───────┴───────┐
        ▼               ▼
     Replica 1       Replica 2
```

---

# 22. Replicación asíncrona

La replicación tradicional puede funcionar de forma asíncrona.

El Source no necesita esperar necesariamente a que la Replica aplique el cambio.

Esto mejora el rendimiento.

Pero puede provocar:

```text
Replication Lag
```

---

# 23. Replication Lag

Representa la diferencia temporal o de estado entre Source y Replica.

Puede deberse a:

- Carga elevada.
- Red lenta.
- Consultas pesadas.
- Almacenamiento lento.
- Diferencias de capacidad.

Debe monitorizarse en sistemas críticos.

---

# 24. GTID

GTID significa:

```text
Global Transaction Identifier
```

Identifica de forma única una transacción.

Facilita:

- Administración de réplicas.
- Recuperación.
- Cambios de topología.
- Failover.

---

# 25. Formatos de replicación

MySQL admite diferentes formatos:

```text
STATEMENT
ROW
MIXED
```

### STATEMENT

Registra sentencias SQL.

### ROW

Registra cambios sobre las filas.

### MIXED

Combina ambos métodos según las circunstancias.

En entornos modernos es habitual utilizar:

```text
ROW
```

---

# 26. Alta disponibilidad

La replicación puede formar parte de una estrategia de alta disponibilidad.

En caso de fallo:

```text
Source

💥

↓

Replica

↓

Failover
```

Una réplica puede promocionarse para asumir el papel principal.

---

# 27. InnoDB Cluster

MySQL proporciona:

```text
InnoDB Cluster
```

basado en:

```text
MySQL Group Replication
```

Permite construir grupos de servidores coordinados para proporcionar:

- Alta disponibilidad.
- Recuperación ante fallos.
- Coordinación entre nodos.

---

# 28. Replica ≠ Backup

Una réplica no sustituye a una copia de seguridad.

Si ejecutamos:

```sql
DROP TABLE clientes;
```

el cambio puede propagarse a las réplicas.

Por tanto:

```text
Backup
+
Replicación
```

son mecanismos complementarios.

# 32. Índices

# 39. Bloqueos

Los bloqueos son necesarios para garantizar la consistencia de las transacciones.

Sin embargo.

Pueden provocar esperas.

Por ejemplo:

```text
Transacción A
    ↓
Bloquea fila 1

Transacción B
    ↓
Espera fila 1
```

Un exceso de bloqueos puede degradar el rendimiento.

---

# 40. Deadlocks

Un deadlock ocurre cuando dos transacciones esperan recursos bloqueados entre sí.

```text
Transacción A
    ↓
Bloquea fila 1
    ↓
Espera fila 2
             ↑
             │
Transacción B
    ↓
Bloquea fila 2
    ↓
Espera fila 1
```

Se forma un ciclo.

MySQL debe resolver la situación abortando una de las transacciones.

La aplicación debe estar preparada para gestionar determinados errores de este tipo.

# 44. Comparativa MySQL / PostgreSQL / Oracle

| Concepto | MySQL | PostgreSQL | Oracle |
|----------|-------|------------|--------|
| Motor principal | InnoDB | Motor integrado | Motor Oracle |

| Alta disponibilidad | InnoDB Cluster | Soluciones de clúster/replicación | RAC / Data Guard |
| Herramienta gráfica | Workbench | pgAdmin | SQL Developer |
