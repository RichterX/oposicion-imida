# ¿Qué es Oracle Database?

Oracle Database es un **Sistema Gestor de Bases de Datos Relacional** (SGBD o DBMS) desarrollado por la empresa Oracle Corporation.

Al igual que PostgreSQL o MySQL.

Su función consiste en:

- Almacenar información.
- Gestionar bases de datos.
- Ejecutar consultas SQL.
- Administrar usuarios.
- Garantizar la integridad de los datos.

Es uno de los gestores de bases de datos más utilizados en grandes organizaciones.

---

```
SQL

# Instancia y base de datos

Instancia

# ¿Qué es una instancia?

La instancia Oracle representa el conjunto de procesos y memoria que permiten que Oracle funcione.

Podemos imaginarla como:

```
El motor.
```

Cuando iniciamos Oracle.

Lo que realmente arrancamos es la instancia.

---

# ¿Qué contiene una instancia?

Una instancia está formada principalmente por dos elementos.

```
Instancia

↓

Memoria

+

Procesos
```

La memoria almacena información temporal necesaria para el funcionamiento.

Los procesos realizan tareas como:

- Ejecutar consultas.
- Escribir datos en disco.
- Gestionar transacciones.
- Recuperar información tras un fallo.

---

# ¿Qué es la base de datos?

La base de datos constituye el conjunto de archivos almacenados en disco.

Entre ellos encontramos:

- Archivos de datos.
- Archivos de control.
- Archivos de registro (*Redo Log Files*).

Es decir.

Mientras la instancia está ejecutándose.

La base de datos permanece almacenada físicamente.

---

# Una analogía

Podemos imaginar Oracle como un automóvil.

```
Instancia

↓

Motor funcionando
```

```
Base de datos

↓

El vehículo aparcado
```

El coche puede existir sin estar arrancado.

De igual forma.

Los archivos de la base de datos existen aunque la instancia esté detenida.

Cuando arrancamos el motor.

La instancia accede a esos archivos y comienza a trabajar con ellos.

---

# Flujo de funcionamiento

Podemos resumir el proceso así.

```
Usuario

↓

Consulta SQL

↓

Instancia Oracle

↓

Archivos de la base de datos

↓

Resultado
```

La instancia actúa como intermediaria entre los usuarios y los datos.

---

# ¿Puede existir una base de datos sin instancia?

Sí.

Los archivos permanecen almacenados.

Simplemente no podrán utilizarse hasta que una instancia los abra.

---

# ¿Puede existir una instancia sin base de datos?

En determinadas tareas de administración.

Sí.

La instancia puede iniciarse antes de montar completamente la base de datos.

Son situaciones habituales para un administrador.

# Tablespaces

Dentro de la base de datos encontramos las:

```
Tablespaces
```

Una tablespace es un contenedor lógico utilizado para organizar el almacenamiento.

No almacena directamente la información.

Agrupa uno o varios archivos físicos de datos.

# ¿Por qué existen?

Supongamos una organización.

Queremos separar distintos tipos de información.

Por ejemplo.

```
Usuarios
```

```
Facturación
```

```
Histórico
```

En lugar de guardar todo mezclado.

Oracle permite distribuir la información en diferentes tablespaces.

---

# Ejemplo

Podemos tener.

```
Base de datos

↓

SYSTEM
```

```
SYSAUX
```

```

```

```
DATOS
```

```

Cada una almacena distintos objetos.

Esto facilita enormemente la administración.

---

# Tablespaces del sistema

Toda instalación Oracle incorpora varias tablespaces importantes.

Entre ellas destacan:

| Tablespace | Función |
|------------|----------|
| SYSTEM | Contiene información esencial del sistema |
| SYSAUX | Componentes auxiliares de Oracle |
| USERS | Objetos creados por los usuarios |
| TEMP | Espacio temporal para operaciones complejas |
| UNDO | Información necesaria para deshacer transacciones |

Como administradores debemos conocer especialmente estas cinco.

---

# Segmentos

Dentro de una tablespace Oracle almacena segmentos.

Un segmento representa el espacio asignado a un objeto.

Por ejemplo.

- Una tabla.
- Un índice.
- Un segmento UNDO.

Cada objeto ocupa uno o varios segmentos.

# Errores frecuentes

### ❌ Confundir instancia y base de datos

La instancia es el conjunto de procesos y memoria.

La base de datos son los archivos almacenados en disco.

---

### ❌ Pensar que una tablespace es una tabla

Una tablespace es un contenedor lógico.

Puede contener muchos objetos distintos.

---

### ❌ Creer que todos los datos se almacenan en SYSTEM

La tablespace `SYSTEM` está reservada para información esencial del gestor.

Las aplicaciones deben utilizar otras tablespaces.

---

### ❌ Pensar que las tablespaces son archivos físicos

No.

Son estructuras lógicas.

Los datos se almacenan realmente en archivos físicos llamados **Datafiles**, que pertenecen a una o varias tablespaces.

---

# Buenas prácticas

- Mantener separados los datos del sistema y los datos de las aplicaciones.
- Utilizar tablespaces diferentes para facilitar la administración y el mantenimiento.
- Evitar almacenar objetos de usuario en la tablespace `SYSTEM`.
- Planificar adecuadamente la distribución del almacenamiento cuando la base de datos crece.

---

# Conceptos importantes

Antes de continuar debes recordar:

- La **instancia Oracle** está formada por procesos y memoria; es el motor que ejecuta la base de datos.
- La **base de datos Oracle** es el conjunto de archivos físicos almacenados en disco.
- Una **tablespace** es un contenedor lógico que organiza el almacenamiento.
- Los datos se almacenan físicamente en **Datafiles**, asociados a las tablespaces.
- Las tablespaces `SYSTEM`, `SYSAUX`, `USERS`, `TEMP` y `UNDO` forman parte de la instalación básica de Oracle.
- Comprender la diferencia entre instancia, base de datos y tablespace es fundamental para administrar Oracle correctamente.

# La instancia Oracle: memoria y procesos

En el apartado anterior aprendimos que una instancia Oracle está formada por:

- Memoria.
- Procesos.

Ambos trabajan conjuntamente para ejecutar consultas, gestionar transacciones y mantener la base de datos.

Podemos representarlo así.

```
Instancia Oracle

↓

Memoria

+

Procesos
```

---

# La memoria de Oracle

Oracle utiliza diferentes áreas de memoria.

Las dos más importantes son:

- SGA (*System Global Area*).
- PGA (*Program Global Area*).

Cada una cumple una función distinta.

---

# SGA (System Global Area)

La **SGA** es la memoria compartida de la instancia.

Todos los procesos del servidor pueden acceder a ella.

Su objetivo es mejorar el rendimiento evitando acceder continuamente al disco.

Podemos imaginarla como una gran zona de trabajo común.

```
Usuarios

↓

SGA

↓

Base de datos
```

---

# ¿Qué almacena la SGA?

Entre otros elementos.

La SGA contiene:

- Caché de datos.
- Caché de instrucciones SQL.
- Información sobre bloqueos.
- Buffers de escritura.
- Información de control.

Su tamaño puede configurarse por el administrador.

---

# Caché de datos (Database Buffer Cache)

Es una de las partes más importantes de la SGA.

Cuando Oracle necesita leer una tabla.

Primero comprueba si los datos ya se encuentran en memoria.

```
Consulta

↓

¿Está en la caché?

↓

Sí

↓

Respuesta inmediata
```

Si no.

Lee la información desde el disco y la almacena posteriormente en la caché.

Esto reduce considerablemente el número de accesos físicos.

---

# Shared Pool

Otra parte importante de la SGA es el:

```
Shared Pool
```

Contiene, entre otros elementos:

- Consultas SQL ya analizadas.
- Planes de ejecución.
- Información del diccionario de datos.

Gracias a ello.

Oracle evita analizar repetidamente la misma consulta.

---

# PGA (Program Global Area)

La **PGA** es diferente.

No es compartida.

Cada proceso dispone de su propia PGA.

Se utiliza para almacenar información privada durante la ejecución de una sesión.

Por ejemplo:

- Variables temporales.
- Operaciones de ordenación.
- Información de una consulta concreta.

---

# Diferencia entre SGA y PGA

| SGA | PGA |
|-----|-----|
| Compartida | Privada |
| Una por instancia | Una por proceso |
| Mejora el rendimiento general | Almacena información temporal de cada proceso |
| Accesible por todos los procesos | Solo por el proceso propietario |

Esta diferencia aparece con frecuencia en preguntas tipo test.

---

# Procesos de Oracle

Además de la memoria.

La instancia incorpora diversos procesos que realizan tareas automáticas.

Los más importantes son:

- DBWn.
- LGWR.
- SMON.
- PMON.
- CKPT.

Veamos su función.

---

# DBWn (Database Writer)

Su misión consiste en escribir en disco los bloques modificados que se encuentran en memoria.

Podemos resumirlo así.

```
Memoria

↓

DBWn

↓

Archivos de datos
```

No escribe inmediatamente después de cada modificación.

Oracle agrupa las escrituras para mejorar el rendimiento.

---

# LGWR (Log Writer)

Antes de modificar definitivamente los archivos de datos.

Oracle registra la operación en los archivos de redo log.

El encargado de esta tarea es:

```
LGWR
```

Su función recuerda al mecanismo WAL que estudiamos en PostgreSQL.

Primero registra la operación.

Después podrán actualizarse los archivos de datos.

---

# SMON (System Monitor)

El proceso:

```
SMON
```

se encarga principalmente de:

- Recuperar la base de datos tras un fallo.
- Limpiar información temporal.
- Realizar determinadas tareas de mantenimiento.

Es uno de los procesos más importantes para garantizar la consistencia de la información.

---

# PMON (Process Monitor)

El proceso:

```
PMON
```

supervisa las sesiones de usuario.

Si un proceso termina de forma inesperada.

PMON:

- Libera recursos.
- Cierra la sesión.
- Recupera información pendiente.

Gracias a ello.

La instancia continúa funcionando correctamente.

---

# CKPT (Checkpoint)

El proceso:

```
CKPT
```

coordina los puntos de control (*Checkpoints*).

Durante un checkpoint.

Oracle sincroniza parte de la información almacenada en memoria con los archivos de datos.

Esto facilita la recuperación tras un fallo del sistema.

---

# ¿Cómo colaboran?

Podemos imaginar el siguiente flujo.

```
Consulta SQL

↓

SGA

↓

LGWR

↓

Redo Log

↓

DBWn

↓

Archivos de datos
```

Mientras tanto.

SMON y PMON supervisan el correcto funcionamiento de la instancia.

---

# ¿Debemos memorizar todos los procesos?

No.

Oracle incorpora muchos procesos adicionales.

Sin embargo.

Para una administración básica y para la mayoría de oposiciones.

Conviene conocer al menos:

- DBWn.
- LGWR.
- SMON.
- PMON.
- CKPT.

Con comprender su función general suele ser suficiente.

---

# Comparación con PostgreSQL

Ambos gestores incorporan mecanismos similares.

| Oracle | PostgreSQL |
|----------|------------|
| Redo Log | WAL |
| DBWn | Escritura de páginas modificadas |
| Shared Pool | Caché de planes de ejecución |
| Database Buffer Cache | Buffer Cache |
| SMON | Recuperación tras fallos |

La filosofía es muy parecida.

Aunque la terminología cambia.

# Errores frecuentes

### ❌ Pensar que la SGA pertenece a un usuario

La SGA es compartida por toda la instancia.

Todos los procesos pueden utilizarla.

---

### ❌ Confundir SGA y PGA

La SGA es memoria compartida.

La PGA pertenece únicamente a un proceso.

---

### ❌ Creer que DBWn escribe inmediatamente cada modificación

Oracle agrupa las escrituras para optimizar el rendimiento.

No todas las modificaciones llegan al disco de forma instantánea.

---

### ❌ Pensar que LGWR almacena los datos de usuario

LGWR escribe la información de recuperación en los archivos **Redo Log**.

Los datos definitivos se almacenan posteriormente en los Datafiles mediante DBWn.

---

# Buenas prácticas

- Comprender la diferencia entre memoria compartida y memoria privada.
- Recordar la función principal de cada proceso sin intentar memorizar todos los procesos internos de Oracle.
- Relacionar los procesos con los mecanismos equivalentes estudiados en PostgreSQL.
- Identificar qué componentes pertenecen a la memoria y cuáles corresponden a procesos de la instancia.

---

# Conceptos importantes

Antes de continuar debes recordar:

- La instancia Oracle está formada por memoria (**SGA** y **PGA**) y procesos en segundo plano.
- La **SGA** es memoria compartida y almacena cachés e información común de la instancia.
- La **PGA** es memoria privada asociada a cada proceso.
- **DBWn** escribe los bloques modificados desde memoria a los Datafiles.
- **LGWR** registra las modificaciones en los archivos **Redo Log**.
- **SMON** realiza tareas de recuperación y mantenimiento tras fallos.
- **PMON** supervisa los procesos y libera recursos cuando una sesión termina de forma anómala.
- **CKPT** coordina los puntos de control (*Checkpoints*) para facilitar la recuperación de la base de datos.

# Usuarios en Oracle

Al igual que PostgreSQL.

Oracle permite que distintas personas trabajen sobre la misma base de datos.

Cada usuario dispone de:

- Un nombre.
- Una contraseña.
- Un conjunto de permisos.
- Un esquema propio.

Ejemplo:

```
PEDRO
```

```
ADMIN
```

```
RRHH
```

```
VENTAS
```

Cada usuario representa una identidad dentro del sistema.

---

# Usuarios y esquemas

Aquí aparece una diferencia importante respecto a PostgreSQL.

En Oracle.

Cada usuario posee automáticamente un esquema con el mismo nombre.

Por ejemplo.

```
Usuario

↓

PEDRO
```

↓

```
Esquema

↓

PEDRO
```

Todo objeto creado por ese usuario pertenece inicialmente a su esquema.

---

# Un ejemplo

El usuario:

```
RRHH
```

ejecuta:

```sql
CREATE TABLE empleados (
    id NUMBER,
    nombre VARCHAR2(100)
);
```

La tabla realmente se crea en:

```
RRHH.EMPLEADOS
```

Aunque no se indique explícitamente.

---

# Acceder a objetos de otro esquema

Supongamos ahora que el usuario:

```
ADMIN
```

quiere consultar la tabla anterior.

Debe indicar el esquema.

```sql
SELECT *
FROM RRHH.EMPLEADOS;
```

Siempre que disponga de permisos suficientes.

---

# Privilegios

Oracle distingue dos grandes categorías de privilegios.

## Privilegios del sistema

Permiten realizar tareas administrativas.

Por ejemplo:

- Crear usuarios.
- Crear tablespaces.
- Crear sesiones.
- Administrar la base de datos.

---

## Privilegios sobre objetos

Permiten trabajar sobre tablas, vistas u otros objetos.

Por ejemplo:

- SELECT
- INSERT
- UPDATE
- DELETE
- EXECUTE

Estos privilegios se conceden sobre objetos concretos.

---

# GRANT

Para conceder permisos utilizamos:

```sql
GRANT
```

Ejemplo:

```sql
GRANT SELECT
ON RRHH.EMPLEADOS
TO PEDRO;
```

Ahora:

```
PEDRO
```

puede consultar esa tabla.

---

# REVOKE

Para retirar permisos:

```sql
REVOKE SELECT
ON RRHH.EMPLEADOS
FROM PEDRO;
```

El privilegio desaparece inmediatamente.

---

# Roles

Cuando existen muchos usuarios.

No resulta práctico asignar permisos uno por uno.

Oracle incorpora:

```
Roles
```

Un rol agrupa distintos privilegios.

Posteriormente puede asignarse a varios usuarios.

Ejemplo.

```
Rol

↓

LECTORES
```

Permisos:

- SELECT

Después:

```sql
GRANT LECTORES
TO PEDRO;
```

Pedro heredará automáticamente dichos permisos.

---

# Principio del mínimo privilegio

Como ya vimos en PostgreSQL.

Una buena práctica consiste en conceder únicamente los permisos imprescindibles.

Por ejemplo.

Un usuario que únicamente consulta información.

No debería poder:

- Eliminar tablas.
- Crear usuarios.
- Modificar la configuración.

Reducir privilegios mejora significativamente la seguridad.

# Copias de seguridad y recuperación: RMAN

Toda base de datos contiene información crítica.

Por ejemplo:

- Clientes.
- Facturas.
- Expedientes.
- Historiales médicos.
- Información financiera.

Perder estos datos puede tener consecuencias muy graves.

Por ello.

Oracle incorpora una herramienta especializada para realizar copias de seguridad y recuperar la información.

Esta herramienta recibe el nombre de:

```
RMAN

(Recovery Manager)
```

---

# ¿Qué es RMAN?

RMAN es la herramienta oficial de Oracle para:

- Crear copias de seguridad.
- Restaurar bases de datos.
- Recuperar archivos dañados.
- Automatizar estrategias de backup.
- Gestionar la recuperación tras fallos.

Es la herramienta recomendada por Oracle para la administración de copias de seguridad.

---

# ¿Por qué utilizar RMAN?

Podríamos copiar manualmente los archivos de la base de datos.

Sin embargo.

RMAN conoce perfectamente la estructura interna de Oracle.

Por ello puede:

- Optimizar las copias.
- Verificar su integridad.
- Recuperar únicamente los archivos necesarios.
- Automatizar gran parte del proceso.

---

# Arquitectura de una copia

Podemos imaginar el siguiente proceso.

```
Base de datos

↓

RMAN

↓

Copia de seguridad
```

Cuando sea necesario.

El proceso se invierte.

```
Copia

↓

RMAN

↓

Base de datos recuperada
```

---

# Tipos de copia

Oracle permite distintas estrategias.

Las más habituales son:

## Copia completa

Incluye toda la base de datos.

Ventajas:

- Restauración sencilla.

Inconvenientes:

- Mayor tiempo.
- Mayor espacio ocupado.

---

## Copia incremental

Solo almacena los bloques modificados desde la copia anterior.

Ventajas:

- Más rápida.
- Menor tamaño.

Inconvenientes:

- Restauración más compleja.

---

# Copias online

Una característica importante de Oracle.

RMAN permite realizar copias de seguridad mientras la base de datos continúa funcionando.

Los usuarios pueden seguir trabajando.

Sin necesidad de detener el servicio.

Esto resulta esencial en sistemas que deben permanecer disponibles las 24 horas.

---

# Restauración

Cuando se produce un fallo.

RMAN puede:

- Restaurar archivos.
- Recuperar tablespaces.
- Recuperar Datafiles.
- Recuperar toda la base de datos.

El administrador puede elegir el nivel de recuperación necesario.

---

# Redo Log

Recordemos lo estudiado anteriormente.

Oracle registra todas las modificaciones importantes en los:

```
Redo Log Files
```

Estos archivos permiten reconstruir operaciones recientes.

Su función es muy similar al:

```
WAL
```

de PostgreSQL.

---

# Archive Log

Cuando un Redo Log deja de utilizarse.

Puede almacenarse como:

```
Archived Redo Log
```

Estos archivos conservan el historial de modificaciones.

Gracias a ellos.

Oracle puede recuperar información incluso mucho tiempo después de realizar una copia completa.

---

# Relación entre RMAN y Archive Log

Podemos representar el proceso así.

```
Copia completa

+

Archived Redo Logs

↓

Recuperación
```

Esta combinación permite recuperar la base de datos prácticamente hasta el instante anterior al fallo.

---

# Recuperación tras un fallo

Supongamos.

```
09:00

↓

Copia completa
```

```
12:35

↓

Actualizaciones
```

```
16:20

↓

Fallo del servidor
```

RMAN puede:

1.

Restaurar la copia.

↓

2.

Aplicar los Archived Redo Logs.

↓

3.

Reconstruir los cambios realizados hasta el momento del fallo.

---

# Automatización

En grandes instalaciones.

Las copias suelen ejecutarse automáticamente.

Por ejemplo.

- Cada noche.
- Cada semana.
- Según políticas definidas por la organización.

RMAN permite automatizar completamente estas tareas.

---

# Verificación

Una ventaja muy importante.

RMAN puede comprobar la integridad de las copias.

No basta con crear un backup.

También debemos asegurarnos de que realmente podrá restaurarse.

Esta verificación constituye una parte fundamental de cualquier estrategia de recuperación.

---

# Oracle y la alta disponibilidad

RMAN suele utilizarse conjuntamente con otras tecnologías Oracle.

Por ejemplo:

- Oracle Data Guard.
- Oracle Real Application Clusters (RAC).

Estas soluciones permiten reducir al mínimo el tiempo de inactividad.

En este capítulo basta con conocer su existencia.

---

# Comparación con PostgreSQL

| Oracle | PostgreSQL |
|----------|------------|
| RMAN | pg_dump / pg_restore |
| Redo Log | WAL |
| Archived Redo Log | Archivos WAL archivados |
| Recuperación avanzada | PITR |
| Copias incrementales integradas | Estrategias basadas en WAL |

Aunque la terminología cambia.

La finalidad es muy similar.

---

# Errores frecuentes

### ❌ Pensar que basta con copiar los Datafiles

Una copia consistente requiere también la información necesaria para recuperar las transacciones.

RMAN gestiona automáticamente estos elementos.

---

### ❌ No verificar las copias

Una copia de seguridad solo es útil si puede restaurarse correctamente.

Es recomendable comprobar periódicamente su integridad.

---

### ❌ Confundir Redo Log con Archive Log

Los Redo Log contienen la información activa.

Los Archive Log conservan los registros históricos necesarios para recuperaciones avanzadas.

---

### ❌ Pensar que RMAN sustituye una estrategia de copias

RMAN es una herramienta.

La organización sigue necesitando definir políticas de:

- Frecuencia.
- Retención.
- Almacenamiento.
- Recuperación.

---

# Buenas prácticas

- Automatizar las copias de seguridad mediante RMAN.
- Verificar periódicamente la restauración de las copias.
- Mantener archivados los Redo Logs cuando la estrategia de recuperación lo requiera.
- Almacenar las copias en ubicaciones diferentes al servidor principal.
- Documentar claramente el procedimiento de recuperación ante desastres.

---

# Conceptos importantes

Antes de continuar debes recordar:

- **RMAN (Recovery Manager)** es la herramienta oficial de Oracle para realizar copias de seguridad y recuperaciones.
- Permite crear copias completas e incrementales.
- Los **Redo Log Files** registran las modificaciones recientes de la base de datos.
- Los **Archived Redo Logs** permiten recuperar los cambios realizados después de una copia completa.
- RMAN puede restaurar desde archivos individuales hasta la base de datos completa.
- Una estrategia eficaz de recuperación combina copias de seguridad, archivos de redo y procedimientos de verificación.

# Rendimiento y alta disponibilidad

Hasta ahora hemos estudiado cómo Oracle:

- Organiza la información.
- Gestiona usuarios.
- Realiza copias de seguridad.
- Recupera la base de datos.

Pero...

¿Qué ocurre si el servidor deja de funcionar?

¿Y si miles de usuarios siguen necesitando acceder a la base de datos?

Oracle incorpora diversas tecnologías destinadas a garantizar la disponibilidad del servicio.

---

# ¿Qué significa alta disponibilidad?

Un sistema de alta disponibilidad intenta minimizar el tiempo durante el cual un servicio permanece inaccesible.

El objetivo consiste en que la base de datos continúe funcionando incluso cuando aparecen fallos.

Por ejemplo:

- Avería de un servidor.
- Fallo de un disco.
- Corte eléctrico.
- Mantenimiento programado.

---

# Oracle RAC

Una de las tecnologías más conocidas de Oracle es:

```
Oracle RAC

(Real Application Clusters)
```

Su objetivo consiste en permitir que varios servidores trabajen conjuntamente sobre una única base de datos.

---

# ¿Cómo funciona?

Podemos imaginar la siguiente arquitectura.

```
Servidor 1

↓

Instancia Oracle

↓

Base de datos compartida

↑

Instancia Oracle

↓

Servidor 2
```

Ambos servidores acceden a la misma base de datos.

Si uno deja de funcionar.

El otro continúa ofreciendo el servicio.

---

# Ventajas de Oracle RAC

Entre sus principales ventajas destacan:

- Alta disponibilidad.
- Balanceo de carga.
- Escalabilidad horizontal.
- Reducción del tiempo de inactividad.

Por ello resulta habitual en sistemas críticos.

---

# Oracle Data Guard

Otra tecnología muy importante es:

```
Oracle Data Guard
```

Su función consiste en mantener una copia sincronizada de la base de datos en otro servidor.

Podemos representarlo así.

```
Servidor principal

↓

Redo Log

↓

Servidor secundario
```

El servidor secundario permanece preparado para sustituir al principal si fuera necesario.

---

# Diferencia entre RAC y Data Guard

Aunque ambas tecnologías mejoran la disponibilidad.

Resuelven problemas diferentes.

## Oracle RAC

Varios servidores trabajan simultáneamente sobre la misma base de datos.

---

## Oracle Data Guard

Existe una base de datos principal y otra de respaldo.

La réplica permanece sincronizada para asumir el servicio en caso de fallo.

---

# Balanceo de carga

Cuando muchos usuarios acceden simultáneamente.

Oracle RAC puede repartir el trabajo entre varios nodos.

```
Usuarios

↓

Nodo 1

↓

Nodo 2

↓

Nodo 3
```

Esto evita que un único servidor soporte toda la carga.

---

# Conmutación por error (Failover)

Si el servidor principal deja de funcionar.

Puede producirse un:

```
Failover
```

Es decir.

El servicio pasa automáticamente al servidor de respaldo.

Los usuarios apenas perciben la interrupción.

---

# Escalabilidad

Una gran ventaja de Oracle consiste en su capacidad para crecer.

Cuando aumenta el número de usuarios.

Es posible:

- Añadir memoria.
- Incorporar nuevos servidores.
- Ampliar el almacenamiento.

Todo ello sin modificar la aplicación.

---

- Recomendaciones de rendimiento.

Muchos de estos procesos funcionan sin intervención del administrador.

# Oracle Optimizer

Finalmente selecciona el plan de ejecución que considera más eficiente.

Este componente recibe el nombre de:

Oracle Optimizer

# Errores frecuentes

### ❌ Confundir Oracle RAC con Data Guard

RAC permite que varios servidores trabajen simultáneamente sobre una misma base de datos.

Data Guard mantiene una base de datos principal y otra de respaldo sincronizada.

---

### ❌ Pensar que RAC sustituye las copias de seguridad

No.

RAC mejora la disponibilidad.

Pero sigue siendo necesario realizar copias mediante RMAN.

Reduce considerablemente el tiempo de inactividad.

Pero no sustituye una estrategia adecuada de recuperación ante desastres.

---

### ❌ Pensar que Oracle Optimizer ejecuta siempre el mismo plan

El optimizador adapta el plan de ejecución según las estadísticas disponibles y las características de la consulta.

# Buenas prácticas

- Utilizar RMAN junto con estrategias de alta disponibilidad.
- Supervisar periódicamente el rendimiento mediante Oracle Enterprise Manager.

- Elegir tecnologías como RAC o Data Guard según las necesidades reales del sistema.
