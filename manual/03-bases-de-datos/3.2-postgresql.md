# ¿Qué es PostgreSQL?

PostgreSQL es un **Sistema Gestor de Bases de Datos Relacional** (SGBD o DBMS) de código abierto.

Su función consiste en:

- Almacenar información.
- Organizarla.
- Consultarla mediante SQL.
- Garantizar la integridad de los datos.
- Gestionar usuarios, permisos y transacciones.

En otras palabras:

Es el software encargado de administrar una o varias bases de datos.

---

# Un poco de historia

PostgreSQL tiene una larga trayectoria.

Su origen se remonta a la Universidad de California en Berkeley.

Durante la década de los 80 surgió el proyecto:

```
POSTGRES
```

Posteriormente incorporó soporte para SQL.

Desde entonces pasó a denominarse:

```
PostgreSQL
```

Actualmente es uno de los proyectos de software libre más importantes del mundo.

Su desarrollo está coordinado por la comunidad internacional conocida como:

```
PostgreSQL Global Development Group
```

# Arquitectura de PostgreSQL

Hasta ahora hemos visto que PostgreSQL es un Sistema Gestor de Bases de Datos.

Pero...

¿Qué organiza realmente?

¿Cuál es su estructura interna?

Para responder a estas preguntas debemos conocer la jerarquía de PostgreSQL.

---

# La jerarquía de PostgreSQL

Podemos imaginar PostgreSQL como una estructura organizada en varios niveles.

```
Servidor PostgreSQL
        │
        ▼
     Clúster
        │
        ▼
 Base de datos
        │
        ▼
    Esquemas
        │
        ▼
     Tablas
        │
        ▼
   Registros
```

Cada nivel contiene al siguiente.

Comprender esta organización facilita enormemente la administración del sistema.

---

# El servidor PostgreSQL

El nivel superior es el servidor PostgreSQL.

Es el proceso que permanece ejecutándose en el sistema operativo.

Su función consiste en:

- Escuchar conexiones.
- Gestionar usuarios.
- Administrar bases de datos.
- Ejecutar consultas SQL.
- Controlar las transacciones.

Cuando iniciamos PostgreSQL realmente estamos iniciando este servidor.

---

# ¿Qué es un clúster?

Aquí aparece un concepto muy característico de PostgreSQL.

```
Clúster
```

En PostgreSQL un clúster es:

> El conjunto de bases de datos administradas por una misma instancia del servidor.

No debe confundirse con el concepto de "cluster" utilizado en alta disponibilidad.

En PostgreSQL significa algo diferente.

---

# ¿Qué contiene un clúster?

Dentro de un mismo clúster encontramos:

- Bases de datos.
- Usuarios (roles).
- Configuración.
- Archivos del sistema.

Visualmente:

```
Clúster

↓

postgres

↓

imida

↓

pruebas

↓

inventario
```

Cada elemento representa una base de datos distinta.

---

# Las bases de datos

Dentro del clúster encontramos las bases de datos.

Cada una constituye un entorno independiente.

Por ejemplo:

```
imida
```

```
recursos_humanos
```

```
catastro
```

Cada base de datos puede contener:

- Sus propias tablas.
- Sus propios esquemas.
- Sus propias vistas.
- Sus propias funciones.

Una aplicación normalmente trabaja con una única base de datos.

---

# ¿Pueden comunicarse dos bases de datos?

En PostgreSQL:

No directamente.

Una consulta SQL ejecutada sobre una base de datos:

```
imida
```

no puede acceder libremente a las tablas de:

```
recursos_humanos
```

Cada base de datos permanece aislada.

---

# Los esquemas

Dentro de una base de datos aparecen los:

```
Schemas
```

o

```
Esquemas
```

Un esquema funciona como una carpeta lógica.

Sirve para organizar los objetos de la base de datos.

Por ejemplo:

```
Base de datos

↓

public

↓

agricultura

↓

cartografia

↓

administracion
```

Cada esquema puede contener sus propias tablas.

---

# ¿Por qué utilizar esquemas?

Supongamos una misma base de datos utilizada por varios departamentos.

En lugar de almacenar todas las tablas juntas:

Podemos organizarlas.

```
public

↓

usuarios
```

```
agricultura

↓

parcelas

↓

cultivos
```

```
cartografia

↓

mapas

↓

coordenadas
```

La organización resulta mucho más clara.

---

# El esquema public

Cuando instalamos PostgreSQL.

Todas las bases de datos incorporan automáticamente un esquema llamado:

```
public
```

Si no indicamos ningún esquema.

Las tablas se crean allí por defecto.

Por ejemplo:

```sql
CREATE TABLE ciudadanos (...);
```

Realmente equivale a:

```sql
CREATE TABLE public.ciudadanos (...);
```

---

# Las tablas

Dentro de cada esquema aparecen las tablas.

Por ejemplo:

```
public

↓

ciudadanos
```

```
agricultura

↓

parcelas
```

```
cartografia

↓

municipios
```

Cada tabla almacena un único tipo de información.

---

# Los registros

Finalmente.

Cada tabla contiene registros.

Ejemplo:

```
Tabla

↓

Ciudadanos
```

| id | nombre |
|----|---------|
|1|Pedro|
|2|Ana|
|3|Luis|

Cada fila representa un registro.

Tal y como estudiamos en el capítulo anterior.

Podemos imaginar la siguiente estructura.

```
Servidor PostgreSQL
        │
        ▼
      Clúster
        │
        ▼
 Base de datos: imida
        │
        ▼
```

# Objetos de una base de datos

Además de tablas.

Una base de datos PostgreSQL puede contener:

- Vistas.
- Índices.
- Secuencias.
- Funciones.
- Procedimientos.
- Tipos personalizados.
- Triggers.

Todos ellos se organizan dentro de un esquema.

---

# Errores frecuentes

### ❌ Confundir servidor con base de datos

Un servidor PostgreSQL puede administrar varias bases de datos.

No son lo mismo.

---

### ❌ Pensar que un esquema es una base de datos

Un esquema existe dentro de una base de datos.

No constituye una base de datos independiente.

---

### ❌ Creer que todas las tablas pertenecen al esquema public

Solo si no indicamos otro esquema.

Podemos crear tantos esquemas como necesitemos.

---

### ❌ Confundir el "clúster" de PostgreSQL con un clúster de alta disponibilidad

En PostgreSQL, un clúster es el conjunto de bases de datos gestionadas por una misma instancia del servidor.

No implica necesariamente replicación ni balanceo de carga.

---

# Buenas prácticas

- Utilizar distintos esquemas para organizar aplicaciones grandes.
- Evitar almacenar todas las tablas en `public` cuando el proyecto crece.
- Utilizar nombres descriptivos para bases de datos y esquemas.
- Mantener una estructura jerárquica clara y coherente.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Un servidor PostgreSQL puede administrar un clúster con varias bases de datos.
- Cada base de datos es independiente del resto.
- Dentro de una base de datos existen uno o varios esquemas.
- Los esquemas organizan los objetos de la base de datos.
- Las tablas, vistas, índices y funciones pertenecen a un esquema.
- El esquema `public` se crea automáticamente y se utiliza por defecto si no se especifica otro.
- Comprender esta jerarquía resulta fundamental para administrar PostgreSQL correctamente.

# psql y administración básica

Hasta ahora sabemos que PostgreSQL funciona como un servidor que administra una o varias bases de datos.

Pero...

¿Cómo nos conectamos a ese servidor?

¿Cómo ejecutamos consultas?

¿Cómo vemos las tablas existentes?

La herramienta clásica para realizar todas estas tareas es:

```
psql
```

---

# ¿Qué es psql?

`psql` es el cliente de línea de comandos oficial de PostgreSQL.

Permite conectarse a un servidor PostgreSQL y administrarlo desde la terminal.

Con `psql` podemos:

- Ejecutar consultas SQL.
- Crear bases de datos.
- Gestionar usuarios.
- Crear tablas.
- Consultar esquemas.
- Administrar permisos.
- Realizar tareas de mantenimiento.

En muchas ocasiones resulta más rápido que utilizar una interfaz gráfica.

---

# Conectarse a PostgreSQL

La sintaxis básica es:

```bash
psql -U usuario -d base_de_datos
```

Por ejemplo:

```bash
psql -U postgres -d imida
```

Donde:

- `-U` indica el usuario.
- `-d` especifica la base de datos.

Si la autenticación es correcta aparecerá el prompt de PostgreSQL.

```
imida=#
```

Desde ese momento podremos ejecutar comandos SQL.

---

# Conexión remota

También es posible conectarse a un servidor remoto.

```bash
psql -h servidor \
     -p 5432 \
     -U postgres \
     -d imida
```

Parámetros:

- `-h` → Host o dirección IP.
- `-p` → Puerto (5432 por defecto).
- `-U` → Usuario.
- `-d` → Base de datos.

---

# El usuario postgres

Durante la instalación se crea normalmente un usuario especial.

```
postgres
```

Este usuario actúa como administrador del servidor.

Posee permisos para:

- Crear bases de datos.
- Crear usuarios.
- Gestionar roles.
- Configurar el servidor.

Es el equivalente al usuario `root` en muchos sistemas Linux, aunque limitado al ámbito de PostgreSQL.

---

# Comandos internos de psql

Una característica muy útil de `psql` es que incorpora comandos propios.

Estos comandos:

- No son SQL.
- Comienzan por una barra invertida (`\`).

Por ejemplo:

```text
\l
```

o

```text
\dt
```

---

# Listar bases de datos

Comando:

```text
\l
```

o

```text
\list
```

Muestra todas las bases de datos existentes en el clúster.

Ejemplo:

```
postgres

template0

template1

imida

catastro
```

---

# Cambiar de base de datos

Comando:

```text
\c nombre_base
```

Ejemplo:

```text
\c imida
```

A partir de ese momento todas las consultas se ejecutarán sobre esa base de datos.

---

# Mostrar tablas

Uno de los comandos más utilizados.

```text
\dt
```

Resultado:

```
ciudadanos

parcelas

municipios

cultivos
```

Muestra las tablas del esquema actual.

---

# Mostrar esquemas

Comando:

```text
\dn
```

Resultado:

```
public

agricultura

cartografia
```

Permite visualizar todos los esquemas existentes.

---

# Mostrar usuarios y roles

Comando:

```text
\du
```

Ejemplo:

```
postgres

pedro

aplicacion

backup
```

Más adelante estudiaremos los roles con detalle.

---

# Describir una tabla

Queremos conocer la estructura de la tabla:

```
ciudadanos
```

Utilizamos:

```text
\d ciudadanos
```

Resultado:

- Columnas.
- Tipos de datos.
- Restricciones.
- Índices.
- Claves.

Es uno de los comandos más útiles durante el desarrollo.

---

# Ejecutar consultas SQL

Dentro de `psql` escribimos SQL exactamente igual que en cualquier otro gestor.

Ejemplo:

```sql
SELECT *
FROM ciudadanos;
```

`psql` envía la consulta al servidor PostgreSQL y muestra el resultado.

---

# Obtener ayuda

Si olvidamos un comando:

```text
\?
```

Muestra todos los comandos propios de `psql`.

Para obtener ayuda sobre SQL:

```text
\h
```

Y para conocer la sintaxis de una instrucción concreta:

```text
\h CREATE TABLE
```

Es una herramienta muy útil para administradores.

---

# Salir de psql

Cuando terminamos:

```text
\q
```

La sesión se cierra y volvemos a la terminal del sistema operativo.

# Roles, usuarios y permisos

Hasta ahora hemos aprendido a:

- Conectarnos a PostgreSQL.
- Explorar bases de datos.
- Utilizar `psql`.

Pero...

¿Quién decide qué puede hacer cada persona?

¿Puede cualquier usuario crear una base de datos?

¿Eliminar tablas?

¿Crear nuevos usuarios?

La respuesta está en el sistema de roles.

---

# ¿Qué es un rol?

En PostgreSQL todo gira alrededor de los:

```
Roles
```

Un rol representa una identidad dentro del servidor PostgreSQL.

Puede utilizarse para:

- Iniciar sesión.
- Ejecutar consultas.
- Crear bases de datos.
- Administrar otros roles.
- Acceder a objetos.

En PostgreSQL:

```
Usuario

↓

Rol con permiso LOGIN
```

Es decir:

Todos los usuarios son roles.

Pero no todos los roles son usuarios.

---

# Tipos de roles

Podemos distinguir dos grandes tipos.

## Rol sin LOGIN

No puede iniciar sesión.

Se utiliza principalmente para agrupar permisos.

Ejemplo:

```
lectores
```

```
administradores
```

```
tecnicos
```

---

## Rol con LOGIN

Puede autenticarse en PostgreSQL.

Actúa como un usuario tradicional.

Ejemplo:

```
pedro
```

```
ana
```

```
postgres
```

---

# El usuario postgres

Durante la instalación suele crearse automáticamente el rol:

```
postgres
```

Este rol dispone normalmente de privilegios de administración.

Puede:

- Crear bases de datos.
- Crear roles.
- Gestionar permisos.
- Modificar la configuración.
- Administrar el servidor.

Es el administrador principal de PostgreSQL.

---

# Crear un rol

La sintaxis básica es:

```sql
CREATE ROLE nombre;
```

Ejemplo:

```sql
CREATE ROLE tecnicos;
```

Este rol existe.

Pero todavía no puede iniciar sesión.

---

# Crear un usuario

Como ya sabemos:

Un usuario es simplemente un rol con capacidad de autenticación.

Ejemplo:

```sql
CREATE ROLE pedro
LOGIN
PASSWORD 'MiClaveSegura';
```

Ahora:

```
pedro
```

puede conectarse al servidor PostgreSQL.

---

# CREATE USER

También existe una sintaxis más sencilla.

```sql
CREATE USER pedro
PASSWORD 'MiClaveSegura';
```

Internamente PostgreSQL crea un rol con el atributo:

```
LOGIN
```

Por ello:

Muchos administradores prefieren utilizar siempre:

```sql
CREATE ROLE
```

porque resulta más flexible.

---

# Privilegios especiales

Un rol puede poseer privilegios adicionales.

Los más habituales son:

- LOGIN
- SUPERUSER
- CREATEDB
- CREATEROLE
- REPLICATION

Veamos cada uno.

---

# LOGIN

Permite iniciar sesión.

Sin este atributo:

El rol existe.

Pero no puede conectarse al servidor.

---

# SUPERUSER

Concede control prácticamente total sobre PostgreSQL.

Puede:

- Crear cualquier objeto.
- Eliminar cualquier base de datos.
- Modificar la configuración.
- Gestionar todos los permisos.

Debe asignarse únicamente a administradores.

---

# CREATEDB

Permite crear nuevas bases de datos.

Ejemplo:

```sql
CREATE ROLE desarrollador
LOGIN
CREATEDB;
```

Este usuario podrá ejecutar:

```sql
CREATE DATABASE pruebas;
```

---

# CREATEROLE

Permite crear y administrar otros roles.

Ejemplo:

```sql
CREATE ROLE administrador
LOGIN
CREATEROLE;
```

No implica automáticamente permisos de superusuario.

---

# REPLICATION

Se utiliza en configuraciones de replicación.

Permite participar en procesos como:

- Streaming Replication.
- Réplicas en caliente.

Es un privilegio orientado principalmente a administradores de sistemas.

---

# Consultar los roles existentes

Dentro de `psql`:

```text
\du
```

Resultado:

```
postgres

pedro

tecnicos

backup
```

Además aparecerán los privilegios asociados a cada uno.

---

# GRANT

Una vez creado un rol.

Debemos conceder permisos sobre los objetos.

Ejemplo:

```sql
GRANT SELECT
ON ciudadanos
TO pedro;
```

Ahora:

```
pedro
```

puede consultar la tabla.

Pero no modificarla.

---

# REVOKE

Para retirar permisos:

```sql
REVOKE SELECT
ON ciudadanos
FROM pedro;
```

El permiso desaparece inmediatamente.

---

# Permisos habituales

Sobre una tabla podemos conceder, entre otros:

- SELECT
- INSERT
- UPDATE
- DELETE
- TRUNCATE
- REFERENCES
- TRIGGER

Ejemplo:

```sql
GRANT SELECT,
      INSERT,
      UPDATE
ON ciudadanos
TO aplicacion;
```

---

# Herencia de roles

Una característica muy interesante de PostgreSQL.

Un rol puede pertenecer a otro.

Ejemplo:

```
Rol

↓

tecnicos
```

Permisos:

- SELECT
- UPDATE

Después:

```
Pedro

↓

Miembro del rol tecnicos
```

Pedro heredará automáticamente esos permisos.

Esto simplifica enormemente la administración.

---

# Ejemplo práctico

Supongamos:

```
Rol

↓

lectores
```

Tiene permiso:

```sql
GRANT SELECT
ON ciudadanos
TO lectores;
```

Después añadimos:

```sql
GRANT lectores
TO ana;
```

Ahora:

```
Ana
```

puede consultar la tabla.

Sin necesidad de asignarle permisos individualmente.

---

# Principio del mínimo privilegio

Una de las reglas más importantes de administración.

Cada usuario debe disponer únicamente de los permisos necesarios para realizar su trabajo.

Por ejemplo:

Un usuario que únicamente consulta información:

No debería poder:

- Eliminar tablas.
- Crear usuarios.
- Modificar permisos.

Reducir privilegios mejora significativamente la seguridad.

---

# Errores frecuentes

### ❌ Conceder privilegios de SUPERUSER innecesariamente

Debe reservarse exclusivamente para administradores.

---

### ❌ Asignar permisos usuario por usuario

Cuando existen muchos usuarios.

Resulta preferible crear roles comunes.

Después basta con añadir usuarios a dichos roles.

---

### ❌ Pensar que CREATE USER y CREATE ROLE son conceptos completamente distintos

En PostgreSQL:

Un usuario es simplemente un rol con el atributo:

```
LOGIN
```

---

### ❌ Olvidar retirar permisos

Cuando un usuario deja de necesitar acceso.

Conviene utilizar:

```sql
REVOKE
```

para eliminar los privilegios correspondientes.

---

# Buenas prácticas

- Utilizar roles para agrupar permisos.
- Conceder únicamente los privilegios necesarios.
- Evitar utilizar `SUPERUSER` salvo cuando sea imprescindible.
- Administrar permisos mediante `GRANT` y `REVOKE`.
- Aplicar siempre el principio del mínimo privilegio.

---

# Conceptos importantes

Antes de continuar debes recordar:

- En PostgreSQL todo gira alrededor de los roles.
- Un usuario es un rol con el atributo `LOGIN`.
- `CREATE ROLE` crea un nuevo rol y `CREATE USER` es una forma simplificada de crear un rol con capacidad de inicio de sesión.
- Los privilegios `SUPERUSER`, `CREATEDB`, `CREATEROLE` y `REPLICATION` permiten realizar tareas administrativas específicas.
- `GRANT` concede permisos y `REVOKE` los retira.
- Los roles pueden heredar permisos de otros roles.
- Aplicar el principio del mínimo privilegio es una de las mejores prácticas de seguridad en PostgreSQL.

---

# MVCC (Multi-Version Concurrency Control)

Hasta ahora hemos aprendido que PostgreSQL soporta:

- Transacciones.
- Propiedades ACID.
- Control de concurrencia.

Pero...

¿Qué ocurre cuando varios usuarios intentan acceder al mismo dato al mismo tiempo?

Por ejemplo:

```
Ana

↓

Lee una fila
```

Mientras tanto:

```
Pedro

↓

Modifica esa misma fila
```

¿Quién tiene prioridad?

¿Debe esperar Ana?

¿Debe bloquearse Pedro?

La respuesta está en:

```
MVCC
```

---

# ¿Qué significa MVCC?

MVCC son las siglas de:

```
Multi-Version

Concurrency

Control
```

En español:

```
Control de concurrencia mediante múltiples versiones.
```

La idea principal es sencilla.

En lugar de bloquear constantemente los datos.

PostgreSQL mantiene distintas versiones de una misma fila.

---

# Un ejemplo

Imaginemos una tabla.

| id | saldo |
|----|-------|
|1|1000|

Ana ejecuta:

```sql
SELECT saldo
FROM cuentas
WHERE id = 1;
```

En ese mismo instante.

Pedro ejecuta:

```sql
UPDATE cuentas
SET saldo = 800
WHERE id = 1;
```

---

# ¿Qué ocurriría sin MVCC?

En algunos gestores antiguos.

Ana quedaría bloqueada.

O bien.

Pedro tendría que esperar.

```
Ana

↓

Leyendo...

↓

Pedro espera
```

Muchos usuarios simultáneos implican muchos bloqueos.

Y eso reduce el rendimiento.

---

# ¿Qué hace PostgreSQL?

PostgreSQL crea una nueva versión de la fila.

Podemos imaginarlo así.

Versión antigua:

| id | saldo |
|----|-------|
|1|1000|

↓

Pedro modifica.

↓

Versión nueva:

| id | saldo |
|----|-------|
|1|800|

Durante un tiempo conviven ambas versiones.

---

# ¿Qué ve cada usuario?

Ana había comenzado su consulta antes.

Por tanto.

Continúa viendo:

```
1000 €
```

Pedro.

En cambio.

Trabaja sobre la nueva versión.

```
800 €
```

Ambos pueden continuar sin interferirse.

---

# ¿Se duplican realmente las filas?

Conceptualmente sí.

Físicamente PostgreSQL almacena distintas versiones de una misma fila.

Cada una contiene información sobre:

- Cuándo fue creada.
- Cuándo dejó de ser válida.
- Qué transacción la creó.

El usuario no ve esos detalles.

El gestor los utiliza internamente.

---

# ¿Qué ventajas aporta?

Gracias a MVCC:

- Las lecturas normalmente no bloquean las escrituras.
- Las escrituras afectan mucho menos a las lecturas.
- Se reduce el número de bloqueos.
- Aumenta el rendimiento cuando muchos usuarios trabajan simultáneamente.

Es uno de los grandes puntos fuertes de PostgreSQL.

---

# Snapshot

Cuando comienza una transacción.

PostgreSQL crea una especie de fotografía del estado de la base de datos.

```
Inicio

↓

Snapshot
```

Durante esa transacción.

El usuario verá esa imagen coherente.

Aunque otros usuarios continúen modificando información.

---

# ¿Por qué es importante?

Supongamos una consulta larga.

```sql
SELECT ...
FROM parcelas
JOIN cultivos
JOIN municipios
...
```

Puede tardar varios segundos.

Mientras tanto.

Otros usuarios siguen trabajando.

Gracias a MVCC.

La consulta continuará viendo un estado consistente de la información.

No observará datos "a medio modificar".

---

# ¿Qué ocurre con las versiones antiguas?

No permanecen para siempre.

Cuando ya no son necesarias.

PostgreSQL las elimina automáticamente.

Este proceso recibe el nombre de:

```
VACUUM
```

Más adelante estudiaremos esta herramienta.

Su función consiste en recuperar espacio ocupado por versiones antiguas.

---

# MVCC y ACID

Observa la relación.

En el capítulo anterior estudiamos:

```
ACID
```

Ahora podemos entender mejor la propiedad:

```
Isolation
```

Cada transacción trabaja sobre una visión consistente de los datos.

Sin interferir con las demás.

MVCC es uno de los mecanismos que permiten conseguir ese aislamiento.

---

# Niveles de aislamiento

PostgreSQL soporta distintos niveles.

Los más conocidos son:

- Read Committed.
- Repeatable Read.
- Serializable.

Cada uno determina qué cambios pueden observar las transacciones.

En la práctica.

El nivel por defecto suele ser:

```
Read Committed
```

En este capítulo basta con conocer su existencia.

---

# ¿MVCC elimina todos los bloqueos?

No.

Algunas operaciones siguen necesitando bloqueos.

Por ejemplo:

- Modificaciones simultáneas sobre la misma fila.
- Cambios en la estructura de una tabla (`ALTER TABLE`).
- Determinadas operaciones administrativas.

Sin embargo.

Gracias a MVCC.

La cantidad de bloqueos es mucho menor que en otros modelos tradicionales.

---

# Errores frecuentes

### ❌ Pensar que MVCC evita completamente los bloqueos

No.

Reduce considerablemente su uso.

Pero determinadas operaciones siguen necesitando sincronización.

---

### ❌ Pensar que todos los usuarios ven siempre la información más reciente

Cada transacción observa una versión coherente de los datos.

No necesariamente la última modificación realizada por otros usuarios.

---

### ❌ Confundir MVCC con las copias de seguridad

Las distintas versiones de las filas son un mecanismo interno de control de concurrencia.

No sustituyen a una estrategia de copias de seguridad.

---

### ❌ Pensar que las versiones antiguas permanecen indefinidamente

PostgreSQL elimina automáticamente las versiones que ya no son necesarias mediante procesos de mantenimiento como `VACUUM`.

---

# Buenas prácticas

- Mantener transacciones cortas para evitar conservar versiones antiguas durante demasiado tiempo.
- Ejecutar periódicamente `VACUUM` (o permitir que `autovacuum` lo haga automáticamente).
- Elegir el nivel de aislamiento adecuado según las necesidades de la aplicación.
- Comprender que MVCC mejora el rendimiento, pero no elimina por completo la necesidad de bloqueos.

---

# Conceptos importantes

Antes de continuar debes recordar:

- MVCC significa **Multi-Version Concurrency Control**.
- PostgreSQL mantiene varias versiones de una fila para permitir un acceso concurrente más eficiente.
- Las lecturas y las escrituras pueden ejecutarse simultáneamente en muchos casos sin bloquearse entre sí.
- Cada transacción trabaja sobre una visión consistente (*snapshot*) de la base de datos.
- Las versiones antiguas se eliminan posteriormente mediante procesos como `VACUUM`.
- MVCC es uno de los pilares que permiten a PostgreSQL ofrecer un excelente rendimiento en entornos con muchos usuarios concurrentes.

---

# WAL (Write-Ahead Logging)

En el capítulo anterior estudiamos las transacciones y las propiedades ACID.

Una de ellas era:

```
Durability

(Durabilidad)
```

Es decir:

Una vez ejecutado un:

```sql
COMMIT;
```

Los cambios deben permanecer almacenados incluso si ocurre un fallo del sistema.

Pero...

¿Cómo consigue PostgreSQL esta garantía?

La respuesta está en:

```
WAL
```

---

# ¿Qué significa WAL?

WAL son las siglas de:

```
Write-Ahead Logging
```

En español:

```
Registro previo de escritura.
```

La idea es muy sencilla.

Antes de modificar físicamente la base de datos.

PostgreSQL escribe la operación en un registro especial.

Solo después actualiza los archivos de datos.

---

# Un ejemplo

Supongamos la siguiente operación.

```sql
UPDATE cuentas
SET saldo = saldo - 200
WHERE id = 1;
```

Podríamos pensar que PostgreSQL modifica inmediatamente la tabla.

En realidad.

Hace algo parecido a esto.

```
Escribir en WAL

↓

Modificar la tabla
```

Siempre en ese orden.

---

# ¿Por qué?

Imaginemos la siguiente situación.

```
Actualizar saldo

↓

Se va la luz
```

Si el cambio solo existiera en memoria.

La información podría perderse.

Gracias al WAL.

La operación ya había quedado registrada.

Tras reiniciar el servidor.

PostgreSQL puede recuperar el estado correcto.

---

# Podemos imaginar el WAL como...

Un cuaderno de bitácora.

Cada operación importante queda anotada.

```
09:15

↓

UPDATE cuentas

↓

Saldo: 1000 → 800
```

```
09:16

↓

INSERT ciudadano

↓

ID: 325
```

```
09:17

↓

DELETE parcela

↓

ID: 91
```

Si ocurre un fallo.

El gestor consulta ese diario.

Y reconstruye las operaciones pendientes.

---

# Flujo de una transacción

Podemos resumir el proceso así.

```
Aplicación

↓

BEGIN

↓

UPDATE

↓

Escribir en WAL

↓

COMMIT

↓

Actualizar archivos de datos
```

El WAL actúa como una red de seguridad.

---

# Recuperación tras un fallo

Supongamos.

```
BEGIN

↓

UPDATE

↓

COMMIT

↓

💥 Corte eléctrico
```

Cuando PostgreSQL vuelve a iniciarse.

Lee los archivos WAL.

Y determina:

- Qué transacciones estaban confirmadas.
- Qué cambios aún no habían llegado a los archivos de datos.

Después completa automáticamente la recuperación.

Este proceso recibe el nombre de:

```
Crash Recovery
```

---

# ¿Dónde se almacena?

Los registros WAL se guardan en archivos especiales dentro del directorio de datos de PostgreSQL.

El administrador normalmente no necesita modificarlos manualmente.

El propio servidor los crea, utiliza y elimina cuando corresponde.

---

# WAL y copias de seguridad

Una de las grandes ventajas del WAL.

Es que permite realizar copias de seguridad muy avanzadas.

Por ejemplo:

- Recuperar la base de datos hasta un instante concreto.
- Restaurar únicamente las operaciones realizadas después de una copia completa.
- Implementar replicación entre servidores.

Estas técnicas se estudian habitualmente en administración avanzada de PostgreSQL.

---

# WAL y replicación

PostgreSQL también utiliza el WAL para enviar cambios a servidores secundarios.

Visualmente.

```
Servidor principal

↓

Archivos WAL

↓

Servidor réplica
```

La réplica reproduce exactamente las mismas operaciones.

Por ello mantiene una copia prácticamente idéntica de la base de datos principal.

---

# ¿El WAL contiene toda la base de datos?

No.

Contiene únicamente la información necesaria para reconstruir los cambios realizados.

Es parecido al historial de modificaciones de un documento.

No almacena una copia completa tras cada operación.

Esto reduce considerablemente el espacio necesario.

---

# ¿Por qué no escribir directamente en la tabla?

Porque hacerlo sería más arriesgado.

Si el sistema fallara durante la escritura.

La información podría quedar inconsistente.

El WAL garantiza que siempre exista un registro fiable de las operaciones realizadas.

---

# WAL y rendimiento

Puede parecer que escribir dos veces ralentizaría el sistema.

Sin embargo.

El WAL está diseñado para escribirse de forma muy eficiente.

Además.

Permite optimizar posteriormente la escritura definitiva sobre los archivos de datos.

Por ello.

El impacto sobre el rendimiento es muy reducido.

---

# Relación entre WAL y MVCC

En el apartado anterior vimos:

```
MVCC
```

Ahora podemos distinguir claramente ambos conceptos.

```
MVCC

↓

Gestiona la concurrencia.
```

```
WAL

↓

Garantiza la recuperación y la durabilidad.
```

Trabajan conjuntamente.

Pero resuelven problemas diferentes.

---

# Errores frecuentes

### ❌ Pensar que el WAL es una copia de seguridad

No.

El WAL ayuda a recuperar la información.

Pero no sustituye una estrategia de copias de seguridad.

---

### ❌ Creer que PostgreSQL modifica primero los archivos de datos

Hace justamente lo contrario.

Primero registra la operación en el WAL.

Después actualiza los datos.

---

### ❌ Pensar que WAL y MVCC son el mismo mecanismo

No.

MVCC gestiona el acceso concurrente.

WAL registra las modificaciones para garantizar la recuperación.

---

### ❌ Eliminar manualmente los archivos WAL

Nunca debe hacerse.

El propio PostgreSQL administra automáticamente estos archivos.

Su eliminación podría comprometer la recuperación de la base de datos.

---

# Buenas prácticas

- Permitir que PostgreSQL gestione automáticamente los archivos WAL.
- Supervisar el espacio ocupado por el directorio de datos.
- Combinar el WAL con una política adecuada de copias de seguridad.
- Comprender que WAL y MVCC son mecanismos complementarios.

---

# Conceptos importantes

Antes de continuar debes recordar:

- WAL significa **Write-Ahead Logging**.
- PostgreSQL registra primero las modificaciones en el WAL antes de escribirlas en los archivos de datos.
- Este mecanismo garantiza la **durabilidad** de las transacciones.
- Tras un fallo del sistema, PostgreSQL utiliza el WAL para recuperar un estado consistente.
- El WAL también constituye la base de funcionalidades como la replicación y la recuperación hasta un instante concreto (*Point-in-Time Recovery*).
- WAL y MVCC cumplen funciones distintas: el primero protege la información frente a fallos, mientras que el segundo gestiona la concurrencia.

---

# Copias de seguridad y restauración

Una base de datos contiene información que, en muchos casos, resulta crítica.

Por ejemplo:

- Ciudadanos.
- Parcelas agrícolas.
- Expedientes.
- Facturas.
- Cartografía.

Si esa información se pierde.

Las consecuencias pueden ser muy graves.

Por ello.

Toda instalación PostgreSQL debe disponer de una estrategia de copias de seguridad.

---

# ¿Qué es una copia de seguridad?

Una copia de seguridad (Backup) es una copia de la información almacenada en la base de datos.

Su objetivo es permitir la recuperación de los datos en caso de:

- Fallo del hardware.
- Error humano.
- Corrupción de archivos.
- Ataques informáticos.
- Eliminación accidental de información.

---

# Tipos de copias de seguridad

En PostgreSQL existen dos grandes categorías.

## Copias lógicas

Exportan el contenido de la base de datos.

Generan:

- Sentencias SQL.

o

- Un formato propio de PostgreSQL.

Permiten restaurar posteriormente la información.

---

## Copias físicas

Copian directamente los archivos que forman la base de datos.

Incluyen:

- Archivos de datos.
- WAL.
- Configuración.

Se utilizan principalmente para administración avanzada y alta disponibilidad.

---

# pg_dump

La herramienta más utilizada para realizar copias lógicas es:

```text
pg_dump
```

Su función consiste en exportar una base de datos.

Ejemplo:

```bash
pg_dump -U postgres imida > imida.sql
```

Resultado:

```
imida.sql
```

Este archivo contiene todas las instrucciones necesarias para reconstruir la base de datos.

---

# ¿Qué contiene el archivo?

Podemos abrir:

```
imida.sql
```

Y encontraremos instrucciones como:

```sql
CREATE TABLE ciudadanos (...);

INSERT INTO ciudadanos (...);

CREATE INDEX ...;

ALTER TABLE ...;
```

Es decir.

La estructura y los datos.

---

# Restaurar una copia SQL

Si disponemos de un archivo:

```
imida.sql
```

Podemos restaurarlo utilizando:

```bash
psql -U postgres imida < imida.sql
```

El cliente `psql` ejecutará automáticamente todas las instrucciones contenidas en el archivo.

---

# Formato personalizado

`pg_dump` también puede generar un formato propio de PostgreSQL.

Ejemplo:

```bash
pg_dump -Fc -U postgres imida -f imida.backup
```

Parámetro:

```
-Fc
```

Significa:

```
Custom Format
```

Este formato suele ser el más recomendable para copias de seguridad completas.

---

# ¿Por qué utilizar el formato personalizado?

Presenta varias ventajas.

- Comprime la información.
- Permite restauraciones selectivas.
- Resulta más flexible.
- Puede utilizarse con `pg_restore`.

Es el formato más habitual en entornos profesionales.

---

# pg_restore

Las copias realizadas en formato personalizado se restauran mediante:

```text
pg_restore
```

Ejemplo:

```bash
pg_restore \
-U postgres \
-d imida \
imida.backup
```

La base de datos recuperará la información contenida en la copia.

---

# ¿Cuándo utilizar pg_dump?

`pg_dump` resulta adecuado cuando queremos:

- Copiar una base de datos.
- Migrar información.
- Realizar copias periódicas.
- Exportar datos antes de una actualización importante.

Es una herramienta muy utilizada por administradores.

---

# ¿Qué ocurre si el servidor está en funcionamiento?

Una ventaja muy importante.

`pg_dump` puede ejecutarse mientras PostgreSQL continúa atendiendo conexiones.

No es necesario detener el servidor.

Esto permite realizar copias sin interrumpir el servicio.

---

# Copias completas e incrementales

Las copias pueden clasificarse según la información que almacenan.

## Copia completa

Contiene toda la base de datos.

Es sencilla de restaurar.

Pero ocupa más espacio.

---

## Copia incremental

Solo almacena los cambios realizados desde la copia anterior.

Reduce el espacio necesario.

Su restauración suele resultar más compleja.

En PostgreSQL estas estrategias suelen apoyarse en los archivos WAL.

---

# Recuperación hasta un instante concreto (PITR)

Una de las funcionalidades más potentes de PostgreSQL.

```
Point-In-Time Recovery

(PITR)
```

Permite restaurar una base de datos exactamente hasta un momento determinado.

Por ejemplo:

```
10:15

↓

Copia completa
```

```
11:42

↓

Se elimina una tabla accidentalmente
```

```
11:41:59

↓

Restauración
```

Gracias al WAL.

PostgreSQL puede reconstruir el estado exacto de la base de datos justo antes del error.

---

# Relación entre WAL y PITR

Recordemos.

En el apartado anterior vimos:

```
WAL
```

Ahora entendemos una de sus aplicaciones.

```
Copia completa

+

Archivos WAL

↓

PITR
```

La combinación de ambos mecanismos permite recuperar la información con gran precisión.

---

# Automatización

Las copias de seguridad suelen ejecutarse automáticamente mediante herramientas del sistema operativo.

En Linux.

Es habitual utilizar:

```
cron
```

Para programar:

- Copias diarias.
- Copias semanales.
- Rotación de copias antiguas.

La automatización reduce el riesgo de olvidos.

---

# Errores frecuentes

### ❌ Pensar que una copia de seguridad nunca debe comprobarse

Una copia no verificada puede resultar inútil.

Conviene realizar restauraciones de prueba periódicamente.

---

### ❌ Conservar todas las copias en el mismo servidor

Si el servidor falla completamente.

También podrían perderse las copias.

Es recomendable almacenarlas en ubicaciones independientes.

---

### ❌ Confundir pg_dump con una copia física

`pg_dump` genera una copia lógica.

No copia directamente los archivos internos del servidor.

---

### ❌ Creer que PITR funciona sin WAL

El WAL es imprescindible para reconstruir la base de datos hasta un instante concreto.

---

# Buenas prácticas

- Programar copias automáticas.
- Conservar varias generaciones de copias.
- Almacenar las copias fuera del servidor principal.
- Verificar periódicamente que las copias pueden restaurarse correctamente.
- Combinar copias completas con los archivos WAL cuando se requieran estrategias avanzadas de recuperación.

---

# Conceptos importantes

Antes de continuar debes recordar:

- Las copias de seguridad permiten recuperar la información ante fallos o errores.
- PostgreSQL distingue entre copias lógicas y copias físicas.
- `pg_dump` crea copias lógicas de una base de datos.
- `pg_restore` restaura copias en formato personalizado.
- El formato `-Fc` ofrece mayor flexibilidad y suele ser el más utilizado en entornos profesionales.
- Los archivos WAL permiten implementar la recuperación hasta un instante concreto (*Point-In-Time Recovery* o PITR).
- Una estrategia de copias de seguridad solo es eficaz si las restauraciones se prueban periódicamente.

---

# Mantenimiento y optimización

En apartados anteriores aprendimos que PostgreSQL utiliza:

- MVCC.
- WAL.
- Transacciones.

Gracias a MVCC.

Cuando una fila se modifica.

La versión antigua no desaparece inmediatamente.

Entonces surge una pregunta.

¿Quién elimina esas versiones antiguas?

La respuesta es:

```
VACUUM
```

---

# Un ejemplo

Imaginemos una biblioteca.

Cada cierto tiempo.

Se retiran libros antiguos.

Sin embargo.

Las estanterías continúan ocupando espacio.

Hasta que alguien reorganiza la biblioteca.

```
Libros antiguos

↓

Espacio ocupado

↓

Reorganización

↓

Espacio reutilizable
```

Eso mismo ocurre en PostgreSQL.

---

# ¿Por qué ocurre?

Supongamos una tabla.

```
Ciudadanos
```

Contiene:

| id | nombre |
|----|---------|
|1|Pedro|

Actualizamos:

```sql
UPDATE ciudadanos
SET nombre='Pedro García'
WHERE id=1;
```

Gracias a MVCC.

La versión antigua permanece almacenada durante un tiempo.

Cuando deja de ser necesaria.

Debe eliminarse.

---

# VACUUM

La herramienta encargada de esta tarea es:

```sql
VACUUM;
```

Su función consiste en:

- Localizar versiones antiguas.
- Liberar espacio reutilizable.
- Mantener el rendimiento.

Ejemplo:

```sql
VACUUM ciudadanos;
```

---

# ¿Qué hace realmente VACUUM?

Es importante entenderlo.

```
NO
```

reduce automáticamente el tamaño del archivo de la tabla.

Lo que hace es:

Marcar el espacio como disponible para reutilizarlo en futuras operaciones.

Por ello.

La tabla continúa teniendo aproximadamente el mismo tamaño.

Pero PostgreSQL podrá aprovechar ese espacio más adelante.

---

# VACUUM FULL

Existe otra variante.

```sql
VACUUM FULL;
```

En este caso.

Sí reorganiza completamente la tabla.

Y libera físicamente el espacio ocupado.

Ventajas:

- Reduce el tamaño del archivo.

Inconvenientes:

- Requiere más tiempo.
- Necesita bloquear la tabla durante la operación.

Por ello.

Debe utilizarse únicamente cuando resulte necesario.

---

# Diferencias

| VACUUM | VACUUM FULL |
|----------|-------------|
| Libera espacio reutilizable | Reduce físicamente el tamaño de la tabla |
| No bloquea completamente la tabla | Requiere bloqueo exclusivo |
| Muy frecuente | Uso ocasional |
| Más rápido | Más lento |

---

# ANALYZE

Además del espacio.

PostgreSQL necesita conocer cómo están distribuidos los datos.

Para ello utiliza:

```sql
ANALYZE;
```

Ejemplo:

```sql
ANALYZE ciudadanos;
```

Esta operación genera estadísticas sobre:

- Número de registros.
- Distribución de valores.
- Selectividad de columnas.

Estas estadísticas ayudan al optimizador.

---

# ¿Para qué sirven las estadísticas?

Supongamos esta consulta.

```sql
SELECT *
FROM ciudadanos
WHERE municipio='Murcia';
```

El optimizador necesita decidir.

¿Utilizo un índice?

¿O recorro toda la tabla?

Para tomar esa decisión.

Consulta las estadísticas generadas por:

```
ANALYZE
```

---

# EXPLAIN

Ya vimos brevemente esta herramienta.

```sql
EXPLAIN
SELECT *
FROM ciudadanos
WHERE dni='12345678A';
```

Su objetivo es mostrar:

- Cómo ejecutará PostgreSQL la consulta.
- Qué índices utilizará.
- Qué coste estima.

Resulta fundamental para optimizar consultas lentas.

---

# EXPLAIN ANALYZE

Existe una versión más completa.

```sql
EXPLAIN ANALYZE
SELECT *
FROM ciudadanos
WHERE dni='12345678A';
```

En este caso.

PostgreSQL:

- Ejecuta realmente la consulta.
- Muestra tiempos reales.
- Indica cuántas filas procesó.

Es una herramienta muy utilizada para analizar el rendimiento.

---

# autovacuum

Sería poco práctico ejecutar:

```sql
VACUUM;
```

manualmente todos los días.

Por ello PostgreSQL incorpora un proceso automático.

```
autovacuum
```

Su función consiste en:

- Ejecutar VACUUM cuando resulta necesario.
- Actualizar estadísticas mediante ANALYZE.
- Mantener la base de datos en buen estado.

En la mayoría de instalaciones modernas.

Permanece activado por defecto.

---

# ¿Por qué es tan importante?

Si autovacuum permaneciera desactivado durante mucho tiempo.

Podrían aparecer:

- Acumulación de versiones antiguas.
- Pérdida de rendimiento.
- Crecimiento innecesario del espacio ocupado.
- Estadísticas desactualizadas.

Todo ello dificultaría el trabajo del optimizador.

---

# Mantenimiento rutinario

Un administrador PostgreSQL suele supervisar periódicamente aspectos como:

- Espacio ocupado.
- Actividad de autovacuum.
- Consultas lentas.
- Índices poco utilizados.
- Estadísticas del sistema.

La mayor parte del mantenimiento diario consiste precisamente en comprobar que estos procesos funcionan correctamente.

---

# Optimización básica

Cuando una consulta resulta lenta.

Conviene seguir un proceso ordenado.

1.

```
EXPLAIN
```

↓

¿Cómo piensa ejecutarla PostgreSQL?

---

2.

```
EXPLAIN ANALYZE
```

↓

¿Cuánto tarda realmente?

---

3.

Comprobar:

- Índices.
- Estadísticas.
- Plan de ejecución.

---

4.

Modificar la consulta o crear nuevos índices si resulta necesario.

---

# Errores frecuentes

### ❌ Ejecutar VACUUM FULL de forma habitual

En la mayoría de situaciones.

`VACUUM` es suficiente.

`VACUUM FULL` debe reservarse para casos concretos.

---

### ❌ Desactivar autovacuum

Salvo situaciones muy específicas.

No resulta recomendable.

Es una pieza fundamental del mantenimiento automático de PostgreSQL.

---

### ❌ Pensar que ANALYZE mejora directamente el rendimiento

ANALYZE no acelera las consultas por sí mismo.

Proporciona información al optimizador para que elija mejores planes de ejecución.

---

### ❌ Interpretar EXPLAIN como un error

EXPLAIN no modifica los datos.

Simplemente muestra cómo PostgreSQL ejecutaría una consulta.

---

# Buenas prácticas

- Mantener `autovacuum` habilitado.
- Utilizar `EXPLAIN` antes de optimizar consultas.
- Revisar periódicamente las estadísticas de la base de datos.
- Crear índices únicamente cuando aporten una mejora real.
- Ejecutar `VACUUM FULL` solo cuando exista una necesidad justificada.

---

# Conceptos importantes

Antes de continuar debes recordar:

- `VACUUM` elimina versiones antiguas creadas por MVCC y libera espacio para su reutilización.
- `VACUUM FULL` reorganiza completamente la tabla y reduce su tamaño físico.
- `ANALYZE` actualiza las estadísticas utilizadas por el optimizador.
- `EXPLAIN` muestra el plan de ejecución previsto de una consulta.
- `EXPLAIN ANALYZE` ejecuta la consulta y proporciona información real sobre su rendimiento.
- `autovacuum` automatiza gran parte del mantenimiento rutinario de PostgreSQL y constituye uno de los mecanismos más importantes para conservar un buen rendimiento.

# Roles y permisos

PostgreSQL utiliza un modelo basado en roles.

Todo usuario es un rol.

Pero no todos los roles pueden iniciar sesión.

Los privilegios más habituales son:

- LOGIN
- SUPERUSER
- CREATEDB
- CREATEROLE
- REPLICATION

Los permisos sobre los objetos se administran mediante:

```sql
GRANT
```

y

```sql
REVOKE
```

---

# MVCC

MVCC significa:

```
Multi-Version Concurrency Control
```

Permite que varios usuarios trabajen simultáneamente.

Cada transacción observa una versión consistente de los datos.

Gracias a este mecanismo:

- Las lecturas apenas bloquean las escrituras.
- Se reduce considerablemente la contención entre usuarios.
- PostgreSQL ofrece un excelente rendimiento en entornos concurrentes.

---

# WAL

WAL significa:

```
Write-Ahead Logging
```

Antes de modificar físicamente los datos.

PostgreSQL registra primero la operación en un archivo WAL.

Este mecanismo permite:

- Recuperar la información tras un fallo.
- Implementar replicación.
- Realizar recuperación hasta un instante concreto (PITR).

Constituye uno de los pilares de la propiedad **Durability** del modelo ACID.

---
