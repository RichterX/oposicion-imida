# 3.6 PostGIS

## 3.6.1 Introducción a PostGIS y conceptos fundamentales

PostGIS es una extensión de PostgreSQL que añade capacidades para almacenar, consultar y analizar información espacial y geográfica.

Mientras PostgreSQL trabaja con datos tradicionales como:

```text
INTEGER
VARCHAR
DATE
BOOLEAN
...
```

PostGIS permite trabajar además con:

```text
Puntos
Líneas
Polígonos
Multipuntos
Multilíneas
Multipolígonos
Geometrías
Geografías
```

Esto permite realizar consultas como:

```text
¿Qué municipios contienen este punto?

¿Qué carreteras intersectan este polígono?

¿Qué tiendas están a menos de 500 metros?

¿Cuál es la distancia entre dos puntos?

¿Qué edificios están dentro de una determinada zona?

¿Qué calles atraviesan un barrio?
```

PostGIS convierte PostgreSQL en una base de datos espacial.

---

# ¿Qué significa GIS?

GIS significa:

```text
Geographic Information System
```

En español:

```text
Sistema de Información Geográfica
```

Un GIS permite almacenar, consultar, analizar y representar información relacionada con una ubicación geográfica.

Por ejemplo:

```text
Ciudad
   │
   ├── Nombre
   ├── Población
   ├── Provincia
   └── Geometría
```

La geometría permite saber dónde está situada espacialmente la ciudad.

---

# Datos tradicionales frente a datos espaciales

Una base de datos tradicional puede almacenar:

```text
id
nombre
población
provincia
```

Por ejemplo:

```text
1 | Murcia | 470000 | Murcia
```

Pero un sistema GIS puede almacenar además:

```text
geom
```

representando la posición o forma de la entidad.

Por ejemplo:

```text
Ciudad
   │
   ├── id
   ├── nombre
   ├── población
   └── geom
```

---

# ¿Qué añade PostGIS?

PostGIS añade tres capacidades fundamentales:

```text
Tipos de datos espaciales
        +
Índices espaciales
        +
Funciones espaciales
```

Estas tres piezas permiten almacenar y consultar información geográfica eficientemente. :contentReference[oaicite:1]{index=1}

---

# Tipos espaciales

PostGIS permite representar diferentes tipos de objetos espaciales.

Los más importantes son:

```text
POINT
LINESTRING
POLYGON
MULTIPOINT
MULTILINESTRING
MULTIPOLYGON
GEOMETRYCOLLECTION
```

---

# POINT

Un `POINT` representa una posición.

Por ejemplo:

```text
Ubicación de una persona
Ubicación de una tienda
Ubicación de una estación
Ubicación de un árbol
```

Conceptualmente:

```text
        Y
        ↑
        │
        │      ●
        │
        │
        └────────────→ X
```

Un punto tiene coordenadas:

```text
X
Y
```

Por ejemplo:

```text
(-1.1307, 37.9922)
```

---

# LINESTRING

Un `LINESTRING` representa una línea formada por una secuencia de puntos.

Puede utilizarse para representar:

```text
Carretera
Río
Ruta
Línea de transporte
Frontera
```

Conceptualmente:

```text
●────────●
         │
         ●────────●
```

Una línea contiene múltiples coordenadas.

---

# POLYGON

Un `POLYGON` representa una superficie cerrada.

Puede utilizarse para:

```text
Municipio
Parcela
Lago
Edificio
Zona administrativa
```

Conceptualmente:

```text
       ●────────●
      /          \
     /            \
    ●              ●
     \            /
      \          /
       ●────────●
```

La geometría debe formar un anillo cerrado.

---

# MULTIPOINT

Representa múltiples puntos dentro de una única geometría.

Por ejemplo:

```text
Ubicaciones de varias estaciones
```

Conceptualmente:

```text
●       ●

     ●

           ●      ●
```

---

# MULTILINESTRING

Representa varias líneas dentro de una única geometría.

Por ejemplo:

```text
Red de carreteras
```

Puede contener varias líneas independientes.

---

# MULTIPOLYGON

Representa varios polígonos.

Es especialmente útil para entidades formadas por varias áreas separadas.

Por ejemplo:

```text
Archipiélago
```

puede representarse como:

```text
MULTIPOLYGON
│
├── Isla 1
├── Isla 2
├── Isla 3
└── Isla 4
```

---

# GEOMETRYCOLLECTION

Una `GEOMETRYCOLLECTION` puede contener diferentes tipos de geometrías.

Por ejemplo:

```text
POINT
+
LINESTRING
+
POLYGON
```

dentro de una misma colección.

Es un tipo más general y menos habitual en aplicaciones GIS sencillas.

---

# Modelo espacial básico

Podemos pensar en PostGIS así:

```text
Entidad
   │
   ├── Datos tradicionales
   │
   │     nombre
   │     población
   │     tipo
   │
   └── Datos espaciales
         │
         └── geom
```

Por ejemplo:

```text
Estación de tren
│
├── id = 10
├── nombre = "Murcia"
└── geom = POINT(...)
```

---

# Geometry

El tipo:

```text
geometry
```

es uno de los tipos espaciales fundamentales de PostGIS.

Representa objetos espaciales utilizando un sistema de coordenadas planar.

Es decir:

```text
Plano cartesiano
```

con coordenadas:

```text
X
Y
```

Las operaciones sobre `geometry` utilizan las unidades del sistema de referencia espacial asociado. :contentReference[oaicite:2]{index=2}

---

# Geography

PostGIS también proporciona:

```text
geography
```

Este tipo representa objetos espaciales utilizando sistemas de coordenadas geodésicos, es decir, teniendo en cuenta la forma de la Tierra mediante un modelo elipsoidal. :contentReference[oaicite:3]{index=3}

Conceptualmente:

```text
GEOMETRY
↓
Plano

GEOGRAPHY
↓
Tierra
```

Esta diferencia es fundamental.

---

# Geometry vs Geography

Podemos hacer una primera aproximación:

| Geometry | Geography |
|----------|-----------|
| Coordenadas planares | Coordenadas geodésicas |
| Trabaja sobre un plano | Trabaja sobre la Tierra |
| Muy flexible | Más orientado a datos geográficos |
| Suele ser más rápido | Puede ser más costoso |
| Requiere elegir correctamente el CRS | Más sencillo para datos globales |

La documentación oficial recomienda considerar `geometry` cuando los datos pueden representarse adecuadamente en un sistema de coordenadas planar, mientras que `geography` resulta especialmente conveniente para datos de extensión global o cuando no se quiere trabajar directamente con sistemas proyectados. :contentReference[oaicite:4]{index=4}

---

# Ejemplo intuitivo

Supongamos dos ciudades:

```text
Madrid
Murcia
```

Si utilizamos:

```text
geometry
```

podemos trabajar sobre un plano proyectado.

Si utilizamos:

```text
geography
```

podemos realizar determinados cálculos teniendo en cuenta la superficie terrestre.

Esto es especialmente importante para:

```text
Distancias
Áreas
Longitudes
```

---

# Coordenadas

Una geometría espacial utiliza coordenadas.

Un punto puede representarse como:

```text
POINT(X Y)
```

Por ejemplo:

```text
POINT(-1.1307 37.9922)
```

Aquí:

```text
X = -1.1307
Y = 37.9922
```

En un sistema geográfico convencional:

```text
X → longitud
Y → latitud
```

Por tanto:

```text
LONGITUD
↓
X

LATITUD
↓
Y
```

---

# Longitud y latitud

La longitud representa la posición:

```text
Este ↔ Oeste
```

La latitud representa:

```text
Norte ↔ Sur
```

Por ejemplo:

```text
Longitud = -1.1307
Latitud  = 37.9922
```

Representaría una posición aproximadamente en la zona de Murcia.

---

# Coordenadas no son suficientes

Un par:

```text
X = 100
Y = 200
```

no tiene significado geográfico por sí mismo.

Necesitamos saber:

```text
¿En qué sistema de coordenadas?
```

Aquí aparece uno de los conceptos más importantes de PostGIS:

```text
SRID
```

---

# SRID

SRID significa:

```text
Spatial Reference System Identifier
```

Es un identificador que indica el sistema de referencia espacial utilizado por una geometría.

Por ejemplo:

```text
EPSG:4326
```

es uno de los sistemas de referencia más conocidos.

---

# EPSG:4326

El código:

```text
4326
```

identifica el sistema:

```text
WGS 84
```

Es ampliamente utilizado para coordenadas geográficas expresadas como:

```text
longitud
latitud
```

Por ejemplo:

```text
POINT(-1.1307 37.9922)
```

puede utilizarse con:

```text
SRID 4326
```

---

# EPSG

EPSG hace referencia al conjunto de códigos utilizados para identificar sistemas de referencia y transformaciones.

Por ello encontramos frecuentemente:

```text
EPSG:4326
```

o:

```text
SRID=4326
```

---

# Asignar SRID

Podemos crear una geometría especificando su SRID.

Por ejemplo:

```sql
ST_SetSRID(
    ST_MakePoint(-1.1307, 37.9922),
    4326
)
```

Aquí:

```text
ST_MakePoint
↓
crea el punto

ST_SetSRID
↓
asocia el SRID
```

---

# ST_SetSRID

Una idea muy importante:

```text
ST_SetSRID
```

**no transforma las coordenadas**.

Simplemente establece o cambia la referencia espacial asociada a la geometría.

Es decir:

```text
Coordenadas
     +
SRID
     ↓
Geometría identificada
```

No debemos confundirlo con:

```text
ST_Transform
```

---

# ST_Transform

`ST_Transform` transforma las coordenadas de una geometría de un sistema de referencia a otro.

Por ejemplo:

```sql
ST_Transform(
    geom,
    25830
)
```

transforma la geometría al SRID:

```text
25830
```

Por tanto:

```text
ST_SetSRID
↓
Asigna referencia

ST_Transform
↓
Transforma coordenadas
```

Esta diferencia es **muy importante**.

---

# Ejemplo conceptual

Tenemos:

```text
POINT(-1.13 37.99)
```

y sabemos que está en:

```text
EPSG:4326
```

Podemos:

```sql
ST_SetSRID(
    geom,
    4326
)
```

para indicar que esas coordenadas corresponden a ese sistema.

Pero si queremos convertirlas a otro sistema:

```sql
ST_Transform(
    geom,
    25830
)
```

las coordenadas resultantes cambiarán.

---

# WKT

WKT significa:

```text
Well-Known Text
```

Es una representación textual estándar de geometrías.

Ejemplos:

```text
POINT(10 20)
```

```text
LINESTRING(0 0, 10 10, 20 0)
```

```text
POLYGON(
    (0 0, 10 0, 10 10, 0 10, 0 0)
)
```

---

# POINT en WKT

```text
POINT(10 20)
```

significa:

```text
X = 10
Y = 20
```

---

# LINESTRING en WKT

```text
LINESTRING(
    0 0,
    10 10,
    20 0
)
```

representa una línea formada por:

```text
Punto 1
↓
Punto 2
↓
Punto 3
```

---

# POLYGON en WKT

Ejemplo:

```text
POLYGON(
    (
        0 0,
        10 0,
        10 10,
        0 10,
        0 0
    )
)
```

Observa que el primer punto:

```text
0 0
```

aparece nuevamente al final.

Esto cierra el anillo.

---

# WKB

También existe:

```text
WKB
```

que significa:

```text
Well-Known Binary
```

Mientras:

```text
WKT
↓
Representación textual

WKB
↓
Representación binaria
```

WKT resulta especialmente cómodo para ejemplos, depuración y lectura humana.

---

# EWKT

PostGIS también puede utilizar una variante extendida:

```text
EWKT
```

que permite incluir información como el SRID.

Por ejemplo:

```text
SRID=4326;POINT(-1.1307 37.9922)
```

Aquí tenemos:

```text
SRID
+
WKT
```

---

# Crear geometrías

PostGIS proporciona funciones para crear geometrías.

Una de ellas es:

```text
ST_GeomFromText
```

Por ejemplo:

```sql
ST_GeomFromText(
    'POINT(-1.1307 37.9922)',
    4326
)
```

Esto crea una geometría a partir de WKT y especifica su SRID.

---

# ST_MakePoint

También podemos crear un punto directamente:

```sql
ST_MakePoint(
    -1.1307,
    37.9922
)
```

Podemos combinarlo con:

```sql
ST_SetSRID
```

```sql
ST_SetSRID(
    ST_MakePoint(
        -1.1307,
        37.9922
    ),
    4326
)
```

---

# Consultar geometrías

PostGIS proporciona funciones para obtener información de una geometría.

Por ejemplo:

```text
ST_GeometryType
ST_SRID
ST_X
ST_Y
ST_NPoints
ST_Area
ST_Length
```

---

# ST_SRID

Devuelve el SRID asociado.

Ejemplo:

```sql
SELECT ST_SRID(geom)
FROM lugares;
```

Resultado:

```text
4326
```

---

# ST_X y ST_Y

Para un punto:

```sql
ST_X(geom)
```

obtiene la coordenada X.

Mientras:

```sql
ST_Y(geom)
```

obtiene la coordenada Y.

Conceptualmente:

```text
ST_X
↓
Longitud / X

ST_Y
↓
Latitud / Y
```

cuando trabajamos con un sistema geográfico habitual.

---

# ST_AsText

Convierte una geometría a WKT.

Ejemplo:

```sql
SELECT ST_AsText(geom)
FROM lugares;
```

Resultado:

```text
POINT(-1.1307 37.9922)
```

---

# ST_AsEWKT

Permite obtener una representación textual extendida incluyendo información como el SRID.

Ejemplo conceptual:

```sql
SELECT ST_AsEWKT(geom)
FROM lugares;
```

Resultado:

```text
SRID=4326;POINT(-1.1307 37.9922)
```

---

# Geometría y atributos

Una tabla espacial puede tener:

```sql
CREATE TABLE ciudades (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100),
    poblacion INTEGER,
    geom geometry(Point, 4326)
);
```

Aquí:

```text
id
nombre
poblacion
```

son atributos tradicionales.

Mientras:

```text
geom
```

es espacial.

---

# geometry(Point, 4326)

Esta definición:

```text
geometry(Point, 4326)
```

indica que:

```text
Tipo de geometría = POINT
SRID = 4326
```

Esto permite restringir el contenido de la columna.

---

# Insertar un punto

Por ejemplo:

```sql
INSERT INTO ciudades (
    nombre,
    poblacion,
    geom
)
VALUES (
    'Murcia',
    470000,
    ST_SetSRID(
        ST_MakePoint(
            -1.1307,
            37.9922
        ),
        4326
    )
);
```

---

# Consultar una ciudad

Podemos utilizar:

```sql
SELECT
    nombre,
    ST_AsText(geom)
FROM ciudades;
```

# Operaciones espaciales

Aquí empieza la verdadera potencia de PostGIS.

Podemos preguntar por relaciones espaciales:

```text
¿A intersecta B?

¿A contiene B?

¿A está dentro de B?

¿A toca B?

¿A se solapa con B?

¿A está cerca de B?
```

PostGIS proporciona funciones espaciales específicas para responder estas preguntas. :contentReference[oaicite:5]{index=5}

---

# ST_Intersects

Comprueba si dos geometrías tienen algún punto en común.

Ejemplo:

```sql
ST_Intersects(
    geom_a,
    geom_b
)
```

Devuelve:

```text
TRUE
```

si intersectan.

O:

```text
FALSE
```

si no intersectan. :contentReference[oaicite:6]{index=6}

---

# ST_Contains

Comprueba si una geometría contiene a otra.

```sql
ST_Contains(
    geom_a,
    geom_b
)
```

Conceptualmente:

```text
A
┌──────────────┐
│              │
│      ● B     │
│              │
└──────────────┘

A contiene B
```

---

# ST_Within

Es la relación inversa conceptual de:

```text
ST_Contains
```

Por ejemplo:

```sql
ST_Within(
    geom_b,
    geom_a
)
```

indica que B está dentro de A.

Podemos memorizar:

```text
ST_Contains(A, B)
       ⇅
ST_Within(B, A)
```

---

# ST_Distance

Calcula la distancia entre dos geometrías.

```sql
ST_Distance(
    geom_a,
    geom_b
)
```

La unidad depende del tipo de datos y sistema de referencia utilizado.

Por ello debemos prestar mucha atención a:

```text
geometry
geography
SRID
unidades
```

---

# ST_DWithin

Permite comprobar si dos objetos están a una distancia determinada o menor.

Por ejemplo:

```sql
ST_DWithin(
    geom_a,
    geom_b,
    500
)
```

conceptualmente significa:

```text
¿A y B están a 500 unidades o menos?
```

Es especialmente útil para consultas del tipo:

```text
¿Qué restaurantes están a menos de 500 metros?
```

La función también puede beneficiarse de índices espaciales cuando están disponibles. :contentReference[oaicite:7]{index=7}

---

# Spatial Join

Una de las operaciones más interesantes es combinar tablas mediante relaciones espaciales.

Por ejemplo:

```text
Ciudades
    +
Provincias
```

podemos preguntar:

```text
¿Qué provincia contiene cada ciudad?
```

Conceptualmente:

```sql
SELECT
    ciudad.nombre,
    provincia.nombre
FROM ciudades ciudad
JOIN provincias provincia
    ON ST_Contains(
        provincia.geom,
        ciudad.geom
    );
```

Esto se denomina:

```text
Spatial Join
```

---

# Índices espaciales

Las consultas espaciales pueden ser costosas.

Imaginemos:

```text
1.000.000 edificios
```

y queremos saber:

```text
¿Qué edificios están dentro de esta zona?
```

Comprobar geométricamente cada edificio puede resultar muy costoso.

PostGIS proporciona índices espaciales para acelerar estas consultas. :contentReference[oaicite:8]{index=8}

---

# GiST

El índice espacial habitual en PostGIS se crea utilizando:

```text
GiST
```

Ejemplo:

```sql
CREATE INDEX idx_ciudades_geom
ON ciudades
USING GIST (geom);
```

La cláusula importante es:

```text
USING GIST
```

Sin ella estaríamos creando un índice B-tree normal, que no es el índice espacial adecuado para una columna de geometría. :contentReference[oaicite:9]{index=9}

---

# Bounding Box

Los índices espaciales utilizan conceptos como:

```text
Bounding Box
```

Una bounding box es el rectángulo mínimo alineado con los ejes que contiene una geometría.

Por ejemplo:

```text
        ┌───────────────────┐
        │                   │
        │    ╱──────╲       │
        │   ╱        ╲      │
        │   ╲        ╱      │
        │    ╲──────╱       │
        │                   │
        └───────────────────┘
```

El rectángulo es la:

```text
Bounding Box
```

---

# ¿Por qué utilizar Bounding Boxes?

Comparar rectángulos es mucho más barato que comparar geometrías complejas.

Por ejemplo:

```text
Consulta compleja
      ↓
¿Estas dos geometrías realmente intersectan?
```

puede reducirse inicialmente a:

```text
¿Sus bounding boxes podrían intersectar?
```

Si ni siquiera las cajas se cruzan:

```text
No pueden intersectar.
```

Esto permite descartar rápidamente muchos candidatos.

---

# &&

PostGIS proporciona el operador:

```text
&&
```

para comprobar si las bounding boxes se superponen.

Ejemplo:

```sql
WHERE geom && otra_geom
```

Esto puede utilizar el índice espacial.

---

# Índices + funciones espaciales

Muchas funciones espaciales comunes incorporan automáticamente una comparación basada en bounding boxes y pueden aprovechar un índice espacial.

Entre ellas:

```text
ST_Intersects
ST_Contains
ST_Within
ST_DWithin
```

entre otras. :contentReference[oaicite:10]{index=10}

Por tanto, normalmente no necesitamos añadir manualmente `&&` a una consulta que ya utiliza una función espacial consciente del índice.

# Conceptos fundamentales

Antes de continuar debes recordar:

- PostGIS es una extensión de PostgreSQL para trabajar con datos espaciales.
- Un GIS permite almacenar y analizar información relacionada con posiciones geográficas.
- PostGIS proporciona tipos espaciales, funciones espaciales e índices espaciales.
- `POINT` representa una posición.
- `LINESTRING` representa una línea.
- `POLYGON` representa una superficie cerrada.
- `MULTI*` permite representar múltiples geometrías del mismo tipo.
- `geometry` representa datos mediante un sistema de coordenadas planar.
- `geography` representa datos mediante sistemas geodésicos asociados a la Tierra.
- Un `SRID` identifica el sistema de referencia espacial.
- `EPSG:4326` corresponde a WGS 84.
- `WKT` representa geometrías en formato textual.
- `WKB` representa geometrías en formato binario.
- `ST_SetSRID` asigna un SRID, pero no transforma las coordenadas.
- `ST_Transform` transforma las coordenadas a otro sistema de referencia.
- `ST_Intersects` comprueba si dos geometrías tienen algún punto en común.
- `ST_Contains` comprueba si una geometría contiene otra.
- `ST_Within` comprueba si una geometría está dentro de otra.
- `ST_Distance` calcula distancias.
- `ST_DWithin` permite realizar consultas basadas en una distancia máxima.
- Los índices espaciales permiten acelerar consultas espaciales.
- En PostGIS, los índices espaciales se crean habitualmente mediante `USING GIST`.
- Las bounding boxes permiten realizar filtros espaciales rápidos.

# 3.6 PostGIS - Creación y manipulación de geometrías

## 3.6.2 Creación y manipulación de geometrías

Una vez comprendidos los conceptos fundamentales de PostGIS, podemos comenzar a trabajar directamente con geometrías desde SQL.

Las operaciones básicas que debemos dominar son:

- Crear geometrías.
- Insertarlas en tablas.
- Consultarlas.
- Convertirlas a texto.
- Obtener sus coordenadas.
- Obtener su SRID.
- Modificar su sistema de referencia.
- Extraer partes de geometrías.
- Construir geometrías a partir de otras.

# Crear una geometría desde WKT

Una de las formas más sencillas de crear una geometría es utilizar:

```text
ST_GeomFromText()
```

Ejemplo:

```sql
SELECT ST_GeomFromText(
    'POINT(-1.1307 37.9922)',
    4326
);
```

La función recibe:

```text
WKT
+
SRID
```

y devuelve una geometría PostGIS.

---

# ST_GeomFromText

Sintaxis:

```sql
ST_GeomFromText(
    wkt,
    srid
)
```

Por ejemplo:

```sql
ST_GeomFromText(
    'POINT(10 20)',
    4326
)
```

crea:

```text
POINT(10 20)
```

con:

```text
SRID = 4326
```

---

# ST_MakePoint

Para crear puntos también podemos utilizar:

```text
ST_MakePoint()
```

Ejemplo:

```sql
SELECT ST_MakePoint(
    -1.1307,
    37.9922
);
```

Esto crea un punto con:

```text
X = -1.1307
Y = 37.9922
```

---

# ST_MakePoint + ST_SetSRID

Una combinación muy habitual es:

```sql
ST_SetSRID(
    ST_MakePoint(
        -1.1307,
        37.9922
    ),
    4326
)
```

Podemos interpretarlo como:

```text
ST_MakePoint
      ↓
Crear punto

ST_SetSRID
      ↓
Asignar sistema de referencia
```

# Crear un punto con WKT frente a ST_MakePoint

Podemos hacer:

```sql

```

o:

```sql

    ST_MakePoint(
        -1.1307,
        37.9922
    ),
    4326

```

Ambos permiten obtener una geometría equivalente.

# Diferencias fundamentales

## ST_SetSRID vs ST_Transform

```text
ST_SetSRID
↓
Asigna información espacial

ST_Transform
↓
Transforma coordenadas
```

---

## ST_Dimension vs ST_CoordDim

```text
ST_Dimension
↓
Dimensión topológica

POINT      → 0
LINESTRING → 1
POLYGON    → 2
```

Mientras:

```text
ST_CoordDim
↓
Número de coordenadas

X Y     → 2
X Y Z   → 3
```

---

## ST_Collect vs ST_Union

```text
ST_Collect
↓
Agrupa geometrías

ST_Union
↓
Combina geométricamente
```

`ST_Union` puede disolver fronteras entre geometrías que se superponen o tocan, mientras que `ST_Collect` simplemente agrupa las geometrías sin realizar esa operación geométrica de unión.

---

# Errores frecuentes

### ❌ Confundir longitud y latitud

En una representación habitual:

```text
X = longitud
Y = latitud
```

---

### ❌ Asignar un SRID incorrecto

Las coordenadas y el SRID deben corresponder al mismo sistema de referencia.

---

### ❌ Utilizar ST_SetSRID para transformar coordenadas

Incorrecto conceptualmente.

```text
ST_SetSRID
≠
ST_Transform
```

---

### ❌ Olvidar cerrar un POLYGON

El primer punto debe coincidir con el último punto del anillo.

---

### ❌ Confundir ST_Dimension con ST_CoordDim

```text
ST_Dimension
↓
Dimensión topológica

ST_CoordDim
↓
Dimensión de coordenadas
```

---

### ❌ Suponer que todas las geometrías son válidas

Los datos espaciales pueden contener geometrías inválidas.

---

### ❌ Simplificar sin tener en cuenta la tolerancia

Una tolerancia excesiva puede modificar significativamente una geometría.

# 3.6 PostGIS - Relaciones espaciales y mediciones

## 3.6.3 Relaciones espaciales y mediciones

Una de las principales capacidades de PostGIS es permitir realizar consultas basadas en la relación espacial entre diferentes geometrías.

Podemos preguntar:

```text
¿Dos geometrías se intersectan?

¿Una geometría contiene a otra?

¿Una geometría está dentro de otra?

¿Dos geometrías están separadas?

¿Cuál es el área de un polígono?
```

Las funciones espaciales permiten expresar estas preguntas directamente en SQL.

# Relaciones espaciales

Las relaciones espaciales describen cómo se relacionan dos geometrías entre sí.

Entre las más importantes encontramos:

```text
ST_Intersects
ST_Contains
ST_Within
ST_Touches
ST_Crosses
ST_Overlaps
ST_Disjoint
```

Estas funciones devuelven normalmente un resultado booleano:

```text
TRUE
```

o:

```text
FALSE
```

---

# ST_Intersects

La función:

```text
ST_Intersects()
```

comprueba si dos geometrías tienen al menos un punto en común.

Sintaxis:

```sql
ST_Intersects(
    geom_a,
    geom_b
)
```

Ejemplo:

```sql
SELECT ST_Intersects(
    ciudad.geom,
    provincia.geom
)
FROM ciudades ciudad,
     provincias provincia;
```

---

# Ejemplo conceptual

Dos geometrías:

```text
A
┌───────────────┐
│               │
│      ┌────────┼───────┐
│      │        │       │
│      │   B    │       │
└──────┼────────┘       │
       │                │
       └────────────────┘
```

Tienen una zona en común.

Por tanto:

```text
ST_Intersects(A, B)
```

devuelve:

```text
TRUE
```

---

# Intersectar no significa contener

Una geometría puede intersectar a otra sin contenerla.

Por ejemplo:

```text
A
┌─────────────┐
│             │
│      ───────┼──── B
│             │
└─────────────┘
```

Existe intersección.

Pero:

```text
A
```

no contiene completamente a:

```text
B
```

Por tanto:

```text
ST_Intersects(A, B)
```

puede ser:

```text
TRUE
```

mientras:

```text
ST_Contains(A, B)
```

sea:

```text
FALSE
```

---

# ST_Contains

La función:

```text
ST_Contains()
```

comprueba si una geometría contiene a otra.

Sintaxis:

```sql
ST_Contains(
    geom_a,
    geom_b
)
```

Conceptualmente:

```text
A
┌────────────────────┐
│                    │
│       ┌──────┐     │
│       │  B   │     │
│       └──────┘     │
│                    │
└────────────────────┘
```

Aquí:

```text
A contiene B
```

Por tanto:

```sql
ST_Contains(A, B)
```

puede devolver:

```text
TRUE
```

---

# Dirección de la relación

El orden de los parámetros es importante.

Por ejemplo:

```sql
ST_Contains(
    provincia.geom,
    ciudad.geom
)
```

significa:

```text
¿La provincia contiene a la ciudad?
```

Mientras:

```sql
ST_Contains(
    ciudad.geom,
    provincia.geom
)
```

pregunta:

```text
¿La ciudad contiene a la provincia?
```

Son preguntas diferentes.

---

# ST_Within

`ST_Within()` representa conceptualmente la relación inversa.

```sql
ST_Within(
    geom_a,
    geom_b
)
```

pregunta si:

```text
A está dentro de B
```

Por ejemplo:

```sql
ST_Within(
    ciudad.geom,
    provincia.geom
)
```

pregunta:

```text
¿La ciudad está dentro de la provincia?
```

---

# Contains y Within

Podemos recordar:

```text
ST_Contains(A, B)
```

significa:

```text
A contiene B
```

Mientras:

```text
ST_Within(B, A)
```

significa:

```text
B está dentro de A
```

Por tanto:

```text
ST_Contains(A, B)
        ⇅
ST_Within(B, A)
```

---

# Ejemplo realista

Supongamos:

```text
municipios
```

y:

```text
provincias
```

Podemos buscar qué provincia contiene cada municipio:

```sql
SELECT
    municipio.nombre,
    provincia.nombre
FROM municipios municipio
JOIN provincias provincia
    ON ST_Contains(
        provincia.geom,
        municipio.geom
    );
```

Estamos realizando un:

```text
Spatial Join
```

---

# Spatial Join

Un `Spatial Join` es una combinación de tablas basada en una relación espacial.

En SQL tradicional podemos hacer:

```sql
ON ciudad.provincia_id = provincia.id
```

En PostGIS podemos hacer:

```sql
ON ST_Contains(
    provincia.geom,
    ciudad.geom
)
```

Es decir:

```text
JOIN
+
Relación espacial
```

---

# ST_Touches

`ST_Touches()` comprueba si dos geometrías tienen puntos en común pero sus interiores no se intersectan.

Conceptualmente:

```text
┌───────────┬───────────┐
│           │           │
│     A     │     B     │
│           │           │
└───────────┴───────────┘
```

A y B comparten una frontera.

Pero no ocupan el mismo espacio interior.

Entonces:

```sql
ST_Touches(A, B)
```

puede devolver:

```text
TRUE
```

---

# Ejemplo geográfico

Dos municipios vecinos pueden:

```text
Compartir frontera
```

sin que uno contenga al otro.

Podemos comprobar esa relación mediante:

```sql
ST_Touches(
    municipio_a.geom,
    municipio_b.geom
)
```

---

# ST_Crosses

`ST_Crosses()` permite comprobar determinadas relaciones en las que una geometría atraviesa otra.

Un ejemplo clásico:

```text
Carretera
───────────────
       │
       │
       │
       │
```

Una línea puede cruzar un polígono.

Por ejemplo:

```text
       │
       │
┌──────┼──────┐
│      │      │
│      │      │
└──────┼──────┘
       │
       │
```

La línea atraviesa el polígono.

---

# ST_Overlaps

`ST_Overlaps()` comprueba si dos geometrías del mismo tipo tienen una zona común pero ninguna contiene completamente a la otra.

Conceptualmente:

```text
       A
    ┌───────┐
    │       │
    │       │
    └───┐   │
        │   │
        │   │ B
        │   │
        └───┘
```

Existe una zona compartida.

Pero:

```text
A no contiene B
B no contiene A
```

---

# ST_Disjoint

`ST_Disjoint()` representa la situación opuesta a la intersección.

Comprueba si dos geometrías no tienen ningún punto en común.

Ejemplo:

```text
┌───────┐          ┌───────┐
│   A   │          │   B   │
└───────┘          └───────┘
```

No existe contacto.

Por tanto:

```sql
ST_Disjoint(A, B)
```

devuelve:

```text
TRUE
```

---

# Disjoint frente a Intersects

Estas relaciones son conceptualmente opuestas:

```text
ST_Intersects
↓
Existe algún punto en común
```

```text
ST_Disjoint
↓
No existe ningún punto en común
```

---

# Resumen de relaciones

| Función | Pregunta |
|---|---|
| `ST_Intersects` | ¿Tienen algún punto en común? |
| `ST_Contains` | ¿A contiene B? |
| `ST_Within` | ¿A está dentro de B? |
| `ST_Touches` | ¿Se tocan sin intersectar sus interiores? |
| `ST_Crosses` | ¿Una geometría atraviesa a la otra? |
| `ST_Overlaps` | ¿Se solapan parcialmente? |
| `ST_Disjoint` | ¿No tienen ningún punto en común? |

# Relaciones y matrices DE-9IM

PostGIS utiliza conceptos topológicos relacionados con:

```text
DE-9IM
```

que significa:

```text
Dimensionally Extended Nine-Intersection Model
```

Este modelo describe las relaciones entre:

```text
Interior
Boundary
Exterior
```

de dos geometrías.

No es necesario memorizar toda la matriz para un nivel introductorio, pero es importante conocer que muchas relaciones espaciales se basan en este modelo.

---

# ST_Relate

Para realizar comprobaciones topológicas más específicas podemos utilizar:

```text
ST_Relate()
```

Ejemplo:

```sql
ST_Relate(
    geom_a,
    geom_b
)
```

Devuelve una representación de la relación topológica entre ambas geometrías.

---

# ST_RelateMatch

También existe:

```text
ST_RelateMatch()
```

que permite comprobar si una relación DE-9IM coincide con un patrón determinado.

Es una herramienta más avanzada para expresar relaciones topológicas específicas.

# Mediciones espaciales

Además de relaciones booleanas:

```text
TRUE / FALSE
```

PostGIS permite realizar mediciones.

Las principales funciones son:

```text
ST_Distance
ST_DWithin
ST_Length
ST_Area
ST_Perimeter
```

---

# ST_Distance

Calcula la distancia entre dos geometrías.

Ejemplo:

```sql
SELECT ST_Distance(
    geom_a,
    geom_b
);
```

La interpretación de la unidad depende del tipo espacial y del sistema de referencia.

Por eso debemos conocer:

```text
geometry
+
SRID
```

o:

```text
geography
```

---

# Distancia con geometry

Si utilizamos:

```text
geometry
```

la distancia se expresa en las unidades del sistema de coordenadas utilizado.

Por ejemplo, si el sistema utiliza:

```text
metros
```

la distancia estará en metros.

Si utiliza:

```text
grados
```

la distancia estará expresada en esas unidades.

Por eso utilizar directamente:

```text
EPSG:4326
```

con `geometry` requiere especial cuidado al interpretar distancias.

---

# Distancia con geography

Con:

```text
geography
```

PostGIS trabaja con coordenadas geodésicas y puede proporcionar distancias expresadas en metros.

Ejemplo conceptual:

```sql
ST_Distance(
    punto_a::geography,
    punto_b::geography
)
```

Esto resulta especialmente útil para consultas geográficas basadas en distancias reales sobre la Tierra.

---

# ST_DWithin

`ST_DWithin()` permite comprobar si dos geometrías se encuentran dentro de una distancia determinada.

Sintaxis:

```sql
ST_DWithin(
    geom_a,
    geom_b,
    distancia
)
```

Ejemplo:

```sql
ST_DWithin(
    tienda.geom,
    usuario.geom,
    500
)
```

Pregunta:

```text
¿La tienda está a 500 unidades o menos del usuario?
```

---

# Ejemplo de búsqueda por proximidad

Supongamos:

```text
tiendas
```

y queremos encontrar las que estén a menos de:

```text
500 metros
```

de un punto.

Podemos hacer:

```sql
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom::geography,
    ST_SetSRID(
        ST_MakePoint(
            -1.1307,
            37.9922
        ),
        4326
    )::geography,
    500
);
```

La conversión a:

```text
geography
```

permite expresar la distancia en metros en este caso.

---

# ST_DWithin frente a ST_Distance

No debemos confundir:

```text
ST_Distance
```

con:

```text
ST_DWithin
```

### ST_Distance

Devuelve:

```text
distancia
```

Ejemplo:

```text
350.72
```

### ST_DWithin

Devuelve:

```text
TRUE / FALSE
```

Ejemplo:

```text
TRUE
```

si están dentro de la distancia especificada.

---

# ST_DWithin y rendimiento

Una ventaja importante de `ST_DWithin()` es que está diseñada para funcionar bien con índices espaciales.

Por ello suele ser apropiada para consultas del tipo:

```text
Dame todos los objetos que estén a menos de X metros.
```

Por ejemplo:

```sql
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom::geography,
    punto::geography,
    500
);
```

---

# ST_Length

Calcula la longitud de una geometría lineal.

Ejemplo:

```sql
SELECT ST_Length(geom)
FROM carreteras;
```

Para un `LINESTRING`:

```text
●────────●────────●
```

`ST_Length()` calcula la longitud de la línea.

---

# Longitud y unidades

Al igual que ocurre con:

```text
ST_Distance
```

debemos prestar atención al sistema espacial.

Con:

```text
geometry
```

la unidad depende del sistema de referencia.

Con:

```text
geography
```

la medición se expresa en metros.

---

# ST_Perimeter

Calcula el perímetro de una geometría superficial.

Por ejemplo:

```sql
SELECT ST_Perimeter(geom)
FROM municipios;
```

Si tenemos un polígono:

```text
┌────────────┐
│            │
│            │
└────────────┘
```

el perímetro corresponde a la longitud de su borde.

---

# ST_Area

Calcula el área de una geometría superficial.

Ejemplo:

```sql
SELECT ST_Area(geom)
FROM parcelas;
```

---

# Área y unidades

Con:

```text
geometry
```

el área se expresa en unidades cuadradas del sistema de referencia.

Por ejemplo:

```text
metros
```

produce:

```text
metros cuadrados
```

Mientras un sistema expresado en grados no produce directamente un área útil en metros cuadrados.

Con:

```text
geography
```

PostGIS puede proporcionar áreas en metros cuadrados.

---

# Ejemplo de área

Supongamos una parcela:

```text
100 m × 50 m
```

Su área sería:

```text
5000 m²
```

En PostGIS:

```sql
SELECT ST_Area(geom)
FROM parcelas;
```

si la geometría está correctamente definida en un sistema cuyas unidades sean metros.

---

# Transformar antes de medir

Una estrategia habitual es transformar una geometría geográfica a un sistema proyectado adecuado antes de realizar determinadas mediciones.

Por ejemplo:

```sql
ST_Area(
    ST_Transform(
        geom,
        25830
    )
)
```

La idea es:

```text
EPSG:4326
   ↓
ST_Transform
   ↓
Sistema proyectado
   ↓
ST_Area
```

El sistema de referencia elegido debe ser apropiado para la zona y el tipo de cálculo.

---

# Geometry vs Geography en mediciones

Podemos recordar:

```text
GEOMETRY
↓
Unidades del CRS

GEOGRAPHY
↓
Mediciones geodésicas
```

Por ello no debemos mirar simplemente:

```text
ST_Distance(...)
```

y asumir automáticamente:

```text
metros
```

Hay que conocer el tipo de datos y el sistema de referencia.

---

# Ejemplo: ciudades cercanas

Supongamos:

```text
ciudades
```

con:

```text
geom geometry(Point, 4326)
```

Podemos obtener ciudades cercanas a un punto:

```sql
SELECT
    nombre
FROM ciudades
WHERE ST_DWithin(
    geom::geography,
    ST_SetSRID(
        ST_MakePoint(
            -1.1307,
            37.9922
        ),
        4326
    )::geography,
    10000
);
```

Aquí:

```text
10000
```

representa:

```text
10 kilómetros
```

porque estamos trabajando con:

```text
geography
```

y la distancia se expresa en metros.

---

# Ordenar por distancia

También podemos calcular la distancia:

```sql
SELECT
    nombre,
    ST_Distance(
        geom::geography,
        punto::geography
    ) AS distancia
FROM ciudades
ORDER BY distancia;
```

Obtendremos algo parecido a:

```text
Ciudad A | 1200
Ciudad B | 4300
Ciudad C | 8700
```

---

# KNN y <->

PostGIS permite realizar búsquedas de vecinos cercanos utilizando el operador:

```text
<->
```

Por ejemplo:

```sql
SELECT
    nombre
FROM ciudades
ORDER BY geom <-> punto
LIMIT 5;
```

Conceptualmente:

```text
Punto de referencia
        ↓
┌──────────────────────┐
│ Vecino 1             │
│ Vecino 2             │
│ Vecino 3             │
│ Vecino 4             │
│ Vecino 5             │
└──────────────────────┘
```

Este patrón es conocido como:

```text
K-Nearest Neighbors
```

o:

```text
KNN
```

y puede aprovechar índices espaciales adecuados.

---

# Consultas de proximidad

Podemos clasificar las consultas de proximidad en:

```text
¿Está dentro de X?
        ↓
ST_DWithin

¿Cuál es la distancia exacta?
        ↓
ST_Distance

¿Cuáles son los K más cercanos?
        ↓
KNN / <->
```

# Ejemplo: restaurantes cercanos

Supongamos:

```text
restaurantes
```

y un punto:

```text
ubicación_usuario
```

Podemos buscar:

```sql
SELECT
    nombre
FROM restaurantes
WHERE ST_DWithin(
    geom::geography,

```

Resultado:

```text

```

Podemos ordenar por distancia:


# Spatial Join con distancia

También podemos realizar joins basados en proximidad.

Por ejemplo:

```text
Tiendas
+
Clientes
```

y queremos encontrar clientes a menos de:

```text

```

Podemos utilizar:

```sql
SELECT
    tienda.nombre,
    cliente.nombre
FROM tiendas tienda
JOIN clientes cliente
    ON ST_DWithin(
        tienda.geom::geography,
        cliente.geom::geography,

```

Esto permite construir relaciones espaciales basadas en proximidad.

# Buenas prácticas

- Elegir correctamente entre `geometry` y `geography`.
- Utilizar un SRID adecuado.
- No asumir que todas las distancias están expresadas en metros.
- Crear índices espaciales para grandes volúmenes de datos.
- Utilizar `ST_DWithin()` para consultas de proximidad.
- Utilizar `ST_Distance()` cuando necesitamos la distancia exacta.
- Utilizar `ST_Contains()` y `ST_Within()` según la dirección de la relación.
- Diferenciar funciones que devuelven booleanos de las que devuelven geometrías.
- Utilizar `EXPLAIN ANALYZE` para estudiar consultas complejas.
- Evitar transformar innecesariamente grandes cantidades de geometrías durante cada consulta si el modelo de datos puede diseñarse mejor.

# Conceptos importantes

Antes de continuar debes recordar:

- `ST_Intersects()` devuelve si dos geometrías tienen algún punto en común.
- `ST_Contains()` comprueba si una geometría contiene a otra.
- `ST_Within()` comprueba si una geometría está dentro de otra.
- `ST_Touches()` comprueba si dos geometrías se tocan sin intersectar sus interiores.
- `ST_Crosses()` comprueba determinadas relaciones de cruce.
- `ST_Overlaps()` comprueba solapamientos parciales.
- `ST_Disjoint()` comprueba que dos geometrías no tengan puntos en común.
- `ST_Distance()` calcula una distancia.
- `ST_DWithin()` comprueba si dos geometrías están dentro de una distancia determinada.
- `ST_Length()` calcula la longitud de geometrías lineales.
- `ST_Area()` calcula el área de geometrías superficiales.
- `ST_Perimeter()` calcula el perímetro.
- `ST_Intersection()` devuelve la geometría de intersección.
- `ST_Difference()` devuelve la diferencia espacial.
- `ST_SymDifference()` devuelve la diferencia simétrica.
- `ST_Union()` combina geométricamente varias geometrías.
- `geometry` utiliza las unidades de su sistema de referencia.
- `geography` permite realizar mediciones geodésicas y expresar distancias en metros.
- El operador `<->` permite realizar consultas de vecinos más cercanos.
- Las consultas espaciales pueden combinarse mediante `JOIN`.
- Los índices espaciales son fundamentales para trabajar con grandes volúmenes de geometrías.

# 3.6 PostGIS - Sistemas de referencia, SRID y transformaciones

## 3.6.4 Sistemas de referencia espacial y transformaciones

Para trabajar correctamente con información geográfica no basta con conocer las coordenadas.

Por ejemplo:

```text
X = -1.13
Y = 37.99
```

Estas coordenadas no tienen significado suficiente por sí solas.

Necesitamos saber:

```text
¿En qué sistema de referencia están expresadas?
```

Aquí aparecen conceptos fundamentales:

```text
CRS
SRID
EPSG
Datum
Proyección
Transformación
```

---

# CRS

CRS significa:

```text
Coordinate Reference System
```

En español:

```text
Sistema de Referencia de Coordenadas
```

Un CRS define cómo se representan las posiciones en un sistema de coordenadas.

Incluye información como:

- Sistema de coordenadas.
- Datum.
- Unidades.
- Proyección, cuando corresponde.
- Parámetros necesarios para interpretar las coordenadas.

---

# ¿Por qué necesitamos un CRS?

Imaginemos:

```text
POINT(500000 4200000)
```

Sin información adicional no sabemos exactamente qué significa.

Podría representar coordenadas:

```text
en metros
```

dentro de un sistema proyectado.

O podríamos estar ante otro sistema completamente diferente.

El CRS proporciona el contexto necesario.

---

# SRID

El:

```text
SRID
```

es un identificador numérico asociado al sistema de referencia espacial.

Por ejemplo:

```text
4326
```

identifica:

```text
WGS 84
```

Por ello podemos encontrar:

```text
SRID=4326
```

o:

```text
EPSG:4326
```

---

# EPSG

EPSG proporciona códigos estandarizados para identificar sistemas de referencia y otros objetos relacionados con coordenadas.

Por ejemplo:

```text
EPSG:4326
```

corresponde a:

```text
WGS 84
```

Otro ejemplo habitual en España es:

```text
EPSG:25830
```

que corresponde a:

```text
ETRS89 / UTM zone 30N
```

---

# EPSG:4326

Es uno de los CRS más conocidos.

Representa:

```text
WGS 84
```

y utiliza coordenadas geográficas.

Normalmente encontramos:

```text
X = longitud
Y = latitud
```

Por ejemplo:

```text
POINT(-1.1307 37.9922)
```

---

# EPSG:25830

Un CRS muy relevante en España es:

```text
EPSG:25830
```

que corresponde a:

```text
ETRS89 / UTM zone 30N
```

Es un sistema proyectado.

Sus coordenadas se expresan en:

```text
metros
```

Esto lo hace especialmente útil para determinadas operaciones métricas en la zona correspondiente.

---

# Geographic vs Projected CRS

Podemos distinguir dos grandes conceptos:

```text
Geographic CRS
```

y:

```text
Projected CRS
```

---

# Geographic CRS

Un sistema geográfico utiliza coordenadas angulares.

Normalmente:

```text
longitud
latitud
```

Por ejemplo:

```text
-1.1307
37.9922
```

Las unidades suelen ser:

```text
grados
```

---

# Projected CRS

Un sistema proyectado transforma la superficie terrestre a un plano.

Las coordenadas suelen expresarse en:

```text
metros
```

Por ejemplo:

```text
X = 660000
Y = 4200000
```

dependiendo del sistema utilizado.

---

# El problema de los grados

Supongamos:

```text
EPSG:4326
```

y:

```text
POINT(-1.13 37.99)
```

Si hacemos determinadas operaciones con `geometry`, las coordenadas están expresadas en grados.

Por tanto:

```sql
ST_Distance(
    geom_a,
    geom_b
)
```

no debe interpretarse automáticamente como:

```text
metros
```

La unidad depende del CRS.

---

# Por qué importa para las distancias

La Tierra no es un plano.

La distancia correspondiente a:

```text
1 grado
```

no es una distancia constante en todas las direcciones y posiciones.

Por eso trabajar directamente con coordenadas geográficas como si fueran:

```text
X / Y en metros
```

puede producir resultados incorrectos o poco útiles.

---

# Geography como alternativa

El tipo:

```text
geography
```

permite realizar determinados cálculos directamente sobre coordenadas geográficas teniendo en cuenta la naturaleza geodésica de los datos.

Por ejemplo:

```sql
ST_Distance(
    geom::geography,
    otra_geom::geography
)
```

permite obtener una distancia expresada en metros.

---

# Geometry + sistema proyectado

Otra estrategia consiste en utilizar:

```text
geometry
```

con un CRS proyectado adecuado.

Por ejemplo:

```text
EPSG:25830
```

y realizar las mediciones sobre coordenadas expresadas en metros.

Conceptualmente:

```text
EPSG:4326
      ↓
ST_Transform
      ↓
EPSG:25830
      ↓
Geometry
      ↓
ST_Distance / ST_Area
```

---

# ST_SetSRID

Una de las funciones más importantes:

```text
ST_SetSRID()
```

permite establecer el SRID asociado a una geometría.

Ejemplo:

```sql
ST_SetSRID(
    ST_MakePoint(
        -1.1307,
        37.9922
    ),
    4326
)
```

---

# Lo que NO hace ST_SetSRID

Esto es fundamental:

```text
ST_SetSRID
```

**no transforma las coordenadas.**

Si tenemos:

```text
POINT(-1.13 37.99)
```

y hacemos:

```sql
ST_SetSRID(
    geom,
    25830
)
```

las coordenadas siguen siendo:

```text
-1.13
37.99
```

Lo único que hemos cambiado es la referencia asociada.

Esto puede hacer que la geometría pase a estar mal interpretada.

---

# ST_Transform

Para transformar realmente las coordenadas utilizamos:

```text
ST_Transform()
```

Ejemplo:

```sql
ST_Transform(
    geom,
    25830
)
```

Aquí sí se produce una transformación de las coordenadas.

Conceptualmente:

```text
Antes

POINT(
    longitud
    latitud
)

EPSG:4326
```

↓

```text
ST_Transform(..., 25830)
```

↓

```text
Después

POINT(
    X
    Y
)

EPSG:25830
```

---

# Diferencia fundamental

Memorizar:

```text
ST_SetSRID
↓
"Estas coordenadas pertenecen a este CRS"
```

Mientras:

```text
ST_Transform
↓
"Convierte estas coordenadas al nuevo CRS"
```

---

# Ejemplo completo

Tenemos:

```sql
geom geometry(Point, 4326)
```

y queremos transformar el punto:

```sql
ST_Transform(
    geom,
    25830
)
```

El resultado:

```text
CRS original
    ↓
EPSG:4326

ST_Transform
    ↓

CRS destino
    ↓
EPSG:25830
```

Las coordenadas cambiarán.

---

# Transformación bidireccional

Podemos transformar:

```text
4326 → 25830
```

y también:

```text
25830 → 4326
```

Por ejemplo:

```sql
ST_Transform(
    geom,
    4326
)
```

si la geometría original utiliza:

```text
25830
```

---

# ST_Transform requiere conocer el CRS original

Para transformar correctamente una geometría:

```text
PostGIS necesita saber
        ↓
CRS origen
```

Por ejemplo:

```text
geom
SRID = 4326
```

Entonces:

```sql
ST_Transform(
    geom,
    25830
)
```

puede realizar la transformación:

```text
4326 → 25830
```

---

# Error conceptual frecuente

Incorrecto:

```sql
ST_SetSRID(
    geom,
    25830
)
```

si las coordenadas originales están realmente en:

```text
4326
```

Esto no convierte las coordenadas.

Simplemente les asigna otro SRID.

---

# Flujo correcto

Si tenemos coordenadas en:

```text
4326
```

y queremos:

```text
25830
```

debemos hacer:

```text
geom
 ↓
SRID 4326
 ↓
ST_Transform
 ↓
SRID 25830
```

---

# Datum

Otro concepto importante es:

```text
Datum
```

Un datum proporciona un modelo de referencia para determinar posiciones sobre la Tierra.

Entre los más conocidos:

```text
WGS 84
ETRS89
ED50
```

Los sistemas de referencia pueden estar asociados a diferentes datums.

---

# WGS 84

Es uno de los sistemas geodésicos más utilizados a nivel mundial.

Está asociado a:

```text
EPSG:4326
```

Es ampliamente utilizado por:

- GPS.
- Aplicaciones web.
- Datos geográficos globales.
- Servicios de localización.

---

# ETRS89

En Europa se utiliza ampliamente:

```text
ETRS89
```

Es especialmente relevante para cartografía oficial europea.

En España encontramos sistemas como:

```text
ETRS89 / UTM zone 30N
```

identificado por:

```text
EPSG:25830
```

---

# UTM

UTM significa:

```text
Universal Transverse Mercator
```

Divide la Tierra en zonas longitudinales.

Cada zona tiene:

```text
6 grados de longitud
```

---

# Zonas UTM

Las zonas UTM se numeran:

```text
1 → 60
```

España se encuentra principalmente dentro de varias zonas UTM.

Entre ellas:

```text
29
30
31
```

Para gran parte de la España peninsular es especialmente importante:

```text
UTM zone 30N
```

---

# EPSG:25830

Por tanto:

```text
EPSG:25830
```

puede descomponerse conceptualmente como:

```text
ETRS89
+
UTM
+
Zona 30N
```

Las coordenadas resultantes se expresan en metros.

---

# Proyección cartográfica

Una proyección cartográfica transforma:

```text
Superficie terrestre
```

en:

```text
Plano
```

Esto es necesario porque la Tierra tiene una superficie curva y un mapa normalmente es plano.

---

# Distorsiones

Toda proyección introduce algún tipo de distorsión.

Dependiendo de la proyección pueden verse afectados:

```text
Distancias
Áreas
Ángulos
Formas
Direcciones
```

Por eso no existe una proyección perfecta para todos los usos.

---

# Elegir una proyección

El CRS adecuado depende de:

```text
Zona geográfica
+
Tipo de análisis
+
Precisión necesaria
```

Por ejemplo:

```text
Mapa mundial
```

puede utilizar un sistema diferente a:

```text
Cálculo preciso de parcelas
```

---

# Ejemplo práctico

Supongamos que tenemos:

```text
parcelas
```

con:

```text
geometry(Point/Polygon, 4326)
```

y queremos calcular superficies.

Podemos transformar temporalmente:

```sql
SELECT ST_Area(
    ST_Transform(
        geom,
        25830
    )
)
FROM parcelas;
```

La transformación permite trabajar en un sistema cuyas unidades son metros.

---

# Guardar en 4326 y calcular en proyectado

Un patrón habitual puede ser:

```text
Almacenamiento
    ↓
EPSG:4326

Análisis métrico
    ↓
ST_Transform
    ↓
CRS proyectado
```

Sin embargo, la elección concreta depende del modelo de datos y de las necesidades de la aplicación.

---

# Transformación y almacenamiento

No siempre es necesario transformar y guardar una segunda geometría.

Podemos transformar durante una consulta:

```sql
SELECT ST_Area(
    ST_Transform(
        geom,
        25830
    )
)
FROM parcelas;
```

Esto mantiene la geometría original.

---

# Geometría original y geometría transformada

Podemos visualizarlo:

```text
geom
│
├── SRID 4326
│
└── ST_Transform(..., 25830)
          │
          └── nueva geometría
```

La transformación devuelve una nueva geometría.

---

# ST_Transform con SRID de destino

La forma habitual:

```sql
ST_Transform(
    geom,
    25830
)
```

indica:

```text
Transformar a SRID 25830
```

También existen variantes más avanzadas utilizando definiciones de CRS, pero para el uso habitual de PostGIS es suficiente conocer la versión basada en SRID.

---

# ST_Transform y columnas

Supongamos:

```sql
CREATE TABLE ciudades (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100),
    geom geometry(Point, 4326)
);
```

Podemos consultar las coordenadas transformadas:

```sql
SELECT
    nombre,
    ST_AsText(
        ST_Transform(
            geom,
            25830
        )
    )
FROM ciudades;
```

---

# Transformar una geometría y mantener el SRID

El resultado de:

```sql
ST_Transform(
    geom,
    25830
)
```

tendrá:

```text
SRID = 25830
```

y coordenadas transformadas.

---

# SRID de una geometría transformada

Podemos comprobarlo:

```sql
SELECT
    ST_SRID(
        ST_Transform(
            geom,
            25830
        )
    )
FROM ciudades;
```

Resultado:

```text
25830
```

---

# Comparar geometrías

Cuando realizamos operaciones espaciales entre geometrías debemos prestar atención a que sus sistemas de referencia sean compatibles.

Por ejemplo:

```text
geom_a
SRID 4326

geom_b
SRID 25830
```

No debemos tratarlas directamente como si sus coordenadas estuvieran expresadas en el mismo sistema.

---

# Transformar para comparar

Podemos transformar una geometría:

```sql
ST_Transform(
    geom_b,
    4326
)
```

y trabajar con:

```text
geom_a
+
geom_b transformada
```

o transformar ambas a un CRS adecuado para la operación.

---

# ST_SRID como comprobación

Antes de realizar operaciones espaciales complejas puede ser útil comprobar:

```sql
SELECT ST_SRID(geom)
FROM tabla;
```

Esto permite detectar problemas como:

```text
SRID inesperado
```

o:

```text
Datos mezclados
```

---

# Geometrías con SRID 0

En PostGIS puede existir una geometría sin un sistema de referencia espacial definido, representada mediante:

```text
SRID = 0
```

Esto significa que las coordenadas no tienen asociado un CRS específico.

Para datos geográficos reales debemos evitar asumir que:

```text
SRID 0
```

significa:

```text
4326
```

No son equivalentes.

---

# SRID incorrecto

Uno de los problemas más peligrosos es:

```text
Coordenadas correctas
+
SRID incorrecto
```

La geometría puede parecer válida desde el punto de vista de almacenamiento, pero las operaciones espaciales pueden producir resultados completamente incorrectos.

---

# Ejemplo conceptual

Tenemos:

```text
POINT(-1.13 37.99)
```

Realmente:

```text
EPSG:4326
```

Pero le asignamos:

```text
25830
```

mediante:

```sql
ST_SetSRID(...)
```

Las coordenadas continúan siendo:

```text
-1.13
37.99
```

pero ahora PostGIS interpreta:

```text
-1.13 metros
37.99 metros
```

dentro del sistema proyectado.

El resultado geográfico será incorrecto.

---

# Validación del CRS

Una buena práctica es conocer:

```text
¿Qué sistema utiliza la fuente?
```

antes de cargar datos.

Por ejemplo:

```text
Shapefile
GeoJSON
CSV
GPS
Servicio web
```

Cada fuente puede utilizar un sistema diferente.

---

# GeoJSON y CRS

GeoJSON se utiliza frecuentemente para intercambiar datos geográficos.

En aplicaciones web es habitual trabajar con:

```text
WGS 84
```

y coordenadas:

```text
longitud
latitud
```

Por ello:

```text
GeoJSON
   ↓
4326
```

es una combinación muy frecuente.

---

# Coordenadas y orden de ejes

Un detalle importante es que diferentes estándares y CRS pueden definir convenciones sobre el orden de los ejes.

En la práctica, en PostGIS y en formatos GIS habituales debemos conocer cuidadosamente cómo se representan las coordenadas.

Para el uso común de:

```text
EPSG:4326
```

en PostGIS:

```text
X = longitud
Y = latitud
```

Por ejemplo:

```text
POINT(-1.13 37.99)
```

significa:

```text
longitud = -1.13
latitud = 37.99
```

---

# Geometry vs Geography

Podemos resumir:

```text
GEOMETRY
│
├── Plano
├── CRS específico
├── Muy flexible
├── Muy utilizado
└── Unidades del CRS

GEOGRAPHY
│
├── Tierra
├── Coordenadas geodésicas
├── Muy útil para datos globales
└── Distancias/áreas geodésicas
```

---

# ¿Cuál utilizar?

No existe una respuesta universal.

Podemos utilizar:

```text
geometry
```

cuando:

- Necesitamos flexibilidad.
- Trabajamos en un área limitada.
- Utilizamos un CRS proyectado adecuado.
- Necesitamos operaciones espaciales específicas.

Podemos utilizar:

```text
geography
```

cuando:

- Trabajamos con coordenadas geográficas.
- Los datos pueden abarcar grandes áreas.
- Necesitamos mediciones geodésicas.
- Queremos trabajar directamente con latitud/longitud y obtener distancias en metros.

---

# Patrón habitual en aplicaciones

Una arquitectura puede ser:

```text
Frontend
   ↓
GeoJSON
   ↓
EPSG:4326
   ↓
PostGIS
   ↓
geometry / geography
```

Y para análisis:

```text
PostGIS
   ↓
ST_Transform
   ↓
CRS proyectado
   ↓
Medición
```

---

# Ejemplo completo

Tenemos:

```sql
CREATE TABLE lugares (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100),
    geom geometry(Point, 4326)
);
```

Insertamos:

```sql
INSERT INTO lugares (
    nombre,
    geom
)
VALUES (
    'Murcia',
    ST_SetSRID(
        ST_MakePoint(
            -1.1307,
            37.9922
        ),
        4326
    )
);
```

Podemos comprobar:

```sql
SELECT
    nombre,
    ST_SRID(geom),
    ST_AsText(geom)
FROM lugares;
```

Resultado:

```text
Murcia
4326
POINT(-1.1307 37.9922)
```

---

# Transformar para análisis

Podemos hacer:

```sql
SELECT
    nombre,
    ST_AsText(
        ST_Transform(
            geom,
            25830
        )
    )
FROM lugares;
```

La geometría resultante estará en:

```text
EPSG:25830
```

y sus coordenadas estarán expresadas en metros.

---

# Medir

Para medir un polígono:

```sql
SELECT
    ST_Area(
        ST_Transform(
            geom,
            25830
        )
    )
FROM parcelas;
```

Para medir una línea:

```sql
SELECT
    ST_Length(
        ST_Transform(
            geom,
            25830
        )
    )

```

# Regla de oro

Antes de realizar una medición espacial pregunta:

```text
1. ¿Qué tipo de dato tengo?
        ↓

2. ¿Qué CRS tiene?
        ↓
SRID

3. ¿Qué unidades utiliza?
        ↓

        ↓

        ↓

```

# Errores frecuentes

### ❌ Usar ST_SetSRID para transformar coordenadas

Incorrecto:

```text
ST_SetSRID
≠
ST_Transform
```

---

### ❌ Pensar que EPSG:4326 utiliza metros

No.

Es un sistema geográfico con coordenadas angulares.

---

### ❌ Suponer que ST_Distance siempre devuelve metros

No.

Depende del tipo espacial y del sistema utilizado.

---

### ❌ Mezclar geometrías con diferentes SRID

Debemos asegurarnos de que las geometrías sean compatibles.

---

### ❌ Confundir WGS 84 con cualquier sistema UTM

Son sistemas diferentes.

Por ejemplo:

```text
EPSG:4326
↓
WGS 84 geográfico

EPSG:25830
↓
ETRS89 / UTM 30N
```

---

### ❌ Cambiar el SRID sin conocer el CRS original

Si no conocemos el sistema de referencia de origen, no podemos realizar una transformación fiable.

# Conceptos importantes

Antes de continuar debes recordar:

- Un CRS define cómo interpretar las coordenadas.
- Un SRID identifica el CRS asociado a una geometría.
- EPSG proporciona códigos estandarizados para sistemas de referencia.
- EPSG:4326 corresponde a WGS 84.
- EPSG:4326 utiliza coordenadas geográficas.
- EPSG:25830 corresponde a ETRS89 / UTM zone 30N.
- Los sistemas UTM son sistemas proyectados.
- Las coordenadas de un CRS proyectado pueden expresarse en metros.
- Las coordenadas geográficas normalmente se expresan mediante longitud y latitud.
- `ST_SetSRID()` asigna un SRID, pero no transforma las coordenadas.
- `ST_Transform()` transforma las coordenadas.
- Para transformar correctamente necesitamos conocer el CRS de origen.
- `geometry` utiliza las unidades del CRS asociado.
- `geography` permite realizar determinados cálculos geodésicos directamente sobre la Tierra.
- No debemos asumir que `ST_Distance()` siempre devuelve metros.
- Para mediciones métricas puede ser conveniente utilizar `geography` o transformar a un CRS proyectado adecuado.
- Un SRID incorrecto puede provocar resultados espaciales incorrectos aunque la geometría esté almacenada correctamente.
- Las mediciones deben realizarse utilizando un sistema de referencia adecuado para el área y el propósito del análisis.

# 3.6 PostGIS - Índices espaciales y optimización

## 3.6.5 Índices espaciales y rendimiento

Las operaciones espaciales pueden ser costosas.

Una consulta como:

```sql
SELECT *
FROM edificios
WHERE ST_DWithin(
    geom::geography,
    punto::geography,
    500
);
```

puede ser muy eficiente con un conjunto pequeño de datos.

Pero si tenemos:

```text
10 edificios
```

es muy diferente de:

```text
10.000.000 edificios
```

En el segundo caso necesitamos mecanismos de indexación que permitan reducir rápidamente el número de geometrías que deben analizarse.

Aquí aparecen:

```text
Índices espaciales
        ↓
GiST
        ↓
Bounding Boxes
        ↓
Filtros espaciales
```

---

# ¿Qué es un índice espacial?

Un índice espacial es una estructura que permite localizar rápidamente objetos basándose en su posición o extensión espacial.

En una tabla convencional podemos tener:

```text
id
nombre
fecha
```

y crear:

```sql
CREATE INDEX idx_nombre
ON lugares(nombre);
```

En una tabla espacial podemos tener:

```text
geom
```

y crear:

```sql
CREATE INDEX idx_geom
ON lugares
USING GIST (geom);
```

---

# GiST

GiST significa:

```text
Generalized Search Tree
```

Es un mecanismo de indexación de PostgreSQL que permite implementar diferentes tipos de estructuras de búsqueda.

PostGIS utiliza habitualmente:

```text
GiST
```

para crear índices espaciales.

---

# Crear un índice espacial

Ejemplo:

```sql
CREATE INDEX idx_lugares_geom
ON lugares
USING GIST (geom);
```

La parte fundamental es:

```text
USING GIST
```

Esto indica que se utilizará el método de acceso GiST.

---

# Índice espacial frente a índice convencional

Podemos tener:

```sql
CREATE INDEX idx_lugares_nombre
ON lugares(nombre);
```

para búsquedas como:

```sql
WHERE nombre = 'Murcia'
```

Y:

```sql
CREATE INDEX idx_lugares_geom
ON lugares
USING GIST (geom);
```

para ayudar en consultas espaciales.

---

# ¿Qué problema resuelve?

Supongamos:

```text
1.000.000 puntos
```

y queremos encontrar:

```text
puntos cercanos a una determinada ubicación
```

Sin índice podríamos tener:

```text
Punto 1 → comprobar
Punto 2 → comprobar
Punto 3 → comprobar
...
Punto 1.000.000 → comprobar
```

Esto puede ser muy costoso.

Con un índice espacial:

```text
Consulta
   ↓
Índice espacial
   ↓
Reducir candidatos
   ↓
Comprobar geometrías candidatas
```

---

# Bounding Box

Una de las ideas fundamentales detrás de muchos índices espaciales es la:

```text
Bounding Box
```

Es el rectángulo mínimo alineado con los ejes que contiene una geometría.

---

# Ejemplo de Bounding Box

Supongamos una geometría:

```text
          ●───────●
         /         \
        /           \
       ●             ●
        \           /
         \─────────/
```

Su bounding box podría ser:

```text
┌──────────────────────┐
│                      │
│     ●────────●       │
│    /          \      │
│   ●            ●     │
│    \          /      │
│     ──────────       │
│                      │
└──────────────────────┘
```

La geometría puede ser compleja.

La bounding box es mucho más sencilla.

---

# ¿Por qué utilizar Bounding Boxes?

Porque comprobar:

```text
¿Dos rectángulos se solapan?
```

es mucho más barato que comprobar:

```text
¿Dos geometrías complejas se intersectan realmente?
```

Por ello podemos realizar un proceso en dos fases:

```text
FASE 1
Bounding Box
        ↓
Descartar candidatos

FASE 2
Geometría real
        ↓
Comprobar relación exacta
```

---

# Filtro aproximado + comprobación exacta

Podemos imaginar una consulta espacial como:

```text
                 Todos los objetos
                        │
                        ▼
                Filtro espacial
                Bounding Box
                        │
              ┌─────────┴─────────┐
              │                   │
          descartados          candidatos
                                  │
                                  ▼
                         Cálculo geométrico
                                  │
                                  ▼
                              resultado
```

Esta estrategia es muy importante para el rendimiento.

---

# Operador &&

PostGIS proporciona el operador:

```text
&&
```

que comprueba si las bounding boxes de dos geometrías se superponen.

Ejemplo:

```sql
WHERE geom && otra_geom
```

No significa necesariamente:

```text
Las geometrías se intersectan realmente.
```

Significa:

```text
Sus bounding boxes se superponen.
```

---

# && frente a ST_Intersects

Tenemos:

```sql
geom_a && geom_b
```

que comprueba:

```text
Bounding Boxes
```

Mientras:

```sql
ST_Intersects(
    geom_a,
    geom_b
)
```

comprueba la relación espacial real.

Conceptualmente:

```text
&&
↓
Filtro rápido

ST_Intersects
↓
Comprobación geométrica
```

---

# Ejemplo

Supongamos:

```text
A
┌──────────────┐
│     ╱╲       │
│    ╱  ╲      │
│   ╱    ╲     │
└──────────────┘

B
      ┌──────────────┐
      │              │
      │              │
      └──────────────┘
```

Las bounding boxes pueden solaparse aunque las geometrías reales no lo hagan.

Por tanto:

```text
A && B
```

puede ser:

```text
TRUE
```

mientras:

```text
ST_Intersects(A, B)
```

sea:

```text
FALSE
```

```text
&&
```

También existen operadores más especializados, pero para el estudio fundamental debemos dominar primero:


Conceptualmente:


# Consultas que pueden utilizar índices espaciales

Las funciones espaciales habituales están diseñadas para trabajar con mecanismos de indexación espacial.

Entre ellas encontramos:

```text
ST_Intersects
ST_Contains
ST_Within
ST_DWithin
```

entre otras.

Esto permite reducir considerablemente el número de geometrías que necesitan un cálculo espacial completo.

---

# ST_DWithin

Recordemos:

```sql
ST_DWithin(
    geom_a,
    geom_b,
    distancia
)
```

Pregunta:

```text
¿Están dentro de la distancia especificada?
```

Esta función es especialmente importante para búsquedas de proximidad.

Ejemplo:

```sql
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom::geography,
    punto::geography,
    500
);
```

---

# ST_DWithin frente a ST_Distance

Podríamos escribir:

```sql
WHERE ST_Distance(
    geom::geography,
    punto::geography
) < 500
```

pero para una búsqueda de proximidad:

```text
ST_DWithin
```

es normalmente la opción preferible.

La diferencia conceptual:

```text
ST_Distance
↓
Calcula la distancia

ST_DWithin
↓
Pregunta si está dentro de un límite
```

Además, `ST_DWithin` está preparada para aprovechar mecanismos de indexación espacial.

---

# Índice y ST_DWithin

Podemos tener:

```sql
CREATE INDEX idx_tiendas_geom
ON tiendas
USING GIST (geom);
```

y después:

```sql
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom,
    punto,
    500
);
```

El planificador puede utilizar el índice espacial para reducir los candidatos.

---

# Geography e índices

Cuando utilizamos:

```text
geography
```

también podemos utilizar índices espaciales.

Por ejemplo:

```sql
CREATE INDEX idx_tiendas_geog
ON tiendas
USING GIST (
    geom::geography
);
```

Esto crea un índice basado en la expresión:

```text
geom::geography
```

---

# Índices sobre expresiones

PostgreSQL permite crear índices sobre expresiones.

Por ejemplo:

```sql
CREATE INDEX idx_tiendas_geog
ON tiendas
USING GIST (
    geom::geography
);
```

Esto puede resultar útil cuando las consultas utilizan repetidamente:

```text
geom::geography
```

---

# Coincidencia entre índice y consulta

Para aprovechar correctamente un índice basado en una expresión debemos utilizar una expresión compatible con la que está indexada.

Por ejemplo, si creamos:

```sql
CREATE INDEX idx_geom_geog
ON lugares
USING GIST (
    geom::geography
);
```

una consulta como:

```sql
WHERE ST_DWithin(
    geom::geography,
    punto::geography,
    500
)
```

puede aprovechar ese índice.

# EXPLAIN

PostgreSQL proporciona:

```text
EXPLAIN
```

para mostrar el plan de ejecución de una consulta.

Ejemplo:

```sql
EXPLAIN
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom,
    punto,
    500
);
```

Esto no ejecuta necesariamente la consulta de la misma manera que `EXPLAIN ANALYZE`.

Muestra el plan que el optimizador estima utilizar.

---

# EXPLAIN ANALYZE

Para ejecutar realmente la consulta y obtener información sobre el comportamiento podemos utilizar:

```sql
EXPLAIN ANALYZE
```

Ejemplo:

```sql
EXPLAIN ANALYZE
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom,
    punto,
    500
);
```

Esto permite comparar:

```text
Estimaciones
vs
Comportamiento real
```

---

# Seq Scan

Si PostgreSQL realiza:

```text
Seq Scan
```

está realizando un recorrido secuencial.

Conceptualmente:

```text
Fila 1
Fila 2
Fila 3
...
Fila N
```

Esto puede ser adecuado para tablas pequeñas o cuando una gran proporción de las filas cumple la condición.

No significa automáticamente que exista un problema.

---

# Index Scan

Si utiliza:

```text
Index Scan
```

está utilizando un índice para localizar las filas candidatas.

En el contexto espacial podemos encontrar planes que aprovechen:

```text
GiST
```

para reducir el conjunto de datos.

---

# Bitmap Index Scan

También podemos encontrar:

```text
Bitmap Index Scan
```

seguido de:

```text
Bitmap Heap Scan
```

Es otra estrategia de PostgreSQL para utilizar índices cuando puede resultar eficiente obtener un conjunto de filas candidatas.

---

# El optimizador decide

No debemos asumir:

```text
Tengo un índice
↓
Siempre se utilizará
```

No necesariamente.

PostgreSQL decide según:

- Estadísticas.
- Coste estimado.
- Tamaño de la tabla.
- Selectividad.
- Distribución de los datos.
- Coste de acceder al índice.
- Coste de recorrer la tabla.

---

# Índice no significa siempre más rápido

Para una tabla:

```text
20 filas
```

puede ser más barato hacer:

```text
Seq Scan
```

que utilizar un índice.

Para:

```text
20.000.000 filas
```

un índice espacial puede ser fundamental.

---

# Selectividad

La selectividad indica, simplificando, qué proporción de filas cumple una condición.

Por ejemplo:

```text
1.000.000 filas

100 cumplen
```

La consulta es muy selectiva.

En cambio:

```text
1.000.000 filas

900.000 cumplen
```

la condición es poco selectiva.

Un índice suele ser especialmente útil cuando permite descartar una gran cantidad de filas.

---

# Consultas espaciales y selectividad

Supongamos:

```text
1.000.000 edificios
```

y buscamos:

```text
edificios dentro de un pequeño polígono
```

Probablemente:

```text
Muy pocos
```

cumplan.

El índice espacial puede descartar rápidamente gran parte de los candidatos.

---

# Bounding Box como filtro

Podemos visualizar:

```text
1.000.000 objetos
        ↓
Bounding Box
        ↓
10.000 candidatos
        ↓
Geometría exacta
        ↓
500 resultados
```

El objetivo es evitar ejecutar operaciones geométricas complejas sobre todos los objetos.

---

# Índices espaciales y JOIN

Los índices también pueden resultar fundamentales en consultas espaciales entre tablas.

Por ejemplo:

```sql
SELECT
    municipio.nombre,
    provincia.nombre
FROM municipios municipio
JOIN provincias provincia
    ON ST_Intersects(
        municipio.geom,
        provincia.geom
    );
```

Con grandes volúmenes de datos:

```text
municipios
+
provincias
```

la indexación espacial puede reducir considerablemente el coste.

---

# Spatial Join eficiente

Un patrón frecuente es:

```text
Tabla A
   +
Tabla B
   ↓
Relación espacial
   ↓
Índices espaciales
   ↓
```

# GiST frente a B-tree

Un índice B-tree tradicional funciona muy bien para:

```text
=
<
>
<=
>=
```

y otras comparaciones ordenadas.

Por ejemplo:

```sql
CREATE INDEX idx_personas_edad
ON personas(edad);
```

Pero una geometría no se presta directamente a una ordenación B-tree tradicional para preguntas como:

```text
¿Estas geometrías se intersectan?
```

Por ello utilizamos estructuras como:

```text
GiST
```

---

# ¿Por qué GiST?

GiST permite construir índices generalizados que pueden representar relaciones espaciales.

PostGIS utiliza esta infraestructura para proporcionar índices espaciales eficientes.

---

# SP-GiST

PostgreSQL también proporciona:

```text
SP-GiST
```

que significa:

```text
Space-Partitioned Generalized Search Tree
```

Puede utilizarse para determinados tipos de datos y estrategias de indexación espacial.

Sin embargo:

```text
GiST
```

es el índice espacial más habitual que debemos conocer para PostGIS.

---

# BRIN

PostgreSQL también proporciona:

```text
BRIN
```

que significa:

```text
Block Range Index
```

Los índices BRIN pueden resultar útiles cuando los datos tienen determinadas características de ordenación o correlación física.

En determinadas situaciones espaciales pueden ser interesantes, pero:

```text
GiST
```

es el mecanismo fundamental que debemos dominar para el estudio general de PostGIS.

---

# Índices parciales

PostgreSQL permite crear índices parciales.

Por ejemplo:

```sql
CREATE INDEX idx_lugares_activos_geom
ON lugares
USING GIST (geom)
WHERE activo = TRUE;
```

El índice solo contiene filas que cumplen:

```text
activo = TRUE
```

Esto puede reducir el tamaño del índice y mejorar determinadas consultas.

---

# VACUUM y ANALYZE

El rendimiento de PostgreSQL depende también de sus estadísticas y mantenimiento.

Una operación habitual es:

```sql
ANALYZE
```

que actualiza estadísticas utilizadas por el optimizador.

Por ejemplo:

```sql
ANALYZE lugares;
```

PostgreSQL puede utilizar estas estadísticas para elegir mejores planes.

# Transformaciones y rendimiento

Una consulta como:

```sql
WHERE ST_DWithin(
    ST_Transform(geom, 25830),
    punto,
    500
)
```

puede implicar transformar muchas geometrías durante la consulta.

Si tenemos:

```text
millones de filas
```

esto puede ser costoso.

Debemos considerar:

```text
¿Necesitamos transformar en cada consulta?
```

---

# Posibles estrategias

Dependiendo de la aplicación podemos considerar:

```text
1. Guardar la geometría en un CRS adecuado.

2. Mantener una geometría adicional transformada.

3. Utilizar geography.

4. Crear un índice sobre una expresión transformada.

5. Transformar únicamente cuando sea necesario.
```

La estrategia adecuada depende del patrón de consultas.


Esto puede ser útil si las consultas realizan repetidamente esa transformación.

# Ejemplo completo

Tabla:

```sql
CREATE TABLE tiendas (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100),
    geom geometry(Point, 4326)
);
```

Índice:

```sql
CREATE INDEX idx_tiendas_geom
ON tiendas
USING GIST (geom);
```

Consulta:

```sql
SELECT *
FROM tiendas
WHERE ST_DWithin(
    geom,
    punto,
    0.01
);
```

Aquí:

```text
0.01
```

representa unidades del CRS de `geom`.

Si `geom` está en:

```text
EPSG:4326
```

esto significa una distancia angular, no directamente:

```text
0.01 metros
```

Por ello debemos tener cuidado.

Aquí:

```text

```

representa:


# Conceptos importantes

Antes de continuar debes recordar:

- Los índices espaciales permiten acelerar consultas sobre geometrías.
- El índice espacial más habitual en PostGIS utiliza `GiST`.
- Un índice espacial puede reducir el número de geometrías que necesitan ser evaluadas.
- Las bounding boxes permiten realizar filtros espaciales rápidos.
- El operador `&&` comprueba la superposición de bounding boxes.
- `&&` no equivale necesariamente a una intersección geométrica real.
- Las funciones espaciales pueden utilizar mecanismos de indexación espacial.
- `ST_DWithin()` es especialmente útil para consultas de proximidad.
- `ST_Distance()` calcula una distancia, mientras que `ST_DWithin()` comprueba un umbral.
- PostgreSQL puede decidir no utilizar un índice si estima que otra estrategia es más eficiente.
- `EXPLAIN` muestra el plan estimado.
- `EXPLAIN ANALYZE` ejecuta la consulta y muestra información real de ejecución.
- `Seq Scan` representa un recorrido secuencial.
- `Index Scan` utiliza un índice.
- `Bitmap Index Scan` es otra estrategia de acceso mediante índices.
- La selectividad influye en la utilidad de los índices.
- Las transformaciones espaciales pueden tener impacto en el rendimiento.
- PostgreSQL permite crear índices sobre expresiones.
- `GiST` es el índice espacial fundamental que debemos conocer para PostGIS.
- `SP-GiST` y `BRIN` existen en PostgreSQL, pero tienen usos diferentes.
- Las estadísticas y el mantenimiento de PostgreSQL también influyen en el rendimiento.
- Las consultas espaciales deben optimizarse utilizando mediciones reales y `EXPLAIN ANALYZE`.

# Buffer de un punto

Supongamos:

```text
       ●
```

Si hacemos:

```sql
ST_Buffer(
    geom,
    500
)
```

obtendremos aproximadamente:

```text
        ┌─────────┐
      /             \
     /       ●       \
    │                 │
     \               /
      \─────────────/
```

El resultado es una superficie alrededor del punto.

---

# Ejemplo práctico

Supongamos que tenemos una estación:

```text
estacion.geom
```

y queremos obtener una zona de:

```text
500 metros
```

alrededor:

```sql
ST_Buffer(
    estacion.geom::geography,
    500
)
```

El resultado será una geometría que representa el área alrededor de la estación.

---

# Buffer de una línea

También podemos aplicar `ST_Buffer()` a una línea.

```text
───────────────
```

Buffer:

```text
══════════════════════
```

Se genera una superficie alrededor de la línea.

Esto puede utilizarse para representar:

```text
Zona de influencia de una carretera
Zona de seguridad de una vía
Área alrededor de un río
Corredor alrededor de una ruta
```

---

# Buffer de un polígono

También podemos crear un buffer alrededor de un polígono:

```text
┌───────────┐
│           │
│     A     │
│           │
└───────────┘
```

Aplicando:

```sql
ST_Buffer(
    geom,
    100
)
```

obtenemos una zona ampliada alrededor del polígono.

---

# Buffer negativo

También podemos utilizar una distancia negativa:

```sql
ST_Buffer(
    geom,
    -100
)
```

Esto permite reducir el área de un polígono hacia su interior.

Conceptualmente:

```text

┌───────────────┐
│               │
│               │
│               │
```

# Unidades de ST_Buffer

Con:

```text

```

la unidad depende del CRS.

Con:

```text

```

la distancia se interpreta en metros.

Por tanto:

```sql

    500
```

representa aproximadamente un buffer de:

# ST_Centroid

La función:

```text
ST_Centroid()
```

calcula el centroide de una geometría.

Ejemplo:

```text
┌──────────────┐
│              │
│      ●       │
│              │
└──────────────┘
```

El punto:

```text

```

representa el centroide.

# Centroide de un polígono

Podemos hacer:

```sql
SELECT ST_Centroid(geom)
FROM municipios;
```

El resultado será:

```text

```

# Importante: centroide no significa necesariamente punto interior

El centroide matemático de una geometría puede quedar fuera de ella.

Esto puede ocurrir con polígonos:

```text
        █████
       █     █
      █       █
       █     █
        █████
```

o geometrías con formas complejas.

Por tanto:

```text

```

no garantiza que el punto resultante esté dentro del polígono.

```text
ST_PointOnSurface
```

Por ejemplo, para colocar una etiqueta sobre un municipio:

puede ser más apropiado que:


Mientras:

# ST_ConvexHull

`ST_ConvexHull()` obtiene la envolvente convexa de una geometría o conjunto de geometrías.

Podemos imaginar una banda elástica rodeando varios puntos:

```text
       ●
   ●       ●
      ●
 ●          ●
```

La envolvente convexa sería aproximadamente:

```text
       ●
      / \
     /   \
    ●     ●
   /       \
  ●─────────●
```

---

# Convex Hull

La característica fundamental es:

```text
Convexa
```

No contiene concavidades hacia dentro.

Es como envolver todas las geometrías con una superficie que no puede hundirse hacia el interior.

---

# Ejemplo

```sql
SELECT ST_ConvexHull(
    ST_Collect(geom)
)
FROM lugares;
```

Aquí:

```text
ST_Collect
↓
Agrupa puntos

ST_ConvexHull
↓
Calcula la envolvente convexa
```

```text
Crear áreas aproximadas
Análisis geográfico
```

# ST_Difference

`ST_Difference()` devuelve la parte de una geometría que no está contenida en la otra.

Conceptualmente:

```text
A
┌───────────────┐
│       ┌───────┼─────┐
│       │   B   │     │
│       └───────┼─────┘
│               │
└───────────────┘
```

La diferencia:

```text
A - B
```

elimina la zona compartida.

---

# Ejemplo

```sql
SELECT ST_Difference(
    geom_a,
    geom_b
);
```

El resultado es:

```text
A sin la parte que comparte con B
```

---

# La diferencia depende del orden

Esto es muy importante.

```sql
ST_Difference(A, B)
```

no es necesariamente igual a:

```sql
ST_Difference(B, A)
```

Porque estamos realizando:

```text
A - B
```

frente a:

```text
B - A
```

---

# ST_SymDifference

La diferencia simétrica obtiene las partes que pertenecen a una geometría o a la otra, pero no a ambas.

Conceptualmente:

```text
A XOR B
```

Si:

```text
A = zona 1 + zona común
B = zona común + zona 2
```

la diferencia simétrica devuelve:

```text
zona 1 + zona 2
```

pero elimina:

```text
zona común
```

---

# ST_Union

`ST_Union()` combina geometrías.

Ejemplo:

```text
┌───────┐
│   A   │
└───────┘
   ┌───────┐
   │   B   │
   └───────┘
```

Después de una unión:

```text
┌───────┐
│       │
│       ├───────┐
│       │       │
└───────┴───────┘
```

Las zonas compartidas pueden quedar disueltas.

---

# ST_Union frente a ST_Collect

Esta diferencia es muy importante.

```text
ST_Collect
↓
Agrupa geometrías
```

Mientras:

```text
ST_Union
↓
Combina geométricamente
```

Tenemos:

```text
Polígono B
```

Con:


podemos obtener una colección.

Con:


podemos obtener una geometría resultante de la unión espacial.


```sql
SELECT

FROM municipios municipio
JOIN carreteras carretera
    ON ST_Intersects(
        municipio.geom,
        carretera.geom
    );
```

# Buenas prácticas

- Utilizar `ST_DWithin()` para búsquedas de proximidad en lugar de crear buffers innecesarios.
- Comprobar la validez de las geometrías antes de operaciones complejas.
- Utilizar un CRS adecuado para mediciones.
- Tener en cuenta que `ST_Centroid()` no garantiza que el punto esté dentro de un polígono.
- Utilizar `ST_PointOnSurface()` cuando necesitemos un punto dentro de una superficie.
- Tener cuidado con el orden de los parámetros en `ST_Difference()`.
- Utilizar índices espaciales para grandes volúmenes.
- Evitar simplificar geometrías sin evaluar el impacto topológico.
- Diferenciar funciones que generan geometrías de aquellas que simplemente comprueban relaciones.

# Conceptos importantes

Antes de continuar debes recordar:

- `ST_Buffer()` crea una zona alrededor de una geometría.
- `ST_Centroid()` calcula el centroide.
- El centroide no garantiza estar dentro del polígono.
- `ST_PointOnSurface()` proporciona un punto situado dentro de una superficie.
- `ST_Envelope()` devuelve el rectángulo mínimo alineado con los ejes que contiene una geometría.
- `ST_ConvexHull()` obtiene la envolvente convexa.
- `ST_Boundary()` devuelve la frontera de una geometría.
- `ST_Intersection()` devuelve la geometría común entre dos geometrías.
- `ST_Difference()` devuelve la parte de la primera geometría que no pertenece a la segunda.
- `ST_Difference(A, B)` no equivale necesariamente a `ST_Difference(B, A)`.
- `ST_SymDifference()` obtiene las partes exclusivas de cada geometría.
- `ST_Union()` combina geometrías espacialmente.
- `ST_Collect()` agrupa geometrías sin realizar una unión geométrica equivalente a `ST_Union()`.
- `ST_ClosestPoint()` obtiene un punto de una geometría cercano a otra.
- `ST_ShortestLine()` obtiene la línea más corta entre dos geometrías.
- `ST_MakeEnvelope()` crea un rectángulo a partir de sus límites.
- `ST_Simplify()` reduce la complejidad de una geometría.
- `ST_SimplifyPreserveTopology()` intenta conservar relaciones topológicas importantes.
- `ST_SnapToGrid()` ajusta coordenadas a una cuadrícula.
- `ST_Multi()` convierte una geometría a su equivalente multi.
- `ST_Buffer()` es apropiado cuando necesitamos generar una zona.
- `ST_DWithin()` suele ser más apropiado cuando simplemente queremos realizar una consulta de proximidad.

# Spatial Join con ST_Contains

Ejemplo:

```sql
SELECT
```

```sql
ST_Contains(
```

significa:

Después de una unión:

```sql
SELECT *
```

# Proximidad y clasificación

Podemos combinar proximidad con agregaciones.


```sql
SELECT
```

# Filtrado mediante Bounding Box

Podemos utilizar:

```sql
SELECT *
FROM lugares
WHERE geom && ST_MakeEnvelope(
    -2,
    37,
    -1,
    38,
    4326
);
```

Esto proporciona un filtro espacial rápido basado en bounding boxes.

# Bounding Box + condición exacta

Podemos combinar:

```text
&&
```

con:

```text
ST_Intersects
```

Por ejemplo:

```sql
SELECT *
FROM lugares
WHERE geom && zona
  AND ST_Intersects(
      geom,
      zona
  );
```

Conceptualmente:

```text
Primero
↓
Filtro rápido

Después
↓
Comprobación exacta
```

# ¿Es necesario añadir &&?

Muchas funciones espaciales de PostGIS ya incluyen internamente una estrategia de filtrado mediante bounding boxes y pueden aprovechar índices espaciales.

Por ello no debemos añadir:

```text
&&
```

automáticamente a todas las consultas.

Debemos conocer el plan de ejecución.

```text
¿Cómo divido una geometría enorme?
↓
ST_Subdivide
```

---

# Conceptos importantes

Antes de continuar debes recordar:

- PostGIS permite combinar operaciones espaciales con las capacidades tradicionales de SQL.
- Un `Spatial Join` combina tablas utilizando relaciones espaciales.
- `ST_Contains()` y `ST_Within()` son especialmente útiles para asignar puntos a polígonos.
- Las agregaciones SQL como `COUNT`, `SUM` y `AVG` pueden combinarse con relaciones espaciales.
- `ST_Union()` puede utilizarse para disolver geometrías.
- `ST_Collect()` agrupa geometrías sin realizar una unión geométrica equivalente.
- `ST_Dump()` permite descomponer geometrías múltiples o colecciones.
- `ST_Subdivide()` divide geometrías grandes en piezas más pequeñas.
- `ST_IsValid()` comprueba la validez de una geometría.
- `ST_IsEmpty()` comprueba si una geometría está vacía.
- `NULL` y `EMPTY` representan situaciones diferentes.
- Las consultas espaciales pueden utilizar `LEFT JOIN` para conservar entidades que no tengan correspondencias.
- `ST_DWithin()` es especialmente útil para análisis de proximidad.
- El operador `<->` permite consultas de vecinos más cercanos.
- PostGIS también puede trabajar con datos raster además de datos vectoriales.
- Los datos vectoriales se representan mediante puntos, líneas y polígonos.
- Los datos raster se representan mediante celdas o píxeles.
- PostGIS permite combinar análisis espacial, agregaciones, agrupaciones e índices.
- Los Spatial Joins pueden requerir índices espaciales para obtener un rendimiento adecuado.

# Resumen final del capítulo

PostGIS extiende PostgreSQL para convertirlo en una base de datos capaz de trabajar con información geoespacial.

Su funcionamiento se apoya en:

```text
PostgreSQL
+
Tipos espaciales
+
CRS / SRID
+
Funciones espaciales
+
Índices espaciales
```

Las geometrías principales son:

```text
POINT
LINESTRING
POLYGON
MULTI*
```

Las relaciones espaciales permiten responder preguntas como:

```text
¿Está dentro?
¿Intersecta?
¿Se toca?
¿Está cerca?
```

Las funciones métricas permiten obtener:

```text
Distancias
Longitudes
Áreas
Perímetros
```

Las funciones geométricas permiten crear:

```text
Buffers
Intersecciones
Diferencias
Uniones
Envolventes
Centroides
```

Los sistemas de referencia permiten interpretar correctamente las coordenadas.

Los índices:

```text
GiST
```

permiten acelerar consultas espaciales.

Los formatos:

```text
WKT
WKB
GeoJSON
```

permiten intercambiar información entre PostGIS y otras aplicaciones.

Finalmente, PostGIS puede integrarse directamente con:

```text
APIs
Aplicaciones web
Sistemas GIS
Mapas
Herramientas ETL
```

formando una arquitectura completa de gestión y análisis geoespacial.
