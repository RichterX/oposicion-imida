# 🔥 BLOQUE 07 · SEGURIDAD
# 7.4 · FIREWALLS
## Parte 3 · ACL, NAT/PAT, VPN, evasión, alta disponibilidad, auditoría y seguridad operativa

> **Objetivo:** completar la parte técnica del capítulo con los mecanismos que suelen aparecer cuando pasamos de "qué es un firewall" a "cómo se administra y cómo puede fallar": ACL, NAT/PAT, VPN, spoofing, evasión, alta disponibilidad, auditoría y mantenimiento.
>
> **Fuentes técnicas de referencia:** NIST SP 800-41 Rev. 1 e INCIBE-CERT. NIST trata expresamente las políticas de firewall, NAT, VPN y alta disponibilidad; además advierte de que NAT no debe confundirse con una función de seguridad del firewall. 

---

# 🧭 1. ACL · ACCESS CONTROL LIST

Una:

> **ACL (Access Control List)**

es una lista de reglas que determina qué tráfico o acciones están permitidos o denegados.

En redes, una ACL puede expresarse conceptualmente como:

```text
ORIGEN
+
DESTINO
+
PROTOCOLO
+
PUERTO
+
ACCIÓN
```

Ejemplo:

```text
ALLOW
10.10.10.0/24
→
10.0.20.10
TCP/443
```

---

# 🧱 2. ACL COMO POLÍTICA

Podemos pensar:

```text
ACL
 ↓
REGLAS
 ↓
TRÁFICO
 ↓
DECISIÓN
```

Ejemplo:

```text
1. ALLOW 10.10.10.0/24 → WEB TCP/443
2. ALLOW 10.10.10.0/24 → WEB TCP/22
3. DENY  ANY           → WEB ANY
```

La última regla actúa como:

```text
DENEGACIÓN
POR DEFECTO
```

si el dispositivo utiliza ese modelo.

---

# ⚠️ 3. ACL IMPLÍCITA

En algunos sistemas de filtrado existe una:

> **regla implícita final**

que deniega el tráfico que no haya coincidido con una regla anterior.

Conceptualmente:

```text
REGLA 1
REGLA 2
REGLA 3
...
DENY ANY
```

Por eso:

> **no debemos asumir que todo lo que no aparece escrito está permitido.**

Hay que conocer la política concreta del dispositivo.

---

# 🔢 4. ORDEN DE LAS ACL

El orden es fundamental cuando las reglas se procesan secuencialmente.

Ejemplo:

```text
1. ALLOW 10.0.0.0/8 → SERVER TCP/443
2. DENY  10.10.10.50 → SERVER TCP/443
```

Si:

```text
10.10.10.50
```

coincide primero con la regla 1:

```text
ALLOW
```

la segunda regla puede no llegar a evaluarse.

Por eso debemos colocar las excepciones específicas donde corresponda.

---

# 🧠 5. REGLA ESPECÍFICA VS REGLA GENERAL

Tenemos:

```text
ALLOW RED_ADMIN → SERVER
DENY  IP_ADMIN  → SERVER
```

La regla específica debería tener una posición coherente con la política que queremos aplicar.

Una mala organización puede provocar:

```text
REGLA GENERAL
      ↓
COINCIDENCIA
      ↓
REGLA ESPECÍFICA
      ↓
NUNCA SE EVALÚA
```

Esto puede producir:

> **sombreado de reglas.**

---

# 🧹 6. REGLAS OBSOLETAS

Una ACL puede crecer durante años:

```text
ALLOW...
ALLOW...
DENY...
ALLOW...
ALLOW...
DENY...
```

Si nunca se revisa:

```text
reglas antiguas
+
excepciones temporales
+
servicios eliminados
+
IPs que ya no existen
```

pueden permanecer activas.

### Riesgo

```text
SUPERFICIE DE ATAQUE ↑
```

---

# 📋 7. CICLO DE VIDA DE UNA REGLA

Una buena práctica:

```text
SOLICITUD
   ↓
JUSTIFICACIÓN
   ↓
APROBACIÓN
   ↓
IMPLEMENTACIÓN
   ↓
PRUEBA
   ↓
MONITORIZACIÓN
   ↓
REVISIÓN
   ↓
ELIMINACIÓN
```

No queremos:

```text
"añádela y ya veremos"
```

# 🔀 8. NAT

NAT significa:

> **Network Address Translation**

y permite traducir direcciones IP entre diferentes espacios de direccionamiento.

Ejemplo:

```text
RED INTERNA

192.168.1.20
     ↓
   NAT
     ↓
203.0.113.20
```

---

# 🔢 9. PAT

PAT significa:

> **Port Address Translation**

y permite multiplexar conexiones utilizando también los puertos.

Ejemplo conceptual:

```text
192.168.1.10:50000
        ↓
203.0.113.20:40001

192.168.1.11:50000
        ↓
203.0.113.20:40002
```

Dos equipos internos pueden compartir una única IP pública.

---

# 🧠 10. NAPT

También podemos encontrar:

> **NAPT (Network Address and Port Translation)**

que refleja la traducción de dirección y puerto.

En muchos contextos:

```text
NAT
PAT
NAPT
```

se utilizan con cierta flexibilidad, dependiendo del fabricante y documentación.

---

# ⚠️ 11. NAT NO ES UN FIREWALL

Esto es:

> **muy importante para examen.**

NAT:

```text
TRADUCE
```

Firewall:

```text
APLICA POLÍTICAS
```

NIST advierte expresamente que NAT no forma parte, por sí mismo, de la funcionalidad de seguridad de un firewall. El hecho de que NAT pueda impedir determinadas conexiones iniciadas desde fuera no significa que sea equivalente a una política de filtrado. 

---

# 🧩 12. NAT Y FIREWALL PUEDEN COEXISTIR

Arquitectura:

```text
INTERNET
    ↓
FIREWALL
    ↓
NAT
    ↓
RED PRIVADA
```

o integrados:

```text
┌─────────────────┐
│    FIREWALL     │
│                 │
│ NAT + FILTERING │
└─────────────────┘
```

Pero conceptualmente:

```text
NAT ≠ FILTRADO
```

---

# 🚪 13. PORT FORWARDING

Una forma de NAT puede permitir:

```text
INTERNET
   ↓
PUBLIC_IP:443
   ↓
FIREWALL/NAT
   ↓
10.0.0.20:443
```

Esto se conoce habitualmente como:

> **port forwarding**.

Puede ser necesario para publicar servicios, pero debe coordinarse con la política de seguridad.

---

# 🧨 14. NAT Y DMZ

Supongamos:

```text
INTERNET
    ↓
NAT
    ↓
SERVIDOR WEB
```

Si la política establece:

```text
"todos los servidores web públicos
deben estar en la DMZ"
```

no debemos crear accidentalmente:

```text
NAT
 ↓
SERVIDOR WEB INTERNO
```

NIST señala precisamente que las configuraciones de NAT deben ser coherentes con la política de firewall y la arquitectura DMZ. 

---

# 🔐 15. VPN

Una:

> **VPN (Virtual Private Network)**

permite crear comunicaciones protegidas sobre una red no confiable.

Conceptualmente:

```text
CLIENTE
   ↓
 INTERNET
   ↓
===================
      TÚNEL
===================
   ↓
VPN GATEWAY
   ↓
RED INTERNA
```

NIST describe las VPN como un requisito habitual en firewalls perimetrales para cifrar y descifrar flujos específicos entre redes protegidas y externas. 

---

# 🌐 16. VPN SITE-TO-SITE

Conecta dos redes:

```text
RED A
  │
VPN GATEWAY
  ║
  ║ TÚNEL
  ║
VPN GATEWAY
  │
RED B
```

Ejemplo:

```text
SEDE MURCIA
     ║
     ║ VPN
     ║
SEDE MADRID
```

Los equipos de ambas redes pueden comunicarse según las políticas establecidas.

---

# 💻 17. VPN REMOTE ACCESS

Conecta un usuario remoto:

```text
PORTÁTIL
   ↓
INTERNET
   ↓
VPN
   ↓
GATEWAY
   ↓
RED CORPORATIVA
```

Es habitual para:

```text
teletrabajo
administración remota
acceso a recursos internos
```

---

# 🔐 18. IPSEC

Uno de los principales mecanismos para VPN es:

> **IPsec**

que proporciona mecanismos de seguridad para comunicaciones IP.

En una arquitectura IPsec pueden aparecer:

```text
ESP
AH
IKE
```

No debemos confundirlos:

```text
ESP
→ protección de datos IP

AH
→ autenticación/integridad del paquete IP
  sin proporcionar cifrado del contenido

IKE
→ negociación y gestión de asociaciones/credenciales
```

---

# 🛡️ 19. ESP

ESP significa:

> **Encapsulating Security Payload**

Puede proporcionar:

```text
confidencialidad
+
integridad/autenticación
```

dependiendo de la configuración y algoritmo utilizados.

Es muy habitual en VPN IPsec.

---

# 🧾 20. AH

AH significa:

> **Authentication Header**

Proporciona mecanismos de:

```text
autenticación
+
integridad
```

pero:

```text
NO CIFRA
```

el contenido.

### 🧠 Trampa

```text
AH
→ autenticación/integridad

ESP
→ puede cifrar
```

---

# 🔄 21. IKE

IKE significa:

> **Internet Key Exchange**

Se utiliza para negociar parámetros y material criptográfico necesario para IPsec.

Simplificando:

```text
PEER A
   ↓
 IKE
   ↓
PEER B
   ↓
NEGOCIACIÓN
   ↓
ASOCIACIÓN SEGURA
```

---

# 🌐 22. SSL/TLS VPN

También existen soluciones VPN basadas en:

```text
SSL/TLS
```

El concepto es:

```text
CLIENTE
   ↓
TLS
   ↓
VPN GATEWAY
```

INCIBE señala que una VPN crea una conexión privada y cifrada entre el usuario remoto y la pasarela VPN, aunque ese cifrado también puede dificultar la inspección del tráfico por los controles perimetrales. 

---

# ⚠️ 23. VPN Y VISIBILIDAD

Tenemos:

```text
ATACANTE
   ↓
VPN
   ↓
RED INTERNA
```

El firewall perimetral puede ver:

```text
CONEXIÓN VPN
```

pero no necesariamente:

```text
CONTENIDO INTERNO DEL TÚNEL
```

Esto puede generar:

```text
PUNTO CIEGO
```

---

# 🛡️ 24. VPN + INSPECCIÓN

Una organización puede plantear:

```text
VPN
 ↓
DESCIFRADO
 ↓
INSPECCIÓN
 ↓
POLÍTICA
 ↓
RED INTERNA
```

INCIBE explica que determinadas arquitecturas de inspección SSL pueden descifrar el tráfico, inspeccionarlo y volver a cifrarlo, precisamente para evitar que ataques ocultos dentro de túneles cifrados atraviesen los controles sin inspección. 

---

# 👤 25. AUTENTICACIÓN VPN

Una VPN no debería significar:

```text
"tengo contraseña → entro en todo"
```

Podemos utilizar:

```text
usuario
+
contraseña
+
MFA
+
certificado
+
comprobación del dispositivo
```

según la arquitectura.

---

# 🧪 26. NETWORK ACCESS CONTROL

Un firewall puede integrarse con:

> **NAC (Network Access Control)**

para tomar decisiones considerando:

```text
identidad
+
estado del dispositivo
+
política
```

Por ejemplo:

```text
USUARIO AUTENTICADO
        +
EQUIPO ACTUALIZADO
        +
ANTIVIRUS ACTIVO
        ↓
      ACCESO
```

Si el equipo no cumple:

```text
CUARENTENA / DENEGACIÓN
```

según la solución.

---

# 🎭 27. SPOOFING

Un atacante puede intentar falsificar información de origen.

Esto se conoce como:

> **spoofing**.

Por ejemplo:

```text
IP REAL
203.0.113.50

ATACANTE
↓
finge ser
↓
10.10.10.10
```

---

# 🛡️ 28. IP SPOOFING

El atacante manipula:

```text
IP ORIGEN
```

para intentar:

```text
bypass
+
ocultación
+
confusión
```

Por eso no debemos basar toda la confianza en una IP de origen sin considerar el contexto y el punto donde se valida.

---

# 🧱 29. INGRESS FILTERING

Una defensa frente al spoofing consiste en aplicar políticas sobre el tráfico que entra desde una interfaz.

Conceptualmente:

```text
INTERFAZ EXTERNA
      ↓
¿ESA IP DE ORIGEN
   ES POSIBLE AQUÍ?
      ↓
     NO
      ↓
   BLOQUEAR
```

Esto ayuda a impedir que tráfico externo utilice rangos de origen que deberían pertenecer a otra red.

---

# 🕵️ 30. EGRESS FILTERING

También podemos controlar:

```text
TRÁFICO SALIENTE
```

para evitar que equipos internos envíen tráfico con:

```text
direcciones de origen
no autorizadas
```

Esto puede ayudar a:

```text
reducir spoofing
+
detectar errores
+
limitar determinados ataques
```

---

# 🧨 31. EVASIÓN DE FIREWALL

Un atacante puede intentar encontrar una ruta que no esté controlada.

Por ejemplo:

```text
ENTRADA A
→ BLOQUEADA

ENTRADA B
→ SIN FIREWALL
```

Resultado:

```text
BYPASS
```

NIST advierte de la importancia de aplicar las políticas de firewall en todos los puntos de entrada relevantes, ya que un acceso alternativo puede permitir que tráfico que debería bloquearse entre por otra vía. 

---

# 🔀 32. BYPASS POR SEGUNDA INTERFAZ

Servidor:

```text
NIC 1
 ↓
FIREWALL
 ↓
RED
```

pero además:

```text
NIC 2
 ↓
OTRA RED
```

Si la segunda interfaz no está controlada:

```text
FIREWALL PERIMETRAL
       ↓
    EVITADO
```

Esto puede crear una vía de ataque.

---

# 🧱 33. BYPASS POR RED INALÁMBRICA

Otra posibilidad:

```text
RED CORPORATIVA
      │
      ↓
   FIREWALL
```

pero:

```text
WIFI NO AUTORIZADO
      ↓
RED INTERNA
```

La política debe contemplar todos los puntos de entrada.

---

# 🧪 34. CASO · SERVIDOR MULTIHOMED

Tenemos:

```text
SERVIDOR
 ├── eth0 → RED INTERNA
 └── eth1 → RED EXTERNA
```

Aunque el firewall principal esté perfectamente configurado:

```text
eth1
 ↓
¿qué controles existen?
```

La arquitectura debe analizar:

```text
rutas
+
interfaces
+
ACL
+
firewall local
```

---

# 🧯 35. ALTA DISPONIBILIDAD

Un firewall es un componente crítico.

Si falla:

```text
INTERNET
   X
FIREWALL
   X
RED
```

podemos perder:

```text
conectividad
+
seguridad
```

Por eso podemos utilizar:

> **High Availability (HA)**.

---

# 🔁 36. FIREWALL EN HA

Arquitectura:

```text
             INTERNET
                 │
          ┌──────┴──────┐
          ↓             ↓
      FIREWALL A   FIREWALL B
          │             │
          └──────┬──────┘
                 ↓
             RED INTERNA
```

Normalmente:

```text
ACTIVO
+
STANDBY
```

aunque existen configuraciones activas-activo.

NIST señala que los firewalls HA pueden permitir que uno tome el relevo de otro si el primero falla o se retira para mantenimiento. 

---

# 🔄 37. FAILOVER

Si:

```text
FIREWALL A
```

falla:

```text
A
X
```

el sistema realiza:

```text
FAILOVER
```

y:

```text
FIREWALL B
```

asume la función.

---

# 🧠 38. STATE SYNCHRONIZATION

En firewalls stateful, una pareja HA puede necesitar sincronizar:

```text
sesiones
+
estado
+
configuración
```

para evitar que el failover destruya todas las conexiones.

---

# 🧩 43. NAT Y LOGS


# 🧪 52. ¿QUÉ PASA SI COMPROMETEN EL WEB?




# 🧠 54. CHECKLIST DE SEGURIDAD OPERATIVA

```text
□ Todas las entradas a la red están controladas.

□ No existen interfaces o rutas alternativas sin supervisión.

□ Las ACL están documentadas.

□ Las reglas tienen justificación.

□ Existe una política de denegación por defecto cuando procede.

□ Las reglas específicas están correctamente ordenadas.

□ Se eliminan reglas obsoletas.

□ NAT está coordinado con la política de seguridad.

□ Los servicios públicos están correctamente segmentados.

□ La DMZ está separada de la red interna.

□ VPN utiliza autenticación adecuada.

□ El acceso VPN sigue mínimo privilegio.

□ Se controla el tráfico saliente.

□ Se contemplan ataques de spoofing.

□ Los firewalls críticos tienen HA cuando procede.

□ Existe sincronización de estado/configuración cuando es necesaria.

□ Los logs se centralizan o conservan adecuadamente.

□ Los cambios están auditados.

□ Las reglas se prueban.

□ Se revisan periódicamente.

□ Existen copias de seguridad de la configuración.
```

# 🎴 58. ANKI

## Tarjeta 1

**P:** ¿Qué es una ACL?

**R:** Lista de reglas que determina qué tráfico se permite o deniega.

## Tarjeta 2

**P:** ¿Qué es NAT?

**R:** Traducción de direcciones de red.

## Tarjeta 3

**P:** ¿Qué es PAT?

**R:** Traducción de direcciones utilizando también los puertos para multiplexar conexiones.

## Tarjeta 4

**P:** ¿NAT es equivalente a firewall?

**R:** No. NAT traduce direcciones; el firewall aplica políticas de control de tráfico.

## Tarjeta 5

**P:** ¿Qué es una VPN site-to-site?

**R:** Una VPN que conecta dos redes o sedes.

## Tarjeta 6

**P:** ¿Qué es una VPN de acceso remoto?

**R:** Una VPN que conecta un usuario/equipo remoto con una red protegida.

## Tarjeta 7

**P:** ¿Qué hace ESP?

**R:** Puede proporcionar confidencialidad e integridad/autenticación en IPsec según la configuración.

## Tarjeta 8

**P:** ¿Qué hace AH?

**R:** Proporciona autenticación/integridad, pero no cifra el contenido.

## Tarjeta 9

**P:** ¿Qué es spoofing?

**R:** Falsificación de información de identificación, como una dirección IP de origen.

## Tarjeta 10

**P:** ¿Qué es HA en firewalls?

**R:** Arquitectura de alta disponibilidad que permite que otro firewall asuma el servicio ante un fallo.

## Tarjeta 11

**P:** ¿Qué es failover?

**R:** Cambio automático o controlado hacia un componente de respaldo cuando falla el principal.

## Tarjeta 12

**P:** ¿Por qué son importantes los logs?

**R:** Permiten auditoría, detección, investigación, correlación y respuesta ante incidentes.
