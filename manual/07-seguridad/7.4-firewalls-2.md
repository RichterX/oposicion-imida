# 🔥 BLOQUE 07 · SEGURIDAD
# 7.4 · FIREWALLS
## Parte 2 · NGFW, UTM, WAF, inspección avanzada, VPN y diseño de reglas

> **Objetivo:** avanzar desde el firewall tradicional hacia las arquitecturas y tecnologías modernas: inspección profunda, firewalls de nueva generación (NGFW), UTM, WAF, VPN, segmentación y diseño de políticas.
>
> **Fuentes técnicas principales:** NIST SP 800-41 Rev. 1, NIST SP 800-215 e INCIBE. NIST describe la evolución desde el filtrado de paquetes y la inspección stateful hacia el análisis de protocolos y funciones de capa de aplicación; INCIBE diferencia firewall tradicional, UTM y NGFW y describe sus capacidades habituales. 

---

# 🧭 1. ¿POR QUÉ EVOLUCIONAN LOS FIREWALLS?

Un firewall clásico puede tomar decisiones basándose principalmente en:

```text
IP
+
PUERTO
+
PROTOCOLO
+
ESTADO
```

Pero una aplicación moderna puede utilizar:

```text
TCP/443
```

para transportar:

```text
una aplicación web legítima
+
una API
+
una aplicación no autorizada
+
contenido malicioso
```

Por tanto:

> **el puerto por sí solo no siempre dice qué está ocurriendo.**

Esta evolución lleva a tecnologías capaces de analizar más contexto. NIST describe precisamente la inspección de protocolos y el análisis de capa de aplicación como una evolución de la inspección stateful tradicional. 

---

# 🔬 2. DE CAPA 3/4 A CAPA 7

Podemos simplificar la evolución:

```text
FIREWALL TRADICIONAL
        ↓
CAPA 3 / CAPA 4
        ↓
IP + PUERTO + PROTOCOLO
```

hacia:

```text
FIREWALL AVANZADO
        ↓
CAPA 7
        ↓
APLICACIÓN + CONTENIDO + CONTEXTO
```

Esto no significa que un NGFW deje de utilizar IP, puertos o estado.

Al contrario:

```text
CAPAS INFERIORES
+
INSPECCIÓN AVANZADA
```

---

# 🧠 3. DPI · DEEP PACKET INSPECTION

La:

> **Deep Packet Inspection (DPI)**

o:

> **inspección profunda de paquetes**

permite analizar información más allá de las simples cabeceras.

Puede utilizarse para identificar:

```text
protocolos
+
aplicaciones
+
patrones
+
contenido
```

NIST describe la inspección profunda/protocol analysis como una extensión de la inspección stateful que incorpora análisis del comportamiento de protocolos en la capa de aplicación. 

---

# 🧪 4. EJEMPLO DE DPI

Tenemos:

```text
CLIENTE
   ↓
TCP/443
   ↓
FIREWALL
```

Un firewall básico puede ver:

```text
TCP
443
```

Un sistema más avanzado puede intentar determinar:

```text
¿QUÉ APLICACIÓN?
¿QUÉ PROTOCOLO?
¿QUÉ COMPORTAMIENTO?
¿ES COMPATIBLE CON LA POLÍTICA?
```

Por ejemplo:

```text
TCP/443
   ↓
Aplicación identificada
   ↓
POLÍTICA
   ↓
PERMITIR / BLOQUEAR
```

---

# 🚀 5. NGFW

NGFW significa:

> **Next-Generation Firewall**

o:

> **Firewall de Nueva Generación.**

INCIBE señala que los NGFW incorporan capacidades avanzadas y pueden aplicar políticas de seguridad a nivel de aplicación, mientras que NIST destaca la conciencia sobre los datos de aplicación como característica diferenciadora de esta generación. 

---

# 🧩 6. ¿QUÉ AÑADE UN NGFW?

Dependiendo del producto, puede integrar:

```text
✓ filtrado tradicional
✓ stateful inspection
✓ identificación de aplicaciones
✓ inspección profunda
✓ control de aplicaciones
✓ funciones IPS
✓ VPN
✓ filtrado web
✓ control de usuarios
✓ registro y monitorización
```

No todos los productos incorporan exactamente las mismas capacidades.

### 🧠 Para examen

Quédate con:

```text
FIREWALL TRADICIONAL
→ tráfico

NGFW
→ tráfico + aplicación + contexto
```

---

# 🎯 7. CONTROL POR APLICACIÓN

Imaginemos:

```text
TCP/443
```

Un firewall tradicional podría permitir:

```text
TCP/443
```

Un NGFW puede intentar distinguir:

```text
Aplicación A → PERMITIR
Aplicación B → BLOQUEAR
```

Aunque ambas utilicen el mismo puerto.

Esto permite crear políticas más específicas.

---

# 👤 8. CONTROL BASADO EN USUARIO

Algunos NGFW pueden integrar información de identidad.

Podemos pasar de:

```text
IP → PERMITIR
```

a:

```text
USUARIO
+
APLICACIÓN
+
DESTINO
→
DECISIÓN
```

Ejemplo:

```text
Usuario: administración
Aplicación: SSH
Destino: servidores
→ PERMITIR
```

mientras:

```text
Usuario: usuario general
Aplicación: SSH
Destino: servidores
→ DENEGAR
```

---

# 🧱 9. MICROSEGMENTACIÓN

La segmentación tradicional puede separar:

```text
RED USUARIOS
        │
        ↓
     FIREWALL
        │
        ↓
RED SERVIDORES
```

La microsegmentación lleva la idea más lejos:

```text
SERVIDOR A
   │
   ├── política
   │
SERVIDOR B
   │
   ├── política
   │
SERVIDOR C
```

El objetivo es limitar las comunicaciones permitidas incluso dentro del mismo entorno.

Esto ayuda a reducir:

```text
MOVIMIENTO LATERAL
```

---

# 🕸️ 10. MOVIMIENTO LATERAL

Supongamos:

```text
ATACANTE
   ↓
SERVIDOR WEB
   ↓
RED INTERNA
   ↓
BASE DE DATOS
   ↓
OTROS SERVIDORES
```

Si todo está permitido:

> comprometer un sistema puede facilitar el acceso a muchos otros.

Con segmentación:

```text
SERVIDOR WEB
     ↓
solo conexiones necesarias
     ↓
BASE DE DATOS
```

se limita el recorrido posible.

---

# 🧰 11. UTM

UTM significa:

> **Unified Threat Management**

o:

> **Gestión Unificada de Amenazas.**

INCIBE describe los UTM como soluciones que concentran diversas funciones de seguridad y que pueden incluir firewall, antivirus, IDS/IPS, VPN, antispam y filtrado de contenidos. 

---

# 📦 12. ¿QUÉ PUEDE INCLUIR UN UTM?

Por ejemplo:

```text
FIREWALL
+
ANTIVIRUS
+
IDS/IPS
+
VPN
+
ANTISPAM
+
FILTRADO WEB
+
CONTROL DE CONTENIDOS
```

La combinación exacta depende de la solución.

---

# 🆚 13. UTM VS NGFW

Aquí aparece una pregunta clásica.

### UTM

La idea central es:

> **integrar muchas funciones de seguridad en una solución unificada.**

### NGFW

La idea central es:

> **ampliar las capacidades del firewall mediante mayor contexto e inspección, especialmente a nivel de aplicación.**

INCIBE destaca que ambos pueden compartir funcionalidades como IPS, VPN, registro, monitorización y control de aplicaciones, pero los diferencia por su enfoque y arquitectura. 

---

# 📊 14. TABLA UTM VS NGFW

| Característica | UTM | NGFW |
|---|---:|---:|
| Firewall | ✅ | ✅ |
| VPN | Habitual | Habitual |
| IDS/IPS | Habitual | Habitual |
| Antivirus | Habitual | Puede integrarse |
| Filtrado web | Habitual | Habitual |
| Control aplicaciones | Puede existir | Muy relevante |
| Gestión unificada | ⭐⭐⭐ | Variable |
| Inspección avanzada | Puede existir | ⭐⭐⭐ |
| Enfoque | Integración | Firewall avanzado |

### ⚠️ Importante

No memorices esto como una frontera absoluta.

Los productos comerciales modernos pueden solaparse muchísimo.

---

# 🧪 15. CASO UTM

Una pequeña organización necesita:

```text
firewall
+
VPN
+
antivirus de red
+
antispam
+
IDS/IPS
+
filtrado web
```

Puede resultar interesante una solución:

```text
UTM
```

porque concentra múltiples funciones.

---

# 🧪 16. CASO NGFW

Una organización grande necesita:

```text
gran volumen de tráfico
+
control de aplicaciones
+
políticas avanzadas
+
segmentación
+
inspección
```

Un:

```text
NGFW
```

puede ser más adecuado.

INCIBE señala precisamente los NGFW como soluciones orientadas a organizaciones con grandes volúmenes de conexiones, mientras que los UTM suelen orientarse a organizaciones que buscan integrar numerosas funciones en una solución unificada. 

---

# 🌐 17. WAF

Recordemos:

> **Web Application Firewall**

Un WAF está especializado en proteger aplicaciones web.

Su foco está principalmente en:

```text
HTTP
HTTPS
```

INCIBE describe el WAF como un cortafuegos específico para aplicar reglas de filtrado sobre comunicaciones HTTP y proteger frente a ataques comunes como XSS e inyección SQL. 

---

# 🧪 18. WAF VS FIREWALL DE RED

### Firewall de red

Pregunta:

```text
¿PERMITO ESTA COMUNICACIÓN?
```

Puede analizar:

```text
IP
puerto
protocolo
estado
```

### WAF

Pregunta:

```text
¿ESTA PETICIÓN WEB ES ACEPTABLE?
```

Puede analizar:

```text
URL
parámetros
cabeceras HTTP
cookies
contenido
patrones de ataque
```

---

# 🧨 19. EJEMPLO SQL INJECTION

Petición:

```text
GET /users?id=1' OR '1'='1
```

Arquitectura:

```text
INTERNET
    ↓
   WAF
    ↓
¿PETICIÓN SOSPECHOSA?
    ↓
   SÍ
    ↓
 BLOQUEAR
```

El WAF puede impedir que la petición llegue a la aplicación si la regla correspondiente la identifica.

---

# 🧨 20. EJEMPLO XSS

Petición:

```text
/search?q=<script>...
```

El WAF puede detectar un patrón asociado a:

```text
Cross-Site Scripting
```

y bloquearlo según la política configurada.

---

# ⚠️ 21. WAF NO ES UNA GARANTÍA ABSOLUTA

Un WAF:

```text
NO
↓
hace segura automáticamente una aplicación vulnerable
```

Puede ayudar a:

```text
reducir riesgo
+
detectar
+
bloquear
```

pero la aplicación debe seguir aplicando:

```text
validación de entradas
+
autorización
+
codificación de salida
+
actualizaciones
+
pruebas de seguridad
```

---

# 🔒 22. FIREWALL + VPN

Una VPN permite crear un:

> **túnel seguro sobre una red no confiable**, normalmente Internet.

INCIBE describe las VPN como herramientas que crean conexiones seguras mediante túneles cifrados para acceder a recursos de una red corporativa.

# 🏛️ 26. ARQUITECTURA DE DOS FIREWALLS

Una arquitectura clásica:

```text

   │
   ↓

   │
```


# 🔢 28. DISEÑO DE REGLAS

Una regla debería responder:

```text
¿QUIÉN?
¿DESDE DÓNDE?
¿HACIA DÓNDE?
¿QUÉ SERVICIO?
¿CUÁNDO?
¿QUÉ ACCIÓN?
¿SE REGISTRA?
```

Por ejemplo:

```text
ORIGEN:      RED_ADMIN
DESTINO:     SERVIDOR_WEB
SERVICIO:    SSH
ACCIÓN:      ALLOW
LOG:         YES
```

---

# 🧹 29. REGLAS ESPECÍFICAS

Mala:

```text
ALLOW
10.0.0.0/8
ANY
ANY
```

Mejor:

```text
ALLOW
10.10.10.0/24
SERVIDOR_WEB
TCP/22
```

Principio:

> **cuanto más precisa sea la regla, menor será la superficie de exposición.**

---

# 🔄 30. ORDEN Y SOMBREADO DE REGLAS

Supongamos:

```text
1. ALLOW 10.0.0.0/8 → SERVER TCP/443
2. DENY  10.10.10.50 → SERVER ANY
```

Si el sistema procesa de arriba abajo:

```text
10.10.10.50 → TCP/443
```

puede coincidir primero con:

```text
REGLA 1
```

y ser permitido.

La regla 2 queda:

> **sombreada para ese tráfico.**

### 🧠 Lección

El orden de reglas importa.

---

# 🧪 31. CASO · REGLAS DE UN SERVIDOR WEB

Tenemos:

```text
WEB = 10.0.10.20
DB  = 10.0.20.30
```

Necesitamos:

```text
Internet → WEB : 443
WEB → DB       : 3306
Admin → WEB    : 22
```

Política:

```text
1. ALLOW ANY → 10.0.10.20 TCP/443
2. ALLOW 10.0.10.20 → 10.0.20.30 TCP/3306
3. ALLOW 10.10.10.0/24 → 10.0.10.20 TCP/22
4. DENY ANY → 10.0.20.30 TCP/3306
5. DENY ANY → ANY
```

---

# 🚨 32. ERROR CLÁSICO

```text
DENY INTERNET → DB/3306
```

También debemos pensar:

```text
¿QUÉ OTRAS REDES PUEDEN ACCEDER?
```

Una política correcta debería permitir únicamente las comunicaciones necesarias.

# 🚨 46. TRAMPAS DE EXAMEN

### ❌ Trampa 1

> "NGFW significa simplemente un firewall más rápido."

Incorrecto.

La evolución está relacionada con capacidades avanzadas de inspección y conocimiento de aplicaciones/contexto.

---

### ❌ Trampa 2

> "UTM y NGFW son exactamente lo mismo."

Incorrecto.

Se solapan mucho, pero el enfoque conceptual es diferente.

```text
UTM
→ integración de funciones

NGFW
→ firewall avanzado / aplicación / contexto
```

---

### ❌ Trampa 3

> "WAF sustituye al firewall de red."

Incorrecto.

Protegen capas y problemas diferentes.

---

### ❌ Trampa 4

> "Si el puerto 443 está permitido, cualquier aplicación HTTPS debe estar permitida."

No necesariamente.

Un NGFW puede aplicar políticas basadas en aplicación y contexto.

---

### ❌ Trampa 5

> "Una VPN concede acceso completo a la red interna."

Incorrecto.

Debe aplicarse mínimo privilegio.

---

### ❌ Trampa 6

> "Un firewall elimina la necesidad de IDS/IPS."

Incorrecto.

Son controles complementarios.

---

### ❌ Trampa 7

> "Una DMZ hace que un servidor sea seguro."

Incorrecto.

Reduce exposición y limita el alcance potencial, pero no elimina vulnerabilidades.

---

### ❌ Trampa 8

> "El firewall puede inspeccionar siempre el contenido de HTTPS."

Incorrecto.

El cifrado limita la visibilidad salvo que se utilicen mecanismos específicos de inspección TLS.

---

### ❌ Trampa 9

> "Más reglas significa más seguridad."

No necesariamente.

Reglas excesivas, contradictorias u obsoletas pueden aumentar el riesgo de errores.

---

### ❌ Trampa 10

> "El orden de las reglas no importa."

Puede importar muchísimo.

---
