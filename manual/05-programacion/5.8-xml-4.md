# 1. INTRODUCCIÓN

Hasta ahora hemos estudiado XML desde el punto de vista del documento:

```text
estructura
DTD
XSD
XPath
XSLT
```

Pero queda una pregunta importante:

> ¿Cómo puede un programa leer y trabajar con un documento XML?

La respuesta pasa por los:

```text
parsers XML
```

Y aquí aparecen dos modelos clásicos que debemos conocer:

```text
DOM
SAX
```

La diferencia entre ambos es especialmente importante para preguntas teóricas.

---

# 2. ¿QUÉ ES UN PARSER?

Un parser es un componente que analiza un documento y comprueba/interpreta su estructura de acuerdo con las reglas del formato.

En XML, un parser puede:

```text
leer el documento
analizar su sintaxis
detectar errores
construir estructuras de datos
proporcionar acceso al contenido
```

Dependiendo del parser y su configuración, también puede participar en la validación frente a:

```text
DTD
XML Schema
```

---

# 3. FLUJO BÁSICO

Conceptualmente:

```text
Documento XML
      │
      ↓
    Parser
      │
      ├── analiza sintaxis
      │
      ├── detecta errores
      │
      └── proporciona acceso a los datos
```

---

# 4. PARSER Y DOCUMENTO BIEN FORMADO

Un parser XML comprueba las reglas sintácticas necesarias para determinar si un documento está bien formado.

Por ejemplo, puede detectar:

```xml
<usuario>
    <nombre>Pedro</usuario>
```

porque las etiquetas no están correctamente anidadas.

---

# 5. ERRORES DE PARSING

Si un documento XML no cumple las reglas sintácticas, el parser puede producir un error.

Ejemplos:

```text
etiqueta sin cerrar
atributo sin comillas
varios elementos raíz
anidamiento incorrecto
caracteres no permitidos
```

---

# 6. PARSER VALIDANTE

Un parser puede trabajar además con mecanismos de validación.

Conceptualmente:

```text
XML
 ↓
parser
 ↓
¿bien formado?
 ↓
¿cumple DTD/XSD?
```

La posibilidad concreta de validar depende de la tecnología y configuración utilizada.

---

# 7. DOS MODELOS CLÁSICOS

Los dos modelos tradicionales que debemos conocer son:

```text
DOM
SAX
```

Sus filosofías son diferentes.

```text
DOM
→ construir una representación en memoria

SAX
→ procesar mediante eventos
```

Esta diferencia es probablemente la idea más importante de esta parte.

---

# 8. DOM

DOM significa:

```text
Document Object Model
```

Es un modelo que representa el documento como un árbol de nodos.

---

# 9. XML COMO ÁRBOL DOM

Dado:

```xml
<empresa>

    <empleado>
        <nombre>Pedro</nombre>
        <puesto>Desarrollador</puesto>
    </empleado>

</empresa>
```

DOM puede representar:

```text
Document
└── empresa
    └── empleado
        ├── nombre
        │   └── "Pedro"
        │
        └── puesto
            └── "Desarrollador"
```

---

# 10. NODOS DOM

El árbol puede contener diferentes tipos de nodos:

```text
Document
Element
Attribute
Text
Comment
```

entre otros.

---

# 11. DOM CARGA EL DOCUMENTO

El enfoque DOM normalmente implica construir una representación del documento en memoria.

Por tanto:

```text
archivo XML
      ↓
parser DOM
      ↓
árbol en memoria
```

---

# 12. VENTAJA PRINCIPAL DE DOM

Una vez construido el árbol podemos navegar por él.

Podemos:

```text
buscar nodos
leer valores
modificar elementos
crear nodos
eliminar nodos
```

Esto proporciona un acceso flexible.

---

# 13. ACCESO ALEATORIO

DOM permite navegar entre diferentes partes del documento sin tener que procesarlo necesariamente de principio a fin cada vez.

Podemos movernos por relaciones como:

```text
padre
hijo
hermano
descendiente
```

---

# 14. MODIFICACIÓN CON DOM

Una característica importante es que el árbol puede modificarse.

Conceptualmente:

```text
crear elemento
     ↓
insertarlo
     ↓
modificar atributos
     ↓
eliminar nodos
```

---

# 15. DESVENTAJA DE DOM

La principal desventaja es el consumo de memoria.

Para documentos XML muy grandes:

```text
archivo grande
      ↓
árbol grande
      ↓
más memoria
```

Puede ser un problema.

---

# 16. DOM Y DOCUMENTOS GRANDES

Si el XML tiene:

```text
10 MB
```

la estructura DOM en memoria puede requerir considerablemente más memoria que el archivo original debido a la representación de nodos y estructuras auxiliares.

Por tanto, no debemos asumir:

```text
tamaño XML = memoria DOM
```

---

# 17. SAX

SAX significa:

```text
Simple API for XML
```

Es un modelo de procesamiento basado en eventos.

---

# 18. FILOSOFÍA DE SAX

En lugar de construir necesariamente un árbol completo:

```text
SAX
→ lee el documento secuencialmente
→ genera eventos
→ el programa responde a esos eventos
```

---

# 19. EJEMPLO CONCEPTUAL

Para:

```xml
<usuario>
    <nombre>Pedro</nombre>
</usuario>
```

podríamos recibir eventos conceptuales:

```text
startDocument
startElement(usuario)
startElement(nombre)
characters("Pedro")
endElement(nombre)
endElement(usuario)
endDocument
```

---

# 20. CALLBACKS

En muchas implementaciones SAX, el programa proporciona manejadores o callbacks que reaccionan a eventos.

Por ejemplo:

```text
startElement()
characters()
endElement()
```

La API concreta puede variar según el lenguaje o biblioteca.

---

# 21. PROCESAMIENTO SECUENCIAL

SAX procesa el documento de forma secuencial.

Conceptualmente:

```text
inicio
 ↓
elemento 1
 ↓
contenido
 ↓
elemento 2
 ↓
...
 ↓
final
```

No necesita construir obligatoriamente todo el árbol en memoria.

---

# 22. VENTAJA PRINCIPAL DE SAX

SAX puede utilizar mucha menos memoria que DOM para documentos grandes.

Especialmente cuando:

```text
solo necesitamos leer/procesar
```

los datos.

---

# 23. SAX Y STREAMING

SAX se asocia con un modelo:

```text
streaming
```

porque el documento puede procesarse conforme se va leyendo.

No es necesario disponer de un árbol completo antes de empezar a reaccionar a los eventos.

---

# 24. DESVENTAJA DE SAX

El acceso no es tan cómodo como DOM para navegar arbitrariamente por el documento.

Si queremos volver atrás:

```text
SAX
→ normalmente necesitamos gestionar nosotros mismos la información necesaria
```

No tenemos un árbol completo listo para navegar.

---

# 25. SAX NO ESTÁ DISEÑADO PARA MODIFICAR EL ÁRBOL

A diferencia de DOM, SAX es fundamentalmente un modelo de lectura/procesamiento mediante eventos.

No ofrece directamente:

```text
árbol editable
```

como DOM.

---

# 26. DOM VS SAX

| Característica | DOM | SAX |
|---|---|---|
| Modelo | Árbol | Eventos |
| Memoria | Mayor | Menor |
| Acceso aleatorio | Sí | No directamente |
| Modificación | Sí | No como árbol |
| Procesamiento secuencial | No es su idea principal | Sí |
| Documentos grandes | Puede ser costoso | Más adecuado |
| Complejidad de navegación | Menor | Mayor |
| Streaming | No es el modelo principal | Sí |

---

# 27. 🧠 REGLA PARA MEMORIZAR

```text
DOM
→ Documento completo en memoria

SAX
→ Sucesión de eventos
```

O incluso:

```text
DOM = árbol
SAX = eventos
```

Si recuerdas esto, puedes reconstruir buena parte de las diferencias.

---

# 28. CASO DE USO DOM

Supongamos que tenemos un XML relativamente pequeño:

```text
configuracion.xml
```

y queremos:

```text
buscar nodos
modificar valores
crear elementos
eliminar elementos
```

DOM es una opción natural.

---

# 29. CASO DE USO SAX

Tenemos un XML enorme con millones de registros:

```text
ventas.xml
```

y queremos:

```text
leer cada venta
calcular estadísticas
generar un resumen
```

No necesitamos conservar todo el documento.

SAX puede ser apropiado.

---

# 30. EJEMPLO CONCEPTUAL SAX

Imaginemos:

```xml
<ventas>

    <venta>
        <importe>100</importe>
    </venta>

    <venta>
        <importe>250</importe>
    </venta>

</ventas>
```

Podemos procesar:

```text
venta 1
→ sumar 100

venta 2
→ sumar 250
```

sin necesitar mantener todo el árbol.

Resultado:

```text
350
```

---

# 31. DOM Y SAX: CRITERIO DE ELECCIÓN

Una regla práctica:

```text
Necesito navegar/modificar
→ DOM

Necesito procesar secuencialmente
→ SAX
```

Y otra:

```text
Documento pequeño/moderado
→ DOM puede ser cómodo

Documento enorme
→ SAX puede ahorrar memoria
```

No es una regla absoluta, pero es una excelente regla de examen.

---

# 32. VALIDACIÓN

Ya vimos:

```text
bien formado
```

y:

```text
válido
```

Ahora podemos relacionarlo con parsers.

Un flujo conceptual:

```text
XML
 ↓
parser
 ↓
comprobación sintáctica
 ↓
bien formado
 ↓
validación DTD/XSD
 ↓
válido
```

---

# 33. VALIDACIÓN VS PARSING

No son exactamente lo mismo.

```text
Parsing
→ analizar la estructura/sintaxis

Validación
→ comprobar que cumple determinadas reglas de estructura/datos
```

Un documento puede ser:

```text
bien formado
```

sin ser:

```text
válido respecto a un XSD
```

---

# 34. XML Y ERRORES

Debemos distinguir entre:

```text
error de sintaxis
```

y:

```text
error de validación
```

Ejemplo de sintaxis:

```xml
<usuario>
    <nombre>Pedro</usuario>
```

Problema:

```text
mal formado
```

Ejemplo de validación:

```text
XSD exige edad
pero el documento no contiene edad
```

Entonces:

```text
bien formado
pero no válido
```

---

# 35. XML BIEN FORMADO

Recordatorio:

```text
un único elemento raíz
etiquetas correctamente cerradas
anidamiento correcto
atributos entre comillas
nombres válidos
```

---

# 36. XML VÁLIDO

Además:

```text
cumple DTD
```

o:

```text
cumple XSD
```

según el mecanismo de validación utilizado.

---

# 37. PARSERS Y NAMESPACES

Los parsers modernos deben poder trabajar con documentos XML que utilizan namespaces.

Ejemplo:

```xml
<lib:libro
    xmlns:lib="urn:libros">

    <lib:titulo>
        XML
    </lib:titulo>

</lib:libro>
```

El parser debe interpretar correctamente:

```text
prefijo
namespace
nombre local
```

---

# 38. XML Y MEMORIA

Podemos comparar:

```text
DOM
```

con:

```text
SAX
```

desde el punto de vista de memoria:

```text
DOM
████████████████████
árbol completo

SAX
██
procesamiento progresivo
```

No son cifras reales, sino una representación conceptual.

---

# 39. COMPLEJIDAD CON DOCUMENTOS GRANDES

Si el documento crece mucho:

```text
DOM
→ crece la estructura en memoria

SAX
→ puede mantener un consumo de memoria mucho más estable
```

Esto hace que los modelos basados en streaming sean especialmente útiles cuando el tamaño del documento es elevado.

---

# 40. LIMITACIÓN DE SAX

Si queremos preguntar:

> "Dame el elemento que estaba 300 nodos atrás"

SAX no mantiene automáticamente un árbol completo para responder a esa pregunta.

Tendríamos que:

```text
guardar nosotros la información necesaria
```

o utilizar otro enfoque.

---

# 41. LIMITACIÓN DE DOM

Si tenemos:

```text
documento XML gigantesco
```

crear todo el árbol puede provocar:

```text
alto consumo de memoria
```

y afectar al rendimiento.

---

# 42. PROCESAMIENTO HÍBRIDO

En aplicaciones reales existen otros enfoques y APIs de procesamiento XML además de los modelos clásicos.

Por ejemplo:

```text
StAX
```

es un modelo de parsing basado en eventos pero con control desde la aplicación, conocido como:

```text
pull parsing
```

No es necesario profundizar demasiado para este temario, pero conviene reconocer el nombre.

---

# 43. SAX VS STAX

Conceptualmente:

```text
SAX
→ el parser genera eventos y llama a callbacks

StAX
→ la aplicación solicita/consume eventos
```

Esto puede resumirse como:

```text
SAX = push
StAX = pull
```

---

# 44. DOM VS SAX VS STAX

| Modelo | Idea |
|---|---|
| DOM | árbol en memoria |
| SAX | eventos push |
| StAX | eventos pull |

Para una pregunta tipo test:

```text
árbol
→ DOM

push events
→ SAX

pull events
→ StAX
```

---

# 45. XML EN DIFERENTES LENGUAJES

Los lenguajes de programación suelen proporcionar bibliotecas para trabajar con XML.

Conceptualmente encontramos:

```text
parsear
consultar
validar
crear
modificar
transformar
```

La API concreta depende del lenguaje.

---

# 46. XML EN PHP

PHP dispone de herramientas para trabajar con XML.

Entre ellas:

```text
DOMDocument
SimpleXML
XMLReader
XMLWriter
```

---

# 47. `DOMDocument`

Permite trabajar con XML mediante una representación DOM.

Conceptualmente:

```php
$dom = new DOMDocument();

$dom->load('archivo.xml');
```

Después podemos navegar y modificar el documento.

---

# 48. `SimpleXML`

PHP también ofrece:

```text
SimpleXML
```

que proporciona una forma sencilla de acceder a datos XML.

Ejemplo conceptual:

```php
$xml = simplexml_load_file(
    'archivo.xml'
);

echo $xml->nombre;
```

Es especialmente cómodo para estructuras relativamente sencillas.

---

# 49. `XMLReader`

PHP dispone de:

```text
XMLReader
```

orientado al procesamiento XML mediante lectura secuencial.

Es adecuado para documentos grandes cuando no queremos cargar todo el documento en memoria.

Conceptualmente:

```text
XMLReader
→ streaming
→ bajo consumo de memoria
```

---

# 50. `XMLWriter`

También existe:

```text
XMLWriter
```

para generar documentos XML de manera controlada.

Conceptualmente:

```text
XMLWriter
→ escribir/generar XML
```

---

# 51. MAPA DE PHP

```text
                 PHP + XML
                     │
        ┌────────────┼─────────────┐
        ↓            ↓             ↓
   DOMDocument   SimpleXML    XMLReader
        │            │             │
      árbol       acceso       streaming
        │          sencillo         │
        └────────────┼─────────────┘
                     ↓
                 XMLWriter
                     │
                  generar
                    XML
```

---

# 52. DOMDocument VS XMLReader

### DOMDocument

```text
árbol
navegación
modificación
más memoria
```

### XMLReader

```text
secuencial
streaming
menos memoria
más control manual
```

Esta comparación puede ser especialmente interesante para ti porque trabajas con PHP.

---

# 53. SIMPLEXML VS DOM

### SimpleXML

```text
sencillo
rápido de escribir
cómodo para lectura
```

### DOM

```text
más control
navegación detallada
modificación estructurada
```

---

# 54. XML EN SERVICIOS WEB

XML ha sido especialmente importante en:

```text
SOAP
```

Un mensaje SOAP utiliza una estructura XML.

Conceptualmente:

```text
Envelope
├── Header
└── Body
```

---

# 55. SOAP

SOAP significa:

```text
Simple Object Access Protocol
```

Es un protocolo/marco de mensajería basado en XML para servicios web.

En aplicaciones modernas REST/JSON es menos habitual como elección nueva, pero sigue siendo relevante en muchos sistemas empresariales y legacy.

---

# 56. XML Y REST

REST no obliga a utilizar XML.

Una API REST puede utilizar:

```text
JSON
XML
texto
otros formatos
```

En la práctica, JSON es muy frecuente en APIs web modernas.

---

# 57. XML VS JSON EN APIs

XML:

```text
más verboso
atributos
namespaces
esquemas
```

JSON:

```text
más compacto
muy utilizado en APIs modernas
encaja naturalmente con objetos/arrays
```

Pero ambos pueden representar datos estructurados.

---

# 58. 🧠 TABLA FINAL DOM/SAX/STAX

| Concepto | DOM | SAX | StAX |
|---|---|---|---|
| Modelo | Árbol | Eventos | Eventos |
| Memoria | Alta | Baja | Baja |
| Acceso aleatorio | Sí | No | No |
| Modificación árbol | Sí | No | No |
| Flujo | Completo | Streaming | Streaming |
| Control | Navegación | Callbacks | Pull |
| Idea clave | Árbol | Push | Pull |
