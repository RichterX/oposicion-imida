# 1. INTRODUCCIÓN

En la Parte 1 estudiamos principalmente la **estructura estática** de UML:

```text
clases
objetos
paquetes
componentes
despliegue
relaciones
```

Ahora pasamos al comportamiento:

```text
¿Qué hace el sistema?
¿Cómo fluye un proceso?
¿Cómo cambia el estado de un objeto?
¿Cómo interactúan varios participantes?
¿En qué orden ocurren los mensajes?
```

Los diagramas que más nos interesan aquí son:

```text
Casos de uso
Actividades
Estados
Secuencia
```

---

# 2. DIAGRAMAS DE CASOS DE USO

Un diagrama de casos de uso representa:

```text
funcionalidades del sistema
+
actores que interactúan con ellas
```

Su objetivo principal es mostrar:

```text
QUÉ hace el sistema
```

desde el punto de vista de los actores.

No pretende describir cómo se implementa internamente cada funcionalidad.

---

# 3. ACTOR

Un actor representa un rol que interactúa con el sistema.

Puede ser:

```text
persona
sistema externo
dispositivo
organización
```

Lo importante es que representa un:

```text
ROL
```

y no necesariamente una persona concreta.

---

# 4. EJEMPLO DE ACTOR

En una aplicación bancaria podemos tener:

```text
Cliente
Administrador
Sistema bancario externo
```

Todos pueden actuar como actores dependiendo de la interacción que tengan con el sistema.

---

# 5. CASO DE USO

Un caso de uso representa una funcionalidad o conjunto de interacciones que proporciona valor a un actor.

Ejemplos:

```text
Iniciar sesión
Consultar saldo
Realizar transferencia
Generar informe
```

Normalmente se representa mediante una elipse:

```text
      _______________
     /               \
    (  Consultar      )
    (     saldo       )
     \_______________/
```

---

# 6. LÍMITE DEL SISTEMA

Los casos de uso suelen situarse dentro de un rectángulo que representa el sistema.

Ejemplo conceptual:

```text
                 Sistema Bancario
┌────────────────────────────────────────┐
│                                        │
│       (Consultar saldo)                │
│                                        │
│       (Realizar transferencia)         │
│                                        │
└────────────────────────────────────────┘
          /
         /
     Cliente
```

El rectángulo ayuda a distinguir:

```text
funcionalidades internas
```

de:

```text
actores externos
```

---

# 7. ASOCIACIÓN ENTRE ACTOR Y CASO DE USO

Un actor se relaciona con un caso de uso mediante una asociación.

Conceptualmente:

```text
Cliente ───────── (Consultar saldo)
```

Indica que:

```text
Cliente
```

participa en:

```text
Consultar saldo
```

---

# 8. GENERALIZACIÓN DE ACTORES

Los actores también pueden participar en relaciones de generalización.

Ejemplo:

```text
             Usuario
                △
                │
        ┌───────┴───────┐
        │               │
    Cliente         Administrador
```

Esto puede representar que ambos comparten características del actor general.

---

# 9. `include`

La relación:

```text
«include»
```

indica que un caso de uso incorpora obligatoriamente el comportamiento de otro caso de uso.

Ejemplo:

```text
(Realizar transferencia)
          |
          | «include»
          ↓
   (Autenticar usuario)
```

Cada vez que se realiza la transferencia, el comportamiento de autenticación forma parte de la ejecución modelada.

---

# 10. ¿CUÁNDO USAR `include`?

Pensaremos:

```text
A incluye B
```

cuando:

```text
A necesita ejecutar B
```

como parte de su comportamiento.

Es útil para extraer comportamiento común reutilizable.

---

# 11. `extend`

La relación:

```text
«extend»
```

representa comportamiento adicional que puede incorporarse al caso de uso base bajo determinadas condiciones.

Ejemplo:

```text
(Comprar producto)
       ↑
       |
   «extend»
       |
(Aplicar descuento)
```

El comportamiento adicional no forma necesariamente parte de todas las ejecuciones del caso base.

---

# 12. `include` VS `extend`

Esta diferencia es muy importante.

### `include`

```text
obligatorio / incorporado
```

Conceptualmente:

```text
A
↓
siempre ejecuta B
```

### `extend`

```text
comportamiento adicional condicionado
```

Conceptualmente:

```text
A
↓
en determinadas condiciones
↓
puede incorporar B
```

### 🧠 Regla rápida

```text
include
→ "esto forma parte de mi comportamiento"

extend
→ "puedo añadir esto bajo ciertas condiciones"
```

---

# 13. DIRECCIÓN DE LAS RELACIONES

La notación de UML utiliza una dirección concreta para `include` y `extend`.

Para `include`:

```text
Caso base ───────→ Caso incluido
      «include»
```

La flecha apunta hacia el caso de uso incluido.

Para `extend`:

```text
Caso de extensión ───────→ Caso base
             «extend»
```

La flecha apunta hacia el caso de uso que está siendo extendido.

### ⚠️ Trampa

No debemos memorizar solamente:

```text
include = obligatorio
extend = opcional
```

También debemos recordar:

```text
include
→ flecha hacia el incluido

extend
→ flecha hacia el caso base
```

---

# 14. GENERALIZACIÓN DE CASOS DE USO

Los casos de uso también pueden especializarse.

Ejemplo:

```text
       (Realizar pago)
              △
              │
       ┌──────┴──────┐
       │             │
(Pagar con tarjeta) (Pagar con PayPal)
```

La generalización representa una relación de especialización.

---

# 15. ¿QUÉ NO REPRESENTA UN CASO DE USO?

Un caso de uso no debería utilizarse para describir:

```text
cada método
cada clase
cada línea de código
cada consulta SQL
```

Representa:

```text
funcionalidad desde la perspectiva del actor
```

---

# 16. DIAGRAMA DE ACTIVIDADES

El diagrama de actividades representa:

```text
flujo de trabajo
procesos
acciones
decisiones
concurrencia
```

Podemos verlo como una representación del flujo de un proceso.

Ejemplo:

```text
Inicio
  ↓
Introducir datos
  ↓
Validar datos
  ↓
¿Correctos?
 ↙       ↘
Sí        No
↓          ↓
Procesar   Mostrar error
↓
Fin
```

---

# 17. NODO INICIAL

El nodo inicial indica dónde comienza el flujo.

Se representa habitualmente mediante:

```text
●
```

Un círculo negro relleno.

Ejemplo:

```text
●
↓
Iniciar proceso
```

---

# 18. ACCIÓN

Una acción representa una unidad de comportamiento.

Se suele representar mediante un rectángulo con esquinas redondeadas:

```text
╭──────────────────╮
│ Validar usuario  │
╰──────────────────╯
```

---

# 19. FLUJO DE CONTROL

Las acciones se conectan mediante flujos.

Conceptualmente:

```text
●
↓
Iniciar sesión
↓
Validar credenciales
↓
Mostrar panel
```

Las flechas representan el flujo de control.

---

# 20. NODO FINAL DE ACTIVIDAD

El nodo final de actividad representa la finalización completa de la actividad.

Se representa normalmente mediante:

```text
◉
```

Un círculo final compuesto.

Conceptualmente:

```text
●
 ↓
Acción
 ↓
◉
```

---

# 21. DECISIÓN

Una decisión representa una bifurcación condicionada.

Se representa mediante un rombo:

```text
     ◇
    / \
 [sí] [no]
  /     \
 A       B
```

Las ramas suelen llevar:

```text
guardas
```

como:

```text
[usuario válido]
[usuario inválido]
```

---

# 22. GUARDAS

Una guarda es una condición que determina si una transición puede seguir un determinado camino.

Ejemplo:

```text
       ◇
      / \
[edad >= 18] [edad < 18]
    /           \
 Adulto        Menor
```

La condición se escribe habitualmente entre:

```text
[ ]
```

---

# 23. MERGE

Un nodo de merge permite unir caminos alternativos.

Conceptualmente:

```text
 A ──┐
     ├──→ ◇ ──→ C
 B ──┘
```

Importante:

```text
decisión
→ divide alternativas

merge
→ reúne alternativas
```

Ambos pueden utilizar el mismo símbolo gráfico de rombo, pero su función depende del flujo.

---

# 24. FORK

Un fork divide un flujo en varios flujos concurrentes.

Se representa normalmente mediante una barra gruesa.

```text
        │
        │
    ═════════
      │    │
      ↓    ↓
     A      B
```

A y B pueden ejecutarse concurrentemente.

---

# 25. JOIN

Un join reúne flujos concurrentes.

```text
     A      B
      ↓    ↓
    ═════════
        │
        ↓
        C
```

### 🧠 Diferencia

```text
Fork
→ uno → muchos

Join
→ muchos → uno
```

---

# 26. DECISIÓN VS FORK

No debemos confundirlos.

### Decisión

```text
una alternativa
```

Ejemplo:

```text
¿Pago válido?
   ↙      ↘
 Sí        No
```

Normalmente solo se sigue una rama.

### Fork

```text
concurrencia
```

Varias ramas pueden ejecutarse simultáneamente.

---

# 27. PARTITIONS / SWIMLANES

Las actividades pueden dividirse mediante:

```text
partitions
```

también conocidas como:

```text
swimlanes
```

Sirven para mostrar quién o qué componente es responsable de cada acción.

Ejemplo:

```text
┌──────────────┬───────────────┐
│ Cliente      │ Sistema       │
├──────────────┼───────────────┤
│ Introducir   │               │
│ datos        │               │
│              │ Validar datos │
│              │ Procesar      │
└──────────────┴───────────────┘
```

---

# 28. DIAGRAMA DE ESTADOS

El diagrama de estados representa:

```text
estados
+
transiciones
+
eventos
```

de una entidad o sistema.

Es especialmente útil cuando el comportamiento depende del estado actual.

---

# 29. ESTADO

Un estado representa una situación en la que puede encontrarse un objeto.

Ejemplo:

```text
Pedido
│
├── Pendiente
├── Pagado
├── Enviado
└── Entregado
```

---

# 30. TRANSICIÓN

Una transición representa el cambio:

```text
Estado A
   ↓
Estado B
```

Ejemplo:

```text
Pendiente
   │
   │ pago recibido
   ↓
Pagado
```

---

# 31. EVENTO

Un evento puede provocar una transición.

Ejemplo:

```text
Pendiente
   │
   │ recibirPago
   ↓
Pagado
```

El evento:

```text
recibirPago
```

provoca el cambio de estado.

---

# 32. GUARDAS EN ESTADOS

Una transición puede estar condicionada:

```text
Pendiente
   │
   │ pagar [importe > 0]
   ↓
Pagado
```

La guarda determina si la transición puede ejecutarse.

---

# 33. ACCIONES DE ENTRADA Y SALIDA

Un estado puede tener comportamientos asociados a:

```text
entrada
salida
```

Conceptualmente:

```text
Estado Pagado
----------------
entry / registrarPago()
exit  / prepararEnvio()
```

---

# 34. ESTADO INICIAL

El estado inicial se representa normalmente mediante:

```text
●
```

y apunta al primer estado.

```text
●
 ↓
Pendiente
```

---

# 35. ESTADO FINAL

El estado final se representa mediante un círculo final:

```text
◉
```

Ejemplo:

```text
Entregado
   ↓
  ◉
```

---

# 36. ESTADOS COMPUESTOS

Un estado puede contener subestados.

Ejemplo:

```text
Pedido en proceso
│
├── Preparando
├── Empaquetando
└── Enviando
```

Esto permite representar máquinas de estados complejas de forma jerárquica.

---

# 37. MÁQUINA DE ESTADOS

Una máquina de estados describe:

```text
estados posibles
+
eventos
+
transiciones
+
condiciones
```

Es muy útil para entidades cuyo comportamiento cambia según su estado.

Ejemplo:

```text
          pagar
Pendiente ───────→ Pagado
   ↑                │
   │                │ enviar
   │ cancelar       ↓
Cancelado        Enviado
                    │
                    │ entregar
                    ↓
                Entregado
```

---

# 38. DIAGRAMA DE SECUENCIA

El diagrama de secuencia representa interacciones:

```text
en el tiempo
```

Su pregunta principal es:

> ¿Quién envía qué mensaje a quién y en qué orden?

---

# 39. LÍNEAS DE VIDA

Los participantes aparecen como:

```text
lifelines
```

con una línea vertical discontinua.

Ejemplo:

```text
Usuario        Sistema        BD
  │               │            │
  │               │            │
  │               │            │
```

El tiempo suele avanzar:

```text
de arriba hacia abajo
```

---

# 40. PARTICIPANTES

Una lifeline puede representar:

```text
actor
objeto
componente
sistema
```

Ejemplo:

```text
Usuario
Frontend
Backend
Base de datos
```

---

# 41. MENSAJES

Los mensajes representan comunicaciones entre participantes.

Ejemplo:

```text
Usuario
  │
  │ iniciarSesion()
  ↓
Backend
```

Después:

```text
Backend
  │
  │ validarUsuario()
  ↓
BD
```

---

# 42. ORDEN TEMPORAL

En un diagrama de secuencia:

```text
arriba
  ↓
antes

abajo
  ↓
después
```

Por tanto:

```text
mensaje A
   ↓
mensaje B
   ↓
mensaje C
```

representa el orden temporal.

---

# 43. MENSAJE SÍNCRONO

Un mensaje síncrono representa normalmente una llamada en la que el emisor espera la respuesta antes de continuar.

Conceptualmente:

```text
A ───────→ B
```

B procesa:

```text
...
```

y devuelve:

```text
A ←─────── B
```

---

# 44. MENSAJE ASÍNCRONO

En un mensaje asíncrono el emisor no necesita esperar a que el receptor termine antes de continuar.

Conceptualmente:

```text
A ───────→ B
```

A puede continuar mientras B procesa la operación.

---

# 45. MENSAJE DE RETORNO

Un retorno puede representarse mediante una flecha discontinua:

```text
A ───────→ B
A ← - - - B
```

La notación concreta puede variar según la herramienta, pero conceptualmente representa:

```text
respuesta
```

---

# 46. CREACIÓN DE OBJETOS

Un diagrama de secuencia puede representar la creación de un participante durante la interacción.

Conceptualmente:

```text
A
│
│ crear()
↓
┌─────────┐
│ Objeto B│
└─────────┘
```

La lifeline de B comienza en el momento de creación.

---

# 47. DESTRUCCIÓN DE OBJETOS

La destrucción de un objeto puede representarse mediante:

```text
X
```

al final de la lifeline.

Conceptualmente:

```text
Objeto
  │
  │
  X
```

---

# 48. ACTIVATION / EXECUTION SPECIFICATION

Durante la ejecución de una operación puede mostrarse una barra vertical sobre la lifeline:

```text
Objeto
  │
  │
  █
  █
  █
  │
```

Representa el periodo durante el cual el participante está ejecutando una operación.

---

# 49. FRAGMENTOS COMBINADOS

Los diagramas de secuencia pueden utilizar fragmentos para representar lógica compleja.

Los más importantes:

```text
alt
opt
loop
par
```

---

# 50. `alt`

Representa alternativas.

Conceptualmente:

```text
┌──────────── alt ────────────┐
│ [usuario válido]            │
│     mostrar panel           │
├─────────────────────────────┤
│ [usuario inválido]          │
│     mostrar error           │
└─────────────────────────────┘
```

Es parecido conceptualmente a:

```text
if / else
```

---

# 51. `opt`

Representa un comportamiento opcional.

Conceptualmente:

```text
┌──────────── opt ────────────┐
│ [recordar usuario]          │
│     guardar sesión          │
└─────────────────────────────┘
```

Es parecido conceptualmente a:

```text
if
```

sin una rama alternativa obligatoria.

---

# 52. `loop`

Representa una repetición.

```text
┌──────────── loop ───────────┐
│ [por cada producto]         │
│     procesar producto       │
└─────────────────────────────┘
```

Conceptualmente:

```text
for / while
```

---

# 53. `par`

Representa interacciones concurrentes.

```text
┌──────────── par ────────────┐
│ operación A                 │
├─────────────────────────────┤
│ operación B                 │
└─────────────────────────────┘
```

Las ramas pueden ejecutarse concurrentemente.

---

# 54. `alt` VS `opt` VS `loop` VS `par`

| Fragmento | Significado |
|---|---|
| `alt` | alternativas |
| `opt` | comportamiento opcional |
| `loop` | repetición |
| `par` | ejecución concurrente |

Esta tabla merece ser memorizada.

---

# 55. DIAGRAMA DE COMUNICACIÓN

El diagrama de comunicación representa las interacciones entre objetos haciendo especial énfasis en:

```text
qué objetos colaboran
```

y:

```text
qué mensajes intercambian
```

A diferencia del diagrama de secuencia, el énfasis visual está más en:

```text
estructura de colaboración
```

que en una línea temporal vertical.

---

# 56. SECUENCIA VS COMUNICACIÓN

### Secuencia

Prioriza:

```text
orden temporal
```

### Comunicación

Prioriza:

```text
relaciones entre participantes
+
mensajes
```

Ambos pueden representar una interacción equivalente desde perspectivas diferentes.

---

# 57. DIAGRAMA DE TIEMPOS

El diagrama de tiempos representa el comportamiento de elementos respecto al tiempo.

Es especialmente útil cuando:

```text
el tiempo
```

es un aspecto importante del sistema.

Puede utilizarse para observar:

```text
cambios de estado
duraciones
eventos
```

a lo largo de una línea temporal.

---

# 58. INTERACCIÓN GENERAL

El diagrama de interacción general combina conceptos de:

```text
actividades
+
interacciones
```

Permite representar el flujo entre diferentes interacciones.

Es menos habitual que:

```text
secuencia
casos de uso
actividad
```

pero forma parte de UML.

---

# 59. MAPA DE DIAGRAMAS DE COMPORTAMIENTO

```text
              COMPORTAMIENTO
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
  Casos de uso   Actividades   Estados
       │            │            │
   actores       acciones      estados
   funciones     decisiones    transiciones
                    │
                    ↓
                Interacción
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   Secuencia   Comunicación   Tiempos
```

# 65. 🧠 LAS 15 COSAS QUE DEBES RECONOCER DE UN VISTAZO

Si aparece una pregunta de UML y ves:

```text
1. Elipse
   → Caso de uso

2. Muñeco/actor
   → Actor

3. Rectángulo redondeado
   → Acción

4. Rombo
   → Decisión / Merge

5. Barra gruesa
   → Fork / Join

6. Círculo negro
   → Inicio

7. Círculo final
   → Fin

8. Línea vertical discontinua
   → Lifeline

9. Flechas entre lifelines
   → Mensajes

10. Rombo vacío
    → Agregación

11. Rombo lleno
    → Composición

12. Triángulo vacío
    → Generalización

13. Línea discontinua + flecha
    → Dependencia

14. Línea discontinua + triángulo
    → Realización

15. «include» / «extend»
    → Relaciones de casos de uso
```

Tener este reconocimiento visual automático puede ahorrarte bastante tiempo en un test.
