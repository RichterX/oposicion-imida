# 1. INTRODUCCIÓN

**UML** significa:

```text
Unified Modeling Language
```

En español:

```text
Lenguaje Unificado de Modelado
```

UML es un lenguaje gráfico utilizado para:

```text
visualizar
especificar
documentar
modelar
```

sistemas de software.

No es un lenguaje de programación.

Tampoco es una metodología de desarrollo.

Podemos utilizar UML para representar un sistema antes, durante o después de su implementación.

---

# 2. ¿PARA QUÉ SIRVE UML?

UML permite representar diferentes aspectos de un sistema.

Por ejemplo:

```text
¿Quién utiliza el sistema?
        ↓
Casos de uso

¿Qué clases existen?
        ↓
Diagrama de clases

¿Cómo interactúan los objetos?
        ↓
Diagrama de secuencia

¿Cómo evoluciona un objeto?
        ↓
Diagrama de estados

¿Cómo se organiza el flujo?
        ↓
Diagrama de actividades
```

---

# 3. UML NO ES UN LENGUAJE DE PROGRAMACIÓN

Una pregunta típica:

> ¿UML sirve para ejecutar directamente un programa?

No.

UML es un:

```text
lenguaje de modelado
```

Podemos utilizarlo para representar conceptualmente un sistema que posteriormente será implementado en:

```text
Java
Python
C#
PHP
JavaScript
...
```

---

# 4. UML NO ES UNA METODOLOGÍA

UML tampoco establece por sí mismo:

```text
qué tareas debe realizar un equipo
```

ni:

```text
cómo debe organizarse un proyecto
```

Es decir:

```text
UML
→ lenguaje de modelado

Metodología
→ proceso / forma de desarrollar
```

---

# 5. MODELO

Un modelo es una representación simplificada de un sistema.

La idea fundamental:

```text
SISTEMA REAL
     ↓
    modelo
     ↓
representación simplificada
```

El modelo no necesita representar absolutamente todos los detalles.

Debe representar aquellos aspectos relevantes para el propósito del modelo.

---

# 6. ABSTRACCIÓN EN UML

UML utiliza la abstracción para representar:

```text
lo importante
```

y evitar detalles innecesarios.

Por ejemplo, para modelar una biblioteca podemos representar:

```text
Libro
Usuario
Préstamo
Bibliotecario
```

sin necesidad de representar cada línea de código de la aplicación.

---

# 7. UML Y POO

UML resulta especialmente útil para representar sistemas orientados a objetos.

Por ejemplo:

```text
Clase
Atributos
Métodos
Herencia
Asociaciones
Agregación
Composición
```

Por eso el capítulo 5.3 y este capítulo están muy relacionados.

En 5.3 estudiamos:

```text
qué significan estas relaciones
```

Ahora aprenderemos:

```text
cómo representarlas gráficamente
```

# 8. TIPOS DE DIAGRAMAS UML

UML incluye diferentes tipos de diagramas.

Una clasificación muy útil es:

```text
DIAGRAMAS ESTRUCTURALES
        +
DIAGRAMAS DE COMPORTAMIENTO
```

---

# 9. DIAGRAMAS ESTRUCTURALES

Representan la estructura estática de un sistema.

Entre ellos encontramos:

```text
Diagrama de clases
Diagrama de objetos
Diagrama de componentes
Diagrama de despliegue
Diagrama de paquetes
Diagrama de estructura compuesta
Diagrama de perfiles
```

---

# 10. DIAGRAMAS DE COMPORTAMIENTO

Representan aspectos dinámicos o de comportamiento.

Entre ellos:

```text
Diagrama de casos de uso
Diagrama de actividades
Diagrama de estados
```

Además, UML incluye diagramas de interacción, que forman parte de los diagramas de comportamiento:

```text
Diagrama de secuencia
Diagrama de comunicación
Diagrama de interacción general
Diagrama de tiempos
```

# 12. DIAGRAMA DE CLASES

El diagrama de clases es uno de los diagramas UML más importantes.

Permite representar:

```text
clases
atributos
operaciones
relaciones
```

Es especialmente útil para modelar la estructura estática de un sistema.

---

# 13. REPRESENTACIÓN DE UNA CLASE

Una clase suele representarse mediante un rectángulo dividido en compartimentos:

```text
┌─────────────────────────┐
│        Persona          │
├─────────────────────────┤
│ - nombre : String       │
│ - edad : int            │
├─────────────────────────┤
│ + saludar() : void      │
│ + cumplirAnios() : void │
└─────────────────────────┘
```

Tenemos:

```text
nombre de clase
atributos
operaciones
```

---

# 14. NOMBRE DE LA CLASE

El compartimento superior contiene:

```text
Persona
```

que representa el nombre de la clase.

---

# 15. ATRIBUTOS

En el segundo compartimento podemos representar atributos:

```text
- nombre : String
- edad : int
```

La sintaxis conceptual:

```text
visibilidad nombre : tipo
```

---

# 16. OPERACIONES

En el tercer compartimento:

```text
+ saludar() : void
+ cumplirAnios() : void
```

Podemos representar:

```text
visibilidad
nombre
parámetros
tipo de retorno
```

---

# 17. VISIBILIDAD UML

UML utiliza símbolos habituales para representar visibilidad.

```text
+  public
-  private
#  protected
~  package
```

### 🧠 Memorizar

```text
+ → público
- → privado
# → protegido
~ → paquete
```

Esta tabla es muy preguntable.

---

# 18. ATRIBUTOS ESTÁTICOS

Un atributo estático puede representarse mediante:

```text
subrayado
```

Por ejemplo, conceptualmente:

```text
------------------
contador : int
```

con el nombre subrayado.

En UML, el subrayado indica que el miembro es:

```text
estático
```

---

# 19. OPERACIONES ESTÁTICAS

La misma convención puede aplicarse a operaciones estáticas.

La notación exacta puede variar según la herramienta, pero conceptualmente:

```text
miMetodo()
```

subrayado indica:

```text
static
```

---

# 20. ATRIBUTOS DERIVADOS

Un atributo derivado puede indicarse mediante una barra:

```text
/ edad : int
```

La barra:

```text
/
```

indica que el valor puede derivarse de otra información.

Ejemplo:

```text
/ edad
```

podría calcularse a partir de:

```text
fechaNacimiento
```

---

# 21. ABSTRACTO

Una clase abstracta suele representarse con el nombre de la clase en:

```text
cursiva
```

o mediante una anotación:

```text
{abstract}
```

Ejemplo conceptual:

```text
┌───────────────────┐
│ Animal            │
│ {abstract}        │
├───────────────────┤
│ nombre : String   │
├───────────────────┤
│ hacerSonido()     │
└───────────────────┘
```

---

# 22. INTERFACES

Una interfaz puede representarse mediante:

```text
«interface»
```

Ejemplo:

```text
┌──────────────────────┐
│ «interface»          │
│ Pagable              │
├──────────────────────┤
│ + pagar() : void     │
└──────────────────────┘
```

Los símbolos:

```text
« »
```

se denominan:

```text
guillemets
```

y se utilizan para estereotipos.

---

# 23. ESTEREOTIPOS

Un estereotipo permite extender o clasificar elementos UML.

Se representa habitualmente:

```text
«estereotipo»
```

Ejemplos:

```text
«interface»
«entity»
«service»
```

Los estereotipos proporcionan información adicional sobre el elemento.

---

# 24. RELACIÓN DE ASOCIACIÓN

Una asociación se representa mediante una línea:

```text
Persona ───────── Dirección
```

Indica que existe una relación entre ambas clases.

---

# 25. NAVEGABILIDAD

Podemos indicar la dirección de navegación:

```text
Persona ───────→ Dirección
```

Esto puede indicar que:

```text
Persona
```

conoce o puede navegar hacia:

```text
Dirección
```

La navegación es diferente de la multiplicidad.

---

# 26. MULTIPLICIDAD

Podemos indicar cuántos objetos pueden participar en una asociación.

Ejemplo:

```text
Cliente 1 ───────── 0..* Pedido
```

Significa:

```text
un Cliente
puede tener
cero o muchos Pedidos
```

---

# 27. MULTIPLICIDADES IMPORTANTES

```text
1
→ exactamente uno

0..1
→ cero o uno

*
→ cero o muchos

0..*
→ cero o muchos

1..*
→ uno o muchos

2..5
→ entre 2 y 5
```

---

# 28. NOMBRE DE LA ASOCIACIÓN

Podemos nombrar una asociación.

Ejemplo:

```text
Cliente ───── realiza ───── Pedido
```

El nombre ayuda a explicar semánticamente la relación.

---

# 29. ROLES

Los extremos de una asociación pueden tener nombres de rol.

Ejemplo:

```text
Cliente ───────── Pedido
          realiza
```

Podemos indicar:

```text
cliente
pedidos
```

como roles en los extremos.

---

# 30. ASOCIACIÓN REFLEXIVA

Una clase puede estar relacionada consigo misma.

Ejemplo:

```text
Empleado
   │
   └───────────┐
               ↓
             Empleado
```

Esto puede representar:

```text
Empleado
   │
   └── supervisa → Empleado
```

La relación se denomina:

```text
asociación reflexiva
```

---

# 31. ASOCIACIÓN N-ARIA

Una asociación puede relacionar más de dos clases.

Por ejemplo:

```text
Profesor
    \
     \
     Curso
     /
    /
Alumno
```

Una asociación de tres clases es:

```text
ternaria
```

También pueden existir asociaciones con más participantes.

---

# 32. GENERALIZACIÓN

La generalización representa herencia.

Se utiliza una línea con:

```text
triángulo vacío
```

apuntando hacia el elemento más general.

Ejemplo:

```text
       △
       │
     Animal
       ▲
       │
     Perro
```

Más claramente:

```text
Perro ───────▷ Animal
```

El triángulo apunta a:

```text
superclase
```

---

# 33. GENERALIZACIÓN Y ESPECIALIZACIÓN

```text
Animal
  ↑
  │
Perro
```

Significa:

```text
Perro
→ especialización

Animal
→ generalización
```

Relación conceptual:

```text
Perro IS-A Animal
```

---

# 34. AGREGACIÓN

La agregación representa una relación todo-parte relativamente débil.

Se utiliza:

```text
rombo vacío
```

Ejemplo:

```text
Equipo ◇──────── Jugador
```

El rombo se coloca en el lado del:

```text
todo
```

---

# 35. COMPOSICIÓN

La composición representa una relación todo-parte fuerte.

Se utiliza:

```text
rombo relleno
```

Ejemplo:

```text
Casa ◆──────── Habitación
```

El rombo se coloca en el lado del:

```text
todo
```

---

# 36. AGREGACIÓN VS COMPOSICIÓN

### Agregación

```text
◇
```

Rombo vacío.

Relación todo-parte más débil.

Las partes pueden existir independientemente del todo.

### Composición

```text
◆
```

Rombo lleno.

Relación todo-parte fuerte.

El ciclo de vida de la parte está fuertemente ligado al todo.

---

# 37. DEPENDENCIA

Una dependencia se representa normalmente mediante:

```text
línea discontinua
+
flecha
```

Ejemplo:

```text
Factura - - - - -→ GeneradorPDF
```

Indica que:

```text
Factura
```

depende de:

```text
GeneradorPDF
```

---

# 38. REALIZACIÓN

La realización representa la implementación de un contrato.

Se representa mediante:

```text
línea discontinua
+
triángulo vacío
```

Ejemplo:

```text
Factura - - - -▷ Pagable
```

La flecha apunta hacia:

```text
interfaz / especificación
```

---

# 39. RESUMEN DE RELACIONES UML

Esta tabla hay que tenerla muy clara:

| Relación | Representación | Significado |
|---|---|---|
| Asociación | línea | relación estructural |
| Generalización | línea + triángulo vacío | herencia |
| Agregación | línea + rombo vacío | todo-parte débil |
| Composición | línea + rombo lleno | todo-parte fuerte |
| Dependencia | línea discontinua + flecha | uso/dependencia |
| Realización | línea discontinua + triángulo vacío | implementación de contrato |

---

Podemos modelar:

```text
                  ┌────────────────┐
                  │ «interface»    │
                  │ Pagable        │
                  ├────────────────┤
                  │ + pagar()      │
                  └───────▲────────┘
                          :
                          :
                   - - - -┘
                          :
                    ┌─────┴──────┐
                    │   Pedido   │
                    ├────────────┤
                    │ - total    │
                    ├────────────┤
                    │ + pagar()  │
                    └─────┬──────┘
                          │
                       1  │
                          │ 0..*
                    ┌─────▼──────┐
                    │  Producto  │
                    └────────────┘
```

Aquí podemos identificar:

```text
Pedido realiza Pagable
Pedido se relaciona con Producto
```

y además podemos añadir multiplicidades.

# 41. DIAGRAMA DE OBJETOS

El diagrama de objetos representa:

```text
instancias concretas
```

en lugar de:

```text
clases generales
```

Ejemplo:

```text
┌─────────────────────┐
│ ana : Persona       │
├─────────────────────┤
│ nombre = "Ana"      │
│ edad = 30           │
└─────────────────────┘
```

---

# 42. CLASE VS OBJETO EN UML

### Diagrama de clases

Representa:

```text
Persona
```

### Diagrama de objetos

Representa:

```text
ana : Persona
```

Es decir:

```text
clase
vs
instancia
```

---

# 43. OBJETOS EN UML

Los objetos suelen representarse como:

```text
nombreObjeto : Clase
```

Por ejemplo:

```text
ana : Persona
```

El nombre del objeto puede aparecer subrayado.

---

# 44. DIAGRAMA DE PAQUETES

Un paquete permite agrupar elementos relacionados.

Conceptualmente:

```text
┌───────────────────────────┐
│ usuarios                  │
│                           │
│   Usuario                 │
│   Perfil                  │
│   Permiso                 │
└───────────────────────────┘
```

Sirve para organizar el modelo y mostrar dependencias entre grupos de elementos.

---

# 45. DEPENDENCIAS ENTRE PAQUETES

Podemos representar:

```text
┌──────────┐       - - - - -→       ┌──────────┐
│ usuarios │                         │ seguridad│
└──────────┘                         └──────────┘
```

Indicando que un paquete depende de otro.

---

# 46. DIAGRAMA DE COMPONENTES

El diagrama de componentes representa componentes del sistema y sus relaciones.

Un componente puede representar una unidad reemplazable de software.

Ejemplo:

```text
┌───────────────┐
│ «component»   │
│ API REST      │
└───────────────┘
       │
       ↓
┌───────────────┐
│ «component»   │
│ Servicio      │
└───────────────┘
```

---

# 47. COMPONENTE

Un componente puede representar:

```text
módulo
biblioteca
servicio
subsystema
unidad desplegable
```

dependiendo del nivel de modelado.

Lo importante es distinguirlo de una clase.

```text
Clase
→ estructura y comportamiento de objetos

Componente
→ unidad modular/reemplazable del sistema
```

---

# 48. DIAGRAMA DE DESPLIEGUE

El diagrama de despliegue representa cómo se distribuyen los artefactos o componentes en nodos físicos o de ejecución.

Ejemplo:

```text
┌────────────────────┐
│ «device»           │
│ Cliente            │
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│ «node»             │
│ Servidor Web       │
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│ «node»             │
│ Servidor BD        │
└────────────────────┘
```

Aquí empieza la parte de UML donde los diagramas dejan de ser principalmente "qué cosas existen" y pasan a representar:

```text
qué ocurre
```

y:

```text
en qué orden ocurre.
```
