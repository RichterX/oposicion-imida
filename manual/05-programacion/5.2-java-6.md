# 2. CONCURRENCIA

La concurrencia consiste en gestionar varias tareas que progresan durante un mismo periodo de tiempo.

Conceptualmente:

```text
Tarea A ────────┐
                ├── ejecución concurrente
Tarea B ────────┘
```

No implica necesariamente que ambas se estén ejecutando físicamente al mismo tiempo.

---

# 3. PARALELISMO

El paralelismo implica ejecutar tareas realmente al mismo tiempo utilizando recursos de procesamiento disponibles.

Por ejemplo:

```text
CPU 1 → tarea A
CPU 2 → tarea B
```

### 🧠 Diferencia

```text
Concurrencia
→ varias tareas progresan de forma intercalada o simultánea

Paralelismo
→ varias tareas se ejecutan simultáneamente
```

Puede existir concurrencia sin paralelismo físico.

---

# 4. PROCESO VS HILO

Un:

```text
proceso
```

es una instancia de un programa en ejecución.

Un:

```text
hilo (thread)
```

es una unidad de ejecución dentro de un proceso.

Conceptualmente:

```text
PROCESO
│
├── Thread 1
├── Thread 2
└── Thread 3
```

Los hilos de un proceso comparten determinados recursos del proceso.

---

# 5. `Thread`

Java proporciona:

```java
java.lang.Thread
```

para representar y gestionar hilos.

Una forma básica:

```java
Thread hilo = new Thread(() -> {
    System.out.println("Ejecutando");
});

hilo.start();
```

---

# 6. `start()` VS `run()`

Esta es una trampa clásica.

```java
hilo.start();
```

solicita el inicio de un nuevo hilo.

En cambio:

```java
hilo.run();
```

es simplemente una llamada normal al método `run()`.

No inicia por sí misma un nuevo hilo.

### 🧠 Regla

```text
start()
→ inicia ejecución en un hilo nuevo

run()
→ ejecuta el método como una llamada normal si lo invocamos directamente
```

---

# 7. CREAR UN THREAD MEDIANTE SUBCLASE

Podemos extender `Thread`:

```java
class MiHilo extends Thread {

    @Override
    public void run() {
        System.out.println("Hola");
    }
}
```

Después:

```java
MiHilo hilo = new MiHilo();

hilo.start();
```

---

# 8. `Runnable`

Una alternativa habitual es implementar:

```java
Runnable
```

Ejemplo:

```java
Runnable tarea = () -> {
    System.out.println("Ejecutando");
};

Thread hilo = new Thread(tarea);

hilo.start();
```

---

# 9. `Thread` VS `Runnable`

En general:

```text
Thread
→ representa el hilo

Runnable
→ representa una tarea ejecutable
```

Por diseño, suele ser preferible separar:

```text
qué trabajo realizar
```

de:

```text
cómo se ejecuta
```

Por eso `Runnable` resulta muy útil.

---

# 10. `Runnable` ES INTERFAZ FUNCIONAL

`Runnable` tiene:

```java
void run()
```

como único método abstracto.

Por ello podemos utilizar:

```java
Runnable tarea =
    () -> System.out.println("Hola");
```

---

# 11. `Callable`

`Callable<V>` representa una tarea que:

```text
devuelve un resultado
```

y puede lanzar excepciones.

Ejemplo:

```java
Callable<Integer> tarea = () -> {
    return 10 + 20;
};
```

Conceptualmente:

```text
Runnable
→ ejecuta
→ no devuelve resultado

Callable<V>
→ ejecuta
→ devuelve V
→ puede lanzar excepciones
```

---

# 12. `ExecutorService`

En aplicaciones reales no suele ser buena idea crear manualmente un hilo para cada tarea.

Java proporciona:

```java
ExecutorService
```

para gestionar grupos de hilos y ejecutar tareas.

Ejemplo:

```java
ExecutorService executor =
    Executors.newFixedThreadPool(4);
```

---

# 13. `submit()`

Podemos enviar una tarea:

```java
Future<Integer> futuro =
    executor.submit(() -> 10 + 20);
```

El resultado se representa mediante:

```text
Future<Integer>
```

---

# 14. `execute()` VS `submit()`

`execute()`:

```java
executor.execute(tarea);
```

está orientado a ejecutar:

```text
Runnable
```

sin devolver un `Future`.

`submit()`:

```java
executor.submit(tarea);
```

permite obtener un:

```text
Future
```

y trabajar con el resultado o el estado de la tarea.

---

# 15. `Future`

Un `Future<V>` representa el resultado futuro de una operación asíncrona.

Ejemplo:

```java
Future<Integer> futuro =
    executor.submit(() -> 42);
```

Podemos obtener el resultado:

```java
Integer resultado =
    futuro.get();
```

---

# 16. `Future.get()`

`get()` puede bloquear hasta que el resultado esté disponible.

Conceptualmente:

```text
submit()
   ↓
Future
   ↓
get()
   ↓
esperar resultado
```

---

# 17. `Future.isDone()`

Permite comprobar si la tarea ha terminado:

```java
futuro.isDone();
```

Resultado:

```text
true / false
```

---

# 18. `Future.cancel()`

Puede intentarse cancelar una tarea:

```java
futuro.cancel(true);
```

El parámetro indica si se permite intentar interrumpir la ejecución si ya ha comenzado.

La cancelación no garantiza que una tarea pueda detenerse inmediatamente en todos los escenarios.

---

# 19. APAGAR EL EXECUTOR

Debemos liberar los recursos del executor.

```java
executor.shutdown();
```

Podemos esperar:

```java
executor.awaitTermination(
    10,
    TimeUnit.SECONDS
);
```

---

# 20. `shutdown()` VS `shutdownNow()`

```text
shutdown()
→ deja de aceptar nuevas tareas
→ permite terminar las tareas enviadas

shutdownNow()
→ intenta detener las tareas activas
→ devuelve tareas pendientes que no comenzaron
```

`shutdownNow()` no garantiza que una tarea en ejecución se detenga inmediatamente.

# 21. TIPOS DE EXECUTOR

Java proporciona utilidades en:

```java
Executors
```

Algunas conocidas:


# 22. FIXED THREAD POOL

```java
Executors.newFixedThreadPool(4);
```

mantiene un número fijo de hilos de trabajo.

Conceptualmente:

```text
Pool
├── Thread 1
├── Thread 2
├── Thread 3
└── Thread 4
```

Las tareas adicionales pueden quedar pendientes en la cola.

---

# 23. SINGLE THREAD EXECUTOR

```java
Executors.newSingleThreadExecutor();
```

utiliza un único hilo para ejecutar las tareas.

Esto proporciona ejecución secuencial de las tareas enviadas al executor, en condiciones normales de uso.

---

# 24. SCHEDULED EXECUTOR

Permite programar tareas:

```java
Executors.newScheduledThreadPool(2);
```

Puede utilizarse para:

```text
ejecuciones retardadas
ejecuciones periódicas
```

# 25. RACE CONDITION

Una condición de carrera ocurre cuando el resultado depende del orden temporal en que varios hilos acceden o modifican un estado compartido.

Ejemplo conceptual:

```text
contador = 0

Thread A → lee 0
Thread B → lee 0
Thread A → escribe 1
Thread B → escribe 1
```

Esperábamos:

```text
2
```

pero obtenemos:

```text
1
```

---

# 26. SECCIÓN CRÍTICA

Una sección crítica es una parte del código que accede a recursos compartidos y debe protegerse frente a accesos concurrentes incompatibles.

Ejemplo:

```java
contador++;
```

Aunque parezca una sola operación, conceptualmente implica varias acciones:

```text
leer
+
incrementar
+
escribir
```

---

# 27. `synchronized`

Java permite sincronizar métodos o bloques.

Método:

```java
public synchronized void incrementar() {
    contador++;
}
```

Bloque:

```java
synchronized (this) {
    contador++;
}
```

---

# 28. ¿QUÉ HACE `synchronized`?

Proporciona exclusión mutua asociada a un monitor.

Conceptualmente:

```text
Thread A
   ↓
entra
   ↓
LOCK
   ↓
sección crítica
   ↓
UNLOCK
   ↓
Thread B
```

Solo un hilo puede ejecutar simultáneamente una sección protegida por el mismo monitor.

---

# 29. MONITOR

Cada objeto Java puede asociarse a un monitor utilizado para sincronización.

Cuando hacemos:

```java
synchronized (objeto) {
    ...
}
```

el hilo necesita adquirir el monitor asociado al objeto.

---

# 30. MÉTODO `synchronized`

Un método de instancia:

```java
public synchronized void incrementar() {
}
```

se sincroniza sobre:

```text
this
```

Un método:

```java
public static synchronized void metodo() {
}
```

se sincroniza sobre el objeto:

```text
Class
```

correspondiente.

---

# 31. `volatile`

La palabra:

```java
volatile
```

indica determinadas garantías de visibilidad entre hilos para una variable.

Ejemplo:

```java
private volatile boolean ejecutando = true;
```

Cuando un hilo modifica esa variable, otros hilos pueden observar el valor actualizado bajo las reglas de memoria de Java.

---

# 32. `volatile` NO HACE TODO ATÓMICO

Esto:

```java
volatile int contador;
```

no convierte necesariamente:

```java
contador++;
```

en una operación atómica.

Porque:

```text
leer
incrementar
escribir
```

siguen siendo pasos separados.

### 🧠 Trampa

```text
volatile
→ visibilidad / ordenación de memoria

synchronized
→ exclusión mutua + garantías de memoria
```

---

# 33. ATOMICIDAD

Una operación atómica se realiza como una unidad indivisible desde el punto de vista de otros hilos.

Java proporciona clases como:

```text
AtomicInteger
AtomicLong
AtomicBoolean
```

en:

```java
java.util.concurrent.atomic
```

---

# 34. `AtomicInteger`

Ejemplo:

```java
AtomicInteger contador =
    new AtomicInteger(0);

contador.incrementAndGet();
```

Esto permite operaciones atómicas sobre el valor.

Métodos habituales:

```text
get()
set()
incrementAndGet()
decrementAndGet()
getAndIncrement()
compareAndSet()
```

---

# 35. `compareAndSet()`

Es una operación de tipo:

```text
compare-and-swap
```

Conceptualmente:

```text
si valor actual == esperado
    cambia al nuevo valor
si no
    no cambia
```

Puede utilizarse para construir algoritmos concurrentes sin recurrir necesariamente a un bloqueo tradicional.

---

# 36. LOCKS

Java proporciona interfaces y clases de bloqueo en:

```java
java.util.concurrent.locks
```

Una de las más conocidas:

```java
ReentrantLock
```

---

# 37. `ReentrantLock`

Ejemplo:

```java
private final Lock lock =
    new ReentrantLock();

lock.lock();

try {
    contador++;
} finally {
    lock.unlock();
}
```

### ⚠️ Regla

Si adquirimos manualmente un lock:

```text
lock()
```

debemos asegurarnos de liberarlo:

```text
unlock()
```

normalmente mediante `finally`.

---

# 38. `synchronized` VS `Lock`

`synchronized`:

```text
simple
integrado en el lenguaje
libera automáticamente el monitor al salir del bloque
```

`Lock`:

```text
más flexible
control explícito
más posibilidades de configuración
```

Por ejemplo:

```java
tryLock()
```

permite intentar adquirir un lock sin bloquear indefinidamente.

---

# 39. DEADLOCK

Un deadlock ocurre cuando varios hilos quedan esperando indefinidamente recursos que están bloqueados entre sí.

Ejemplo conceptual:

```text
Thread A
   │
   ├── posee Lock 1
   └── espera Lock 2

Thread B
   │
   ├── posee Lock 2
   └── espera Lock 1
```

Resultado:

```text
A espera a B
B espera a A
```

Nadie progresa.

---

# 40. EVITAR DEADLOCKS

Algunas estrategias:

```text
orden consistente de adquisición de locks
evitar locks innecesarios
mantener secciones críticas pequeñas
usar tryLock() cuando sea apropiado
```

Una regla muy útil:

```text
siempre adquirir múltiples locks
en el mismo orden
```

---

# 41. STARVATION

La inanición ocurre cuando un hilo no consigue suficiente acceso a los recursos necesarios porque otros hilos reciben continuamente preferencia.

Conceptualmente:

```text
Thread A → obtiene recursos
Thread B → obtiene recursos
Thread C → obtiene recursos
Thread D → sigue esperando...
```

---

# 42. LIVENESS

La propiedad de "liveness" se refiere a que el sistema pueda continuar progresando.

Problemas como:

```text
deadlock
starvation
```

pueden impedir el progreso adecuado.

---

# 43. `wait()`, `notify()` Y `notifyAll()`

Los objetos Java proporcionan mecanismos clásicos de coordinación:

```text
wait()
notify()
notifyAll()
```

Se utilizan con el monitor del objeto y normalmente dentro de un contexto sincronizado apropiado.

---

# 44. `wait()`

Un hilo puede hacer:

```java
synchronized (objeto) {
    objeto.wait();
}
```

Esto:

```text
libera temporalmente el monitor
+
pone el hilo a esperar
```

hasta que sea notificado o se produzcan otras condiciones de finalización.

---

# 45. `notify()`

Despierta uno de los hilos que están esperando en el monitor correspondiente, si existe alguno.

```java
synchronized (objeto) {
    objeto.notify();
}
```

---

# 46. `notifyAll()`

Despierta todos los hilos que esperan en ese monitor:

```java
synchronized (objeto) {
    objeto.notifyAll();
}
```

Después competirán por adquirir nuevamente el monitor.

---

```java
Condition
```

```java
Condition condicion =
```

Métodos:

```text
await()

signalAll()
```

# 48. `CompletableFuture`

Java proporciona:

```java
CompletableFuture
```

para construir operaciones asíncronas y composables.

Ejemplo:

```java
CompletableFuture<Integer> futuro =
    CompletableFuture.supplyAsync(

    );
```

---

# 49. `thenApply()`

Permite transformar el resultado:

```java
futuro.thenApply(
    numero -> numero * 2
);
```

Conceptualmente:

```text
42
 ↓
84
```

---

# 50. `thenAccept()`

Permite consumir el resultado:

```java
futuro.thenAccept(
    numero -> System.out.println(numero)
);
```

No produce otro resultado del mismo tipo de transformación.

---

# 51. `thenCompose()`

Permite encadenar operaciones asíncronas evitando una estructura anidada:

```text
Future<Future<T>>
```

Conceptualmente:

```text
resultado A
   ↓
operación asíncrona B
   ↓
resultado final
```

---

# 52. `thenCombine()`

Permite combinar dos futuros independientes.

Conceptualmente:

```text
Future A ──┐
           ├── combinación
Future B ──┘
```

---

# 53. `CompletableFuture.allOf()`

Permite esperar a que varios futuros terminen:

```java
CompletableFuture.allOf(
    futuro1,
    futuro2,
    futuro3
);
```

---

# 54. EXCEPCIONES EN `CompletableFuture`

# 55. CONCURRENCIA VS ASINCRONÍA

No son exactamente sinónimos.

```text
Concurrencia
→ varias tareas progresan

```

Una API asíncrona puede utilizar concurrencia, pero los conceptos no son idénticos.

# 59. `@Deprecated`

Ejemplo:


# 65. REFLEXIÓN Y ACCESO

La reflexión puede permitir operaciones dinámicas que no son habituales en código normal.

Sin embargo:

```text
más flexibilidad
→ más complejidad
→ más coste
→ posibles problemas de seguridad/mantenibilidad
```

No debemos utilizar reflexión simplemente porque podamos.

# 66. MÓDULOS

Desde Java 9 existe el:

```text
Java Platform Module System
```

conocido como:

```text
JPMS
```

Permite organizar aplicaciones en módulos con dependencias y límites de encapsulación explícitos.

---

# 67. `module-info.java`

Un módulo puede declararse mediante:

```text
module-info.java
```

Ejemplo:

```java
module com.ejemplo.app {
    requires java.sql;
    exports com.ejemplo.api;
}
```

---

# 68. `requires`

Indica una dependencia:

```java
requires java.sql;
```

Conceptualmente:

```text
mi módulo
   ↓
necesita
   ↓
java.sql
```

---

# 69. `exports`

Indica qué paquetes del módulo se exponen a otros módulos:

```java
exports com.ejemplo.api;
```

Esto ayuda a controlar la encapsulación a nivel de módulo.

---

# 70. `opens`

`opens` está relacionado con permitir acceso reflexivo a los paquetes.

Ejemplo:

```java
opens com.ejemplo.modelo;
```

Es especialmente relevante para frameworks que utilizan reflexión.

---

# 71. `requires transitive`

Puede declararse:

```java
requires transitive otro.modulo;
```

Esto hace que determinadas dependencias se expongan transitivamente a módulos que dependen del módulo actual.
