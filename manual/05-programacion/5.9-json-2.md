# 1. INTRODUCCIÓN

En la Parte 1 vimos la sintaxis de JSON.

Ahora aparece una pregunta fundamental:

> ¿Cómo podemos definir qué estructura debe tener un JSON?

Por ejemplo, imaginemos que una API espera:

```json
{
    "nombre": "Pedro",
    "edad": 30,
    "email": "pedro@example.com"
}
```

¿Cómo podemos indicar formalmente que:

```text
nombre
→ obligatorio
→ string

edad
→ entero

email
→ string
```

Aquí aparece:

```text
JSON Schema
```

---

# 2. ¿QUÉ ES JSON SCHEMA?

JSON Schema es un vocabulario utilizado para describir y validar la estructura y las restricciones de documentos JSON.

Permite definir:

```text
tipos
propiedades
campos obligatorios
valores permitidos
rangos
longitudes
patrones
arrays
objetos anidados
```

Conceptualmente:

```text
JSON
 ↓
JSON Schema
 ↓
validación
```

---

# 3. JSON SCHEMA VS JSON

Un documento JSON contiene:

```text
datos
```

Un JSON Schema contiene:

```text
reglas sobre esos datos
```

Por ejemplo:

### JSON

```json
{
    "edad": 30
}
```

### Schema

```json
{
    "type": "object",
    "properties": {
        "edad": {
            "type": "integer"
        }
    }
}
```

---

Tipos habituales:

```text

array
string
number
integer
boolean
null
```

```json
{
```

Indica que el valor debe ser un objeto JSON.

# 6. `array`

```json
{
    "type": "array"
}
```

Indica que el valor debe ser un array.

# 7. `string`

```json
{
    "type": "string"
}
```

# 8. `number`

```json
{
    "type": "number"
}
```

Permite números.

---

# 9. `integer`

```json
{
    "type": "integer"
}
```

Indica un número entero.

---

# 10. `boolean`

```json
{
    "type": "boolean"
```

Valores:

```text
true
```

---

# 11. `null`

También podemos exigir:

```json
{
    "type": "null"
}
```

---

# 12. `properties`

En un objeto podemos definir sus propiedades mediante:

```text
properties
```

Ejemplo:

```json
{
    "type": "object",

    "properties": {

        "nombre": {
            "type": "string"
        },

        "edad": {
            "type": "integer"
        }

    }
}
```

---

# 13. `required`

Una propiedad declarada en:

```text
properties
```

no es necesariamente obligatoria.

Para hacerla obligatoria utilizamos:

```text
required
```

Ejemplo:

```json
{
    "type": "object",

    "properties": {
        "nombre": {
            "type": "string"
        },
        "edad": {
            "type": "integer"
        }
    },

    "required": [
        "nombre",
        "edad"
    ]
}
```

---

# 14. 🧠 TRAMPA IMPORTANTE

Esto:

```json
"properties": {
    "nombre": {
        "type": "string"
    }
}
```

**no significa que `nombre` sea obligatorio.**

Para hacerlo obligatorio:

```json
"required": [
    "nombre"
]
```

Esta distinción es muy importante.

---

# 15. `additionalProperties`

Podemos controlar si se permiten propiedades que no aparecen en:

```text
properties
```

Ejemplo:

```json
{
    "type": "object",

    "properties": {
        "nombre": {
            "type": "string"
        }
    },

    "additionalProperties": false
}
```

En este caso, el objeto no puede incluir propiedades adicionales no definidas.

---

# 16. EJEMPLO

Schema:

```json
{
    "type": "object",

    "properties": {
        "nombre": {
            "type": "string"
        }
    },

    "required": [
        "nombre"
    ],

    "additionalProperties": false
}
```

JSON válido:

```json
{
    "nombre": "Pedro"
}
```

JSON inválido:

```json
{
    "nombre": "Pedro",
    "edad": 30
}
```

porque:

```text
edad
```

no está declarada y:

```text
additionalProperties = false
```

---

# 17. `items`

Para definir qué puede contener un array utilizamos:

```text
items
```

Ejemplo:

```json
{
    "type": "array",

    "items": {
        "type": "string"
    }
}
```

Esto indica:

```text
array
↓
todos sus elementos deben ser strings
```

---

# 18. ARRAY DE ENTEROS

```json
{
    "type": "array",

    "items": {
        "type": "integer"
    }
}
```

Ejemplo válido:

```json
[
    1,
    2,
    3
]
```

---

# 19. `minItems`

Permite indicar el número mínimo de elementos.

Ejemplo:

```json
{
    "type": "array",

    "minItems": 1
}
```

El array debe contener al menos:

```text
1 elemento
```

---

# 20. `maxItems`

Indica el número máximo:

```json
{
    "type": "array",

    "maxItems": 5
}
```

---

# 21. `uniqueItems`

Puede exigirse que los elementos sean únicos:

```json
{
    "type": "array",

    "uniqueItems": true
}
```

Ejemplo:

```json
[
    1,
    2,
    3
]
```

es compatible.

Mientras:

```json
[
    1,
    2,
    2
]
```

no cumpliría esa restricción.

---

# 22. STRINGS

JSON Schema permite restringir strings.

Palabras clave importantes:

```text
minLength
maxLength
pattern
format
```

---

# 23. `minLength`

Ejemplo:

```json
{
    "type": "string",
    "minLength": 3
}
```

El texto debe tener al menos:

```text
3 caracteres
```

---

# 24. `maxLength`

```json
{
    "type": "string",
    "maxLength": 50
}
```

---

# 25. `pattern`

Permite definir una expresión regular/patrón.

Ejemplo:

```json
{
    "type": "string",
    "pattern": "^[A-Z][a-z]+$"
}
```

El valor debe cumplir el patrón definido.

---

# 26. `format`

Permite expresar formatos semánticos conocidos.

Ejemplos habituales:

```text
email
date
date-time
uri
hostname
ipv4
ipv6
uuid
```

Ejemplo:

```json
{
    "type": "string",
    "format": "email"
}
```

---

# 27. FORMAT Y VALIDADORES

Un detalle importante:

El tratamiento de determinados formatos puede depender del vocabulario/versión del estándar y del validador utilizado.

Para el examen, lo importante es recordar:

```text
format
→ restricción semántica/formato
```

---

# 28. NÚMEROS

JSON Schema permite restringir números.

Palabras clave importantes:

```text
minimum
maximum
exclusiveMinimum
exclusiveMaximum
multipleOf
```

---

# 29. `minimum`

Ejemplo:

```json
{
    "type": "number",
    "minimum": 0
}
```

Permite:

```text
0
1
10
...
```

---

# 30. `maximum`

```json
{
    "type": "number",
    "maximum": 100
}
```

---

# 31. `exclusiveMinimum`

Permite exigir que el valor sea estrictamente mayor que un límite.

Por ejemplo, conceptualmente:

```text
valor > 0
```

La sintaxis exacta depende de la versión de JSON Schema.

---

# 32. `exclusiveMaximum`

Análogamente:

```text
valor < 100
```

La forma exacta también depende de la versión del estándar.

---

# 33. `multipleOf`

Permite indicar que un número debe ser múltiplo de otro.

Ejemplo:

```json
{
    "type": "number",
    "multipleOf": 5
}
```

Valores válidos:

```text
0
5
10
15
20
```

---

# 34. `enum`

Permite restringir un valor a una lista concreta.

Ejemplo:

```json
{
    "enum": [
        "activo",
        "inactivo"
    ]
}
```

Solo se permiten:

```text
activo
inactivo
```

---

# 35. `const`

Permite exigir un único valor concreto.

Ejemplo:

```json
{
    "const": "España"
}
```

El valor debe ser exactamente:

```text
España
```

---

# 36. `default`

Puede utilizarse para documentar o indicar un valor predeterminado asociado a un esquema:

```json
{
    "type": "string",
    "default": "activo"
}
```

### ⚠️ Importante

`default` **no significa automáticamente que el validador vaya a insertar ese valor**.

La aplicación o herramienta que procese el esquema puede decidir cómo utilizarlo.

---

# 37. `description`

Podemos documentar una propiedad:

```json
{
    "type": "string",
    "description": "Nombre completo del usuario"
}
```

Esto no es una restricción de validación, sino metadatos/documentación.

---

# 38. `title`

También podemos proporcionar un título:

```json
{
    "title": "Usuario",
    "type": "object"
}
```

Es información descriptiva.

---

# 39. `examples`

Dependiendo de la versión/dialecto utilizado, pueden incluirse ejemplos para documentar valores.

Conceptualmente:

```json
{
    "type": "string",
    "examples": [
        "Pedro",
        "Ana"
    ]
}
```

---

# 40. OBJETOS ANIDADOS

JSON Schema puede describir estructuras complejas.

Ejemplo:

```json
{
    "type": "object",

    "properties": {

        "usuario": {

            "type": "object",

            "properties": {

                "nombre": {
                    "type": "string"
                },

                "edad": {
                    "type": "integer"
                }

            },

            "required": [
                "nombre"
            ]

        }

    }
}
```

---

# 41. ARRAY DE OBJETOS

Muy habitual en APIs:

```json
{
    "type": "array",

    "items": {

        "type": "object",

        "properties": {

            "id": {
                "type": "integer"
            },

            "nombre": {
                "type": "string"
            }

        },

        "required": [
            "id",
            "nombre"
        ]

    }
}
```

---

# 42. `oneOf`

Permite que un valor cumpla exactamente una de varias alternativas.

Ejemplo conceptual:

```json
{
    "oneOf": [
        {
            "type": "string"
        },
        {
            "type": "integer"
        }
    ]
}
```

---

# 43. `anyOf`

Permite que un valor cumpla al menos una de varias alternativas.

```json
{
    "anyOf": [
        {
            "type": "string"
        },
        {
            "type": "integer"
        }
    ]
}
```

---

# 44. `allOf`

Indica que deben cumplirse todos los esquemas indicados.

```json
{
    "allOf": [
        {
            "type": "object"
        },
        {
            "properties": {
                "nombre": {
                    "type": "string"
                }
            }
        }
    ]
}
```

---

# 45. `not`

Permite negar un esquema.

Ejemplo conceptual:

```json
{
    "not": {
        "type": "null"
    }
}
```

Indica que el valor no debe ser `null`.

---

# 46. `if`, `then`, `else`

JSON Schema puede expresar lógica condicional.

Conceptualmente:

```json
{
    "if": {
        "properties": {
            "tipo": {
                "const": "empresa"
            }
        }
    },

    "then": {
        "required": [
            "cif"
        ]
    },

    "else": {
        "required": [
            "dni"
        ]
    }
}
```

Esto permite expresar reglas del tipo:

```text
si tipo = empresa
→ exigir CIF

si no
→ exigir DNI
```

---

# 47. `$schema`

Un JSON Schema puede indicar qué vocabulario o versión utiliza mediante:

```text
$schema
```

Ejemplo conceptual:

```json
{
    "$schema":
        "https://json-schema.org/draft/2020-12/schema"
}
```

La URL concreta depende de la versión/draft.

---

# 48. `$id`

Permite identificar el esquema.

Ejemplo:

```json
{
    "$id": "https://example.com/schemas/usuario"
}
```

---

# 49. `$ref`

Permite reutilizar o referenciar otro esquema.

Ejemplo conceptual:

```json
{
    "$ref": "#/$defs/usuario"
}
```

Esto evita duplicar definiciones.

---

# 50. `$defs`

Permite definir esquemas reutilizables dentro de un esquema.

Ejemplo conceptual:

```json
{
    "$defs": {

        "usuario": {

            "type": "object",

            "properties": {
                "nombre": {
                    "type": "string"
                }
            }

        }

    }
}
```

Después podemos referenciarlo mediante:

```json
{
    "$ref": "#/$defs/usuario"
}
```

---

# 51. EJEMPLO COMPLETO

```json
{
    "$schema":
        "https://json-schema.org/draft/2020-12/schema",

    "title": "Usuario",

    "type": "object",

    "properties": {

        "id": {
            "type": "integer",
            "minimum": 1
        },

        "nombre": {
            "type": "string",
            "minLength": 2,
            "maxLength": 100
        },

        "email": {
            "type": "string",
            "format": "email"
        },

        "roles": {

            "type": "array",

            "items": {
                "type": "string"
            },

            "minItems": 1,

            "uniqueItems": true

        }

    },

    "required": [
        "id",
        "nombre",
        "email"
    ],

    "additionalProperties": false
}
```

```json
    "roles": [
        "admin",
```

# 53. JSON INVÁLIDO

Por ejemplo:

```json
{
    "id": "15",

    "nombre": "Pedro",

    "email": "pedro@example.com"
}
```

El problema:

```text
id
→ debería ser integer
→ se ha enviado string
```

---

# 54. OTRO JSON INVÁLIDO

```json
{
    "id": 15,

    "nombre": "Pedro",

    "email": "pedro@example.com",

    "foo": true
}
```

Si:

```text
additionalProperties = false
```

entonces:

```text
foo
```

no está permitido.

# 55. JSON SCHEMA Y API

Podemos utilizar JSON Schema para definir el contrato esperado de una API.

Por ejemplo:

```text
POST /api/usuarios
```

Esperamos:

```json
{
    "nombre": "Pedro",
    "email": "pedro@example.com"
}
```

El schema define:

```text
qué campos existen
qué tipo tienen
cuáles son obligatorios
qué valores son válidos
```

# 58. JSON SCHEMA Y OPENAPI

JSON Schema está estrechamente relacionado con la descripción de estructuras de datos utilizadas por APIs.

OpenAPI permite describir APIs y utiliza un sistema de esquemas para definir:

```text
request bodies
responses
parameters
modelos de datos
```

Las versiones modernas de OpenAPI están alineadas con conceptos de JSON Schema, aunque no debe asumirse que todas las versiones de OpenAPI sean idénticas a un JSON Schema concreto.

---

# 59. VALIDACIÓN EN CLIENTE Y SERVIDOR

Aunque validemos JSON en el frontend:

```text
Frontend
→ validación
```

el servidor debe seguir validando los datos.

```text
Cliente
→ no es una frontera de seguridad
```

Por tanto:

```text
validación cliente
+
validación servidor
```

es una práctica habitual.

---

# 60. JSON Y SEGURIDAD

JSON no proporciona seguridad por sí mismo.

La seguridad depende de:

```text
HTTPS
autenticación
autorización
validación
sanitización
control de acceso
manejo de errores
```

No debemos pensar:

```text
"Como utilizo JSON, los datos son seguros"
```

---

# 61. JSON Y SQL

JSON recibido por una API no debe concatenarse directamente en consultas SQL.

Ejemplo conceptual incorrecto:

```text
SQL + entrada del usuario
```

Debe utilizarse el mecanismo apropiado de consultas parametrizadas/ORM.

En Laravel:

```text
Eloquent
Query Builder
prepared statements
```

son mecanismos habituales.

---

# 62. JSON Y XSS

Si datos JSON contienen texto proporcionado por usuarios:

```text
JSON
→ datos no confiables
```

El frontend debe evitar insertar contenido arbitrario en HTML de manera insegura.

Por ejemplo, en JavaScript:

```text
innerHTML
```

requiere especial cuidado con contenido no confiable.

# 68. ⚠️ TRAMPAS DE OPOSICIÓN

## Trampa 1

```text
properties
```

no significa:

```text
propiedades obligatorias
```

Para eso:

```text
required
```

---

## Trampa 2

```text
items
```

se utiliza para definir restricciones sobre los elementos de un array.

---

## Trampa 3

```text
additionalProperties: false
```

impide propiedades adicionales no permitidas por el esquema.

---

## Trampa 4

```text
minItems
```

se refiere a:

```text
cantidad de elementos del array
```

Mientras:

```text
minLength
```

se refiere a:

```text
longitud de un string
```

---

## Trampa 5

```text
minimum
```

se refiere a:

```text
valor numérico
```

No a cantidad de elementos.

---

## Trampa 6

```text
enum
```

permite varios valores concretos.

```text
const
```

permite un valor concreto.

---

## Trampa 7

```text
oneOf
→ una alternativa

anyOf
→ al menos una

allOf
→ todas
```

---

## Trampa 8

```text
default
```

no implica necesariamente que el validador vaya a modificar automáticamente el JSON para insertar ese valor.

---

## Trampa 9

```text
JSON Schema
```

valida estructura/restricciones, pero no sustituye la validación de negocio de una aplicación.

---

## Trampa 10

La validación del frontend:

```text
NO
```

sustituye la validación del backend.
