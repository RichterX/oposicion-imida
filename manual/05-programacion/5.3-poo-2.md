# 1. INTRODUCCIÓN

En la primera parte vimos:

```text
clases

comportamiento
encapsulación
abstracción
herencia
polimorfismo
asociación
agregación

cohesión
acoplamiento

```

Ahora vamos a profundizar en cómo se relacionan las clases y cómo podemos diseñar sistemas orientados a objetos evitando dependencias innecesarias.

El objetivo no es memorizar patrones de código.

El objetivo es aprender a reconocer:

```text
qué relación existe
qué responsabilidad tiene cada objeto
quién depende de quién
cómo podemos reducir el acoplamiento
```

---

# 2. RELACIONES ENTRE CLASES

Las relaciones más habituales que debemos distinguir son:

```text
Asociación
Dependencia
Agregación
Composición
Generalización
Realización
```

Algunas aparecerán con especial importancia cuando estudiemos UML.

---

# 3. ASOCIACIÓN

Una asociación representa una relación estructural entre objetos.

Ejemplo:

```text
Profesor ───────── Alumno
```

Un profesor puede estar asociado con uno o varios alumnos.

La asociación puede ser:

```text
unidireccional
```

o:

```text
bidireccional
```

---

# 4. ASOCIACIÓN UNIDIRECCIONAL

Ejemplo:

```text
Pedido ───────→ Cliente
```

El `Pedido` conoce a su `Cliente`, pero el modelo no obliga a que el `Cliente` conozca directamente al `Pedido`.

Conceptualmente:

```text
Pedido
   ↓
Cliente
```

---

# 5. ASOCIACIÓN BIDIRECCIONAL

Puede existir una relación en ambos sentidos:

```text
Profesor ↔ Alumno
```

El profesor conoce a sus alumnos y el alumno conoce a su profesor.

Esto puede ser útil, pero también aumenta la complejidad y el acoplamiento del modelo.

---

# 6. MULTIPLICIDAD

Una relación puede tener diferentes cantidades de objetos participantes.

Ejemplos:

```text
1
0..1
*
1..*
0..*
```

Interpretación:

```text
1
→ exactamente uno

0..1
→ cero o uno

*
→ cero o muchos

1..*
→ uno o muchos

0..*
→ cero o muchos
```

Estas notaciones serán especialmente importantes en UML.

---

# 7. DEPENDENCIA

Una dependencia representa una relación más débil y normalmente temporal.

Un objeto puede depender de otro porque lo utiliza para realizar una operación.

Ejemplo:

```text
Factura
   ↓
GeneradorPDF
```

La factura puede recibir un `GeneradorPDF` como parámetro para realizar una operación, sin necesidad de mantenerlo como parte permanente de su estado.

---

# 8. EJEMPLO DE DEPENDENCIA

Conceptualmente:

```java
void generar(GeneradorPDF generador) {
    generador.generar(...);
}
```

Aquí `Factura` utiliza `GeneradorPDF`.

La relación es:

```text
Factura
   ↓
GeneradorPDF
```

pero no necesariamente:

```text
Factura HAS-A GeneradorPDF
```

---

# 9. ASOCIACIÓN VS DEPENDENCIA

### Asociación

```text
relación estructural
```

Existe una relación relativamente estable entre objetos.

### Dependencia

```text
uso
```

Un componente necesita temporalmente otro para realizar una operación.

### 🧠 Regla útil

```text
Asociación
→ conoce / mantiene relación

Dependencia
→ utiliza
```

---

# 10. GENERALIZACIÓN

La generalización representa una relación:

```text
superclase
      ↑
subclase
```

Ejemplo:

```text
Vehículo
   ↑
   │
Coche
```

La subclase hereda características de la superclase.

En términos conceptuales:

```text
Coche IS-A Vehículo
```

---

# 11. ESPECIALIZACIÓN

La especialización es el proceso inverso desde el punto de vista conceptual.

Partimos de:

```text
Vehículo
```

y creamos una clase más específica:

```text
Coche
Moto
Camión
```

Todas representan especializaciones de:

```text
Vehículo
```

---

# 12. REALIZACIÓN

La realización representa una relación mediante la cual una clase proporciona la implementación de un contrato definido por una interfaz.

Conceptualmente:

```text
Interfaz
    ↑
    │
Implementación
```

Por ejemplo:

```text
Pagable
   ↑
   │
Factura
```

Si `Factura` implementa `Pagable`, está realizando el contrato definido por esa interfaz.

En UML esta relación tiene una representación específica que estudiaremos con más profundidad en 5.4.

---

# 13. INTERFAZ COMO CONTRATO

Una interfaz define normalmente:

```text
qué operaciones están disponibles
```

sin obligar a que todas las implementaciones utilicen la misma lógica interna.

Ejemplo:

```text
Notificador
│
├── enviar()
```

Implementaciones:

```text
EmailNotificador
SMSNotificador
PushNotificador
```

Todas cumplen:

```text
Notificador
```

pero pueden funcionar de manera diferente.

---

# 14. CLASE ABSTRACTA

Una clase abstracta representa una abstracción que no necesariamente debe instanciarse directamente.

Ejemplo:

```text
Animal
│
├── nombre
├── comer()
└── hacerSonido()
```

Podemos especializarla:

```text
Perro
Gato
```

La clase abstracta puede proporcionar:

```text
estado común
comportamiento común
métodos abstractos
```

---

# 15. INTERFAZ VS CLASE ABSTRACTA

Una diferencia conceptual:

### Interfaz

Representa principalmente:

```text
contrato
capacidad
comportamiento esperado
```

### Clase abstracta

Representa principalmente:

```text
abstracción común
estado compartido
comportamiento común
```

En Java existen detalles adicionales sobre métodos `default`, métodos `static`, campos, herencia múltiple de interfaces, etc., que ya hemos estudiado en 5.2.

Aquí nos interesa la diferencia conceptual.

---

# 16. ¿CUÁNDO USAR INTERFAZ?

Una interfaz resulta especialmente útil cuando queremos definir una capacidad o contrato común entre clases que pueden no pertenecer a la misma jerarquía conceptual.

Ejemplo:

```text
Volador
```

podría ser implementado por:

```text
Pájaro
Avión
Dron
```

No necesitamos que exista una única jerarquía de herencia entre ellos.

---

# 17. ¿CUÁNDO USAR CLASE ABSTRACTA?

Una clase abstracta puede ser adecuada cuando existe:

```text
una familia conceptual
```

y queremos compartir:

```text
estado
+
comportamiento
```

Ejemplo:

```text
Empleado
│
├── nombre
├── salario
├── calcularNomina()
└── ...
```

y después:

```text
EmpleadoFijo
EmpleadoTemporal
Autonomo
```

---

# 18. DELEGACIÓN

La delegación consiste en hacer que un objeto encargue una responsabilidad a otro objeto.

En lugar de:

```text
Objeto A
→ hace todo
```

podemos hacer:

```text
Objeto A
→ delega
→ Objeto B
```

Ejemplo:

```text
Pedido
   ↓
CalculadorDePrecios
```

El pedido no necesita implementar toda la lógica de cálculo.

---

# 19. VENTAJA DE LA DELEGACIÓN

La delegación puede ayudar a:

```text
reducir complejidad
reducir acoplamiento
aumentar cohesión
favorecer reutilización
```

También evita crear jerarquías de herencia innecesarias.

---

# 20. HERENCIA VS DELEGACIÓN

### Herencia

```text
Clase hija
   ↓
hereda comportamiento
```

### Delegación

```text
Objeto A
   ↓
utiliza objeto B
```

Una jerarquía de herencia puede ser más rígida.

La delegación permite cambiar el objeto colaborador con mayor facilidad.

---

# 21. COMPOSICIÓN SOBRE HERENCIA

Uno de los principios de diseño más conocidos:

```text
Prefer composition over inheritance
```

La idea es favorecer la composición cuando esta proporcione un diseño más flexible.

Ejemplo:

En lugar de:

```text
ClaseA
   ↑
ClaseB
   ↑
ClaseC
```

podemos tener:

```text
Objeto
│
├── EstrategiaA
├── EstrategiaB
└── Servicio
```

El objeto puede delegar responsabilidades en sus colaboradores.

---

# 22. INYECCIÓN DE DEPENDENCIAS

La inyección de dependencias consiste en proporcionar a un objeto las dependencias que necesita desde fuera, en lugar de crearlas internamente.

### Mal acoplado

```java
class Servicio {

    private Repositorio repo =
        new Repositorio();
}
```

El servicio decide qué implementación concreta utilizar.

---

# 23. INYECCIÓN POR CONSTRUCTOR

Una alternativa:

```java
class Servicio {

    private final Repositorio repo;

    public Servicio(Repositorio repo) {
        this.repo = repo;
    }
}
```

Ahora la dependencia se proporciona desde fuera.

Conceptualmente:

```text
Aplicación
    ↓
Servicio
    ↓
Repositorio
```

pero `Servicio` no necesita construir directamente el repositorio.

---

# 24. VENTAJAS DE LA INYECCIÓN

Puede favorecer:

```text
bajo acoplamiento
testabilidad
reutilización
sustitución de implementaciones
configuración
```

Por ejemplo, durante una prueba podemos proporcionar:

```text
RepositorioReal
```

o:

```text
RepositorioFalso
```

si ambos cumplen el contrato esperado.

---

# 25. INVERSIÓN DE DEPENDENCIAS

Esto conecta directamente con:

```text
DIP
```

de SOLID.

En lugar de:

```text
Servicio
   ↓
RepositorioConcreto
```

buscamos:

```text
Servicio
   ↓
Repositorio
   ↑
RepositorioConcreto
```

La dependencia importante pasa a ser una abstracción.

---

# 26. DEPENDENCY INVERSION VS DEPENDENCY INJECTION

No son exactamente lo mismo.

### Dependency Inversion

Es un:

```text
principio de diseño
```

que busca invertir la dirección de las dependencias respecto a detalles concretos.

### Dependency Injection

Es una:

```text
técnica
```

para proporcionar dependencias a un objeto.

La inyección puede utilizarse para aplicar el principio de inversión de dependencias.

---

# 27. TIPOS DE INYECCIÓN

Los tipos más conocidos:

```text
Constructor Injection
Setter Injection
Method Injection
```

La inyección por constructor suele ser especialmente clara porque permite expresar qué dependencias necesita el objeto para existir correctamente.

---

# 28. EJEMPLO CON INTERFAZ

Podemos definir:

```text
Repositorio
```

como abstracción.

Después:

```text
RepositorioMySQL
RepositorioMemoria
RepositorioAPI
```

implementan el contrato.

El servicio puede depender de:

```text
Repositorio
```

y no de:

```text
RepositorioMySQL
```

---

# 29. POLIMORFISMO + INYECCIÓN

Aquí aparecen dos conceptos trabajando juntos:

```text
Interfaz
   ↓
Polimorfismo
   ↓
distintas implementaciones
   ↓
inyección
   ↓
el objeto recibe una implementación
```

Esto permite cambiar implementaciones sin modificar necesariamente el consumidor.

---

# 30. COHESIÓN EN PROFUNDIDAD

Una clase tiene alta cohesión cuando sus responsabilidades están estrechamente relacionadas.

Ejemplo:

```text
Factura
├── calcularSubtotal()
├── calcularIVA()
└── calcularTotal()
```

Estas responsabilidades están relacionadas.

En cambio:

```text
Factura
├── calcularTotal()
├── enviarEmail()
├── comprimirPDF()
└── crearUsuario()
```

mezcla responsabilidades distintas.

---

# 31. ACOPLAMIENTO EN PROFUNDIDAD

Una clase presenta mayor acoplamiento cuando depende de muchos componentes concretos.

Ejemplo:

```text
Servicio
│
├── MySQL
├── SMTP
├── Redis
├── API externa
├── sistema de archivos
└── logger concreto
```

Los cambios en cualquiera de ellos pueden afectar directamente al servicio.

Podemos reducir el acoplamiento utilizando:

```text
interfaces
inyección de dependencias
composición
delegación
```

---

# 32. COHESIÓN Y ACOPLAMIENTO

Podemos visualizar el objetivo:

```text
        DISEÑO DESEABLE

      ALTA COHESIÓN
            ↑
            │
            │
            │
            └──────────→ BAJO ACOPLAMIENTO
```

Queremos componentes:

```text
internamente coherentes
externamente independientes en lo razonable
```

---

# 33. PRINCIPIO DE RESPONSABILIDAD ÚNICA

Recordemos:

```text
SRP
```

No significa:

```text
una clase = un método
```

Significa que la clase debería tener:

```text
una responsabilidad coherente
```

y un motivo relacionado para cambiar.

---

# 34. OPEN/CLOSED

El principio:

```text
Open/Closed Principle
```

indica que una entidad debería estar:

```text
abierta para extensión
cerrada para modificación
```

Ejemplo conceptual:

```text
Forma
│
├── Circulo
├── Rectangulo
└── Triangulo
```

Podemos añadir una nueva forma sin tener que modificar continuamente el código que trabaja con la abstracción `Forma`.

---

# 35. LISKOV

El principio de sustitución de Liskov exige que las subclases respeten el contrato esperado por el código que utiliza el supertipo.

Una subclase no debería:

```text
romper precondiciones
violar invariantes
producir comportamientos incompatibles
```

de forma que deje de poder utilizarse como el tipo base.

---

# 36. INTERFACE SEGREGATION

Una interfaz demasiado grande puede obligar a una clase a implementar operaciones que no necesita.

Mejor:

```text
Imprimible
Escaneable
Fax
```

que:

```text
Multifuncion
├── imprimir()
├── escanear()
├── enviarFax()
├── copiar()
└── ...
```

si no todos los clientes necesitan todas esas capacidades.

---

# 37. DEPENDENCY INVERSION

Los módulos de alto nivel deberían depender de:

```text
abstracciones
```

y no directamente de:

```text
detalles concretos
```

Esto permite sustituir implementaciones.

---

# 38. DISEÑO ORIENTADO A INTERFACES

Una práctica habitual es programar contra abstracciones:

```java
List<String> nombres =
    new ArrayList<>();
```

La variable está declarada como:

```text
List
```

y la implementación concreta es:

```text
ArrayList
```

Esto permite cambiar la implementación con menor impacto:

```java
List<String> nombres =
    new LinkedList<>();
```

cuando el diseño lo permita.

---

# 39. PROGRAMAR CONTRA ABSTRACCIONES

La idea general:

```text
NO

Consumidor
   ↓
Implementación concreta


SÍ

Consumidor
   ↓
Abstracción
   ↑
Implementación
```

Esto no significa que nunca debamos conocer la implementación concreta.

Significa que debemos evitar depender innecesariamente de detalles concretos.

---

# 40. PRINCIPIO DE MENOR CONOCIMIENTO

Relacionado con:

```text
Law of Demeter
```

La idea básica es que un objeto debería conocer y utilizar un número limitado de colaboradores directos.

Evitar cadenas excesivas como:

```java
a.getB().getC().getD().hacerAlgo();
```

cuando ese diseño revela demasiados detalles internos.

---

# 41. "TELL, DON'T ASK"

Principio de diseño que sugiere que debemos indicar a un objeto qué debe hacer en lugar de extraer continuamente sus datos para realizar fuera de él operaciones que conceptualmente le corresponden.

### Enfoque problemático

```text
obtener estado
↓
calcular fuera
↓
modificar objeto
```

### Enfoque orientado a objetos

```text
objeto.realizarOperacion()
```

El comportamiento relacionado con el estado permanece junto al objeto que lo posee.

---

# 42. OBJETOS DE VALOR

Un objeto de valor representa un concepto por su:

```text
valor
```

y no principalmente por una identidad individual.

Ejemplos:

```text
Dinero
Dirección
Coordenadas
Rango de fechas
```

Dos objetos de valor con los mismos componentes pueden considerarse equivalentes según el modelo.

---

# 43. ENTIDADES

Una entidad suele distinguirse por:

```text
identidad
```

que permanece aunque cambien algunos atributos.

Ejemplo:

```text
Cliente
```

Puede tener:

```text
id = 42
nombre = Ana
```

Si cambia:

```text
nombre = María
```

seguimos hablando del mismo cliente si su identidad permanece.

---

# 44. ENTIDAD VS OBJETO DE VALOR

```text
ENTIDAD
→ identidad

OBJETO DE VALOR
→ valor
```

Ejemplo:

```text
Cliente
→ entidad

Dirección
→ objeto de valor
```

Este concepto aparecerá con fuerza en otros enfoques de diseño como DDD, pero aquí basta con dominar la diferencia conceptual.

---

# 45. INMUTABILIDAD

Un objeto inmutable no cambia su estado después de ser creado.

Ejemplo conceptual:

```text
Dinero
```

en lugar de:

```text
dinero.setImporte(500)
```

podríamos crear:

```text
nuevoDinero =
    dinero.conImporte(500)
```

La instancia original permanece sin cambios.

---

# 46. VENTAJAS DE LA INMUTABILIDAD

Los objetos inmutables pueden facilitar:

```text
seguridad
concurrencia
razonamiento
caché
uso compartido
```

Al no cambiar, disminuye el riesgo de modificaciones inesperadas.

Ejemplos conocidos en Java:

```text
String
Integer
LocalDate
```

son inmutables.

---

# 47. OBJETOS Y RESPONSABILIDADES

Un diseño orientado a objetos saludable intenta colocar el comportamiento cerca de los datos que necesita.

Ejemplo:

```text
Cuenta
│
├── saldo
└── retirar()
```

En lugar de:

```text
Cuenta
└── saldo

ServicioExterno
└── lógica enorme para manipular saldo
```

cuando esa lógica pertenece conceptualmente a la cuenta.

---

# 48. ANEMIC DOMAIN MODEL

Un modelo anémico es aquel en el que los objetos contienen principalmente:

```text
datos
```

pero muy poco:

```text
comportamiento
```

Ejemplo:

```text
Usuario
├── nombre
├── email
└── getters/setters
```

mientras toda la lógica está dispersa en múltiples servicios.

No siempre es incorrecto, pero desde una perspectiva de diseño orientado al comportamiento puede indicar un modelo pobremente encapsulado.

---
