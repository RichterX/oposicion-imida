# El problema

Imaginemos que un usuario llama al departamento de informática.

Dice simplemente:

> **"No tengo Internet."**

Esa frase puede significar muchas cosas.

Por ejemplo:

- El cable está desconectado.
- El Wi-Fi no funciona.
- No tiene dirección IP.
- El servidor DNS no responde.
- El gateway está caído.
- El servidor remoto está apagado.
- El firewall está bloqueando la comunicación.

Si comenzáramos a cambiar configuraciones sin comprobar nada...

Probablemente empeoraríamos la situación.

Por eso un administrador de sistemas sigue siempre un procedimiento de diagnóstico.

---

# El objetivo del diagnóstico

Cuando existe un problema de red debemos responder varias preguntas.

```
¿Tengo dirección IP?

↓

¿Llego al gateway?

↓

¿Funciona DNS?

↓

¿Existe conectividad con Internet?

↓

¿El problema está en el servidor remoto?
```

Cada una de estas preguntas tiene una herramienta específica.

---

# Un administrador no adivina

Uno de los errores más frecuentes de los principiantes consiste en probar soluciones al azar.

Por ejemplo:

- Reiniciar el equipo.
- Cambiar la IP.
- Reiniciar el router.
- Desactivar el firewall.

Sin comprobar previamente cuál es la causa.

Un administrador experimentado hace exactamente lo contrario.

Primero obtiene información.

Después toma decisiones.

# Primera pregunta

Antes de comprobar Internet debemos verificar una cosa mucho más básica.

```
¿Tengo configuración de red?
```

Si un ordenador no posee:

- Dirección IP.
- Máscara.
- Gateway.
- DNS.

No podrá comunicarse correctamente.

---

# ipconfig (Windows)

En Windows la herramienta más utilizada para consultar la configuración de red es:

```
ipconfig
```

Ejemplo:

```cmd
ipconfig
```

La salida muestra información como:

```
Dirección IPv4

Máscara

Gateway predeterminado
```

Con esta información podemos detectar rápidamente muchos problemas.

---

# ipconfig /all

La opción más utilizada es:

```cmd
ipconfig /all
```

Además de la configuración básica, muestra:

- Dirección MAC.
- Servidor DHCP.
- Servidores DNS.
- Estado de DHCP.
- Descripción del adaptador.
- Sufijo DNS.
- Fecha de obtención de la concesión DHCP.

Es uno de los comandos más utilizados en soporte técnico.

---

# Ejemplo

Supongamos la siguiente salida:

```text
IPv4:

169.254.25.14
```

Inmediatamente debería llamarnos la atención.

Recordemos el capítulo anterior.

Las direcciones:

```
169.254.x.x
```

pertenecen al rango **APIPA**.

Esto suele indicar que el equipo **no ha podido obtener una dirección IP del servidor DHCP**.

Sin ejecutar ninguna otra herramienta ya tenemos una primera pista.

---

# Comandos equivalentes en Linux

En Linux encontramos principalmente dos herramientas.

Históricamente se utilizaba:

```bash
ifconfig
```

Aunque hoy en día la recomendada es:

```bash
ip
```

Por ejemplo:

```bash
ip addr
```

Muestra:

- Interfaces.
- Direcciones IPv4.
- Direcciones IPv6.
- Estado de cada interfaz.
- Dirección MAC.

También es frecuente utilizar:

```bash
ip route
```

para consultar la tabla de rutas.

---

# Comparativa

| Windows | Linux |
|----------|--------|
| ipconfig | ip addr |
| ipconfig /all | ip addr + ip route |
| ipconfig /release | dhclient -r (según distribución) |
| ipconfig /renew | dhclient (según distribución) |

No es necesario memorizar todas las opciones, pero sí conocer los comandos principales de cada sistema operativo.

# Conceptos importantes

Antes de continuar debes recordar:

- El diagnóstico debe seguir un orden lógico.
- El primer paso consiste en comprobar la configuración de red.
- `ipconfig` es la herramienta básica en Windows.
- `ip addr` cumple esa función en Linux.
- Una dirección APIPA suele indicar un problema con DHCP.

# Ping

Una vez comprobado que el equipo dispone de dirección IP, el siguiente paso consiste en verificar la conectividad.

La herramienta más utilizada para ello es:

```bash
ping
```

Su función consiste en comprobar si existe comunicación entre dos equipos.

---

# ¿Cómo funciona Ping?

Ping utiliza el protocolo:

```
ICMP

(Internet Control Message Protocol)
```

Concretamente emplea dos tipos de mensajes:

```
Echo Request

↓

Echo Reply
```

El funcionamiento es muy sencillo.

```
PC

↓

"¿Estás ahí?"

↓

Servidor

↓

"Sí."
```

Si llega la respuesta, sabemos que existe conectividad.

---

# Ejemplo

En Windows:

```cmd
ping 192.168.1.1
```

En Linux:

```bash
ping 192.168.1.1
```

Obtendremos una salida similar a:

```text
Reply from 192.168.1.1

Bytes=32

Time=2ms

TTL=64
```

Cada línea representa una respuesta recibida.

---

# ¿Qué información proporciona?

Ping permite conocer varios aspectos.

### Conectividad

¿Existe comunicación?

---

### Tiempo de respuesta

```
Time

2 ms
```

Indica cuánto tarda el paquete en ir y volver.

Cuanto menor sea este valor:

Mayor será la rapidez de la comunicación.

---

### Pérdida de paquetes

Al finalizar la ejecución aparece un resumen.

Ejemplo:

```text
Packets:

Sent = 4

Received = 4

Lost = 0
```

Si existen pérdidas de paquetes pueden aparecer problemas como:

- Cortes.
- Lentitud.
- Videollamadas entrecortadas.

---

### TTL

También aparece el valor:

```
TTL

(Time To Live)
```

No debe confundirse con el TTL de DNS.

En este contexto representa el número máximo de saltos que puede realizar un paquete antes de ser descartado.

Cada router reduce el TTL en una unidad.

Si llega a cero:

El paquete se elimina para evitar bucles infinitos en la red.

---

# ¿A quién hacer ping?

Cuando aparece un problema de conectividad conviene seguir siempre el mismo orden.

## Paso 1

Comprobar la propia pila TCP/IP.

```cmd
ping 127.0.0.1
```

Si este ping falla:

El problema está en el propio sistema operativo o en la pila TCP/IP.

---

## Paso 2

Comprobar la propia dirección IP.

```cmd
ping 192.168.1.25
```

Verifica que la interfaz de red funciona correctamente.

---

## Paso 3

Comprobar el gateway.

```cmd
ping 192.168.1.1
```

Si falla aquí:

El problema suele encontrarse en la red local.

---

## Paso 4

Comprobar una dirección IP pública.

```cmd
ping 8.8.8.8
```

Si responde:

Existe salida a Internet.

---

## Paso 5

Comprobar un nombre DNS.

```cmd
ping google.es
```

Si:

```
8.8.8.8

↓

Sí responde

------------------

google.es

↓

No responde
```

La conectividad funciona.

El problema probablemente sea:

```
DNS
```

Observa cómo este razonamiento conecta directamente con el capítulo anterior.

---

# Traceroute

A veces Ping responde.

Pero la comunicación sigue siendo lenta.

O simplemente queremos saber:

> **¿Por dónde está viajando el tráfico?**

Aquí aparece:

```
Traceroute
```

En Windows:

```cmd
tracert
```

En Linux:

```bash
traceroute
```

---

# ¿Qué hace Traceroute?

Cada paquete atraviesa varios routers antes de llegar a su destino.

Traceroute muestra precisamente ese recorrido.

Por ejemplo:

```
PC

↓

Router empresa

↓

Proveedor

↓

Operador nacional

↓

Operador internacional

↓

Servidor destino
```

Cada uno de esos pasos recibe el nombre de:

```
Hop

(Salto)
```

---

# Ejemplo

```cmd
tracert google.es
```

Salida simplificada:

```text
1   1 ms

192.168.1.1

2   8 ms

Proveedor

3   12 ms

Operador

4   25 ms

Google
```

Gracias a esta información podemos localizar aproximadamente dónde aparece un problema de red.

---

# ¿Cuándo utilizar Traceroute?

Es especialmente útil cuando:

- Un servidor responde muy lentamente.
- Existe pérdida de conectividad en algún punto de Internet.
- Queremos identificar el recorrido seguido por los paquetes.
- Se sospecha de un problema de enrutamiento.

---

# Diferencia entre Ping y Traceroute

Es muy frecuente que el tribunal pregunte esta diferencia.

| Ping | Traceroute |
|-------|------------|
| Comprueba conectividad | Muestra el recorrido hasta el destino |
| Utiliza ICMP | Utiliza ICMP (Windows) o UDP/ICMP (Linux, según implementación) |
| Indica tiempo de respuesta | Indica cada salto realizado |
| Muy rápido | Más detallado |

No sustituyen uno al otro.

Son herramientas complementarias.

# Conceptos importantes

Antes de continuar debes recordar:

- Ping verifica la conectividad mediante ICMP.
- Traceroute muestra el recorrido seguido por los paquetes.
- Ambos comandos proporcionan información diferente y complementaria.
- Un problema con `ping google.es` pero no con `ping 8.8.8.8` suele indicar un fallo en la resolución DNS.
- Seguir siempre un procedimiento ordenado permite localizar incidencias mucho más rápido.

# nslookup

Supongamos la siguiente situación.

```
ping 8.8.8.8

↓

Funciona


ping google.es

↓

No funciona
```

La conectividad existe.

Pero los nombres no se resuelven.

Aquí aparece:

```cmd
nslookup
```

---

# ¿Qué hace nslookup?

Permite consultar directamente un servidor DNS.

Por ejemplo:

```cmd
nslookup google.es
```

Respuesta:

```text
Servidor:

192.168.1.1

Nombre:

google.es

Dirección:

142.250.xxx.xxx
```

Si no obtiene respuesta:

El problema probablemente esté relacionado con DNS.

---

# dig

En sistemas Linux es muy habitual utilizar:

```bash
dig
```

(Domain Information Groper)

Realiza consultas DNS mucho más completas.

Ejemplo:

```bash
dig google.es
```

Permite consultar:

- Registros A.
- AAAA.
- MX.
- TXT.
- CNAME.
- NS.

Entre otros.

Es una de las herramientas favoritas de administradores de redes y servidores DNS.

---

# ARP

En capítulos anteriores vimos que ARP permite conocer la dirección MAC correspondiente a una dirección IP.

También podemos consultar la caché ARP del equipo.

En Windows:

```cmd
arp -a
```

En Linux:

```bash
ip neigh
```

o

```bash
arp -n
```

(según la distribución).

---

# ¿Para qué sirve?

Permite comprobar si el equipo conoce la dirección MAC de otros dispositivos de la red.

Ejemplo:

```
192.168.1.1

↓

00:15:5D:AA:10:22
```

Si una entrada esperada no aparece, puede indicar un problema de comunicación en la red local.

---

# netstat

Otra herramienta clásica es:

```cmd
netstat
```

Su nombre proviene de:

```
Network Statistics
```

Permite visualizar:

- Conexiones activas.
- Puertos abiertos.
- Puertos en escucha.
- Tabla de rutas (según opciones).
- Estadísticas de red.

Ejemplo:

```cmd
netstat -an
```

Salida simplificada:

```text
TCP

192.168.1.20:49520

172.217.xxx.xxx:443

ESTABLISHED
```

Podemos comprobar qué conexiones mantiene abiertas un equipo en un momento determinado.

---

# ss

En Linux, la herramienta recomendada actualmente es:

```bash
ss
```

(Socket Statistics)

Cumple una función similar a netstat, pero:

- Es más rápida.
- Consume menos recursos.
- Proporciona información más detallada.

Por ejemplo:

```bash
ss -tuln
```

Muestra los puertos TCP y UDP en escucha.

---

# tcpdump

Hasta ahora hemos trabajado con información resumida.

Pero...

¿Y si queremos observar exactamente qué paquetes circulan por la red?

Aquí aparece:

```bash
tcpdump
```

Es una herramienta de captura de paquetes para sistemas Linux.

Ejemplo:

```bash
tcpdump -i eth0
```

Permite visualizar en tiempo real:

- Direcciones IP.
- Puertos.
- Protocolos.
- Tráfico ICMP.
- Consultas DNS.
- Sesiones TCP.

Es una herramienta extremadamente potente para el diagnóstico avanzado.

---

# Wireshark

Cuando necesitamos un análisis mucho más visual utilizamos:

```
Wireshark
```

Es probablemente el analizador de protocolos más conocido del mundo.

Permite capturar y analizar el tráfico de red mediante una interfaz gráfica.

---

# ¿Qué puede mostrar Wireshark?

Entre otras muchas cosas:

- Tramas Ethernet.
- Paquetes IP.
- Consultas DNS.
- Mensajes DHCP.
- Comunicación HTTP.
- HTTPS.
- ARP.
- SMTP.
- ICMP.

Cada paquete puede analizarse hasta el más mínimo detalle.

---

# ¿Cuándo utilizar Wireshark?

Es especialmente útil cuando:

- Existe una incidencia difícil de localizar.
- Se sospecha de pérdidas de paquetes.
- Es necesario comprobar el funcionamiento de un protocolo.
- Queremos estudiar el tráfico de una aplicación.

Es una herramienta muy utilizada tanto por administradores de sistemas como por especialistas en ciberseguridad.

# Procedimiento completo

Cuando un usuario informa de un problema de red, un administrador podría seguir este orden:

```
1.

ipconfig

↓

¿Tengo IP?


2.

ping Gateway

↓

¿Hay red local?


3.

ping 8.8.8.8

↓

¿Hay salida a Internet?


4.

nslookup

↓

¿Funciona DNS?


5.

tracert

↓

¿Dónde se pierde la comunicación?


6.

netstat

↓

¿Existe la conexión?


7.

tcpdump / Wireshark

↓

¿Qué está ocurriendo realmente?
```

Este flujo evita perder tiempo y permite localizar la mayoría de incidencias de forma sistemática.

---

# ⚠️ Errores clásicos de oposición

❌ Ejecutar `ping google.es` como primera prueba.

➡️ Si falla, no sabrás si el problema es de conectividad o de DNS.

Empieza siempre comprobando una dirección IP.

---

❌ Pensar que `ping` muestra el recorrido del tráfico.

➡️ Esa función corresponde a `tracert` o `traceroute`.

---

❌ Confundir `nslookup` con `ping`.

➡️ `nslookup` únicamente consulta DNS.

No verifica la conectividad completa.

---

❌ Pensar que `Wireshark` modifica el tráfico.

➡️ Wireshark se utiliza para capturar y analizar paquetes, no para alterarlos.

# 🎓 Resumen del capítulo

Al finalizar este capítulo debes recordar:

- El diagnóstico debe seguir un orden lógico.
- `ipconfig` e `ip addr` permiten comprobar la configuración de red.
- `ping` verifica la conectividad mediante ICMP.
- `tracert` y `traceroute` muestran el recorrido seguido por los paquetes.
- `nslookup` y `dig` permiten consultar servidores DNS.
- `arp` muestra la correspondencia entre direcciones IP y MAC.
- `netstat` y `ss` permiten consultar conexiones y puertos.
- `tcpdump` y `Wireshark` capturan y analizan el tráfico de red.

---

# 📖 Resumen final

El diagnóstico de redes requiere seguir un procedimiento ordenado y utilizar la herramienta adecuada en cada fase. Comandos como `ipconfig`, `ping`, `tracert`, `nslookup` o `netstat` permiten localizar rápidamente problemas de configuración, conectividad o resolución de nombres, mientras que herramientas avanzadas como `tcpdump` y **Wireshark** ofrecen una visión detallada del tráfico que circula por la red. Más que memorizar comandos, un buen administrador debe comprender **qué pregunta responde cada herramienta** y aplicarlas de forma sistemática para identificar la causa real de una incidencia.
